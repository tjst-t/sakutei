## #159：CLI でしか設定できない装置を扱う口（§29.1）

- **背景**: 管理 API に設定の口が無い装置（syslog の宛先・NTP・ソフトの更新など）は、装置の CLI を ssh で打つしかない。機種ごとに
  provider を書くと、機種の数だけ本体が増え、機種の CLI の知識が本体に入る。
- **決定**（§29.1「CLI でしか設定できない装置を扱う口」）:
  - 汎用の provider **`cli-device`**（`internal/clidevice`）。本体は機種を知らず、機種ごとの中身（項目ごとの観測のコマンドと
    読み方〈名前付きの正規表現・キーと値・表の列〉、変えるコマンドの雛形、エラーの印、設定の入り方・出方・確定・取り消し、
    一度きりの操作）は**機種の定義のファイル**で与える。使う側が持ち、provider の設定（`cli_definition`・`cli_definitions`）から指す。
  - intent には管理する項目と望む値だけ（ID `<装置>/<項目>`）。つなぎ方は対象の一覧（`remote_config`、#130）。
  - やりとりは exec（コマンドごとに ssh の exec の 1 行）と対話（pty を取ってプロンプトを待つ。ページ送りの印にキーを打つ）。
    実行の層に、引用しないで 1 行を流す `RunLine` と、pty つきの殻を開く `OpenShell` を足した（どちらも接続を使い回さない）。
  - 値の形（`pattern`）は必須で、合わない値・改行・制御文字を含む値は intent の読み込みの時点で断る（コマンドへの差し込みを防ぐ）。
  - 出力が定義に合わないときは観測できない（unknown）。absent は定義の `absent` の印が当たったときだけ。何もしない。
  - Apply は同じやりとりでまず観測し（合わなければ何も流さない）、コマンド列を順に流し、エラーの印でそこで止め、どこまで流れたかを
    エラー（Event・通知の口）に出す。取り消しのある定義は取り消して確定しない。無ければ次の周で観測し直した現実から直す（level）。
    流した後は必ず観測し直す。同じ失敗が 3 回続けば PermanentError。
  - 秘密のフィールドは SecretRef。値はコマンド・エラー・出力の行・plan・観測に出さない。観測は「このプロセスが書いた値と同じなら
    その参照」だけ（プロセスごとの鍵の HMAC だけを覚える）。
  - 項目ごとの `disruptive` で Apply を予算に数える。
  - 定義の `actions` を Workflow の `action`（`provider.Actioner`）として同じ口で流す。ソフトの更新を承認ゲートつきのステージで
    1 台ずつ流せる。
- **見送り**:
  - 名前に値を含む項目（インタフェースごとの項目など）。項目は定義に名前で書いたものだけ。
  - リストの値。値は 1 つの文字列。
  - 同じ観測のコマンドの出力を項目の間で使い回すこと（BulkObserve）。項目ごとに打ち直す。
  - 本物の sshd と装置の CLI を使う統合試験。偽の装置（`internal/clidevice/clifake`）と、偽の ssh と exec 型の偽の装置を使う
    本物の CLI の受け入れテストで確かめた。
