## #88：入れ直しを宣言で起こす（§6.3・§13.3・§29.1）

- **背景**: 一度 done になった Workflow はもう走らない。入れ直すには `sakutei workflow cancel <名前>` か定義の書き換えしかなく、「この台を入れ直したい」を宣言で表す口が無かった。§13.3 の `kind: reimage` は Plan の Delete+Create の対だけを数え、物理サーバの入れ直し（台は消えも生まれもしない）とつながっていなかった。
- **変更内容**:
  - Workflow に `trigger: reimage` を足した。対象の scope を覆う `kind: reimage` の宣言のレーンが開いている（窓の中・承認・cooling-off）ときだけ、その宣言ごとに 1 回 run を起こす。run は起こした宣言の Key を S2（Run の `trigger`）に持ち、同じ宣言では二度起こさない。宣言が無い間は対象を Workflow に持たせず、収束ループに任せる。`target.scope` が要る。
  - 対象ごとに手を付ける前に宣言の `max_count` を 1 つ使う（Run の `reserved`、S4 の `planned_change.executed`）。通常予算の破壊的変更には数えず、入れ直しの中の破壊的な一度きりの操作（ForceRestart）も通常予算に通さない。使い切った宣言は run を起こさない。走っている run の次の対象で使い切っていた・宣言が取り下げられた・窓を過ぎたなら halt。
  - Workflow の S2 を失って起こし直しても、S4 の使用量で `max_count` を越えて入れ直さない（`--audit-log` があるとき）。
  - ついでに直したこと：Workflow の一度きりの操作を予算に通すとき、その周の planned_change の知らせ（`PlannedChangeOpened` など）を取り込んで捨てていた。周の予算の判定に戻すようにした。
- **見送り**: 入れ直しの多相 Task 化（OS の導入は手順の並びが利用者ごとに違うので Workflow のまま）。走っている run を宣言の取り下げで途中で止めること（対象の途中で止めると台が壊れたまま残るので、対象の切れ目で止める）。

## 統合テスト

`make integration-guestos` に TestReimage を足した（qemu-bmc 0.10.0）。宣言が無い・承認が無い間は走らず、承認された宣言（`max_count: 1`）で 2 台のうち 1 台だけが入れ直されて目印つきの OS が起動し、宣言を外すと走らず、新しい宣言で動いている台がもう一度入れ直されることを確かめる。
