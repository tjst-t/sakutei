## #145：採番の値のテンプレート（§19.1・§19.8・§29.1）

- **背景**: v1 のプールは整数だけ（§19.8）で、「払い出したアドレスを A レコードや VM の cloud-init に入れる」が書けなかった
  （2026-10-23 の採番の試用、`docs/trial/allocation` の見つけたこと 4）。IP のプール（CIDR の範囲）か、整数を値に埋め込む
  テンプレートかは決めていなかった（#108 の「決めること」の 1）。
- **決定**: テンプレートにする。プール・採番記録・authority（ファイル版・HTTP の API・HA・Lookup キャッシュ）は整数のまま
  変えず、要求の側に書く。
  - 要求は `{ from_pool: <プール>, template: "192.0.2.{n}", kind: ipv4 }`（`template`・`kind` は任意）。render のフェーズ1
    （§9.1）が `{n}` を払い出した整数（10 進）に置き換えた文字列をフィールドに入れる。
  - 写し方は `{n}` の置き換えだけ（何度書いてもよい）。足し算などの形は持たず、`{n}` 以外の `{` `}` はロード時に拒否する
    （足したい数はプールの範囲で表す）。要求に `from_pool`・`template`・`kind` 以外のキーがあれば拒否する。
  - `kind: ipv4 / ipv6` を書くと、範囲のすべての値をテンプレートに通した文字列がそのアドレスになることをロード時に確かめ、
    ならなければ最初の誤りの値を挙げて intent ごと拒否する。`kind` だけ（テンプレートなし）は拒否する。
  - 採番記録・owner・`rendered_revision` の入力は整数のまま。plan・status の割り当て待ちの仮の値はテンプレートに通さない。
- **CIDR のプールを採らなかった理由**: 採番記録の値の型・範囲の縮小の検査・claim の重なりの判定・HTTP の API がみな整数を
  前提にしており、変える範囲が大きい。v1 の使い方（1 つのサブネットの中のホスト部を配る）はテンプレートで足りる。
- **見送り**: サブネットをまたぐ範囲・IPv6 の 16 進の写し方（`{n}` は 10 進のまま）・別のテンプレートどうしの値の重なりの検査。
- **#108**: 1 はこの改訂で済んだ。2 は #116（v3.20）で済み。残るのは 3（採番記録を現実から作り直す、§19.7）。
