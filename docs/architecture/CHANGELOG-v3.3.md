# Sakutei 設計書 v3.3 変更一覧（CHANGELOG）

対象: v3.2 → v3.3。改訂日 2026-07-24。骨格（§1〜§29 の機構）は不変。本改訂は**段0-zero（非常駐・クライアント PC からの一回性収束）の第一級化**（ADR-0024）を反映する小改訂である。新モードの追加ではなく、既存要素（`reconcile` verb・観測 state レス・段0-minimal の論理）の組み合わせの明文化である。

形式: **変更ID / 対応 / 章 / 変更内容 / 設計判断の理由**。

---

## CHG-Z1 — §23.7「段0-zero」新設（旧 §23.7 dogfooding は §23.8 へ繰り下げ）

- **対応**: ADR-0024
- **章**: §23.7（新設）・§23.8（旧 §23.7 の番号繰り下げ。§26.2 の参照も更新）
- **変更内容**: 制御面専用ノードを持たず、クライアント PC から `sakutei reconcile` で任意タイミングに一回性収束させる運用形態を、段0-minimal の下の最下段として定義。位置づけ（「人間 triggered な起床、level-triggered な真実」・§23.6 の制御面停止論理の極限形）、失うもの（ドリフトは検知すらされない → 「開いたらまず status / plan」の作法）、二重 writer（fencing 世代流用）、制約（多相 Task 実行中はプロセス終了不可・S3 喪失は保守側で安全）、採用ファネル（段0-zero → 段0-minimal → 段0）を明文化。
- **理由**: 段0-minimal でも「常時稼働ノード 1 台」の確保がホームラボには重い（scenario 01/02 の最大ギャップの残余）。観測 state レスは実行間の状態保持を要求しないため、一回性運用は設計を裏切らずに成立する。OSS 初期利用者の最初の体験（clone → plan → reconcile）を最小まで軽くする（§29.4 の位置づけと整合）。

## CHG-Z2 — solo cooling-off のゲート化（非常駐対応）

- **対応**: ADR-0024
- **章**: §14.5
- **変更内容**: cooling-off の「planned_change 宣言から N 時間後に自動実行」に、非常駐運用では「次回 reconcile 時に N 時間経過していれば通す」ゲート条件として評価する再解釈を追記。
- **理由**: 非常駐ではタイマーによる自動実行が成立しない。ゲート条件化は「時刻ではなく状態で判定する」level-triggered 思想にむしろ整合する。

## CHG-Z3 — CLI 節に非常駐運用の正当性を注記

- **対応**: ADR-0024
- **章**: §26.6
- **変更内容**: 「常駐せず `reconcile` だけで運用する形態も正当（段0-zero）」を追記。`apply` を主動詞に置かない方針は維持（一回性運用でも毎回リアルを再観測する収束であり、`reconcile` という動詞が意味を保つ）。
- **理由**: 「本来の姿 = 常駐」の宣言と段0-zero が矛盾しないことを CLI の正典箇所で明示する。

## 見送り

- **常時稼働の小型ノード（Raspberry Pi 等）を段0-zero の推奨構成にする**: 読み取り専用の常時 observer を置けば「検知されない」欠点は緩和できるが、構成要素を増やすと段0-zero の存在意義（ゼロ点の軽さ）が崩れる。必要になったらそれは段0-minimal への昇格である。
- **一回性運用向けの state ファイル導入（Terraform 型別モード）**: 観測 state レスを捨てると three-way-diff 問題を持ち込む。一回性でも毎回リアル再観測が本設計の価値（ADR-0024 代替案3）。
- **cron / systemd timer による疑似常駐の規定**: クライアント PC の起動時間は不定で成立しない。定時起動できる機械があるならそれは段0-minimal である。
