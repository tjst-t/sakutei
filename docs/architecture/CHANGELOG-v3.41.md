## #151：部品の版の互換の表（§6.2・§29.1）

- **背景**: FW・ソフトの部品どうしには合う版の組み合わせがある（BMC と BIOS など）。`redfish-firmware`（#148）や
  `strategy: manual`（#150）で版を宣言できるようになったが、合わない組み合わせ、または 1 つずつ更新する間に合わない組み合わせを
  通る順序で更新すると装置が使えなくなりうる。
- **決定**:
  - intent のトップレベルに `compatibility:`。表ごとに `name`・`components`（部品の名前 → `id` と `field`〈既定 `version`〉）・
    `allow`（許す版の組み合わせの行。`"*"` はどの版でもよい）。`id` の `{名前}` に合った値が同じ宣言が 1 つの組（同じ装置）。
  - 版は文字列の完全一致で比べる。表に無い部品は対象外。表の部品で intent に宣言の無いものはその組で「どの版でもよい」。
  - **望む版の組み合わせ**が表に合わなければ、plan・一回性の reconcile は観測の前に終了コード 1（部品・版・Local ID を出す）、
    常駐はその周を飛ばす。
  - **途中の組み合わせ**：観測した版と望む版が違う部品を、depends_on の推移的な順序に沿って 1 つずつ更新する間の組み合わせを
    すべて表に照らす（順序の無い部品は両方の順を数える）。合わなければ plan は止まり（終了コード 1）、一回性の reconcile は
    何もせず終了コード 1、常駐はその組の変わる部品を止めて（Apply も Task も起こさない、下流は待つ）`VersionIncompatible`
    （level）で知らせる。合う順序があれば `<後> depends_on <先>` を案内する。
  - 組の部品が観測できないときは、変わる部品を止める（unknown ≠ ok。plan は知らせるだけ）。
  - 周の要約に `incompatible=N`。`CycleResult.Incompatible`。
- **見送り**:
  - 「部品ごとに要る相手の版の範囲」（`>= 2.0` のような範囲・順序）の書き方。版の上げ下げの順序は Sakutei が持たない
    （#148 と同じ）ので、許す組み合わせを並べる形だけにした。
  - 宣言の無い表の部品の版を観測すること（今はどの版でもよいとして通す）。
  - tier の違う部品を同じ組に置いたときに両方を同じ周で観測すること（同じ tier に置く、§29.1 の既知の限界）。
  - plan --json の項目（止まったときは `error` に理由が入る）。

## 受け入れテスト

`tests/acceptance/version_compat_test.go`（fake provider の `size` を部品の版とみなし、`node1/bmc`・`node1/bios` の組を表で縛る）:

- `[AC-151-1]` 合う組み合わせ（depends_on で bmc を先に）は plan も reconcile も通り、表に無い部品は対象外。
- `[AC-151-2]` 望む版の組み合わせが表に無い → plan は部品と版を出して止まり、reconcile も何もしない。
- `[AC-151-3]` 途中の組み合わせが合わない順序（順序の無い更新・bios を先にする depends_on）→ plan は止まり depends_on の案内を
  出す。reconcile は何もしない。
- `[AC-151-4]` 表を直せば同じ intent が通る。
- `[AC-151-5]` 常駐（`strategy: task`）：合わない順序では Task を起こさず `VersionIncompatible` で知らせ、depends_on を書けば
  bmc → bios の順に Task が走って収束し、知らせは resolved。
- `[AC-151-6]` 表の書き誤り（行に部品が欠ける・版が真偽）は読み込みで断る。
