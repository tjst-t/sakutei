## #177：依存先の Apply のあとの観測し直し（§8.1・§8.4・§29.1）

- **背景**: Observe は周の頭で Apply の前にまとめて行う（§8.1 の手順 2）。FW の許可（依存先）と、その許可を通って初めて届く
  ホストの上のリソース（依存元、`depends_on` で依存先を指す）を同じ回で組むと、依存元は観測できず（unknown）skip され、
  一回性の `reconcile` は終了コード 1 で終わる。2 回目で収束する。空から組む構成が 1 回で収束しない。
- **決定**:
  - **対象**：周の頭で観測できなかった（Observe のエラー・Availability ≠ Ok）リソースのうち、依存先を直接・間接にたどると
    この回に Apply して**効いたことを確かめた**（§11.1 Tier2）リソースに行き当たり、直接の依存先がすべて収束しているもの
    だけ。保留したもの（採番待ち・Task・Workflow・Apply の停止・`external_owners`）は対象にしない。効かなかった・確かめ
    られなかった・失敗した Apply の下流は観測し直さない。観測し直しは Read（最小階級は ReadFor）で、周の BulkObserve の
    結果（Apply の前のもの）は使わない。
  - **一回性の `reconcile`**：届けばその回のうちに Diff に戻し、周の頭と同じ保留（observe-only・alert-only の scope・Task・
    Workflow・Apply の停止・互換の表）・予算（この回に Apply した・認めて残っている変更を in-flight と同じに数える）・承認・
    wave の順序・Apply のあとの確かめを通す。観測し直したものとその依存元の部分 DAG だけを回し、効けばその下流をまた
    観測し直す（鎖は 1 回のうちに進む）。予算か容量で止まっていた回は観測し直さない。
  - **常駐**：Apply は非同期で、Apply を出したリソースの下流は同じ周に出さない（§8.4、#12）。Apply の goroutine の中で効いた
    ことを確かめたあと、その周に観測できなかった直接の依存元を観測し直し、届けば Interval を待たずに次の周を始める。届いた
    観測は使わない（次の周が新しく観測する）。
  - **上限**：1 つのリソースを観測し直す回数（`--reobserve-max`、既定 3、続けて観測し直す間は 0.5 秒、`0` で観測し直さない）と、
    回（周）の全体で観測し直しに使う時間（`--reobserve-time`、既定 30 秒、1 回の Observe も残りで打ち切る）。常駐と一回性の
    `reconcile` の両方の旗。当たれば、いまどおり unknown で skip し、次の回に任せる。観測し直しても届かないときも同じ。
  - **終了コード**の意味（0・1・3・4）は変えない。観測し直して Apply したものが効かなければ 4（#166）。
- **見送り**:
  - 常駐で同じ周のうちに依存元を Apply すること。周の壁と、予算を周の頭で 1 回評価する決まりを崩すので、次の周の繰り上げに
    留めた。
  - 届いていた（観測できた）依存元についても、上流の Apply が効いたら次の周を繰り上げること——**再検討トリガ**：長い Interval で
    鎖の収束が遅いと試用で出たとき。
  - 早期収束の scoped 経路（§8.6）での観測し直し（次の定期の周が拾う）。

## 影響

- §8.1 に観測し直しの決まりを、§8.4 に周の壁との関係を、§29.1 に 1 行を足した。
- 旗 `--reobserve-max`・`--reobserve-time`（常駐・一回性の `reconcile`）。`docs/exit-codes.md` に 1 の条件の注を足した。

  `observe_after_reads`）と Read の遅れ `observe_delay` を足した（テスト専用）。
