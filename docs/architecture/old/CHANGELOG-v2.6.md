## J. 本文の新機能決定

### CHG-J1 — 計画変更宣言(`planned_change`)の第一級化を §10.9 に新設

- **章**:§10.9(新設)、§8.6-b(List 急減 halt の planned_change 連動 + scope 単位閾値宣言化)、
  §10.2(異常検知の halt-all 凍結解除条件を planned_change に接続・`approved-large-change` タグの統合)、
  §24.1a(v1a スライスに追加)、冒頭「v2.5 からの主な変更」
- **要約**:intent 内の第一級宣言 `planned_change`(対象 scope / 変更種別 delete・update・reimage・recreate 等 /
  上限件数 `max_count` / 時間窓 window / 承認情報)を新設。**宣言自体が PR 承認を経る**(人の意図の明示)。
  効果は **窓内・scope 内・種別一致の変更に宣言上限までの専用予算レーンを与える**——通常の累積時間窓予算
  (§10.2)・cycle rate limit とは**別枠で計上**され、**バイパスではない**(上限を超えれば止まる)。List 急減 halt も
  「宣言済み削除/再作成」は急減とみなさない。窓を過ぎたら自動失効し通常予算に戻る。**宣言外の変更は引き続き
  通常予算で評価**され「宣言中でも宣言外の暴発は止まる」を明記。HPC 500 台一斉再イメージが delete に誤計上される
  問題(13)は変更種別 `reimage` の宣言で解決。既存 `approved-large-change` タグはこの宣言に統合(置換)。
- **理由**:安全機構(累積予算・rate limit・List 急減 halt)は「誤操作・暴発」を止めるが、**大量の正当作業**
  (棚卸し削除・一斉再イメージ・一括退去)と正面衝突する。恒常的に予算を緩めると暴発が止まらない。「専用予算レーン」
  として別枠で計上することで、正当作業を通しつつ宣言外の暴発を止める両立を、intent 内の宣言(=人の意図の明示)で
  達成する。コミットタグより構造化宣言の方が対象・種別・上限・窓・承認を機械可読に持て、halt-all 凍結の解除条件
  としても直接使える。
- **応答**:11(DBaaS の大量正当作業)、13(HPC 一斉再イメージの delete 誤計上)、09(棚卸し削除による List 急減の
  誤発火)。

### CHG-J2 — 承認ゲートの N-of-M 拡張を §10.5 に追記

- **章**:§10.5(承認ゲートのフローに承認者要件を追記)、§24.1.5(v1.5 スライスに追加)、
  §17.5(全承認者の S4 記録に接続)、冒頭「v2.5 からの主な変更」
- **要約**:v1.5 最小 Workflow の手動承認ゲートに **承認者要件**を追加。ゲート定義の `requirements`
  (N-of-M `quorum` / 役割制約 `roles` / `separation: applicant_ne_approver`)と、承認 API
  `POST .../gates/{gate}/approve` への **承認者 ID + 署名**の追加のみで実装(新プリミティブ不要)。役割判定は
  上位 IdP に委譲(コアは認可を持たない)。**全承認者を S4 監査に記録**(誰が・いつ・どの署名で承認したか)。
  requirements を宣言しないゲートは従来どおり単一承認(team 既定・§10.10)。
- **理由**:規制環境(金融・§17 構成)が要求する 4-eyes(申請者≠承認者・複数承認)は、単一承認では表現できなかった。
  ゲート API とゲート定義の拡張のみで実装でき、収束コアの認可非保持(§12.1)を崩さずに実現できる。
- **応答**:17(規制環境の 4-eyes)。

### CHG-J3 — 災害時運用経路(DR モード)を §18.1 に新設

- **章**:§18.1(新設)、§24.1.5(v1.5 スライスに追加)、§15.6(Break Glass の書込版として接続)、
  §17.5(break-glass 書込の検出・監査に接続)、冒頭「v2.5 からの主な変更」
- **要約**:2 経路で「被災サイトへの承認・署名依存」を断つ。**(a) DR intent のプリステージ**:大阪が東京 scope を
  引き継ぐ構成(claim 変更を含む)を平時にレビュー・承認済みで保持し、発動は `enabled: true` / claim 切替のみ
  (新規レビュー不要)。**(b) 緊急ローカル書込経路**:git の正へ到達不能時、被災を免れたサイトのローカルミラーへの
  **署名付き break-glass コミット**を許可。使用は必ず検出され(`BreakGlassWriteUsed` Event + S4)、**正への事後合流
  (reconciliation)手順とセット**(復旧後に PR として起票し事後レビュー)、使用後 rotate。既存 Break Glass 原則
  (§15.6 相当・「使えるがこっそりは使えない」)の**書込版**として位置づけ。
- **理由**:マルチサイト DR で、被災サイトが持つ通常の書込経路(git の正・PR 承認・署名鍵)そのものが被災で到達
  不能になると、生存サイトが引き継げても平時のガバナンスが DR の障壁になる。(a) で承認を平時に前倒し、(b) で緊急書込を
  検出可能な break-glass に閉じ込めることで、「事前チェック最小・事後監査最大」(§15.6)を DR 書込にも適用する。
- **応答**:06(DR 中の PR 承認・署名経路の東京依存=最後の障壁)。

### CHG-J4 — 運用プロファイル(solo / team / enterprise)を §10.10 に新設

- **章**:§10.10(新設)、§19.8(段0-minimal と solo の対応を明記)、§24.1a(v1a スライスに追加)、
  §10.2(solo の cooling-off 代替を承認必須の例外として接続)、冒頭「v2.5 からの主な変更」
- **要約**:規模別の安全既定値セット。**solo**:platform 破壊的大量変更の事前承認を **cooling-off(遅延実行)で
  代替可**——`planned_change` 宣言から N 時間後に自動実行、その間いつでも halt 可能。監査記録は同等、PR は自己マージ可。
  **team(既定)**:現行どおり(単一承認)。**enterprise**:N-of-M + 役割制約(§10.5)を既定化。段0-minimal(§19.8)は
  solo を既定とする。プロファイルは「よく使う既定の束」を1語で選ぶ糖衣であり、個別の `ownership` / ゲート /
  remediation 宣言が常に優先する(上書き可能)。
- **理由**:v2.5 までの安全既定(platform 破壊的変更に他者承認必須)はチーム運用前提であり、1名運用(ホームラボ・
  スモールオフィス・段0-minimal)では「自分で書いて自分でレビュー」の承認儀式が空回りして運用を阻害する。1名運用では
  「他者レビュー」を「時間差 + 自己による中断機会(cooling-off)」で置き換える方が実効的な安全になる。逆に規制環境は
  N-of-M を最初から要るため、規模で既定を切り替える。
- **応答**:01(ホームラボ)、02(スモールオフィス)——「1名運用に承認儀式が空回り」。

## K. 横断更新(§26 カテゴリ A の最終消し込み・型確定・スライス反映)

### CHG-K1 — コア型 `State`/`Plan`/`Scope`/`Event` の正準形を §4.6 で確定

- **章**:§4.6(「未定義」表を「正準形を v2.6 で確定」に書き換え + Go 型定義を追加)、§26.1 A-1
- **要約**:v2.5 まで「決定待ち」だった4型の**正準形を型として確定**。**`State`** = Schema 付き map
  (フィールドは Schema 宣言に紐づく型付き値)。**`Plan`** = 操作列(Create/Update/Delete)+ destructive flag +
  cause tag + 対象 ID + 差分診断(人間可読)を持つ構造体。**`Scope`** = provider 非依存のラベル集合 + パス形式
  (claim の scope-selector・prune 境界・`intent/<scope>/` パス規約と同一語彙)。**`Event`** = 単一型 + kind enum +
  scope/resource 参照 + revision 参照。`ID` は v2.4 で `(provider, scope, id)` 複合に確定済み。
- **理由**:これらは「型を書き始めた瞬間に露呈し後から変えると全 provider に波及する」着手前決定であり、A に残る最大の
  未決だった。構造(何を持つか)を本改訂で固定し、細部の命名・タグ体系のみ実装中の調整に委ねる。
- **応答**:§26.1 A-1(コア型の定義)。

### CHG-K2 — S4(監査 state)の永続化先を §17.5 で正式決定(§26.2 から格上げ)

- **章**:§17.5(監査に S4 永続化先の正式決定を追記)、§26.1 A-4b(表に追加)
- **要約**:S4 は **WORM ストレージ or 外部即時 push** を正式な永続化先とする(§17.5 の S-11 決定を §26 から本文の
  正式決定へ格上げ)。どちらか一方(または併用)で「侵害ホストが自分の犯行ログを改竄できない」を満たせば足りる
  ——WORM は書込後改竄が物理的に不可能、外部即時 push は侵害ホスト外に記録が出た後の改竄が不可能。S2(A-4・v2.5 確定)に
  続き S4 も確定し、状態クラス S1〜S4 の置き場がすべて決まった。
- **理由**:S4 の永続化先は改竄耐性(監査の根幹)に直結するため、着手前に確定すべき A 項目である。v2.5 まで §26 に留まって
  いたのを本文の正式決定へ引き上げ、A を空にする。
- **応答**:§26.1 A-4(S2/S4 永続化先)、S-11(監査改竄耐性)。

### CHG-K3 — remediation schedule × ownership の優先規則(most-restrictive-wins)を §10.8 に追記

- **章**:§10.8(優先規則を追記)
- **要約**:複数の mode 決定源(schedule / ownership 既定 / scope 明示 / freeze)が同一リソースに異なる mode を指す
  とき、**より制限的な mode が常に勝つ**(`alert-only` > `auto`)。**auto は「全ての決定源が auto を許した」ときだけ
  成立**する。優先順位でなく「最も制限的」で解決するのは、安全側への非対称原則(§2-3)を mode 解決にも一貫適用する
  ため——どこか1つでも「止めろ」と言えば止まる。取り違え(窓を開けたつもりが freeze 中/platform)が安全側に倒れる。
- **理由**:v2.5 は freeze の最優先だけを定めていたが、schedule と ownership 既定と scope 明示が衝突したときの解決規則が
  未定義だった。most-restrictive-wins で一意に解決し、「止めたつもりが動く」を構造的に排除する。
- **応答**:20(ベアメタル。mode 決定源の衝突解決)。

### CHG-K4 — List 急減閾値の scope 単位宣言化を §8.6 に追記

- **章**:§8.6-b(scope 単位閾値宣言 + planned_change 連動を追記)
- **要約**:List 急減 halt(§8.6-b)の閾値(既定 50%)を **scope 単位で `list_drop_threshold` として宣言・上書き可能**
  にする。流動性の高い scope(短命 VM 群)は緩め、破壊が致命的な scope(volume・VLAN)は厳しめに設定できる。
  **planned_change(§10.9)との連動**:窓内・scope 内・種別一致の宣言済み削除/再作成は「急減」とみなさない(棚卸し削除の
  誤発火対策)。
- **理由**:単一固定閾値では、正当な大量削除(棚卸し)で誤発火する一方、破壊が致命的な scope では緩すぎる場合があった。
  scope 単位の宣言化 + planned_change 連動で、誤発火と見逃しの両方を減らす。
- **応答**:09(棚卸し削除による List 急減の誤発火)、20(scope 特性に応じた閾値)。

### CHG-K5 — §26 カテゴリ A を空に、B〜E を整理し直す

## 本改訂で採用しなかった選択肢(見送り理由つき)

- **planned_change を予算のバイパス(無制限に通す)にする**:**見送り/棄却**(CHG-J1)。宣言上限(`max_count`)までの
  **別枠計上**とし、宣言外の変更は通常予算で止める。バイパスにすると「宣言中は何でも通る」穴になり、宣言外の暴発を
  止められなくなる。
- **DR で平時のガバナンス(PR 承認・署名)を発動時に丸ごと無効化する**:**見送り**(CHG-J3)。(a) 平時前倒し(プリ
  ステージ)+ (b) 検出可能な書込 break-glass + 事後合流の二段構えにする。丸ごと無効化は「DR を口実にした無監査書込」を
  許してしまう。
- **solo プロファイルで承認・監査そのものを省く**:**見送り**(CHG-J4)。承認は cooling-off(遅延 + 中断機会)で
  代替するが、**監査記録は team と同等**に残す。監査を省くと 1 名運用でも事故時の追跡ができなくなる。
- **mode 衝突を優先順位(schedule > ownership 等)で解決する**:**見送り/棄却**(CHG-K3)。most-restrictive-wins
  (最も制限的が勝つ)にする。優先順位は「高優先の auto が低優先の alert-only を上書きして動く」危険側の解決を生む。
- **§26 カテゴリ A に新規の着手前決定を積み続ける**:**方針として棚上げ**(CHG-K5)。A は本改訂で空にし、以降は
  「積むべき着手前決定が現れたら A を再オープンする」運用にする。空を維持することで実装着手のブロッカーが可視化される。
- **コア型のタグ体系・命名まで本改訂で凍結する**:**見送り**(CHG-K1)。構造(何を持つか)は確定するが、細部の命名・
  enum 値は実装中の調整に委ねる(構造さえ固定すれば全 provider 波及は防げる)。
