# Sakutei 設計書 v3.5 変更一覧（CHANGELOG）

対象: v3.4 → v3.5。改訂日 2026-10-20。骨格（§1〜§29 の機構）と設計判断（原則・機構）は不変。本改訂は **planned_change と専用予算レーン（§13.3、Backlog #39）の実装**に合わせ、§29.1 で「実装中に決める」としていた 2 項目（reimage の delete/create ペアリング判定・kind 整合検証）を決めて書き足す小改訂である。

## CHG-01 — planned_change の実装を §13.3 に書き足す

- **対応**: #39
- **章**: §13.3・§21.3
- **変更内容**: §13.3 に「v1.5 の実装」を足した（書式・窓の書き方と UTC 既定・kind と操作種別の対応・対の判定・枠の消費時点・Event 名・List 急減 halt との連動・レーンを開く経路・既知の限界）。§21.3 のトップレベルのキーの表に `planned_change` を足した。「型と専用予算レーンは v1a」という記述に、実装は v1.5 にずれ込んだことを注記した（§27.3・§27.4 も同様）。
- **理由**: 設計では v1a の範囲だったが未実装のまま v1b を終えていた。機構（バイパスでなく別枠・宣言外は通常予算・窓で失効・急減 halt の抑止）は設計どおりで、変えていない。

## CHG-02 — §29.1 の 2 項目を決める

- **対応**: #39
- **章**: §29.1・§13.3
- **変更内容**:
  - **reimage の delete/create ペアリング判定**: 同じ周期の Plan にある Delete X と Create Y を、同じ provider・scope のラベル集合が完全一致・1 対 1（同じ scope の中で Local ID 昇順）のとき対とする。対 1 組で枠を 1 消費し、どちらも破壊予算の delete に数えない。`recreate` も同じ対を使う。
  - **kind 整合検証**: kind ごとに通す操作種別を固定する（delete→Delete、update→Update、reimage / recreate→対の Delete+Create）。有効な宣言の scope 内で kind が合わない破壊的 op はレーンに入れず通常予算で評価し、`PlannedChangeKindMismatch` を出す。
- **理由**: 「宣言 scope の内側にある」だけで対とみなすと、scope 内の純粋な削除が再イメージを装って破壊予算を素通りできる。scope の完全一致を要求すれば、置き場所ごとの入れ替えだけが対になる（機体ごとのラベルを持てば 1 台単位の入れ替えになる）。不一致は止めずに通常予算へ回すので、宣言の書き損じは「通常予算で halt する」安全側に倒れる（原則3）。

## CHG-03 — 枠の消費時点と List 急減 halt の抑止範囲を決める

- **対応**: #39
- **章**: §13.3・§12.4
- **変更内容**: レーンの枠は op を provider へ発射する直前に消費する（発射しなかった op は減らさない、失敗した op は戻さない）。List 急減 halt で数えないのは、常駐ループが宣言の下で自分で消した ID が次の List から消えた分だけとした。
- **理由**: 判定時に枠を取ると、capacity gate などで止まっている間に毎周期枠が減ってしまう。急減の抑止を「宣言 scope 内の減少すべて」にすると、宣言中の List の欠落まで見逃す。自分の削除だけを差し引けば、宣言外の減少は従来どおり halt する。

## CHG-04 — one-shot reconcile はレーンを開かない

- **対応**: #39
- **章**: §13.3・§29.6
- **変更内容**: one-shot の `sakutei reconcile` は宣言があっても全変更を通常予算で評価し、その旨を表示する。予算カウンタ（とレーン使用量）が S3 のままで再起動をまたいで残らないことを §29.6 に足した。
- **理由**: one-shot は呼び出しごとに予算エンジンを作り直すので、`max_count` を呼び出しをまたいで守れない。守れない枠を開くより、開かない方が安全側である。
