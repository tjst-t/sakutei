作庭S A K U T E I

庭は放っておくと乱れる。庭師は毎日見回り、設計図と現実を見比べ、 伸びた枝を刈り、枯れたものを補う。

Positioning

k8s から借りたのは
収束原理であって、スコープではない

k8s の実装機構(apiserver / etcd 分散合意 / scheduler / admission)は持たない。 借りたのは level-triggered な収束ループという動作原理だけ。それを データセンター運用という別ドメインに移植し、k8s が扱っていない複雑さ (手続き・物理・テナント・DR・自己運用)を引き受けた。

ツール理想状態観測 state駆動帰結
Ansible外部宣言 持たない一回 push 収束しない(drift を放置)
Terraform外部宣言 持つ一回 push state drift 地獄(三項差分)
Kubernetes内部 etcd 持つ(status subresource)ループ コンテナに閉じる
Sakutei外部宣言(git) 持たないループ drift 検知漏れゼロ

Ansible の冪等性 + k8s のループ。 観測 state を持たないため、Terraform の三項差分問題(宣言 / state / 現実)が構造的に消える。 k8s ですら status を etcd に永続化するが、Sakutei はそれすら持たず、毎周、現実を観測しに行く。

8 Principles

設計を貫く原則

個々の判断は、この8原則の適用として導かれる。逆に言えば、原則から導けない機能は入れない。前半6つは core を貫く基本原則、後半2つはスケール・分散・衛星の設計で結晶した原則である。

01

level-triggered + 観測 state レス

毎周 desired と actual を突き合わせる。持つ state は4クラスに分類し、喪失が事故になるものだけ永続化する。

02

いつ = 収束 / どう = 手続き

経路依存・非冪等・中断が致命的な手続き(migration / firmware / DR)は収束ループに載せない。収束はトリガとゲートだけを担う。

03 — 最も広く貫く

確信が持てないとき、
加算はしても減算はしない

unknown ≠ absent / pruneable 既定 false / 分断時の破壊保留 / 爆発半径 halt / 採番の Release まで、すべてこの一つの規律の適用。

04

持たない。委譲する

シークレット値は Vault、配置最適化は DRS、時系列予測は Prometheus、認可は上位へ。持たないことが強み——漏洩面が縮み、core が小さく保たれる。

05

seam は今切る、split は後

将来の分離点を interface として先に切り、実際の分割は必要になってから。コアを無変更のまま拡張を吸収できる。

06

ownership がすべてを貫く

ただ一つの区別(platform / tenant)が、書き込みポリシー・修復モード・rate limit・爆発半径・供給源・シャード境界を決める。

07

シャード間協調は現実を介して行う

シャード同士は互いに問い合わせない。相手が作った現実を Observe して gate する。シャード間 RPC / 状態交換は正しさに一切関与しない——観測 state レス思想(原則01)のスケール版。

08

衛星の停止は、変化を止めるが、維持を止めない

定常収束は衛星コールゼロで回る。割当事実は Release まで不変なのでキャッシュしてよい。衛星が止まっても、止まるのは変化だけで維持は止まらない。QPS はフリート規模でなく churn に比例する。

Architecture

庭師と、その周りの小さな衛星群

収束エンジン core(Niwashi)は単一バイナリ・単一デーモン。 衛星を分けたのは機能膨張ではなく、ライフサイクル差・可用性の逆転・攻撃面の分離という 責務境界を正しく引いた結果。core は小さいまま保たれている。

Core

Niwashi(庭師)

収束エンジン本体。毎周 render → Observe → Diff → Apply を回し、宣言された理想へインフラを 寄せ続ける。単一バイナリ・単一デーモン。配置も、シークレットの値も、認可も持たない。

設計上の要点 観測 state を持たないため、毎周ゼロから現実を観測する。これが drift 検知漏れゼロの源泉。
Reconcile Loop

毎周、庭を見回る

niwashi は常駐して回り続ける。plan で刈る前に見せ、 reconcile で一度だけ手を入れることもできる——が、本来の姿は止まらないループである。

  • 1 · render desired を生成する。外部入力(CMDB / シークレット世代 / 採番)を解決し、 合成リソースを展開する。render が先頭なのは——何を Observe するかも、どの scope を prune するかも、desired から導かれるからである。
  • 2 · observe 現実を見る。キャッシュは持たない。並列で全リソースを観測し、 prune 対象 scope は List する。observe は desired を知らない。
  • 3 · diff 集合 diff(create / delete 判定)→ フィールド diff(update 判定)。 diff は現実を触らない。この分離が plan の正しさの根拠になる。
  • 4 · apply DAG を波に分解し、依存順に並列適用。Apply は非同期—— VM 作成や firmware で分単位かかっても、ループは止まらない。
  • 5 · record Diff の推移を記録。縮まなければ振動(綱引き)、 突然膨らめば異常(誤った理想の混入)として検知する。
  • 6 · sleep jitter を付けて眠り、また見回る。庭師は毎日来る。
plan と reconcile で Observe は2回走る。これは正しい。
plan の観測を持ち越せば「古い現実に基づいて手を入れる」ことになり、 排除したはずの観測 state を再導入することになる。毎回、新しく庭を見る。
The Asymmetry

刈るのは、植えるより危うい

level-triggered の収束は「速く確実に理想へ寄せる」能力を持つ。それは裏返すと 「速く確実に破壊する」能力でもある。しかも毎周繰り返すので底がない。 だから収束エンジンには、非対称な手綱が要る。

＋

加算 — 作る・直す・起動する

理想に足りないものを補う操作。古い理想に基づいて実行しても、たいてい無害である(理想に戻すだけ)。

  • 観測が unknown でも → 実行してよい
  • 制御面と分断中でも → 実行してよい
  • 大量でも → 警告して進めてよい
−

減算 — 消す・止める・返す

理想に無いものを取り除く操作。古い理想・不確かな観測に基づいて実行すると、破壊になる。取り返しがつかない。

  • 観測が unknown → 「消えた」と断じない
  • 理想が stale → 「消せ」を実行しない
  • pruneable 既定 false → 明示 opt-in のみ
  • 採番の返却 → 現実の削除を確認してから

確信が持てないときは、加算はしても減算はしない。

この一行が、設計の隅々まで貫いている。
unknown ≠ absent(観測不能を「消えた」と読まない)、closed-world prune(境界を宣言した範囲だけ消す)、 分断時の段階縮退(加算のみ / lease 失効で停止)、爆発半径の halt(破壊的変更だけ止める)、 allocation の Release(理想からではなく現実から消えたことを根拠にする)—— すべて同じ一つの規律の適用にすぎない。
Three Primitives

手入れと、普請は違う

収束(Resource)だけでは、手続き的作業——マイグレーション、ファームウェア更新、 ローリングアップグレード、DR フェイルオーバー——は表現できない。経路依存で、非冪等で、 中断が致命的だからである。毎周回るループに載せれば、確実に壊す。

Resource — 収束

宣言的状態

「こう在るべき」を宣言し、毎周寄せ続ける。冪等で、何度適用しても同じ結果に落ちる。

DNS record · VM · volume
設定ファイル · FW ルール
Task — 単一の手続き

一回性の作業

順序があり、中断できない。多相型はステートマシンになり、進行フェーズだけを永続化する。

DB マイグレーション
firmware 更新(リブート跨ぎ)
Workflow — 複数の手続き

不変条件つきの段取り

集合をまたぎ、全体制約(常に N 台 active)を各ステップで検証しながら進む。失敗したら止めて人を呼ぶ。

ローリングアップグレード
DR フェイルオーバー · canary
いつ・どの順で変えるか は 収束 が 判定 する。
どう変えるか は Task / Workflow が 実行 する。
The Axis

ただ一つの区別が、
七つの関心事を決める

バラバラの議論で個別に導いた結論が、後から見るとすべて同じ軸に乗っていた。 これは設計の分解が正しかったことの、最も強い証拠である。

層platform(共有基盤)tenant(専有)
書き込みPR 必須(人が承認)即時(レビュー無し)
修復alert-only 寄りauto でよい
爆発半径大(全テナントに波及)小(砂場内に閉じる)
理想の供給源FileSource(git)DBSource(API)

テナントがレビュー不要なのは、砂場の境界が切ってあるからだ。他テナントも基盤も壊せない。 テナント内でレビューが要るかどうかは、テナント自身が決めればよい。 プラットフォームは砂場の境界だけを保証し、砂場の中の統治は委ねる。

Blast Radius

同じ差分でも、
なぜ生じたかで危険度が逆転する

収束ループが見るのは「desired ≠ actual」という結果だけで、原因を区別しない。 だが原因が違えば、取るべき対応は正反対になる。だから diff に原因タグを持たせる。

A
意図的
intent_revision が変化
人が理想を書き換えた。適用してよい(ただし規模制御は効かせる)。
B
drift
消去法で判定
現実が勝手にズレた。自己修復するか、報告だけにするかは remediation mode 次第。
C
ツール更新
provider_version が変化
幽霊 diff。理想も現実も変わっていないのに、解釈が変わっただけで全リソースが再適用されかける。正しい修正でもバグでも見た目が同じ——最も見逃されやすい。
D
カスケード
上流の変化に連鎖
image を1つ更新したら、依存する 50 VM が作り直しになる。波及規模は直感を超える。plan で見せる。
E
外部入力変化
rendered だけ変化・intent 不変
人の commit なしに desired が変わる。シークレット rotate、採番、CMDB 変更。A と混同すると、監査の帰属もレビューの前提も rate limit の重みも、すべて誤る。
手綱は3階層。 remediation mode(そもそも自動で直すか)→ rate limit(一度にどれだけか)→ staged rollout(どう刻んで適用するか)。
いずれもデフォルトは止まる、明示で進む。間違いは止め、意図は通す。
Satellites

関守・台帳・図面

衛星は core から切り出された独立ソフト。切り出す理由はそれぞれ違い、 どれも「機能が増えたから」ではない。

関守
Sekimori · credential broker

関所の番人。通行のたびに手形を検め、その場で発行する。静的な資格情報を配らず、使う瞬間に短命の資格を発行して失効させる——保存しないものは漏れない。

なぜ分けるか: 認証は core の依存先であって一部ではない。core が死んでも認証が生きていなければ、 緊急時に人が機器へ入れない。可用性が逆立ちしている。
台帳
Daicho · allocation authority

VLAN・IP・ASN の払い出しを記録する。「前回何を払い出したか」の記憶装置があって初めて、二重払い出しを防げる=冪等性が回復する。

なぜ分けるか: 払い出しは state を持つ。core は観測 state レスを貫くので、この記憶は外に置く。 結果として、並行・シャード環境でも採番が競合しない。
図面
Zumen · intent UI

人が意図を描く、薄い入口。正は庭(git)の側にあり、図面はそこへの入力手段にすぎない。UI に独自のデータモデルを持たせない。

なぜ薄くできるか: 下の仕組みが厚いから。カタログの各商品は合成リソースとして実現され、 書き込み経路は ownership が決める。
借景(しゃっけい)——自分が所有しない景を、設計に取り込む。
シークレットの値は Vault に、配置最適化は DRS に、時系列監視は Prometheus に、 認可と課金は上位プラットフォームに委ねる。作らないことが、設計である。
Verification

坪庭で試し、縮景で確かめる

このシステムが検証すべきは正常系ではない。危険な収束——prune、爆発半径、 drift の自己修復、converging の誤認——であり、つまり 「わざと壊れる状況」を安全に再現する必要がある。実機は論外である。

Layer A — 主戦場

フェイク Provider

収束ロジックの検証に本物は要らない。むしろフェイクの方が良い——障害注入が自由で、高速で、決定的。Provider interface に挿すだけ。開発の8割はここで済む。

Tsuboniwa — 坪庭

隔離された検証 DC

物理1台に、ネストで段0〜段2を丸ごと再現する。Proxmox ネスト、containerlab、MinIO。坪庭自体を Sakutei で建てる——ドッグフーディング。

Shukkei — 縮景

デジタルツイン

本番と同じ宣言・同じ庭師で建てる。ツインとは「render の外部入力を差し替えた環境」である——専用の台帳と、専用のシークレット。本番のプールも鍵も汚さない。

最も重要なのは、壊す検証である。 provider をわざと落とす。drift を注入する。大量削除を引き起こす。 そして——爆発半径制御が止めるか。alert-only に縮退するか。unknown を absent と読み違えないか。
このシステムの肝は「壊れそうなときに、止まる」ことにある。ならば、壊す検証こそが本番である。
Scope

作るもの、後にするもの、作らないもの

設計の質は、何を作るかより何を作らないかで決まる。

作庭 Sakutei

新しいプリミティブは Task と Workflow の二つだけだった。 オンプレ運用の広域——物理から運用ライフサイクルまで——を、 3プリミティブと少数の横断項目と seam 群で吸収できた。 衛星が生えたのは機能の膨張ではなく、責務境界を正しく引いた結果である。 芯は小さく、適用面は広い。
