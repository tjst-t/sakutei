From Stage 0 to a Running Cluster

段0だけがある状態から、
動くクラスタまで積む

Ansible が作った段0(不変の最小核)しか存在しない。そこへ、リーフスイッチ2台・サーバ20台規模の 新しいポッドを丸ごと迎え入れる——ネットワーク到達性 → BMC → ハイパーバイザー導入 → クラスタ構築 という4層を、一つの intent PR から、複数 Cycle にまたがって段階的に積み上げる様子を追う。 層が変わるたびにプリミティブも安全機構も変わる——それがなぜかを、各層で立ち止まって見る。

登場人物:leaf-01 / leaf-02(ToR スイッチ)· host-01〜host-20(物理サーバ)· 既存の段0(3ノード・Ansible 構築済み)
Premise

すでにあるもの、まだ無いもの

境界線は §23.4 が定める一つの問いに要約される——「それを壊したとき、Sakutei が自分でそれを直せなくなるか」。直せなくなるものだけが段0、それ以外はすべて段1(=これから歩く4層)。

すでにある(段0 · Ansible 構築済み)
  • reconciler / Vault / broker 候補(3ノード・VM-HA)の管理NW接続
  • 管理NWコアの到達性の最小核(段0収容ポート + 最小 L2/L3)
  • Vault unseal 済み・reconciler は起動シーケンス通り稼働中(§23.5)
  • OOB / コンソールサーバ(Break Glass 経路)
これから積む(段1 · この 4 層)
  • leaf-01 / leaf-02:ラック済み・工場出荷設定のまま
  • host-01〜host-20:電源投入済み・BMC はデフォルト IP で応答するのみ
  • ハイパーバイザーは未導入、クラスタも未形成
  • = 「◎ネットワーク → ②BMC → ③ハイパーバイザー → ④クラスタ」がここから始まる
The Pod

新設ポッドの姿(20台規模)

これは単一デーモンの天井(§16)に楽々収まる規模である——NETCONF/gNMI 経由の泥臭い機器でも 30s 間隔で ~107 台まで届く。claim シャーディング(§17)は不要、段1a のコアループだけで足りる。

One Composite Intent, Four Layers

4層は、1つの PR から段階展開される

運用者が書くのはpod_buildoutという一つの合成リソースの PR だけである。以下の4層は「4回の作業」ではなく、render フェーズ2 による実子リソース展開 + depends_on/ready_condition による自然な段階解放(§9.5・§8.3)である。

01
リーフスイッチ構築 —— 到達性の土台
対象:leaf-01 / leaf-02(管理NW の「末端」= 段1所属。段0の到達性最小核はここに含まない)
Resource CommitConfirm 必須 tier: foundation v1 では未 Apply(観測のみ)
  1. intent で宣言。leaf-01/02 の VLAN(mgmt/data)・ポート割当・uplink 構成を書く。管理NWコア変更にあたるため platform ownership + PR 必須。
  2. render → observe → diff。現時点で VLAN/ポートが未設定 → create/update 判定、原因タグ A。
  3. apply は commit-confirm 付きでのみ許可。NW機器 provider は Capabilities.CommitConfirm を持たない限り「Apply 不可・観測のみ」に型で強制される——config push 一つで BMC への到達経路を自分で切る(self-lockout)のを防ぐ安全装置。
  4. 到達性を再確認できなければ自動ロールバック。これが通って初めて「network_ready」の ready_condition が立つ。

地雷はここにある

レイヤ別適合表(§3.9)で NW 機器は「○(収束できるが地雷あり)」——主な地雷は管理断ロックアウトと順序付きリスト(FW ルール等)。CommitConfirm はまさにこの地雷への型レベルの応答である。

正直な但し書き。CommitConfirm capability は v2 の NW 機器 provider で入る(v1a/v1b には無い)。したがって「leaf スイッチの自動 Apply」は設計上は表現できるが、安全に実行できるようになるのは v2——これは妥協ではなく、ロックアウト経路を型で塞ぐための意図的な順序である。 spec: §23.4 / §5.6
02
サーバの BMC 設定
対象:host-01〜host-20 の BMC(Redfish)
depends_on: leaf-switch ready_condition: network_ready
Resource SecretRef(Vault) 標準階級(List 無しで可)
  1. intent で宣言。BMC 管理 IP・NTP・SNMP/Syslog 通知・ローカル管理ユーザを 20 台分書く。管理ユーザの値は SecretRef で自動マスクされ、Vault から Apply 直前に JIT 解決される。
  2. observe → diff。20 台とも工場出荷値のまま → 全 update 判定、原因タグ A。
  3. 1台の失敗は他台に波及しない。「各サーバの BMC 設定は1台死んでも他は生きる」(§23.4 の表)——leaf のような CommitConfirm 必須化は要らない。transient エラー(一時応答無し)は指数 backoff で個別に再試行される。
  4. 20台全部が Ready で「bmc_ready」。次層はこの ready_condition を待つ。

進行スナップショット

設定完了 一時エラー・backoff 再試行中
「1台死んでも他は生きる」がこの層の安全設計そのもの。host-14 が一時応答不能でも、他19台の収束を止める理由がない——これが「管理NWコア(全体を全盲にしうる)」と「末端機器(部分故障で閉じる)」を分けて扱う理由である。 spec: §23.4 / §5.5 transient/permanent
03
ハイパーバイザーのデプロイ
対象:host-01〜host-20 へのベアメタル OS インストール
depends_on: bmc ready_condition: bmc_ready
Task(多相型) 1-outstanding rate limit(バッチ分割) unknown ≠ absent(リブート中)

imaging は中断不可・非冪等・リブート跨ぎ——収束ループに直接載せられない。差分検知は「Task 起動イベント」を発火するだけに留める(§6.5)。

Idle→ NetBoot→ Imaging→ Rebooting→ Configuring→ Verifying→ Done
↳ 失敗 → Failed→Rollback(再 Imaging)
  1. NetBoot。Task が BMC の virtual media / boot device を一時的に変更し、installer を起動する(BMC への書込みは Task 自身が担う手続き)。
  2. Imaging → Rebooting。Rebooting 中は host が一時的に消える → unknown ≠ absent で「今はリブート中」と解釈し、タイムアウト付きで再出現を待つ。
  3. Configuring → Verifying。hostname・管理NW設定・join 用鍵配布のあと、ハイパーバイザー API が健全応答するかを確認して初めて Done。
  4. 20台を一気にやらない。BMC の同時 virtual media 接続数のような現実制約を模して、rate limit で 5台ずつ4波に分割する。1-outstanding 制約が同一ホストの二重デプロイを防ぐ。

進行スナップショット(バッチ2/4が進行中)

Done(バッチ1) 進行中(バッチ2) 未着手(バッチ3-4待ち)
「いつ = 収束 / どう = 手続き」がここでも一貫している。収束が担うのは「差分を検知して Task を起動する」ことと「メンテ窓・バッチ枠を守る」ことだけ。NetBoot〜Verifying という危険な手順そのものは Task の中に閉じている。 spec: §3.2 / §6.2 / §6.5
04
クラスタ構築
対象:host-01〜host-20 を1つのハイパーバイザークラスタへ
depends_on: hypervisor-deploy ready_condition: hv_ready
Resource(Workflow 不要) depends_on chain ready_condition: quorum_formed
  1. 3台をシードにする。host-01 が初期化(cluster init)、host-02 は depends_on: host-01 ready:quorum_seed、host-03 は両方に依存——この3台だけは順序を持つ。
  2. quorum 形成。3/3 が揃うと ready_condition: quorum_formed が立つ。
  3. 残り17台は条件が1つだけ。depends_on: quorum_formed のみを満たせばよく、互いへの依存が無いため wave で一括並列 apply できる——quorum を脅かすリスクがもう無いから。
  4. Ceph OSD 追加・プール拡張も合わせて収束。合成リソースの子として、各ホストの join と同じ wave でストレージプールも拡張される。
  5. 20台 healthy で「pod_ready」。これで4層すべてが converged。

quorum 形成の前後

quorum 形成前
→
quorum 形成後(残り一括 join)
シード(順序あり) quorum 待ち join 完了
なぜここに Workflow が要らないのか。Workflow が要るのは「今動いている何かを、止めずに守りながら変える」場面(不変条件・承認ゲートが要る)。この新規クラスタにはまだ守るべき稼働中の invariant が無い——だから depends_on + ready_condition という Resource の標準機構だけで、安全に、しかも一括で足りる。同じ20台クラスタでも、稼働開始後のローリング更新は話が別で、そこでは min_active のような invariant を守る Workflow が必要になる。 spec: §6(3プリミティブ)/ §8.3 ready_condition
The Whole Picture

1つの PR が、複数 Cycle にまたがって展開する

wave は「1 Cycle 内の並列単位」であって「依存解決の最終形」ではない——物理サーバの起動や imaging のような長時間操作をまたぐ依存解放は、複数 Cycle にわたって段階的に進むのが正式なモデルである。

毎 Cycle、全 DAG を見ている。特定 Cycle が失敗・遅延しても、次の定期周期が自然に回収する——level-triggered の本体はこの「毎周・全部・間引きなし」であり、依存が複数 Cycle にまたがることは設計の欠陥ではなく正式なモデルである。 spec: §8.2 モデルA / §8.3 wave
