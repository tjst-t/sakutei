Operations Walkthrough

一つの仮想基盤で、
五つの現場を歩く

3ノードのハイパーバイザークラスタを一つの題材に固定し、構築・増設・物理ホスト交換・ ファームウェア更新・ハイパーバイザーのローリング更新という5つの作業が、Sakutei の中で 実際にどのプリミティブ・原因タグ・安全機構を通って実行されるかを追う。 すべて 設計の正 に定義された機構の適用であり、 新しい概念は一つも足していない。

同じ登場人物が5回出てくる:host-a / host-b / host-c(3ノード)· 統合 Ceph · VLAN(mgmt/app)· その上の VM 群

Scenario 1 · Build

構築 —— 何もない状態から一括で立ち上げる

段0(3ホスト分の Proxmox 相当基盤)は Ansible で作られている。その上に、ストレージ・ネットワーク・初期 VM フリートを一つの合成リソースとして宣言し、初めて Sakutei に収束させる。

Resource(合成) 原因タグ A · 意図 capacity gate render 二フェーズ wave 分解
  1. intent を書き PR。合成リソース hv_cluster(ceph_pool + virtual_network×2 + fw_rule + vm×5)を YAML で宣言する。platform ownership のため書込みは PR 必須。 §7.1 platform=PR必須 / §9.5 合成リソースの展開
  2. 承認・マージ。intent_revision が進む。差分は PR 上で dry-run(plan)としてそのまま見えている。
  3. render。フェーズ1で外部入力(ここでは無し)を解決、フェーズ2で合成リソースを実子リソース(ceph_pool・virtual_network・vm 各実体)に決定的に展開する。 §9.1 二フェーズ / §9.5
  4. observe → diff。3ホストは既に実在するが、ceph_pool・virtual_network・vm は List 上に存在しない → 全て create 判定、原因タグ A。
  5. apply。依存 DAG を wave に分解し並列適用する:vlan/fw → ceph_pool → vm の順。Apply は非同期なので、VM 作成が数分かかってもループ全体は止まらない。 §8.2 モデルA / §8.3 wave / §8.4 非同期 Apply
  6. capacity gate。一括 create が下位基盤(Ceph 等)の受容量を超えないよう、進行中件数を capacity gate で絞る。加算方向なので既定は「通す」が、暴走はここで抑える。 §11.4 / §13.4 capacity gate
  7. record → status。diff が縮小し converged。sakutei status で drifted=0 を確認すれば、PR の diff どおりに世界が出来上がったことが監査として残る。

desired(抜粋)

  pool: ceph-main

「作る」は本質的に安全側の操作である。非対称原則(確信が持てないとき、加算はしても減算はしない)が効くのは主に減算側だが、その裏返しとして create は既定で積極的に進めてよい——だからこそ大量 create の唯一の歯止めは capacity gate と wave の依存順序だけでよい。 spec: §3.9(適用境界:ゼロタッチ物理は責務外)/ §8 / §9.5
Scenario 2 · Expand

増設 —— 需要増でフリートを 5 → 8 台に広げる

アプリ層の負荷が増え、host-c の空き容量に VM を 3 台追加する。ここで初めて採番(台帳)——具体 IP の払い出し——が登場する。

Resource 原因タグ A · 意図 Reserve → Confirm rate limit planned_change(任意)
  1. intent に 3 台追加して PR。vm_fleet に vm-app-4/5/6(すべて host-c)を書き足す。
  2. PR 生成時に IP を仮予約。render フェーズ1が allocator に Reserve(TTL 付き)を発行し、PR の diff に具体 IP が表示される——却下されれば TTL 切れで自動的にリークなく解放される。 §19.4 仮予約(Reserve → Confirm)
  3. 承認・マージ。マージ直後に走る render フェーズ1が仮予約を Confirm し、本payoutに昇格する。
  4. observe → diff。List 結果に 3 台の ID が存在しない → create 判定、原因タグ A。既存 5 台には触れない(加算のみ = 無停止)。
  5. rate limit の確認。3 台の create は非破壊的なので緩やかに通る。だがこれが「一晩で 300 台」のような急拡大なら、変更予算(cycle 単位 rate limit / 累積時間窓予算)に引っかかり halt する——そのときは planned_change(専用予算レーン + 承認)で正当な大量作業として宣言する。 §13.1 rate limit / §13.3 planned_change
  6. apply → record → status。host-c に 3 台出現、converged。以降の定常収束では allocator の Lookup はシャードローカルにキャッシュされ、衛星呼び出しはゼロになる。 §19.6 QPS はフリート規模でなく churn に比例

Scenario 3 · Physical Swap

物理ホスト交換 —— host-b の老朽ハードを入れ替える

計画的なハードウェア交換。VM の退避は収束(Resource)だけで表現でき、実機の抜き差しだけが Sakutei の責務外(段0/人手)に残る——境界がどこにあるかが最もよく見える例。

Workflow(骨格)+ Resource 原因タグ A · 計画 unknown ≠ absent(不意故障時) planned_change fencing token S2-free 復旧
  1. 交換を計画し宣言。運用者が planned_change(種別:replace, scope:host-b, window:メンテ窓)を intent に宣言する——専用予算レーンで「これは正当な大量作業だ」と明示する。 §13.3 planned_change
  2. VM を退避(= 収束だけで表現できる)。host-b 上の VM の node desired 値を host-a/host-c に書き換える PR。Task ではなくただの Resource 収束——加算(host-a/c への作成)+ 減算(host-b からの削除)の組で表現される。 §6.1 Resource / 非対称原則は減算側にのみ厳格に効く
  3. host-b が空になったことを List で確認。「退避完了」は Observe 単発ではなく List(集合演算) を根拠にする——Release の非対称原則と同型。
  4. 物理作業(責務外)。人が電源を落とし、実機を交換する。新ハードの最小核構築は段0 = Ansibleの領域であり、Sakutei はここに関与しない。 §3.9 適用境界:ゼロタッチ物理は責務外
  5. 新ハードが名乗り出る。段0 が新 host-b の最小核(NW到達性・OS)を再構築し終えると、Sakutei の scope に「host-b」として再登場する。ローカル state(S2)を何も持たないハードなら、再イメージ → pull → 収束で完全復旧——失うものはゼロ。 §17.5 S2-free シャード
  6. fencing 世代を確認。旧 host-b の資格や書込み経路が万一残っていても、新しい fencing 世代が古い writer を拒否する——二重 writer による事故(FW/ルーティングの発振)を防ぐ。 §15.2 fencing token
  7. 基盤リソースを再収束。ceph_pool への再参加・virtual_network の再適用を、intent が元々持っていた desired との diff(cause A、中身は変わっていない)として通常収束する。
  8. (任意)VM を戻す。負荷分散のため一部 VM の node を host-b に戻す PR。ここも通常の Resource 収束。

Scenario 4 · Firmware

ファームウェア更新 —— host-a の BMC を 3.4.0 → 3.4.1 へ

中断不可・リブート跨ぎ・非冪等。収束ループには絶対に直接載せられない、多相 Task の典型例。

Task(多相型) strategy: task 1-outstanding 制約 メンテ窓ゲート unknown ≠ absent(リブート中)
  1. 収束は差分を検知するだけ。target_version: "3.4.1" と現在値の不一致を diff が検出しても、直接 Apply せず Task 起動イベントだけを発火する——非冪等操作を収束ループから排除する型。 §6.5 RequiresTaskEvent
  2. 1-outstanding 制約。同一リソースへの Task 起動は未完了インスタンス高々 1 つに制限される。level-triggered な収束は同じ差分を毎周検知し続けるため、抑止がないと Task が周期ごとに乱造される。 §6.2
  3. メンテ窓ゲート。window: "Sat 02:00-04:00" の外では起動しない。
  4. 状態機械を進行。各相の入口で「もう済んでいるか」を現実 Observe で確認してから進む(べき等な再開)。
  5. Rebooting 中は host-a が一時的に消える。unknown ≠ absent で「リブート中」と解釈し、タイムアウト付きで再出現を待つ——シナリオ3の物理故障と紛れないのは、Task 自身が「今どの相にいるか」を知っているから。
  6. Confirming で完了確認。進行フェーズだけを外部永続化(S2)し、Done 判定は稼働バージョンを現実 Observe で問うだけ——完了印は現実側にある。

収束への接続

resource: host_bmc_fw
id: host-a
target_version: "3.4.1"
update_policy:
  strategy: task        # 直接 Apply せず Task を起動
  window: "Sat 02:00-04:00"
  rollback_on_fail: true
Idle→ Staging→ Verifying→ Applying→ Rebooting→ Confirming→ Done
↳ いずれかの相で失敗 → Failed→Rollback
「いつ = 収束 / どう = 手続き」の型レベルの実装がこれ。収束はトリガとメンテ窓ゲートだけを担い、書込み・検証・リブート待ちという危険な手順そのものは Task に閉じ込める。実行中は converging 扱いになり、収束の介入は止まる。 spec: §3.2 / §6.2 / §6.5
Scenario 5 · Rolling Upgrade

ハイパーバイザーのローリング更新 —— 3台を1台ずつ、止めずに

単一リソースの手続きでは足りない。動的な状態依存(隣が今 healthy か)と全体不変条件(常に2台以上 active)を持つ、Workflow の実例。内部では毎ステップでシナリオ4の多相 Task を呼ぶ——3プリミティブの階層構造がそのまま現れる。

Workflow invariant: min_active 承認ゲート N-of-M canary → broad on_failure: halt
  1. Workflow 起動。invariant: min_active=2(3台中常に2台以上 active)を各ステップ前後で検証しながら進む。
  2. canary ステージ。影響度最小の1台(least-loaded-first)から。health_check(自動ゲート)と manual_approval(N-of-M=2/3、申請者≠承認者)を通過して初めて次へ。
  3. 1台ずつ:drain → failover → wait → firmware-update(Task 呼び出し)→ health-check → undrain → verify。drain/undrain は VM の node 書き換え(シナリオ3と同型の Resource 収束)、firmware-update はシナリオ4の多相 Task そのもの。
  4. ゲートで停止 → 承認 API → 次ステージ。ステージ完了で StageAwaitingApproval Event が発火し sink 経由で人へ通知、Workflow は S2 に永続化された「待ち」フェーズで停止する。POST /workflows/{id}/gates/{gate}/approve で次へ進む。
  5. broad ステージ。残り2台を同じ手順で(canary で検証済みの手順を横展開)。
  6. 失敗時は halt。ローリングは全ロールバックが困難なため、既定は「その場で止めて人を呼ぶ」(keep_drained: true)——無理に自動で戻そうとしない。

invariant を保ったまま進む(1台ずつ)

hostdrainfirmware(Task)healthundrainverify
host-a(canary)済済済済済
host-b進行中待ち———

host-a・host-c が active な間だけ host-b を drain してよい(min_active=2 を常に満たす)

on_failure:
  policy: halt          # 既定。全ロールバックは困難
  keep_drained: true
これは過剰な抽象化ではない。「順序・不変条件・失敗回復」を持つ手続きは、どのツールで組んでも本質的に必要になる複雑さである。Workflow はそれを第一級プリミティブとして構造化しているだけで、Task を隠さずそのまま子として呼ぶ——収束(shape)・Task(手続き)・Workflow(段取り)は積み木のように組み合わさる。 spec: §6.3 / §6.4 承認ゲート
At a Glance

5つの現場、一つの型

どの作業も、3プリミティブと横断的な安全機構の組み合わせに落ちる。新しい機構を都度発明していない。

作業主プリミティブ原因タグ主な安全機構破壊性
構築Resource(合成)A capacity gate / wave 依存順低 — 加算のみ
増設ResourceA Reserve→Confirm / rate limit低 — 加算のみ
物理ホスト交換Workflow(骨格)+ ResourceA(不意なら B) planned_change / fencing / S2-free中 — 一時的に容量低下
ファームウェア更新Task(多相型)— (Task 起動のみ) メンテ窓 / 1-outstanding / rollback中 — 対象1台が一時停止
ハイパーバイザー更新Workflow(→ 内部で Task)— (Task 起動のみ) invariant / N-of-M ゲート / halt低 — min_active を常時維持

「いつ・どの順で変えるか」は常に収束が判定し、「どう変えるか」だけが Task/Workflow に委ねられる—— この一線が、5つの現場すべてで揺らいでいない。
