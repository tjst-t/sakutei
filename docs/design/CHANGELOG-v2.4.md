## E. 提案1:早期収束パス(トリガ収束)——「edge-triggered な起床、level-triggered な真実」

### CHG-E1 — 早期収束パス(scoped reconcile)を §6.8 に新設
- **章**:§6.8(新設)、§6.1(scoped run の位置づけ注記を追加)、冒頭「v2.3 からの主な変更」
- **要約**:トリガによる早起き(edge ヒント)+ 定期周期(level 保証)のハイブリッドを第一級化。**原則
  「トリガは "いつ収束するか" のヒントであり "何が真実か" を一切運ばない」** を確定。トリガ喪失=次の定期
  周期が拾う(正しさ無傷・遅延のみ)。収束の中身は通常と同じ新鮮な Observe→Diff→Apply で、観測 state レス
  は無傷。部分収束は「新旧 rendered desired 同士の diff(決定的・リアル非接触)から影響サブ DAG を算出し、
  そのサブ DAG だけ Observe→Diff→Apply」と定義。制御プレーン追加レイテンシは秒オーダー。
- **理由**:level-triggered=周期律速で、人の意図変更(特に tenant セルフサービス API)の反映が周期待ちに
  なる構造問題(構成07の核心)への応答。k8s の informer watch(edge ヒント)+ resync(level 保証)と同型
  であり、既存の「毎周・全 DAG」(§6.1)を置き換えず上に重ねることで、観測 state レス思想を崩さずに
  レイテンシだけを短縮できる。

### CHG-E2 — `DesiredSource.Watch`(任意 capability)を §13.5 / §13.1 に追加
- **章**:§13.1(`Watcher` interface + `ChangeHint` 型を追加)、§13.5(新設)、§3.4 seam 表
- **要約**:`DesiredSource` に任意 capability **`Watch(ctx) <-chan ChangeHint`** を追加(`Provider` に対する
  `Lister` と同じ宣言制)。`ChangeHint = {intent_revision, 触られた scope 群}` のみを流し、変更後の値・状態は
  運ばない。FileSource=git webhook/merge フック(v1a)、DBSource=書込通知(v2)。実装しない供給源では
  定期周期だけが動く(正しさ不変・遅延のみ)。
- **理由**:早期収束の「発火源」を seam として宣言制で切ることで、供給源ごとに実装有無を選べる。真実を
  運ばない `ChangeHint` に限定することで、トリガに含まれる情報を「現在状態」として信じる罠(観測 state の
  再導入)を型レベルで塞ぐ。

### CHG-E3 — 早期収束パスの安全柵を確定
- **章**:§6.8(安全柵の項)
- **要約**:速い経路を汎用修復チャネルにしないための柵を決定:(1) 速い経路は **desired が変わったリソース
  のみ**を扱う(構造上 cause tag A/E のみ)。道中で見つけた drift B は定期ループに残す。(2) **集合差 prune は
  速い経路で禁止**(prune の正しさは List 完全性(§8.6)に依存)。テナントの即時削除は DBSource 側 tombstone
  =明示 absent(`ExplicitAbsentOnly`)で表現。(3) **rate limit・累積破壊予算のカウンタは定期経路と共有**
  (バイパス不可)。(4) 同一 scope へのヒントは合流(coalesce)し、実行時に最新 desired を読む(level 意味論
  維持)。scoped run の同時実行に上限、溢れは定期周期へ縮退。(5) per-resource in-flight 排他は共有。
- **理由**:「速く収束する力は速く壊す力」(§10.1)は速い経路でも変わらない。速い経路を drift 修復や prune
  にまで広げると、List 完全性検証・累積予算・非対称原則の防御を素通りする穴になる。役割を「desired 変更の
  即時反映」に純化し、正しさの最終保証を定期周期に一元化する。

### CHG-E4 — ownership 整合と allocator 可用性の UX 直結を明記
- **章**:§6.8(ownership との整合の項 / 注意点の項)
- **要約**:tenant 層(即時書込)が主客。platform 層は「PR マージ=ヒント発火」で承認直後に収束(ガバナンス
  不変・レイテンシのみ短縮)。注意点として、render フェーズ1 の副作用(採番)が速い経路に乗るため
  **allocator の可用性が UX に直結する**ことを明記(§12.4 の「次の天井=allocator/Vault の QPS」と合流)。
- **理由**:早期収束は tenant セルフサービスの UX 改善が主眼だが、platform 層でもガバナンスを保ったまま
  レイテンシ短縮の恩恵が得られる。採番が速い経路に乗る帰結(衛星可用性への依存)を正直に明示する。

## F. 提案2:スケールアウト経路 — 3段階

### CHG-F1 — 段1:`BulkObserve`(バルク Observe capability)を §5.7 / §4.3 / §12.2 に追加
- **章**:§5.7(新設)、§4.3(`Capabilities.BulkObserve` フィールド追加)、§12.2(天井表に BulkObserve 列を
  追加)、§3.4 seam 表(`BulkObserver`)
- **要約**:Provider の任意 capability **`BulkObserve(ctx, scope) ([]Observation, error)`** を追加
  (Capabilities に宣言、SDK が per-resource `Read` への fallback を吸収)。vCenter PropertyCollector /
  Proxmox `/cluster/resources` / AWS Describe / NetBox 等のバルク API で「1リソース1コール」前提の算術を
  書き換える。§12.2 の天井表に BulkObserve 列を追加(API 系:単一デーモン1万規模へ。バルクを持たない生 NW
  機器は台数が自然に有界という非対称も明記)。**毎周・全量再観測の原則は不変**(取り方が「N コール→1コール」
  に変わるだけ)。
- **理由**:単一デーモン天井(§12.2 実機算術)は「1リソース=1コール」を暗黙前提にしていた。現実の権威の
  多くはバルク API を持ち、これを第一級化すれば分散の前に単一を大きく延ばせる。`List`(prune の前提)とは
  型を別に保つ——prune の安全性は §8.6 の List 完全性検証に依存し、Observe の高速化とは要件が異なるため。

### CHG-F2 — 段2:静的シャーディング=claim-as-intent を §12.4 に新設
- **章**:§12.4(新設)、§1.3 CLI(`--claim` 追加)、§12.2(割当表=ルーターの S2 記述をこの方式で v1b 段階
  として上書き)
- **要約**:デーモンは `--claim <scope-selector>` で起動し全 intent を pull して自分の claim 分だけ収束。
  **シャード割当そのものを git の intent として宣言**(PR レビュー・履歴つき)。二重 claim 検知は既存の
  fencing token(§12.3)。ルーターという新可用性部品も新 S2 も増やさない(fencing 世代番号のみ S2)。§12.3 の
  「割当表=ルーターの S2」記述をこの方式で v1b 段階として上書きし、**動的ルーター/自動リバランスだけを v2 に
  残す**。scope 移動(再シャード)= drain→claim 変更 PR→fencing 世代更新の Workflow(最小 Workflow・v1.5 で
  表現可能)。
- **理由**:動的ルーターは割当表(S2)とその可用性が新たな中心依存になる。割当を git(既存の intent 経路)に
  載せる claim-as-intent は、新 S2 を fencing 世代番号のみに抑え、割当を PR レビュー・監査の対象に格上げする。
  「コンセプトを曲げずにスケールする」——共有物を衛星へ外出しした分解(§12.2)を、そのままシャードの分解に
  再利用する。

### CHG-F3 — 段3(v2 のまま)の整理
- **章**:§12.4(スライスの項)、§24.2(v2 の記述を静的/動的で整理)
- **要約**:動的ルーター、自動リバランス、`RemoteExecutor`、lease 縮退は **v2 のまま**であることを明記。
  §24.2 の「シャーディング + fencing」を、v1b 前倒し済みの静的シャーディングと、v2 に残る動的ルーター/
  自動リバランスに分けて整理した。
- **理由**:提案2は「段1(BulkObserve・v1a 型/v1b 実装)/段2(静的シャーディング・v1a 型/v1b 実装)/
  段3(動的・v2)」の3段階であり、どこまでが前倒しでどこからが v2 かを版帰属で明確にする。

### CHG-F4 — 原則の格上げ:「シャード間協調は現実を介して行う」
- **章**:§12.2(格上げ原則の段落を追加)
- **要約**:シャード同士は互いに問い合わせない。相手の作った現実を Observe して gate する(§12.2 の
  「観測 ready 待ち」を妥協ではなく**観測 state レス思想の延長**として明文化)。シャード間 RPC・状態交換は
  正しさに関与しない。共有物は衛星に外出し済み(採番=allocator、秘密=Vault、intent=git)であり、この分解が
  そのままスケールアウトの分解になる。
- **理由**:「観測 ready 待ち」を v2.3 では妥協的なニュアンスで書いていたが、実際は観測 state レス思想の
  必然的帰結である(交換した状態を信じることは観測 state を持つのと同じ罠)。原則として格上げすることで、
  分散化の設計判断の一貫した拠り所になる。

### CHG-F5 — 段2 の正直な限界を明記
- **章**:§12.4(正直な限界の項)
- **要約**:シャード間の強い順序保証は放棄(結果整合)/全域不変条件(総容量等)はシャード内 gate+外部集約で
  しか扱えず単体では強制不可/次の天井は allocator・Vault の QPS(提案1の「allocator が UX 直結」と合流する
  論点)を明記。
- **理由**:スケールアウトが何を得て何を放棄するかを正直に示すのが v2.3 以来の流儀(§12.2/§12.3)。全域
  不変条件と衛星 QPS が次の壁であることを隠さない。

## Z. 両提案にまたがる横断更新(コア型の確定・§26 カテゴリ A への反映)

### CHG-Z1 — `ID` を `(provider, scope, id)` 複合で確定
- **章**:§26.1 A-1、§4.6(未定義表の `ID` 行を「確定」へ更新)、§24.1a(着手前決定型に反映)
- **要約**:`ID` は `(provider, scope, id)` 複合で**確定**(scope=ルーティングキー)。**global-unique(単一
  フラット ID 空間)案は棄却**——再シャード(scope 移動)で ID が変わり、`depends_on` 参照・監査帰属が
  壊れるため。scope を ID に含めることで、シャードのルーティング(§12.4 `--claim`)が ID から直接引ける。
- **理由**:提案2の静的シャーディングは scope をルーティングキーにする。ID がグローバル一意だと再シャードで
  識別子が変わり参照が壊れる。scope を ID に織り込み、scope が移っても `id` 部分は不変を保つ設計が、
  分散と参照整合の両方を満たす。テナント跨ぎ衝突を型で防ぐ(§12.1)効果は v2.3 の推奨を確定に格上げした形。

### CHG-Z2 — `rendered_revision` を scope 単位で算出可能に定義
- **章**:§26.1 A-3、§4.6(`Scope` 行に「rendered_revision 算出単位」を追記)
- **要約**:`rendered_revision` は **scope 単位で算出可能**に定義(あるシャードの render が他シャードの観測に
  依存しない保証)。scope の render 入力(intent + その scope の外部入力)だけからその scope の
  rendered_revision が決まり、部分収束(§6.8 scoped reconcile)も scope 単位でハッシュ再計算できる。
- **理由**:全域一括ハッシュだと、1 scope の変更が全シャードの再収束を誘発し、部分収束もシャード独立性も
  壊れる。提案1(部分収束)と提案2(shared-nothing 独立収束)の**両方の前提**が scope 単位の決定的ハッシュ
  であり、着手前決定(§26.1 A)に織り込む。

### CHG-Z3 — rate limit・累積予算カウンタをシャード単位と明記
- **章**:§26.1 A-1(`Scope` の項)、§12.4(正直な限界の項)
- **要約**:rate limit・累積破壊予算のカウンタは**シャード(=ownership 境界=爆発半径境界)単位**で持つ。
  全域予算はシャード単体では強制できず外部集約に委ねる。速い経路(§6.8)と定期経路は同一シャード内で予算を
  共有する(CHG-E3)。
- **理由**:シャードが独立収束器である以上、予算もシャード境界で閉じるのが自然。ownership 境界=爆発半径
  境界=シャード境界が一致する(原則6)ことの帰結であり、安全機構の粒度をこの一軸に揃える。

### CHG-Z4 — v1a スライスへの追加(型切り)と v2 記述の整理
- **章**:§24.1a(項目 11〜13 を追加/更新)、§24.1b(BulkObserve 実装・静的シャーディング実動作を追加)、
  §24.2(v2 記述を整理)、冒頭「v2.3 からの主な変更」
- **要約**:v1a に **Watch seam + scoped run(部分収束)+ 合流キュー**(reconcile/plan とほぼ同一コードパス
  のため増分小)、および **`--claim` / `BulkObserve` の型切り**(実装は必要時)を追加。v1b に BulkObserve の
  実バルク実装と静的シャーディングの実動作(claim フィルタ + fencing + 再シャード Workflow)を追加。
  DBSource 連動 Watch と動的ルーター/自動リバランスは v2 のまま。
- **理由**:「seam は今切る、split は後」(原則5)。Watch/scoped run は既存コードパスの部分 DAG 適用で増分が
  小さいため v1a に入れられる。BulkObserve/`--claim` は型だけ v1a で切り、実インフラ provider や規模が要求した
  段(v1b)で実装する。

## 本改訂で採用しなかった選択肢(見送り理由つき)

- **早期収束パスで drift B も即時修復する案**:**見送り**。速い経路を汎用修復チャネルにすると List 完全性・
  累積予算の防御を素通りする(CHG-E3)。B は周期律速のままとし、速い経路の役割を「desired 変更の即時反映」に
  純化した。
- **動的ルーター/自動リバランスの前倒し**:**見送り**。割当表(S2)とその可用性が新たな中心依存になる。
  静的シャーディング(claim-as-intent)で大半のスケール要求は満たせるため、動的化は §26.4 D の再検討トリガ
  (§6.2 の早期警戒線)に委ねて v2 に残す。
- **`ID` の global-unique 案**:**棄却**(CHG-Z1)。再シャードで識別子が壊れるため、`(provider, scope, id)`
  複合で確定した。
