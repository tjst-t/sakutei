# 対象構成17: 金融機関の高規制環境(FISC準拠・勘定系周辺基盤)への Sakutei 適用性検討

**総合判定:○ 条件付き成立**(remediation を全面 `alert-only` に固定した「ドリフト検出器+適合レポート生成器」として使い、Apply の全実行を承認ゲート付き Workflow(v2)に閉じ込める限り成立。cause tag B の自動収束を使う運用は監査文化と矛盾するため封じる)

---

## 1. 構成の前提整理

- **対象**:勘定系周辺(本体はメインフレームで対象外)。Linux/Windows VM 400、専用線接続、インターネット直結なし(エアギャップに近い)。外部 git 利用不可・社内 GitLab のみ。
- **統制**:FISC 安全対策基準。全変更が CAB 承認+作業申請+二人承認(4-eyes)+事前/事後エビデンス必須。「自動で勝手に変更が走る」こと自体が監査指摘対象になりうる文化。
- **環境**:本番/DR/検証/開発の4面。本番との構成一致性の証明が監査要件。
- **運用**:ベンダ SE 常駐、変更は数十ページの手順書ベース。

この構成は Sakutei が本来価値を出す「常時自律収束(cause tag B のドリフト自動修復)」と、規制側が要求する「人間の承認が変更の直前にある証明」とが**正面から衝突する**。ただし Sakutei は §10.2 で `alert-only`(爆発半径ゼロ)を第一級モードとして持ち、§23.2 で「最初は一切 Apply しない・可視化から」を導入戦略として明示している。**衝突するのは自動収束であって、検出・可視化・plan・監査アンカーは衝突しない**——ここに成立の芯がある。

## 2. リソースモデリング と「手順書」の Workflow 化

3プリミティブ写像は素直。「産む/焼く/join する瞬間=手続き、前提と産まれた後=収束」(§20.2)。

**必要 Provider 一覧**

| Provider | 階級 | List(prune/import) | 備考 |
|---|---|---|---|
| proxmox_vm / vmware_vm | 完全 | ○ | managed fields(DRS配置・動的IP)除外必須(§11.2-4) |
| windows_guest(WinRM/agent) | 標準〜最小 | △ | Windows 400台の Observe 経路確保。TrueObserve 限定 |
| linux_guest(SSH/agent) | 標準 | △ | 同上 |
| nw_switch(NETCONF/gNMI・専用線側) | 完全(CommitConfirm 必須) | ○ | 管理断ロックアウト対策(§11.2-5) |
| fw / lb | 標準〜完全 | ○ | 順序付きリスト(§8.5) |
| dns / dhcp / ntp | 完全 | ○ | `tier: foundation`(§6.1) |
| ad(Windows ドメイン) | 最小(Ansible) | ✕ | TrueObserve/List 困難。存在確認まで |
| monitoring(監視設定) | 標準 | ○ | observability as Resource(§17.2) |
| cert / pki | 標準 | ○ | expiry health + rotation |

**「手順書」文化の Workflow 化**:数十ページの手順書は、経路依存・非冪等・中断が致命的な手続きであり、まさに §9 の Task/Workflow が扱う領域。ローリング適用・firmware・DR は Workflow(invariant + wave + フェーズ永続化 S2)へ写像できる。**手順書の「各ステップと確認ポイント」が Workflow の step と gate/invariant にほぼ一対一で対応する**。決定的に重要なのは §10.5 の**承認ゲート**——ステージ完了 → `StageAwaitingApproval` Event → 人が承認 API を叩く → 次ステージ、という流れが「人間の承認が変更の直前にある」ことをそのまま構造化する。ただし承認ゲート/段階適用/Task/Workflow は**すべて v2 以降(§24.2)**であり、v1 には存在しない。これが後述の最大論点。

## 3. ownership・DesiredSource・sharding と 4面の環境モデル化

- **ownership**:勘定系周辺の全リソースは事実上 `platform` 層扱い(PR 必須・alert-only 寄り・rate limit 厳格・FileSource=git・§12.1)。テナント層の「即時・レビュー無」は規制文化と両立しないため、この現場では基本的に使わない(または砂場テナントを持たない)。
- **DesiredSource**:社内 GitLab を FileSource として使う。§19.4 は「git は外部・GitHub/GitLab」を想定しており、**社内 GitLab は要件に適合する**(外部 SaaS は不要)。各 reconciler にローカルミラーを持てば GitLab 断でも収束継続(ここでは収束=Observe/検出のみ)。
- **4面(本番/DR/検証/開発)のモデル化**——ここが本構成の核心的な適合点。§22.5 の **twin(デジタルツイン)= 「render の外部入力を差し替えた環境」**という定義が、そのまま「同一 intent・パラメータ違い」を実現する。本番と DR/検証/開発は**同一の intent(git)を共有**し、差し替えるのは render フェーズ1の外部入力(inventory / allocation / secret backend)だけ。
  - 4面それぞれに専用 AllocationAuthority(本番スナップショットから seed すれば具体 ID 忠実度も確保)+ 専用/フェイク SecretBackend + 面別 inventory スナップショット。
  - **これにより「本番と構成が一致していることの証明」が、intent の同一性 + render 入力差分の明示という形で機械的に示せる**。監査が最も欲しがる「本番=DR の構成一致」が、`sakutei plan` を各面に対して流し「intent 起因の diff がゼロ」を示すことで証明可能になる。これは digital twin/plan 機能が監査要件に直撃する数少ない好例。

## 4. render(inventory/allocation/secret)の使い方

- **inventory**:社内 CMDB or ファイル。エアギャップなので外部 CMDB SaaS は不可。ファイル inventory + 段階的に社内 CMDB を RenderedSource 化。生成物は `generated/` 規律(§13.1)で手編集禁止。
- **allocation**:IP/VLAN の払い出しは allocator の最小実装(SQLite・§16.5)で足りる。4面それぞれ独立プール。PR 必須の platform 層なので **reserve → confirm の仮予約**(§16.3)を使い、PR diff に具体 ID を出す(CAB が「何が使われるか」を事前に見られる=審査材料になる)。
- **secret**:社内 Vault が root。エアギャップでも Vault は自己完結して動く。SecretRef 世代キャッシュ(§7.3)で Vault sealed-restart 中も検出継続。**ただし本構成では「新規自動生成」秘密の Apply は走らせないため、secret の収束機能の大半は使わず、Observe(存在・鮮度の検出)のみ**が実働する。

## 5. 安全機構の適用(最重要)

**(a) alert-only 常用の是非**:§10.2 は `alert-only` を「爆発半径ゼロ、最も保守的な本番リソース向け」として第一級に定義し、§10.6 の freeze は「全体を alert-only に倒すマクロ」、§23.2 は「導入初期は全 alert-only」と、**設計は alert-only 常用を完全に正当なモードとして扱っている**。したがって remediation auto を一切使わない運用は**設計思想と矛盾しない**——むしろ §23.7 が「価値が出るのは Apply ではなく可視化」と明言し、alert-only を到達点として許容している(§23.7-4「永久に alert-only のままでも構わない」)。

**(b) ドリフト検出器+適合レポートとしての価値(本構成の主戦場)**:Sakutei の観測 state レス設計は「drift 検知漏れゼロ」(§1.2, §6.2)を構造的に保証する。§17.1 の **conformance チェック**(宣言どおり在るか)を毎周実行し、`sakutei status`(§1.3)で drifted 一覧=適合レポートを出す。金融機関にとってこれは強力——「本番が承認済み構成に適合していることの継続的証明」「誰かが手順書外で手を入れた瞬間の検出」が自動化される。**これは監査対応の武器そのものであり、自動修復より価値が高い**(規制文化では「勝手に直す」より「逸脱を漏れなく検出し記録する」方が求められる)。cause tag(A/B/C/D/E・§10.3)で「人の commit 由来(A)か・現実側の drift(B)か・ツール更新(C)か」を区別でき、B の検出=手順書外変更の発見として監査帰属に直結する。**B を自動収束せず「検出してアラート・レポートするだけ」に留めるのが、この現場では正しい使い方**。

**(c) S4 監査 state + 外部アンカーは FISC 監査に耐えるか**:§17.5 は append-only + 連鎖ハッシュ + **外部アンカー**(日次 head hash を git に記録)+ git commit 連鎖 + Vault audit log の三者併用で監査を組む。改竄耐性・帰属(原因タグ)・秘密アクセス履歴が揃う点は FISC が求めるエビデンス性に方向として合致する。**ただし**:(1) 外部アンカーの想定先が「git push 先」だが、エアギャップ環境では社内 GitLab がアンカー先になる——外部第三者アンカー(公開タイムスタンプ等)が使えないため、**アンカーの独立性が社内に閉じる**。FISC 監査が「システム自身と独立した改竄検知」を厳格に要求する場合、社内 GitLab では不十分と指摘されうる(RFC3161 タイムスタンプ局を社内に立てる等の補強が要る)。(2) 「事前・事後エビデンス取得」の要件に対し、Sakutei の監査は「変更が起きた事実」の記録には強いが、**手順書ベース監査が要求する「作業前スクショ・作業後スクショ」形式のエビデンスとは粒度・形式が異なる**。承認ゲート通過記録(§10.5「承認された事実は監査に記録」)は 4-eyes の片方を機械化できるが、**エビデンス様式の適合は追加実装**が要る。

**(d) 承認ゲート(v2+)なしの v1 で成立するか**:v1 には承認ゲート・段階適用・Task/Workflow が無い(§24.2)。v1 で成立するのは **alert-only 固定のドリフト検出器+適合レポート+import+plan による構成一致検証**までであり、**「Apply を伴う変更に承認ゲートを付ける」機能は v1 に存在しない**。したがって:
- **v1 の範囲(検出・可視化・plan・監査アンカー)なら成立する**——この範囲は Apply を一切しないので 4-eyes/CAB と衝突しない(そもそも変更を実行しない)。
- **Apply を Sakutei にやらせる(手順書を Workflow 化する)なら v2 の承認ゲートが必須**。v1 でこれをやると「承認の直前性の証明」が構造的に作れず、監査指摘になる。

## 6. 段0ブートストラップの当てはめ(エアギャップ)

- 段0 = Ansible(open-world・pull 型・稀・意図的)で構築(§19.2)。エアギャップと親和的——段0 の思想はもともと「作って忘れる不変基盤」で外部依存を嫌う。
- **依存ソフトの調達が最大の実務課題**:Vault / Proxmox / Ceph / provider バイナリ / Ansible collection / Go モジュールを、外部ネット無しで社内ミラー(社内リポジトリ・オフライン媒体)経由で調達する必要がある。§19.4 は「git は稼働必須依存にしない・ローカルミラー」を既に定めており思想は合うが、**エアギャップでの初期調達・アップデート供給の運用は設計外**(Sakutei の責務でなくベンダ SE の作業)。
- Vault の sealed-on-restart(§19.4)で unseal は人手。エアギャップでも Vault は自己完結動作する。unseal key は人の金庫(§3.1)——これは FISC の鍵管理要件とも整合しやすい。
- Break Glass(§15.6)のオフライン物理保管・分割管理(Shamir)は、金融機関の既存の鍵管理・二人権限文化と方向が一致する。

## 7. 成り立たない点・苦しい点・設計ギャップ・必要な拡張(忖度なし)

1. **自動収束(cause tag B の自動修復)は使えない**。これは Sakutei の看板機能だが、規制文化では「勝手に変更が走る=監査指摘」であり**構造的に封じるしかない**。Sakutei の価値の中心である「触っていないのに理想へ戻る」体験(§24.4)を捨てることになる。残るのは「高精度な検出器」としての価値のみ——これは成立するが、**Sakutei である必然性が薄れる**(検出だけなら他の構成管理監査ツールでも代替余地がある)。twin/plan による構成一致検証と観測 state レスの検知漏れゼロが差別化点。
2. **承認ゲート・Task/Workflow が v2 以降**。手順書の Workflow 化(=Sakutei で Apply させる本命価値)は v1 では実現不能。v1 は検出専用に留まる。手順書自動化を求めるなら v2 待ちかつ**承認ゲートのエビデンス様式を FISC 準拠に拡張**する実装が要る(承認者 ID・二人承認の二重化・事前事後エビデンス添付)。
3. **4-eyes(二人承認)が承認ゲートの単一承認モデルと不一致**。§10.5 の承認 API は単一承認(`POST .../approve`)を想定し「認可は上位 IdP に委譲」する。**二人承認・職務分掌(申請者と承認者の分離)・CAB 承認との連携は Sakutei 本体に無く、上位プラットフォーム側の拡張**が要る。承認 API の N-of-M 承認化は設計に無い拡張。
4. **監査エビデンスの様式ギャップ**。連鎖ハッシュ+原因タグ+Event は「変更事実の改竄耐性」には強いが、手順書監査が要求する「作業前後の画面エビデンス」形式ではない。**エビデンス生成器(plan/Observe 結果を作業前後スナップショットとして整形・保管)は追加実装**。
5. **外部アンカーの独立性**。エアギャップで外部第三者アンカーが使えず、改竄検知アンカーが社内 GitLab に閉じる。厳格な監査では独立タイムスタンプ局(社内 RFC3161 等)の補強が要る。
6. **Windows 400台の Observe 経路**。TrueObserve できる agent/WinRM 基盤の確保が前提。ここが弱いと検出器としての網羅性(=本構成の唯一の価値)が崩れる。Ansible ラップだと TrueObserve:false に縮退し cause tag A/B 区別が効かず(§21.3)、「手順書外変更の検出」精度が落ちる——**検出器価値の要が Windows 側 Observe 品質に依存する**。
7. **エアギャップでの依存ソフト調達・更新供給**が設計外の運用課題(provider version 更新は cause tag C=幽霊 diff の管理も絡み、オフライン更新運用の設計が要る)。

## 8. 総合判定

**○ 条件付き成立**

- **理由**:Sakutei は自動収束を封じても価値が残る稀有な設計になっている——`alert-only` が第一級モード、§23.2/§23.7 が「可視化を到達点として許容」、観測 state レスが検知漏れゼロを保証、twin/plan が「本番=DR/検証の構成一致」を機械証明する。これらは金融機関の監査要件(継続的適合証明・逸脱検出・環境一致証明)に**驚くほど正確に噛み合う**。cause tag B を「自動修復せず検出・レポートする」使い方は設計と矛盾せず、むしろ規制文化では自動修復より価値が高い。
- **○ に留まり ◎ にならない構造的理由**:(1) Sakutei の中核価値である自動収束を丸ごと使えず「検出器+適合レポート+構成一致検証」に限定される、(2) 手順書自動化(承認ゲート付き Workflow)は v2 以降で v1 では検出専用、(3) 4-eyes・CAB 連携・監査エビデンス様式・外部アンカー独立性が本体機能では埋まらず上位/追加実装を要する。
- **○(条件付き成立)の条件**:(a) remediation を全 scope 恒久 `alert-only` 固定(または freeze 常用)、cause tag B の auto 修復を組織ポリシーで禁止。(b) Sakutei の役割を「ドリフト検出器+適合レポート生成器+4面構成一致検証器(plan/twin)」に定義し、Apply は当面 Sakutei 外(手順書・人)に残す。(c) Apply を Sakutei にやらせる段階に進むなら v2 の承認ゲートを、二人承認(N-of-M)・CAB 連携・事前事後エビデンス添付に拡張してから。(d) 外部アンカーを社内 RFC3161 タイムスタンプ等で補強。(e) Windows/Linux 400台の TrueObserve 経路(agent/WinRM)を確保し検出網羅性を担保。(f) エアギャップでの依存ソフト調達・provider 更新供給の運用を段0 として設計。この範囲なら、**「承認済み構成への継続的適合の自動証明」と「4面の構成一致証明」という、金融機関が手作業で苦しんでいる監査対応を Sakutei が堅く肩代わりできる**。
