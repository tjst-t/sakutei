# 対象構成14: エッジ/小売多拠点インフラ Sakutei 適用可能性レポート

**総合判定: △ 大幅な拡張が必要(ただし「店舗ローカル自律デーモン」を前提にすれば ○ に届く)**

Sakutei の中核思想——観測 state レス・level-triggered・非対称原則(加算はしても減算はしない)・§12.3 の
分散 Executor 段階縮退——は、WAN 切断が日常のエッジ多拠点に本質的に強い。設計書には「サイトごとシャード +
薄いルーター、各サイト独立収束、DR 時も生存」(§12.2 の地理分散行)という答えが既に書かれている。だが
その実装体である**分散 Executor(§12.3)/ シャーディング / lease・revision 縮退**はすべて v2 送り(§24.2)であり、
かつ 300 拠点の「段0 の分散」「credential-broker への WAN 越し依存」という v1〜v2 のどこにも正面から
書かれていない構造的ギャップが残る。方向は正しいが、v1 のままでは動かない。

---

## 1. 構成の前提整理

- **規模**: 300 店舗 × (小型サーバ 1〜2 台 + エッジルータ + L2SW + AP)。各店舗の Resource 数は小さい
  (POS 基盤 VM・店舗内サービス VM・ローカルキャッシュ・NW 機器数点 = 十数〜数十 Resource/店舗)。
  総和は 300 × 数十 ≒ 数千〜1 万 Resource。**総和は単一デーモン天井(§12.2 の数千〜1 万)の境界付近**だが、
  真の問題はリソース数ではなく**300 の独立した分断ドメイン**にある。
- **WAN が第一級の外力**: モバイル/フレッツ混在、切断が日常(数時間の孤立が週数十件、台風時は数日)。
  中央から見れば店舗は**常時どれかが unknown**。これは §2-3 非対称原則と §12.3 分散縮退が
  「例外処理」ではなく**定常状態**として要求される、という設計の急所を突く構成。
- **店舗に技術者ゼロ**: 物理作業は「電源を入れ直す」まで。→ 店舗ローカルに人手 unseal を要する Vault は
  置けない(§19.4 の「Vault は再起動で sealed、unseal はオペレータ起動」が致命的に効く)。
- **中央 DC 2 拠点**: 制御面はここに置く。DC 間は健全な回線がある前提。
- **店舗の均質性**: 3 パターンの店舗タイプ。**合成リソース + テンプレート render(§7.5)に理想的**な均質性。
- **高頻度な出入り**: 開店 月 5〜10 件、閉店 月数件。閉店 = ハード回収 + 構成削除 = **prune の安全性**が
  実運用で毎月問われる。

## 2. リソースモデリング

### 店舗 = 合成リソース `store_site`(3 パターン × 300 展開)

各店舗を 1 つの合成リソース `store_site`(§7.5)として人が書く。**見せる面は 1 つ、render フェーズ2 が
下位群へ扇状展開**する:

```yaml
resource: store_site
id: store-0042
site_type: type-B          # 3 パターンのどれか(テンプレート選択キー)
region: kanto
wan: { primary: mobile, backup: flets }
# ↓ render フェーズ2 が site_type=type-B テンプレートで展開
#   → bare_server{ id: store-0042-srv1 }, (type-C なら srv2 も)
#   → proxmox_vm{ role: pos-base }, proxmox_vm{ role: local-svc }, cache_service{...}
#   → edge_router{...}, l2_switch{...}, wifi_ap{...}
#   → dns/dhcp スコープ, 監視設定(§17.2), バックアップ構成(§18)
```

- **子を独立 Resource として展開する**(§7.5 の正)。単一 Provider に隠蔽しない。理由が本構成で決定的:
  合成を 1 Provider にすると閉店時の「子 20 個削除」が rate limit(§10.2)を **1 件として通過**してしまう。
  子が独立だからこそ「1 店舗閉店 = 20 削除」を halt 対象として数えられる。
- **3 パターン × 300 = 900〜1200 の展開差分**は、`site_type` をテンプレート選択キーにした純粋な
  render フェーズ2(決定的展開・§7.1)で吸収。IaaS カタログの商品と同型。

### 開店/閉店 = Workflow

- **開店**: `bare_server`(電源)→ `installed` → `data_network_verified` → `proxmox_node` の
  `ready_condition` 連鎖(§6.7)で、店舗立ち上げが数十 Cycle に跨って進行。技術者ゼロ環境ゆえ
  「機器を送って電源を入れるだけ」の**遠隔ゼロタッチ立ち上げ Workflow**が要る(現地作業を Task 化できない)。
- **閉店**: ハード回収 → 構成削除。**§16.4 の非対称 Release**(下流削除を Observe 確認後のみ・cooldown)と
  **§8.3 pruneable** を厳守する削除 Workflow。WAN 断中の店舗を「消えた」と誤認しないことが命綱(後述 §5)。

### 必要 Provider 一覧

| Provider名 | 対象 | Capabilities(TrueObserve/List/Converging/CommitConfirm) | クラス | identity 設計 | 実装難度 |
|---|---|---|---|---|---|
| `bare_server`(IPMI/Redfish) | 店舗サーバ電源・BMC | ✓/✓/△/✗ | 標準 | **物理トポロジ座標**(store-id+slot)。serial は computed(§5.5) | 中(店舗 BMC 到達性が前提) |
| `proxmox_node` | 店舗ハイパーバイザ | ✓/✓/△/✗ | 標準 | store-id+role | 中 |
| `proxmox_vm` | POS 基盤/店舗内サービス VM | ✓/✓/✓(task)/✗ | 完全 | store-id+role(不変論理キー)。current 状態は managed | 中 |
| `cache_service` | ローカルキャッシュ | ✓/✓/△/✗ | 標準 | store-id+svc | 低〜中 |
| `edge_router` | エッジルータ(WAN 終端) | △/✓/△/**✓(必須)** | 標準 | store-id | **高**(管理断ロックアウト=commit-confirm 必須・§11.2-5) |
| `l2_switch` | 店舗 L2SW | △/✓/△/△ | 標準 | store-id+port | 中 |
| `wifi_ap` | 店舗 AP | ✓(info)/✓/△/✗ | 標準(Ansible ラップ可) | store-id+ap | 低〜中 |
| `dns_record`/`dhcp_scope` | 店舗内基盤サービス | ✓/✓/-/- | 完全 | store-scoped | 低(tier: foundation) |
| `observability` | 監視設定(§17.2) | ✓/✓/-/- | 標準 | 店舗リソースに従属 | 低(店舗削除で自動 prune=孤児 monitor 防止) |

**注意点の写像**:
- **`edge_router` の管理断ロックアウト**(§11.2-5)が最も危険。WAN 終端機器の config push で自分の
  WAN 到達性を切ると、技術者ゼロの店舗では二度と直せない=**恒久ロックアウト**。`CommitConfirm` を
  **必須**とし「確認が来なければ自動ロールバック」を Apply 契約に組み込む。これは §19.3 の
  「管理NW ロックアウトの DC 版」の**店舗版**である。
- **AP/L2SW は Ansible ラップ**(§21.3)で TrueObserve 縮退を許容し、参入コストを下げてよい。

## 3. ownership・DesiredSource・sharding 設計(3 案比較)

分割軸は `site`(§12.2 の推奨軸そのもの)。3 案を比較する。

| 案 | 収束の実行体 | WAN 断時 | 段0 の数 | S2(進捗)の置き場 | 評価 |
|---|---|---|---|---|---|
| **A. 中央集中** | DC の reconciler が 300 店舗を RemoteObserve | **常時どれかが unknown → 全店舗 alert-only 縮退**。断中は Observe すら不可 | 1(DC) | DC(集約) | ✗ WAN 断で全盲。台風時数日は店舗が完全放置 |
| **B. 店舗ローカルデーモン** | 各店舗に reconciler(300 個の段0?) | 断中も**自律収束継続**(§12.3 通常=フル。ただし理想 stale) | **300** | 各店舗ローカル+DC | △ 分断耐性は最強だが 300 個の Vault/broker/段0 が非現実 |
| **C. ハイブリッド(推奨)** | 各店舗に**軽量 RemoteExecutor/agent**、制御面(reconciler+render+理想)は DC | 断中 agent は **§12.3 縮退**(加算のみ/lease 失効で Observe のみ) | **1(DC のみ)** | DC(制御面)+ agent は revision/leaseUntil のみキャッシュ | ○ 段0 は DC 1 個、分断耐性は §12.3 で担保 |

- **推奨は C(ハイブリッド)**。設計書の §12.3「実行体を別ホストへ出す(RemoteExecutor)+ ネットワーク分断が
  常態化」が**まさにこの構成のために書かれた縮退モデル**である。agent は理想状態と `revision`/`leaseUntil`
  だけをキャッシュし、DB を持たない(§12.3 の「DB は不要」)。**段0 の完全複製(Vault/broker/reconciler)を
  店舗に置かず、agent だけを置く**ことで、案 B の「300 個の段0」問題を回避する。
- **なぜ B(店舗ローカルデーモン)を推さないか**: 分断耐性は最強だが、「300 個の段0(Vault sealed-on-restart の
  人手 unseal を技術者ゼロの店舗で 300 回)」が破綻する(§6 で詳述)。ローカルに完全自律収束を置くと
  §12.3 が警告する「stale な理想で削除を実行/復活させ続ける」暴走リスクを 300 拠点で抱える。
- **shard router(§12.2「上位は司令塔ではなくルーター」)**: 「どの Resource がどの店舗(agent)か」を引く
  薄い層。割当表は **S2(§6.5)= 外部永続化必須**。300 エントリ規模で軽量だが、**喪失 = 誤配送**なので DC で
  冗長永続化。router 自体はメタ収束器にしない(§12.2「k8s federation の轍を踏まない」)。
- **S2 進捗 state の置き場所**: 開店/閉店 Workflow のフェーズ・承認待ちは S2。**DC 側に集約**する
  (店舗に人手 unseal 前提の永続化を置けないため)。ただし Workflow の実行対象が WAN 断で unknown の間は
  `converging`/待ちで留まる(S2 が留めるので再起動安全・§10.5)。
- **ownership**: 店舗構成は 3 パターンのテンプレート正 = **platform 層(FileSource/git・PR 必須)**。
  店舗ごとの個別化(採番結果・店舗固有パラメータ)は render 入力。テナント払い出し的な即時性は本構成に薄い。

## 4. render(inventory/allocation/secret)の使い方

- **店舗ごとの IP/VLAN 採番(§16 allocator)**: 300 店舗 × 各店舗内 VLAN/IP を allocator が払い出す。
  店舗ごとに**プールを分ける**(`pool: store-0042-ips`)ことで、店舗単位の割当が独立し、閉店時の Release も
  店舗プール単位で閉じる。開店時は §16.3 の reserve→confirm(PR で具体 IP が見える)。
  **§7.3 の非対称**: allocator 不達時は前回割当保持・**新規払い出しは保留**(新店舗は blocked で次周回収)。
- **inventory 合成(§7.1 フェーズ1)**: 「どの店舗が存在し、どの site_type か」を inventory ソースとする。
  店舗マスタ(開店/閉店の台帳)が inventory の権威。**§7.3 で inventory 不達時は前回生成物保持 →
  空 desired を生成しない**(= WAN や CMDB 断で全店舗一斉削除、という最悪事故を構造的に防ぐ)。
- **secret(§14 / 店舗ローカル資格)**: **これが本構成の最難関**。店舗機器(edge_router/POS VM)の資格を
  reconciler が使うには CredentialProvider/SecretRef 経路が要るが、店舗に Vault は置けない(§6 で詳述)。
  v1 暫定(§14.5)では Vault(DC)保存の SecretRef を注入するが、**WAN 断中は DC の Vault に到達できない**
  ため、店舗ローカルで完結する Apply の資格が枯れる。→ agent 側に **TTL 内キャッシュ**(§15.5(a))が必須。
- **テンプレート展開のロジック**(§7.5 実装):店舗タイプ別の CIDR 計算・VLAN 自動割当は render フェーズ2 の
  カスタム関数で埋める(v1 方式)。3 パターンしかないので複雑度は低い。

## 5. 安全機構の適用(WAN 断 unknown / 閉店 prune)

- **WAN 断店舗 = unknown の扱い**(§2-3 の中核):断中の店舗は Observe が届かず `unknown`。
  **unknown ≠ absent** を徹底し「店舗が消えた」と断じない。300 拠点で常時どれかが unknown なのが定常なので、
  **unknown を alert 疲れの原因にしない設計**(level 通知の firing/resolved・§17.4、Since からの
  transient↔stuck 自動昇格)が効く。WAN 断は「transient な unknown」であり、閉店の「恒久 absent」と
  峻別される——**この峻別ができることが Sakutei がこの構成に向く最大の理由**。
- **「加算はしても減算はしない」が 300 拠点で成り立つか**: §12.3 の分散縮退がそのまま答え。
  agent は **制御面と分断 → 加算のみ(作る/直す/起動)、破壊的操作(削除/停止)は保留**、
  **lease 失効 → Observe のみに縮退**。破壊的操作だけが制御面到達を要求する(§12.3 規律)。
  → **原理としては 300 拠点でも成り立つ**。ただし成立の前提が「agent が案 C で存在すること」であり、
  中央集中(案 A)では断中に Observe すら止まるため、この規律を掛ける対象(自律実行体)が存在しない。
- **閉店時の prune**: 最も事故りやすい経路。閉店 = 現実に機器がある間に構成を消す。危険な連鎖は
  「閉店処理中にたまたま WAN 断 → unknown を absent と誤認 → 別店舗まで巻き込む」。防御は多層:
  (1) `pruneable:false` 既定(§8.3)+ 閉店 scope だけ明示 opt-in。
  (2) §16.4 非対称 Release(下流削除を Observe 確認後・cooldown)で IP/VLAN の即時再払い出しを防ぐ
      (回収した店舗の IP を翌月の新店舗が掴む事故の回避)。
  (3) rate limit を **店舗(scope)単位**で設定し、`halt-destructive-only`。1 店舗閉店 = 20 削除は通すが、
      2 店舗同時削除が想定を超えたら halt(§10.2、in-flight 込み評価)。閉店は月数件なので閾値は低く引ける。
  (4) 閉店を Workflow 化し、「回収完了(現実から機器消滅)を Observe 確認 → prune 解禁」の順序を強制。

## 6. 段0 ブートストラップの当てはめ(最大の構造的難所)

- **店舗に段0(Vault)は置けない**: §19.4 の「Vault は VM-HA でも再起動で sealed に戻り、unseal は
  オペレータ起動 → MTTR に人間の unseal 時間を含む」が、**技術者ゼロ・電源再投入しかできない店舗で致命的**。
  停電後の再起動で Vault が sealed のまま誰も unseal できず、店舗が永久に立ち上がらない。
  → **店舗ローカル段0(案 B)は Vault の性質だけで却下**される。段0(Vault/broker/reconciler)は
  DC 2 拠点に集約する(案 C の根拠)。
- **credential-broker への依存が WAN 断で切れる問題**(本構成が突く核心):§15.5 が「broker 断 = 認証が要る
  全ターゲットの Observe が止まる = システム全盲」と規定する。300 拠点構成では **WAN 断 = 店舗 agent から
  DC の broker/Vault への到達断**が定常的に起きる。設計書の緩和がそのまま効く:
  - **(a) 発行済み短命資格を agent 側に TTL 内キャッシュ**(§15.5(a))— 断中も TTL 満了まで店舗内 Observe/
    加算 Apply を継続。**TTL を店舗の平均断時間(数時間)より長く設計する必要**があり、台風時の数日断では
    TTL が枯れる → agent は Observe のみに縮退(§12.3 lease 失効)。これは安全側だが、**断が TTL を超える間の
    店舗内 drift 自己修復は止まる**(POS が動き続ける限りは業務影響は限定的)。
  - **(b) broker 不達中は該当リソースを unknown 扱い**(§15.5(b))。
  - **broker/Vault は DC 段0 の VM-HA 保護**(§15.5(c))。DC 2 拠点なので DC 単一障害には耐える。
- **ネットワーク版 Break Glass(§15.6 L2.5)**: 店舗の WAN が死んで agent も broker も到達不能なとき、
  現地に OOB(コンソール)は無い(技術者ゼロ・コスト)。→ **本構成では L2.5 の現地復旧経路が事実上存在せず、
  「電源再投入で直る/直らないなら回線復旧を待つ」しかない**。これは設計ギャップというより構成側の制約だが、
  Sakutei 側で「WAN 断 = 業務は店舗内で自律継続、制御は回線復旧まで待つ(alert-only 縮退)」を
  明示的に許容する設計が要る。

## 7. 成り立たない点・苦しい点・設計ギャップ・必要な拡張(忖度なし)

1. **中核機能がすべて v2 送り(最重要)**: この構成の成立に必須の **分散 Executor(§12.3)/ シャーディング
   (§12.2)/ agent の lease・revision 縮退** は、v1 スコープ(§24.1)に一切なく **v2 以降(§24.2)**。
   v1 は「単一デーモン・毎周全 Observe・LocalExecutor のみ」であり、**WAN 断が定常の 300 拠点を v1 で動かす
   手段は無い**。→ **判定を △ にする最大要因**。方向は正しい(§12.3 がこの構成を予見して書かれている)が、
   「あれば良い」ではなく「無いと動かない」。
2. **段0 の分散が設計されていない**: 設計書の段0(§19)は **単一 DC の 3 ノード Proxmox+Ceph** を前提にし、
   「300 拠点に段0 の何を配るか」は書かれていない。案 C の「agent だけ配る(Vault/broker は配らない)」は
   §12.3 から**導出はできるが明文化されていない**。特に **店舗ローカルの Apply が要求する資格を、Vault 無しで
   どう供給し続けるか**(TTL キャッシュの TTL 設計・台風時数日断での枯渇)は設計ギャップ。
3. **TTL キャッシュと断時間の不整合**: §15.5(a) の短命資格 TTL は「数時間断」なら救えるが「台風時数日断」で
   枯れる。**断が TTL を超える間、店舗の加算 Apply(自己修復)も止まる**。安全側だが、「数日 drift を放置しても
   業務(POS)が店舗内で回り続ける」ことを保証する店舗内自律性(制御面ゼロでもデータ面が動く・§19)への
   依存が強い。**agent が持つべきキャッシュの範囲(理想状態+資格+どこまで)が §12.3 の 2 フィールド
   (revision/leaseUntil)だけでは不足**し、資格・render 済み理想を含めた拡張が要る。
4. **300 の分断ドメインの監視ノイズ**: 常時どれかが unknown。§17.4 の level 通知(firing/resolved)と
   Since 昇格で緩和できるが、「WAN 断由来の unknown(正常)」と「機器故障由来の unknown(異常)」を
   Sakutei 単体で区別できない(到達できない理由まではわからない)。→ **WAN 状態を別入力として突き合わせる
   相関(回線監視 × Sakutei unknown)が設計ギャップ**。§04 レポートの「inventory 妥当性検証ギャップ」と同種。
5. **ゼロタッチ開店の物理段の穴**: 技術者ゼロで「機器を送って電源を入れるだけ」で立ち上げるには、
   §6.7 の ready_condition 連鎖の**最初の一歩(BMC 到達・素の OS 起動)を現地作業ゼロで踏む**必要がある。
   これは §19 の provisioner(起動方式と OS 種別を分離)相当が店舗規模で要るが、店舗に PXE/管理NW 核を
   置けるかは構成側の詰めが要る(段0 の店舗版の最小核をどう作るか)。
6. **shard router の割当表(S2)の一貫性**: 300 拠点 × 高頻度な開店/閉店(月 10 件前後の出入り)で
   割当表が頻繁に変わる。喪失=誤配送(§6.5)。DC 2 拠点で冗長化するが、**router 自体を分散合意にしない
   (§12.2)一方で 2 DC 間の割当表整合をどう取るか**は未設計(§26 の S2 永続化先も未決)。
7. **必要な拡張の総括**: (a) 分散 Executor + agent 段階縮退(§12.3・v2 設計済み・実装必須)、
   (b) シャーディング + shard router(§12.2・v2 設計済み)、(c) **段0 の分散モデル**(agent のみ配布・
   資格 TTL キャッシュの店舗版・ゼロタッチ立ち上げの最小核)= **設計ギャップ**、
   (d) WAN 状態相関による unknown の原因分類 = **設計ギャップ**、(e) 高品質な edge_router provider
   (commit-confirm 必須)= 実装工数。(a)(b) は v2 設計済み、(c)(d) は新規設計、(e) は工数。

## 8. 総合判定

**△ 大幅な拡張が必要**(案 C = 店舗ローカル agent + DC 制御面 を前提にすれば ○ 条件付き成立)

- **理由**: Sakutei の思想はこの構成に**構造的に適合**する——観測 state レス(300 拠点の drift 検知漏れゼロ)、
  unknown≠absent(WAN 断を「消えた」と誤認しない)、§12.3 の分散段階縮退(加算のみ/lease 失効で Observe のみ)、
  §7.3/§16.4 の非対称(空 desired・誤 Release の防止)、§7.5 合成リソース + テンプレート(3 パターン × 300 の
  均質展開)、§17.4 の level 通知。設計書の §12.2「サイトごとシャード + 薄いルーター・DR 時も生存」は
  **この構成の解を名指しで書いている**。しかし実装体(分散 Executor・シャーディング・lease/revision 縮退)は
  すべて v2 送りで、v1 では 300 の分断ドメインを扱えない。さらに **段0 の分散(店舗に Vault を置けない中で
  資格をどう供給し続けるか)と WAN 断由来 unknown の原因分類は、設計書に明文がなく新規設計が要る**。
- **○ に到達する条件**:
  1. **案 C(ハイブリッド)を採る**——店舗に軽量 agent(RemoteExecutor)、Vault/broker/reconciler/理想状態は
     DC 2 拠点に集約。店舗に段0 を複製しない。
  2. v2 の **分散 Executor(§12.3)+ シャーディング(site 軸)+ shard router(S2 割当表)** を実装対象に含める。
     agent の縮退は §12.3 の revision/leaseUntil に加え、**render 済み理想 + 資格 TTL キャッシュ**を持たせる拡張を行う。
  3. **段0 の店舗版最小核**(ゼロタッチ立ち上げ・資格 TTL 設計)を新規に詰める。TTL は平均断時間より長く、
     台風時数日断では「Observe のみ縮退 + 業務は店舗内自律継続」を許容する運用を明示。
  4. **閉店 prune を Workflow 化**し、回収完了(現実消滅)を Observe 確認後にのみ Release/prune(§16.4)。
     rate limit を店舗 scope 単位で `halt-destructive-only`。
  5. **WAN 状態を別入力として相関**し、unknown の「正常(回線断)/異常(故障)」を分類する層を足す。
- この条件下では「均質な 3 パターンをテンプレート展開し、店舗内は agent が自律収束、WAN 断は加算のみで
  安全側に縮退、制御は回線復旧まで待つ」という **○(条件付き成立)** に届く。逆に **v1 のまま・中央集中(案 A)で
  300 拠点を RemoteObserve しようとすると ✗**——WAN 断で常時全盲になり、設計の分断耐性を活かせない。
  「店舗に段0 を 300 個複製する(案 B)」も Vault sealed-on-restart で ✗。**agent を配り段0 は配らない**という
  一点が、この構成を成立側に倒す分水嶺である。
