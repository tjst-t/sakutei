# 対象構成20:ベアメタルホスティング/専用サーバプロバイダ — Sakutei適用可能性レビュー

**総合判定:○ 条件付き成立**(ライフサイクル遷移=多相Task/Workflowという設計の主戦場に正面から合致し、「利用中はOSに触らない」がmanaged境界とownershipで綺麗に表現できる。ただし ①provisioner・Task/Workflow・承認ゲート・credential-broker が全て v2+(§24.2)、②消去証明の証跡は Sakukei外、③30分プロビジョニング目標と収束周期の整合、の3点が成立の前提条件)

---

## 1. 構成の前提整理

在庫1,000台(10モデル混在・稼働率85%=約850台稼働)、BMC 1,000台、PXE/イメージサーバ、スイッチポートVLAN、IPAM。日次で割当5-10件・解約3-5件と**変更頻度は低い**が、1件あたりが重い経路依存手続き(BIOS/RAID→OSインストール→NW設定、ワイプ→ファーム更新)である。運用8名。

この構成の本質は「宣言的状態の維持(Resource収束)」ではなく**ライフサイクル状態遷移(多相Task/Workflow)**にある。設計書が §9(3プリミティブ)・§20.2(ベアメタル導入=多相Task+Workflow)・§1.3(provisioner)で明示的に想定した領域そのものであり、パブリックIaaS(構成07)のような「即時・大量・テナント即時書込」の緊張は無い。むしろ**リソースの大半(顧客OS)が管理境界の外にある**点が特徴で、これは §11.2-4(managed fields)・§8.1(境界の宣言)で扱える。Redfish/BMCのObserveが遅い点だけがスケール上の注意点となる。

## 2. リソースモデリング

**サーバのライフサイクル状態機械**を、Resourceの宣言的状態(BMC/電源/ポートの「あるべき姿」)と、状態間の遷移を担う多相Task/Workflowに分ける。identityは筐体交換耐性のため**物理トポロジ座標**(`rack07-u12` / `leaf03-p12`)にし、シリアル・BMC MACは `managed:true`+`computed` で観測のみ(§5.5 の設計指針そのまま)。

ライフサイクル状態は理想状態の`phase`フィールド(収束が監視する「あるべき状態」)で表現し、遷移は`update_policy: {strategy: task/workflow}`(§9.1)で手続きに委譲する:

| 状態 | 収束が維持するResource | 遷移(→次状態) |
|---|---|---|
| **在庫(電源断)** | BMC到達性・電源OFF・ポートを隔離VLAN・IP未割当 | 割当申請 → **プロビジョニングWorkflow** |
| **プロビジョニング中** | (converging扱い・収束は介入停止) | 多相Task:BIOS/RAID設定→PXE boot→OSインストール→NW設定 |
| **顧客利用中** | **BMC/電源/ポートVLAN/IPのみ**(OSはmanaged境界外) | 解約申請 → **解約Workflow** |
| **解約処理中** | (converging扱い) | Workflow:データワイプ(証明書発行)→ファーム更新(多相Task)→在庫戻し |
| **在庫へ復帰** | 在庫と同じ | ループ先頭へ |

**「利用中はOSに触らない」managed境界設計**:1台のサーバResourceの中で、Sakuteiが管理するフィールド(BMC電源状態・BMC資格・接続ポートのVLAN・払い出しIP)と、intentに書かない/observe対象外にするフィールド(OS種別・OS内設定・稼働状況)を分ける。これは §19.3 で「同じ管理NWコアスイッチの中で段0/段1を分ける」のと同型、§11.2-4 の managed fields と同型である。顧客利用中サーバは `remediation: alert-only` 相当に固定し、BMC電源を「意図的にonにした顧客サーバを勝手にoff/onしない」(§20.4 の電源managed field注意がそのまま該当)。

**ワイプ+証明書発行Workflow(監査可能性)**:解約はWorkflow(§9.2)。invariantは「顧客VLANが完全に切断されてからワイプ開始」「ワイプ完了署名が取れるまで在庫戻しへ進まない」。多相Task(§9.1)としてワイプ本体をモデル化し、進行フェーズをS2永続化、Done判定はワイプツールの完了署名を現実Observe。各step(切断→ワイプ→証明書生成→ファーム更新→在庫戻し)を**Event→sink(§17.4)+ append-only監査ログ(§17.5・連鎖ハッシュ)**に流すことで、NIST SP 800-88準拠の消去証明の**実行記録の証跡**をSakukei側で担保する(証明書PDFの生成・法的様式は外部ツール)。

**必要Provider一覧:**

| Provider | 対象 | 階級(§5.4) | 主な地雷 |
|---|---|---|---|
| redfish / ipmi | BMC電源・BIOS/RAID・ブート順・健全性 | 標準〜完全(REST=Read/Apply、List可能なら完全) | **Observeが遅い**(BMC API秒単位)・意図的off電源のmanaged境界・converging(BIOS適用中) |
| provisioner(PXE/image) | ネットブート・OSインストール起動 | 多相Task基盤(§1.3・v2+) | インストールは長時間=非同期Apply(§6.4)・ready判定はチェックサム/署名(§20.3) |
| switch_port | ポートVLAN切替(顧客分離) | 完全(NETCONF/gNMI) | 順序付きACL(§8.5)・commit-confirm(§11.2-5)・管理ポートロックアウト |
| ipam(allocator) | 顧客IP払い出し・回収 | §16 interface | Release非対称原則(§16.4)=使用中IPの再払い出し衝突防止 |
| wipe/attestation | データワイプ実行・完了署名 | 多相Task | 中断不可・証明義務・冪等再開(§9.1) |
| firmware | ファーム更新 | 多相Task(§9.1) | リブート跨ぎ・unknown≠absent |

## 3. ownership・DesiredSource・sharding設計

**顧客割当=tenant ownershipとして表現できる**。1台のサーバは、在庫状態では `ownership: platform`(プロバイダ所有の共有プール)、顧客割当中は `ownership: tenant` + `tenant: <顧客ID>` に**遷移する**。この所有権遷移そのものがライフサイクルの核心であり、tenant scopeが「顧客に貸し出した専有領域(=BMC/ポート/IPだけ、OSは境界外)」を切る。テナントのclosed-world scopeは自テナント割当分に限定され、**prune が他顧客のサーバや在庫プールを消さない**(§12.1)。DAGは扇状(管理NWコア=platform共通上流、顧客間エッジなし=独立並列)。

**DesiredSource**:割当/解約の申請は日次5-15件と低頻度で、かつ**顧客データの物理的消去という取り返しのつかない操作を伴う**ため、tenant層の即時DBSource(§13.1)よりも**FileSource(git)+ PR/承認ゲート**寄りが適切。この構成では「テナント層=即時・レビュー無」の前提を意図的に外し、割当・解約の状態遷移トリガに人の承認を挟む方が安全設計と整合する(後述§5)。inventory(1,000台の在庫台帳)は RenderedSource/外部CMDB(§7.1)から合成。

**1,000台のObserve負荷試算(BMC APIは遅い)**:これが本構成唯一の実スケール懸念。BMC Redfish の1台Observeを仮に**300ms-1s**とし、1,000台・並列度16(§6.2 のsemaphore)なら、1,000×0.5s÷16 ≈ **31秒/周**。§6.2の早期警戒線「Observe全体が間隔に対し無視できない比率」に**該当する**——BMC Observeは遅く、間隔を短くできない。緩和は §12.2 の設計済み手段:(a) 在庫(電源断)サーバは状態変化が稀なので **Observe間引き(N周に1回)**、(b) BMCがRedfishイベント/SSEを持てば **watch併用**、(c) tier別頻度(遷移中サーバは高頻度、在庫は低頻度)。1,000台は単一デーモンの実用上限(数千〜1万・§12.2)内であり、シャーディングは不要。ただし**reconcile間隔は分オーダーで許容**(Day-2のdrift検知に秒単位は要らない)なので、31秒/周は実用上問題にならない——律速するのはObserveではなくプロビジョニング所要時間(§7参照)。

## 4. render(inventory/allocation/secret)の使い方

**inventory合成(render フェーズ1・§7.1)**:1,000台の在庫台帳(モデル・ラック位置・BMC IP・スペック)を外部CMDB/ファイルから合成。世代・スペック混在の10モデルは、モデルごとのテンプレート(§7.5 render フェーズ2)で「このモデルのBIOS/RAIDプロファイル」を展開する。CMDB不達時は前回生成物を保持(§7.3)=在庫が空desiredで全削除される事故を防ぐ(本構成では最重要)。

**IP/VLAN払い出し(allocator・§16)**:顧客IPは割当時にallocatorから払い出し、解約時に回収。**Release非対称原則(§16.4)が本構成の急所**:解約で理想からサーバが消えても、`(a)下流の現実削除(ワイプ完了・ポート切断)をObserve確認してからRelease`、`(b)返却後cooldown/検疫TTL`(前顧客IPの即時再払い出しを避ける)、`(c)pruneable:false下位残存中はRelease保留`。これにより「解約手続き未完のまま次顧客にIP再割当→誤配送」を防ぐ。platform層のPR必須割当では reserve→confirm(§16.3)でPR却下時のリークも防げる。

**BMC資格情報1,000台のローテーション**:1,000台のBMCは典型的な**層B(レガシー機器=静的資格のみ)**(§15.2)。v1暫定では SecretRef(Vault保存)+定期rotate(§14.5)、credential-broker導入後は CredentialProvider経路(§15.5)へ移行。rotationは「新値生成→BMCに設定→旧無効化」の順序付き手続き=Workflow(§14.4)。1,000台一斉rotateは §10.5 の段階適用(canary→broad)+ invariantで「一度に切断するBMCを制限」。BMC初期共通パスワードは §14.3「既存・手動登録→自動生成/rotationの系に合流」で、初回接触時に個体別資格へ置換。

## 5. 安全機構の適用(最重要)

**最悪事故「稼働中の顧客サーバを誤って在庫扱い→ワイプ」への多層防御**。level-triggeredは「速く確実に破壊する能力の裏返し」(§10.1)であり、ここでは物理的なデータ消失=法的責任に直結する。防御を層で積む:

1. **pruneable:false 既定(§8.3)**:ワイプ/在庫戻しは破壊的操作の最たるもの。顧客割当サーバResourceは `pruneable: false` を既定とし、closed-world scopeで「理想に無い=在庫化」と判定されても**自動でワイプさせない**。
2. **ワイプはResource収束ではなくWorkflow(§9.2)**:在庫化=収束で自動実行ではなく、解約Workflowの明示トリガでのみ起動。「理想からサーバが消えた」だけでワイプは絶対に発火しない——§16.4と同じ「理想消滅では破壊しない」規律。
3. **Workflow不変条件(invariant)**:解約Workflowのinvariantに「対象サーバが**顧客解約フラグを持つ**」「顧客VLANが既に切断されている」「稼働中トラフィックが無い(health検証)」を置き、破れるなら進まない(§9.2)。稼働中サーバは定義上このinvariantを満たさないため、Workflowが構造的に停止する。
4. **承認ゲート(§10.5)**:ワイプ前に `manual_approval: required` を必須化。`StageAwaitingApproval` Eventで人へ通知、承認API経由でのみ次stepへ。承認事実は監査記録(§10.5・§17.5)。DC常駐オペレータ8名の運用体制と整合。
5. **rate limit + halt(§10.2)**:「破壊的側に重み付け」で、複数台の在庫化/ワイプが同時発火したら halt-destructive-only。誤ってCMDB全体が壊れ「全850台が在庫扱い」になっても、破壊的変更のrate limitが即halt。
6. **remediation: alert-only(§10.2)**:顧客利用中サーバは alert-only 固定(爆発半径ゼロ)。drift検知は続けるが自動修復しない。
7. **原因タグ(§10.3)**:在庫化判定が「A.意図的(解約PR)」か「B.drift(CMDB読み損ね)」か「E-inventory(CMDB変更)」かを区別。人のcommit(A)由来でない在庫化は破壊に繋げない。

**評価**:設計の安全機構がこの最悪事故に対して**多層で正面から効く**。特に「破壊は理想消滅ではなくWorkflow明示トリガ+invariant+承認ゲートでのみ」という多重化は、本構成の核心リスクを構造的に封じている。ここがSakuteiが本構成に最も価値を出す点。

## 6. 段0ブートストラップの当てはめ

段0(Proxmox 3ノード+統合Ceph+VM-HA、§19.2)に Vault/credential-broker/reconciler を載せる形はそのまま当てはまる。**管理NW到達性の最小核とOOB/コンソールサーバ(§19.3・L2.5)は1,000台BMC規模で必須**——管理NWが死ぬと credential-broker が全BMCに到達できず全盲(§15.5)になるため、OOB経由の人手復旧経路を段0外に確保する。BMC/PXE/イメージサーバ/スイッチ管理ポートへの到達性の最小核は段0、各BMC個別設定・各ポート設定は段1(§19.3の表そのまま)。git外部・稼働必須依存にしない(§19.4)も維持。§19.5「1コミットで全削除が原理的に可能」がここでは「全顧客サーバワイプ」に相当するため、rate limit+halt+remediation modeの段0必須要件(§19.5)がこの構成で最も切実。

## 7. 成り立たない点・苦しい点・設計ギャップ・必要な拡張(最重要・忖度なし)

- **G1. クリティカルパスがほぼ v2+**:本構成の主戦場である **Task/Workflow・承認ゲート・段階適用・credential-broker が全て v2以降**(§24.2)。v1が持つのはResource収束・render・rate limit・importまでで、**ライフサイクル遷移(=この事業の商品そのもの)を担う手続きプリミティブが v1 に無い**。構成07と違い即時DBSource/シャーディングは不要だが、代わりにTask/Workflow機構の完成度が事業成否に直結する。v1では「在庫/割当/利用中のBMC・ポート・IPを宣言的に維持する」ところまでしか動かず、プロビジョニング/ワイプ自動化は動かない。

- **G2. 30分プロビジョニング目標 vs 収束周期の整合(最重要)**:目標「手作業込み4時間→30分」の律速は **Sakuteiの収束周期ではなく、物理作業そのものの所要時間**(BIOS/RAID適用・OSインストール・リブート数回)。これは §6.7「収束は複数Cycleに跨る」「1台の立ち上げが数十Cycleに跨る」で正しくモデル化できる——プロビジョニングは in-flight(§6.4)+ converging(§10.4)+ ready_condition(§6.7)の組み合わせで、`bare_server(電源投入)→installed→network_verified→customer_ready` と段階解放される。**ここでの緊張点は「30分の内訳のうちSakukeiが足せる/削れる時間」**:(a) 収束はポーリング型なので、あるフェーズ完了を次周のObserveで検知する遅延(reconcile間隔ぶん)が各遷移に加算される。30分予算に対しreconcile間隔を**プロビジョニング中サーバだけ短周期**(tier別頻度・§12.2)にしないと、10フェーズ×間隔ぶんのポーリング遅延が積算して目標を圧迫する。(b) 逆にSakukeiの価値は「手作業込み4時間」の**手作業ゼロ化**(BMC設定・PXE・VLAN・IPを人手からWorkflow自動化)であり、削減の主因はそこ。**結論:目標達成は収束周期ではなくprovisioner/Workflowの並列度と各Taskの実所要に律速される。収束周期は「プロビジョニング中サーバは短周期ポーリング」で吸収可能だが、この分周(tier別頻度)はv2+**。

- **G3. 消去証明の法的様式はSakukei外**:NIST SP 800-88準拠の**消去証明書の生成・署名・法的様式・顧客への発行**はSakukeiの責務外。Sakukeiが担えるのは「ワイプWorkflowが規定手順で完了したことのappend-only監査証跡(§17.5)」まで。証明書PDF生成・ワイプツール(例:certified erasure)の署名検証・監査法人向けフォーマットは外部ツール連携で、Sakuteiは実行記録の改竄耐性アンカー(§17.5・git+連鎖ハッシュ)を提供する下半分に留まる。証明義務の**契約充足はこの外部連携が正しく組まれて初めて成立**する。

- **G4. provisionerは設計書で名前だけ・実装未定義**:§1.3で「起動方式とOS種別を分離した汎用ベアメタル導入基盤」と定義されるが、**具体interface・多相Taskの状態機械・PXE/iPXE/Redfish Virtual Media・cloud-init連携の実装は本設計書に無い**(参照実装文書送り・§1.5)。10モデル混在のBIOS/RAIDプロファイル差、UEFI/Legacy混在、ベンダー固有Redfishの癖(§1.5「この機種のBMC APIの癖」)を吸収する層が丸ごと新規開発。ここが最大の実装ギャップで、Metal³/MAAS/Foreman相当を作るか統合する話になる。

- **G5. BMC ObserveのレイテンシとConverging検知**:BMC APIは遅く(§3試算)、BIOS/RAID/ファーム適用中は「作業中」を返さないベンダーが多い。§10.4 のTier2(自傷猶予settle)/Tier3(振動推定)で床は張れるが、リブート跨ぎ(§9.1「unknown≠absentでリブート中と解釈」)のタイムアウト設計を機種ごとにチューニングする必要がある。twin(§22.5)/フェイクProvider(§22.2)でのBMC障害注入検証が必須。

- **G6. 承認ゲート依存の運用負荷**:安全側に倒すほど承認ゲート(§5)が増え、日次5-15件×複数ゲートを8名で捌く。自動化と安全のトレードオフで、承認を厚くしすぎると「30分目標」と競合する。どのstepに人を挟むか(ワイプ前は必須、BIOS設定は自動 等)の線引きが運用設計の肝。

**必要な拡張の総量**:Task/Workflow + 多相Task状態機械 + 承認ゲート + 段階適用 + credential-broker(全てv2+コアロードマップ)+ provisioner実装(新規・Metal³/MAAS相当)+ 消去証明の外部ツール連携 + tier別Observe頻度。前段はSakukei v2ロードマップ、provisionerと証明連携はSakukei外/参照実装。

## 8. 総合判定

**○ 条件付き成立**。

**理由**:本構成はSakuteiの**設計思想と最も素直に噛み合うシナリオの一つ**である。(1) 主戦場が「宣言的状態の維持」ではなく「ライフサイクル遷移=多相Task/Workflow」であり、§9・§20.2が正面から想定した領域。(2) 「顧客利用中はOSに触らない」がmanaged境界(§11.2-4)・ownership遷移(§12.1)・alert-only(§10.2)で綺麗に表現できる。(3) 最悪事故「稼働サーバの誤ワイプ」に対し pruneable:false・Workflow明示トリガ・invariant・承認ゲート・rate limit・原因タグの多層防御が構造的に効く(§5)——ここがSakuteiの最大の価値。(4) 1,000台のBMC Observe負荷は単一デーモン上限内で、間引き/tier別頻度で吸収可能。即時性やシャーディングの緊張は無い(構成07より遥かに楽)。

**成立条件**:(1) Sakukei v2ロードマップの **Task/Workflow・多相Task・承認ゲート・段階適用・credential-broker** を完遂する(v1では宣言的維持のみで、事業の核であるプロビジョニング/ワイプ自動化が動かない)。(2) **provisioner を実装**する(§1.3は名前のみ、10モデル混在のBIOS/RAID/UEFI・ベンダー固有Redfishを吸収する新規基盤=Metal³/MAAS相当)。(3) **消去証明の外部ツール連携**を組み、Sakukeiの監査証跡(§17.5)と証明書生成を接続して証明義務を充足する。(4) **プロビジョニング中サーバのtier別短周期Observe**を用意し、収束周期のポーリング遅延が30分予算を圧迫しないようにする(律速自体は物理作業時間であり、収束周期ではない)。この4条件を満たせば ◎ に近い成立となる。構成07(△)と異なり、Sakuteiが**事業の下半分ではなく大半を担える**——上位に必要なのは受付ポータルと課金程度で、インフラ制御の本体(ライフサイクル・分離・安全)はSakuteiに載る。ここが本構成の相対的な有利点である。
