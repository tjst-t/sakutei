## 2. 判定変更の理由

**可視化道具:○ → ◎ に引き上げ。** 決め手は3点。

1. **G1 の解消が構成の性格を変えた。** 前回、本構成の本体は「Observe すらできない機器」であり、それを型で持てないことが最大の弱点だった。§23.9 の `ledger_only` により、L5 は「射程外の運用回避」から「台帳に第一級で存在する unknown 資産」へ格上げされた。`unknown≠absent` の台帳版として、Excel 台帳の電子化・正典化(前回 §4 で価値ありと評価)が、いまや placeholder のハックではなく設計の正規機構になる。しかも `ledger_only` が List 集合演算から除外されるため、L5 が prune の巻き添えで消える経路も同時に塞がれた(G1 と G2 の相乗)。

2. **G2 の解消で「安全に始める」の底が上がった。** 前回は多層緩和(prune 禁止・halt-destructive-only・freeze・データ面独立)を並べたが、`halt-destructive-only` が「その周の超過分保留」であるがゆえに「毎周10件ずつ50周で全消し」が通る穴が残っていた。CHG-B1 の累積時間窓予算と `max_scope_fraction`、CHG-B2 の List 急減 halt がこの穴を塞いだ。「触ると壊れる」環境で最も恐れた事故モードが、瞬間量だけでなく時間軸でも監視されるようになった。

3. **G8 の部分解消で段0 の足元が固まった。** レガシー DC 内に新規で段0 を建てる構図(前回 §6)の最大の懸念——段0 が旧管理NW に依存する自傷——が §19.7/§19.3 で型ガードされた。

**収束エンジン:△ のまま(判定変更なし)。** レガシー中核(VMware 5.5・旧 NW・触ると壊れる機器)を自動収束させないことが正しい、という前回結論は v2.3 でも不変。むしろ §23.9 が「観測できないものは収束対象にしない」を型として明言したことで、「収束させないのが正解」がより明確な設計判断になった。収束の真価は依然として第3年の greenfield 部分でのみ発現する。

## 3. v2.3 で新たに気づいた問題・残存課題

- **N1. `last_verified` の運用が v1b、型は v1a という時間差。** §23.9 は「型は v1a、運用フローは v1b」。本構成は L5 が大量にあるため、v1a だけ導入して v1b を待つ段階では、`ledger_only` 資産を台帳に置けても `last_verified` の health 述語運用(§17.2 は v2)が回らない。実際に「目視確認せよ」が昇る仕組みは、health(observability as Resource)が v2 送りである点と噛み合わせて確認が要る。台帳に載せる価値は v1a で出るが、鮮度管理の完成は後段。

- **N2. v1b が本構成の実質的な主戦場だが、内容が厚い。** import・Sync Mode・AllocationAuthority・ready_condition・capacity gate が v1b に集約された(§24.1b)。本構成の第1年(可視化)で価値を出す import と Sync Mode はまさに v1b。つまり **v1a だけでは「alert-only の実態レポート」までしか出せず、継続的な現実→git 記録(Sync Mode)には v1b が要る**。3年プロジェクトの第1〜2年は v1b の完成に律速される。ロードマップ上、v1a→v1b の到達時期がプロジェクト計画の前提になる。

- **N3. §8.6 の List 厳格化が L4 を締め出す副作用。** CLI scrape の List は「打ち切り検知で error」「partial は prune 保守側」の対象になりやすく、L4 は Sync Mode・prune の実用対象からさらに外れる方向。安全側だが、L4 の可視化価値(前回 △)は実務上さらに縮む可能性がある。L4 は「読めるが継続管理には乗せない」層と割り切るのが妥当。

- **N4. G5(組織リスク)は依然として最大の非技術リスク。** 型がどれだけ堅牢になっても、drift 報告を捌く責任主体の不在は解けない。v2.3 でも見送り(F M-7)。本構成の成否は依然ここに乗る。

## 4. この構成で成立させるための条件(更新版)

**可視化道具として ◎ 成立させる条件:**

1. **対象を Observe/List 可能な層(L0〜L3)に限定し、L4 は「読むが継続管理しない」と割り切る**(§8.6 の List 厳格化で L4 は Sync/prune から実務上外れる前提で計画)。
2. **import → alert-only を厳守**(§23.2/23.3)。当面 Apply しない。
3. **L5(観測不能機器)は §23.9 の `observability: none` + `ledger_only` で台帳に第一級で載せる**(前回の placeholder 回避から正規機構へ更新)。`last_verified` で鮮度を管理するが、health 述語運用の完成は v1b/後段に依存する点を織り込む。
4. **prune は §23.4 の N 日 diff ゼロ昇格を厳守しつつ、CHG-B1/B2 の累積予算・List 完全性検証を有効化**して初めて auto を検討する(前回の「多層緩和」に時間窓・List 検証が加わり底が上がった)。
5. **段0 は §19.7/§19.3 に従い、自身の到達資格を収束対象から除外し、管理NWコアは v1 alert-only 限定**。OOB/コンソールサーバは物理的に別途確保。
6. **git 単一書き込み経路と「drift 報告を捌く責任主体」を組織的に確立する**(G5・依然として最大リスク・型では解けない)。

**収束エンジンとしての結論(更新版):**

レガシー中核は §23.7-4/§23.9 の通り**永久 alert-only ないし収束対象外(`ledger_only`)が正しい運用**。v2.3 で「観測できないものは収束しない」が型で明示されたため、これは逃げではなく設計思想の忠実な適用。収束の価値は第3年の新基盤 greenfield(§23.7-3・最初から auto)でのみ本格発現する。本構成における Sakutei の正しい役割は前回同様「**第1年の実態暴き(import + alert-only、L5 は ledger_only で台帳化)と第3年の greenfield 化**」であり、中間のレガシー中核は観測可能範囲だけ alert-only で台帳化して廃止へ送る——この割り切りが成立条件そのものである、という結論は維持される。ただし v2.3 は、その割り切りを「型で表現できる」ようにした点で、可視化道具としての実用度を明確に押し上げた。
