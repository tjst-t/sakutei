# 対象構成20:ベアメタルホスティング/専用サーバプロバイダ — Sakutei適用可能性 再評価(v2.3)

**新判定:○ 条件付き成立(判定は据え置き。ただし「事業の核が動き始める到達点」が v2 から v1.5 へ前倒しされ、成立の確度が実質的に上がった)**
— v2.2 では核となる手続きプリミティブが全て v2 送りで「v1 では商品が一切動かない」状態だったが、v1.5(単純Task+最小Workflow〈直列+不変条件+手動承認ゲート〉)の前倒しにより、**ワイプWorkflowの安全骨格と割当の承認ゲートが v1.5 で成立**する。一方、10モデル混在のプロビジョニングを担う**多相Task状態機械は v2 のまま**であり、完全自動化は依然 v2 待ち。

**前回判定(v2.2時):○ 条件付き成立**

構成前提は前回§1のまま(在庫1,000台・10モデル混在・稼働率85%≈850台、BMC 1,000台、PXE/イメージ、スイッチポートVLAN、IPAM、日次割当5-10件・解約3-5件と低頻度だが1件が重い経路依存手続き、運用8名)。本質は宣言的維持ではなく**ライフサイクル遷移(多相Task/Workflow)**。

## 2. 判定変更の理由(据え置きだが確度が上がった理由)

総合判定は前回同様 **○ 条件付き成立**。ただし v2.2 の「○」は「事業の核(プロビジョニング/ワイプ自動化)が v2 まで一切動かない」という重い前提の上での条件付きだった。v2.3 で以下が変わり、**成立の確度が実質的に前進**した。

- **G1 の性質が「未前倒し」から「部分前倒し」へ**:本構成の最悪事故防御(§5)の骨格——pruneable:false・ワイプはResource収束でなくWorkflow明示トリガ・invariant・手動承認ゲート——は、いずれも v1.5 の「最小Workflow(直列+不変条件+手動承認ゲート)」で**そのまま表現できる**。解約Workflowの invariant「顧客VLAN切断済み」「稼働トラフィック無」「解約フラグ有」は静的な直列+不変条件検証で足り、動的select・自動canaryを要さない。つまり**この構成が Sakutei に最も価値を出す部分(構造的な誤ワイプ封じ)が v2 でなく v1.5 で立ち上がる**。前回§7で「事業の商品を担う手続きプリミティブが v1 に無い」と断じた点の、少なくとも安全骨格側は v1.5 に降りた。

- **1,000台BMC実機レイテンシ再試算(精査結果)**:§12.2 の実機表で BMC Redfish は「高速REST 0.15s」帯だが、前回§3で用いた保守値 0.3-1s(BMC APIは秒単位が現実)で再計算する。並列度16で 1,000×0.5s÷16 ≈ **31秒/周**、最悪 1s なら **62.5秒/周**。§6.2 の早期警戒線は「30s間隔に対し Observe 予算10s」であり、30s間隔なら 1,000台×0.5s は明らかに超過する。しかし本構成の reconcile 間隔は**分オーダーで許容**(Day-2 drift検知に秒単位不要)なので、間隔を 5分に置けば 62.5秒/周でも予算比は健全。よって **1,000台は単一デーモンで成立**(表の「REST/標準階級=数千〜1万」内)、シャーディング不要という前回結論は維持される。律速はObserveでなく物理作業時間(BIOS/OS/リブート)である点も不変。

- **プロビジョニング中サーバの短周期Observe要求(精査結果)**:ここが tier別頻度の**方向性のミスマッチ**として残る。§12.2/CHG-C2 が v1b に前倒したのは「**安定リソースを N 周に1回に間引く**」低頻度化 seam であり、明文の目的は在庫サーバのような不変リソースの負荷削減。プロビジョニング中サーバが要るのは逆の**高頻度化(各フェーズ完了を次周で速く検知して30分予算内に10フェーズ遷移を収める)**。`tier` で頻度を上書きできる型の余地は v1b で入るが、「遷移中サーバだけ短周期」を実効化する最適化は §24.2 で v2。したがって G2 は「型の器は v1b・実効チューニングは v2」の部分解消に留まる。ただし前回§7の結論どおり**律速は物理作業時間**なので、収束周期側の遅延は 30分予算の主因ではなく、この未解消が判定を下げるほどではない。

## 3. v2.3で新たに気づいた問題・残存課題

- **N-1. v1.5 の最小Workflowは「直列」限定——ワイプの並列度が制約される**:§24.1.5 は最小Workflowを one-at-a-time(直列)に限定し、動的select・自動段階ロールアウトは v2。解約Workflow自体は1台単位の直列で表現できるが、**日次解約3-5件×多相Task(ワイプ→ファーム更新)を並列に流す運用**をすると、v1.5 の骨格では「複数解約の同時進行を安全に束ねる」動的な調停(隣が今どのフェーズか)が持てない。少量なので実害は小さいが、ワイプ本体を担う多相Task(§9.1多相型)が v2 である以上、**v1.5 で成立するのは「ワイプの起動ゲートと不変条件」までで、ワイプ実行のリブート跨ぎ状態機械は v2 待ち**。G1 部分解消の内実はここに集約される。

- **N-2. credential-broker が v2 据え置きで、1,000台BMC資格の到達性が段0の全盲リスクに直結**:§24.2 で broker は v2、v1 は SecretRef 直結(§14.5)。前回§6で指摘した「管理NW断→broker全盲」に対し §19.7(CHG-B3)が段0コールドスタート順序と自己収束自傷除外を固めたのは前進だが、**1,000台規模のBMC個体別資格の動的発行(§15.2 層B)は v2 まで来ない**。v1 は SecretRef(Vault保存)+定期rotate(§14.5)の静的資格運用に留まり、rotationはWorkflow(§14.4)で段階適用するが、1,000台一斉rotateの canary→broad 自動段階ロールアウトも v2(§24.2)。v1.5 の手動承認ゲート付き直列Workflowで代替は効くが運用負荷は高い。

- **N-3. remediation schedule と「顧客利用中サーバ alert-only 固定」の関係整理が必要**:§10.8 は時間帯でmodeを張る宣言で、顧客利用中サーバは時間帯に関係なく恒久 alert-only 固定であるべき(§5-6)。schedule と ownership 別の固定modeが**どちらが優先か**は §10.8 が freeze>schedule の優先しか明記せず、ownership由来の恒久alert-onlyとの合成規則は本構成で要確認(保守窓に顧客サーバが誤って auto に切り替わらない保証)。運用パラメータ(§26.3)で埋める領域。

- **N-4. provisioner(G4)未解消が判定の上限を規定**:v2.3 は Sakutei コア設計の穴を広範に埋めたが、**本構成の商品価値の半分を担う provisioner は名前定義のまま**。Sakutei が v1.5+v2 を完遂しても、provisioner(Metal³/MAAS相当)を別途実装・統合しない限りプロビジョニング自動化は動かない。これは Sakutei の責務外(§24.3 委譲)として正しいが、「Sakutei で成立」の表現がこの外部実装込みである点は v2.2 と変わらず明示が要る。

## 4. この構成で成立させるための条件(更新版)

前回の4条件を、v2.3 の前倒しを反映して更新する。

1. **【前倒しで前進】安全骨格は v1.5 で立ち上げる**:pruneable:false・ワイプはWorkflow明示トリガ・invariant・手動承認ゲート・remediation schedule は v1.5 で成立。**まず「誤ワイプを構造的に封じる可視化+承認運用」を v1.5 で価値実証**できる(前回は v2 待ちだった)。あわせて §10.2 累積破壊予算+§8.6 List急減halt+§7.6 incomplete≠empty で「CMDB読み損ね全ワイプ」を塞ぐ(v1a)。

2. **【依然 v2】自動化本体は v2 完遂が必要**:ワイプ/ファーム更新の**多相Task状態機械**(リブート跨ぎ・べき等再開)、**1,000台BMC資格の credential-broker**、**1,000台一斉rotateの自動段階ロールアウト+canary**は §24.2 で全て v2。事業のフル自動化はここに依存する。

3. **【Sakutei外・不変】provisioner を実装/統合する**:10モデル混在のBIOS/RAID/UEFI・ベンダー固有Redfishを吸収する Metal³/MAAS相当の新規基盤(§1.3 は名前のみ)。**これが最大の実装ギャップで v2.3 でも未着手**。

4. **【Sakutei外・強化】消去証明の外部ツール連携**:証明書PDF生成・署名検証は外部。Sakutei 側は §17.5 の即時push監査証跡(WORM/SIEM・別権限プロセス)で NIST SP 800-88 の実行記録側を担保——v2.3 で改竄窓が 24h→毎周に縮み下半分が強化された。

5. **【新規・型はv1b/実効はv2】プロビジョニング中サーバの短周期Observe**:tier別頻度の器は v1b seam で入るが、遷移中サーバの高頻度化の実効チューニングは v2。ただし律速は物理作業時間なので 30分目標への影響は限定的。reconcile間隔は在庫向けに分オーダーで置き、1,000台BMCは単一デーモン(31-62.5秒/周)で成立。

**総括**:本構成は依然として Sakutei の設計思想に最も素直に噛み合うシナリオの一つであり、v2.3 で判定 **○** は据え置き。変化は「事業の核が動く到達点」が **v2 一括 → v1.5(安全骨格)+ v2(自動化本体)** に分解され、**価値実証の初期到達点が前倒しされた**こと。構成07(△)と異なり、Sakutei が事業の大半を担える相対的有利は不変で、v1.5 で誤ワイプ封じの中核価値が先に立ち上がる分、成立の確度は前進した。上限を規定するのは Sakutei 外の provisioner(G4)である。
