# 対象構成16:CDN/エッジPoPネットワーク — Sakutei 適用可能性 再評価(v2.3)

**新判定:○ 条件付き成立(v1.5+v1b で"日常運用+段階撤退の骨格"まで前倒し成立、自動段階BGP展開のみ v2 依存に縮小)**
**前回判定(v2.2時):○ 条件付き成立(ただし PoP ライフサイクル全体が v2 機能に全面依存)**

前回も今回も総合判定の記号自体は「○ 条件付き成立」で不変だが、**条件の中身が大きく前進した**。前回は「v2(Task/Workflow/承認ゲート/段階適用/シャーディング/分散Executor)が実装済みでなければ不成立に落ちる」という重い前提だったのに対し、v2.3 では v1.5(単純Task+最小Workflow=直列+不変条件+手動承認)と v1b(採番・capacity gate・ready_condition・tier別Observe seam)で PoP 撤退・日常運用・段階撤退の骨格までが v1 系に降りてきた。残るのは「自動段階ロールアウト(canary 自動判定込みの PoP 1→5→全部 BGP 展開)」と「本番規模の分散Executor/シャーディング」に絞り込まれた。

## 2. 判定変更の理由

記号は「○ 条件付き成立」で不変だが、**成立に必要な前提の"重さ"が一段軽くなった**。前回レポートの総合判定は「日常運用は◎級だが、PoPライフサイクルと40拠点規模が v2 に全面依存するため ○」だった。v2.3 の核心的変化は次の3点である。

第一に、**手続きの最小形(単純Task+最小Workflow+手動承認ゲート)が v1.5 に前倒し**された(CHG-C1)。これにより「PoP撤収を drain→退避確認→BGP撤回→物理撤去 と不変条件付きで直列に、各段人手承認で刻む」という、この構成の生命線が **v2 を待たずに** 表現可能になった。前回「v1コアだけでは PoP ライフサイクルは回らない=v2実質必須」と断じた最大の穴が、v1.5 で塞がる。

第二に、**anycast撤退gate連携のフックが第一級化**された(CHG-D2 §11.4)。前回「BGP撤退の安全判定を外部トラフィック制御/監視シグナルにgateする連携フックが設計に明示されていない=ギャップ」と指摘した点に対し、`external_owner` による除外宣言と「外部の収束結果を ready_condition として Observe で待つ一方向協調seam」が明示的に追加された。トラフィック制御プレーンが「N拠点で迂回健全」を出すのを ready_condition 化し、撤収Workflowの承認ゲート前段に置く設計が、新プリミティブ無しで書けるようになった。

第三に、**スケール算術が実機レイテンシで書き直され(CHG-C2)、40拠点の可否が数値で評価可能**になった。§12.2 の新表により、CDNキャッシュ/エッジルータの Observe 手段別に上限台数が判明する(後述)。加えて tier別Observe seam が v1b に前倒しされ、「毎周全PoP Observe」の律速を v1 段階で緩和できるようになった。

これらにより「v2 が全部揃わないと不成立」から「v1.5+v1b で骨格は成立し、**自動段階ロールアウトと本番規模の分散化のみ v2 依存**」へと、条件が具体化・軽量化した。判定記号を上げなかったのは、40拠点×無人×地理分散という本番規模での「単一デーモン集中の律速」と「自動無人段階展開」がなお v2 に残り、かつ OOB(#7)の構成側実在性リスクが解消しないためである。

## 3. 40拠点・100ms超Observe の実機レイテンシ再評価(§12.2 新表適用)

v2.3 の算術は「30s間隔に収まる上限台数 ≈ 10s(Observe予算)× 16(並列度)/ 1回レイテンシ」。この構成に当てはめる:

- **CDNキャッシュ(Varnish/nginx、REST/HTTP的の設定・版数取得)**:高速REST寄り(0.15s)なら上限 ~1,067。ただし**地理分散で管理系RTTが100ms超**乗るため実効レイテンシは 0.15s+RTT。40PoP×キャッシュ4〜10台=160〜400リソースは、RTTが乗っても単一デーモンの射程内。
- **エッジルータBGP(NETCONF/gNMI)**:1.5s級→上限 ~107。40PoP×2台=80台はギリギリ単一デーモンで収まるが、**100ms超RTTが加わると 1.6s 相当となり余裕が薄い**。
- **CLI scrape の旧機種が混じる場合**:4.0s級→上限 ~40。ロングテール機器がCLIなら40拠点で早期警戒線(§6.2:間隔30sに対しObserve 10s超)に触れる。

結論:**総リソース数(数百〜千規模)は v2.3 の実機算術上、単一デーモン+tier別Observe間引き(v1b)で本番射程に収まりうる**。前回「単一リージョン集中は本番規模で律速」の懸念は、(a)PoP近傍/リージョンにシャードを寄せ管理系RTTを縮める(v2 シャーディング)ことで根治するが、(b)v1b の tier別Observe seam で安定PoPを間引けば**単一デーモンでも数百規模までは延命可能**という現実解が v2.3 で開けた。ただし100ms超RTTがNETCONF/CLI階級のレイテンシに直接加算される点は、40拠点を1プロセスで束ねる限り消えない律速であり、地理シャーディング(v2)の税金は本番では依然推奨。

## 4. v2.3 で新たに気づいた問題・残存課題

1. **anycast協調seam が「一方向・受動」に閉じる設計上の限界**。§11.4(b)は「Sakuteiから外部へ指示は出さない/観測して待つ一方向」と明記する。これは健全な境界だが、**BGP撤退の"能動的な迂回検証"(撤回前に実際にトラフィックが迂回するか試験)は canary Workflow(§17.3)であり v2**。v2.3 でフックは第一級化したが、「受動的に ready を待つ」までで、能動検証は依然 v2 依存。撤退安全判定を外部監視の受動シグナルだけに委ねる場合、外部監視の健全性が新たな暗黙依存になる。

2. **自動段階ロールアウトが v2 に残ったことで「無人運用」との緊張が残存**。運用6名グローバル分散・無人拠点というこの構成では、PoP撤退の各承認ゲートに人が張り付く必要がある(v1.5 は手動承認のみ)。§10.5 の manual_approval タイムアウト(24h で halt)はあるが、**無人・少人数分散で「health自動ゲートで無人昇格」ができない**のは運用実態と最も噛み合わない残存点。この構成に限れば自動段階ロールアウト(v2)の需要は高く、v1.5 は緩和にとどまる。

3. **Release非対称の List依存が anycast prefix/ASN に効くか要確認**(CHG-A4/§16.4新)。v2.3 は「削除完了= List結果に現れないこと(集合演算)」「Release は Lister を持つ下流にのみ許可」と厳格化した。これは PoP撤収時の ASN/loopback IP/anycast prefix 解放の安全性を大きく高める(誤解放=別PoP再割当=経路事故 を List根拠で防ぐ)一方、**allocator の下流(BGPセッション・prefix広告)が List完全性(§8.6)を満たす provider で実装されている必要**がある。List できない機器の Release は保守側保留に倒れるため、撤収が「物理は撤去したがIPが返らない」状態で滞留しうる。§16.6 の「サイトごと静的プール分割」は40PoPの分断耐性に有効だが、anycastは全PoP同一prefixのため prefix プールのサイト分割は素直に効かない(loopback/管理IPには効くが anycast prefix は共有)——この構成特有の要検討点。

4. **累積時間窓予算(§10.2)の window/max_deletes が anycast の"最低N拠点広告"不変条件と別レイヤ**。destructive_budget は「24hで50削除」等の量的ガードだが、「常にN PoPが広告」という anycast の質的不変条件は Workflow invariant(§9.2 min_active 相当)で別途書く必要がある。両者は補完的で、**撤退設計では両方を明示的に設定しないと**「予算内だが最低広告数を割る」穴が残る。

5. **段0-minimal(§19.8)はこの構成に無関係**だが、**段0本体の Ceph SPOF(§19.7)は中央リージョン集約で40PoPの制御面を握るため影響大**。v2.3 で SPOF が正直化・障害ドメイン分散が人手要件化されたのは前進だが、40PoPの制御を1つの段0 Ceph に集約する設計は、その段0全損=40PoP全盲を意味する。地理分散シャーディング(v2)で段0も複数リージョンに置けるまで、この集約リスクは残る。

## 5. この構成で成立させるための条件(更新版)

前回条件(a)〜(d)を v2.3 の粒度で更新する:

- **(a′) 手動段階撤退で妥協するなら v1.5+v1b で成立**。PoP撤収を「最小Workflow(直列+invariant+手動承認)+累積時間窓予算+Release非対称(List根拠)」で組む。**自動段階ロールアウト(無人 health 自動ゲートでの1→5→全部 BGP展開)を要件とするなら v2 が必須**。この構成の無人運用実態を踏まえると、実運用では v2 の自動段階ロールアウトを強く推奨。
- **(b′) 本番40拠点規模では地理シャーディング+分散Executor(v2)を推奨**。ただし v1b の tier別Observe seam で**数百規模までは単一デーモンで延命可能**。段0を複数リージョンに置く必要が出た時点で分散化(v2)へ。fencing 契約(§12.2/§16.6)は割当表の型定義時から持たせる(後付け不可)。
- **(c′) anycast撤退gate連携は §11.4 の ready_condition 一方向seamで設計**する。トラフィック制御プレーン/監視の「迂回健全」シグナルを ready_condition 化し、撤収Workflowの承認ゲート前段に前置。**能動的な迂回検証まで要るなら canary(§17.3・v2)が必要**。外部監視の健全性が撤退安全判定の暗黙依存になる点を運用で担保。anycast「最低N拠点広告」は Workflow invariant で、量的暴走は destructive_budget で、**二重に**設定する。
- **(d′) 無人PoPのOOB/Break Glass L2.5 は依然構成側で現実的に用意**(v2.3 でも設計守備範囲外)。40無人拠点のコンソールサーバ/OOB網のコストが構成側で担保されないと段0原則が崩れる。ここは v2.3 でも改善しない残存条件。
- **(e′・新規)Release下流のList完全性を保証する provider**。ASN/IP/anycast prefix の下流(BGPセッション・広告状態)が §8.6 List完全性を満たす provider で実装されていること。満たさない機器は Release が保守側保留に倒れ撤収が滞留する。anycast prefix は全PoP共有のためサイトごとプール分割(§16.6)が素直に効かない点に留意した allocator 設計を要する。
