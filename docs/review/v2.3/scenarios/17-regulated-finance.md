## 2. 判定変更の理由（v1.5 最小 Workflow の効果の精査）

前回 ○ に留めた最大の理由は「Apply を Sakutei にやらせる本命価値（手順書の Workflow 化）が v2 送り」だった。v2.3 はこれを **v1.5 に前倒し**し、律速が緩んだ。以下、指示された3点を精査する。

**(a) v1.5 の手動承認ゲートは 4-eyes／N-of-M に届くか — 届かない。**
§24.1.5 の最小 Workflow は「直列＋不変条件＋**手動承認ゲート**」で、§10.5 の承認 API（`POST .../approve`）を使う。これは**単一承認**であり、承認 API 自体は認可を持たず「誰が叩けるか」を上位 IdP に委譲する。したがって v1.5 の承認ゲートは「**人間の承認が変更の直前にある**」という一次要件（承認直前性）は構造的に満たすが、「**申請者と承認者の分離（職務分掌）**」と「**二人承認（N-of-M）**」は満たさない。CHG-B6 で「platform 破壊的大量変更は A タグでも承認必須」が入ったが、これも単一承認ゲートの発火条件が増えただけで、二人承認化ではない。→ **4-eyes は依然として上位プラットフォーム側の拡張（承認者 ID の二重取得・申請者除外・CAB 連携）が必須**。v1.5 は 4-eyes の「片翼（承認の機械化）」までしか担えない、という前回の評価は維持される。

**(b) remediation schedule は「人間の承認が変更の直前にある証明」に使えるか — 部分的に、かつ条件付き。**
§10.8 の schedule は「保守窓のみ auto」を宣言する。保守窓が CAB 承認済み作業時間と一致する運用にすれば、「**承認された窓の中でのみ自動修復が走る**」という**時間帯レベルの承認境界**は作れる。しかしこれは「その窓を開けることを承認した」証明であって、「**窓内で走った個々の変更を、変更の直前に人が承認した**」証明ではない。level-triggered で窓内に検知された drift が自動修復される以上、個々の Apply は無人で走る。→ **schedule は「承認済み時間帯に閉じ込める」統制には有効だが、FISC が典型的に求める「変更単位の事前承認」の代替にはならない。**変更単位の直前承認を求めるなら、schedule（auto 窓）ではなく **v1.5 の承認ゲート付き Workflow**（step ごとに `StageAwaitingApproval` → 人が承認 → 次 step）を使うべきで、両者は目的が異なる。この構成では **schedule は日常 drift の窓限定修復に、承認ゲート Workflow は手順書化された計画変更に**、と役割を分けるのが正しい。

**(c) S4 永続化先決定＋外部アンカー（社内 GitLab 閉域）の監査耐性 — 前進したが独立性は未解決。**
CHG-A3（§26.1 A-4）で **S4 永続化先が着手前決定に格上げ**され、監査ストアの置き場が「動かしながら決める」曖昧さから外れたのは実装確度として前進。CHG-B6／§17.5 で **監査を外部 SIEM／WORM／append-only 専用サービスへ即時 push**・append-only をストレージ層で強制・監査書き込みを reconciler と別権限別プロセス化、が入り、**改竄窓の短縮**と**侵害ホストの自己犯行ログ書き換え防止**は明確に強化された。しかし §17.5 は依然「**git push 先が事実上の改竄耐性の実体**」を前提とし、エアギャップでは push 先＝社内 WORM／社内 GitLab に閉じる。FISC 監査が「**システム自身から独立した第三者による改竄検知**」を厳格に要求する場合、社内 WORM は「別権限・別プロセス」ではあっても「独立第三者」ではない。→ **前回指摘した社内 RFC3161 タイムスタンプ局等での独立アンカー補強は依然必要**。ただし WORM 化により「補強すべき残差」は前回より小さくなった（毎周 push＋別権限で改竄実行難易度は上がった）。

**総合として**、律速だった「Apply 本命価値の v2 送り」が v1.5 で部分的に解け、schedule で「窓限定自動修復」も宣言化された。前回 ○ の中でも実現時期・実装確度が改善したため、**○＋（◎ に一歩届く条件付き成立）**へ更新する。◎ に達しない構造的理由は、4-eyes／N-of-M・監査様式・アンカー独立性が**依然として本体外**である点（後述）。

## 3. v2.3 で新たに気づいた問題・残存課題

1. **schedule と承認ゲートの混同リスク（新規）**。§10.8 の schedule（窓内 auto）は便利だが、規制現場で「schedule を張ったから承認統制は満たした」と誤解すると、**変更単位の直前承認が抜ける**。schedule はあくまで日常 drift 用、計画変更は承認ゲート Workflow、という運用境界を組織ポリシーで明文化しないと、監査指摘の新しい火種になる。

2. **CHG-B6「platform 破壊的大量変更は A タグでも承認必須」が単一承認である（新規に顕在化）**。この追加ゲートは悪意/大量破壊対策として有効だが、承認モデルが単一のままなので、金融機関からは「**大量破壊こそ二人承認が要る**のに一人で通せる」と逆に指摘されうる。安全機構の強化が、規制側の 4-eyes 要求との落差を**むしろ目立たせる**。

3. **v1.5 前倒しでも「多相 Task・自動段階ロールアウト・自動 canary」は v2 のまま**。手順書には「firmware 更新（多相 Task）」「クラスタのローリング（自動段階＋canary 判定）」が含まれることが多く、v1.5 の「直列＋手動承認ゲート」だけでは**手順書の一部しか写像できない**。手順書全体の Workflow 化はやはり v2 を要する。§26.2 B の「firmware 相の途中 death は人手ゲート」も v2 前提。

4. **v1a で管理NWコアが Apply 不可（§19.3・CHG-C5）**。commit-confirm が v2 のため、v1a/v1b では管理NWコア（専用線側スイッチ含む）を `alert-only` 限定・Capabilities で Apply 経路を型封じ。専用線接続が主要素の本構成では、**NW 側の Apply 自動化は v2 待ち**が確定。前回「nw_switch は完全（CommitConfirm 必須）」と楽観した箇所が、v1 では観測のみに縮退することが明確化された（＝設計の正直化であり、悪化ではないが期待値は下がる）。

5. **段0-minimal（CHG-D1）は本構成には非該当**。400VM・4面の規模なので段0-minimal（1〜2台）は使わず、Vault-HA＋broker（v2）前提の本来の段0を要する。broker が v2 のため、**v1 では SecretRef 直結（§14.5）**で回す点は前回同様。

6. **エアギャップでの provider version 更新供給は依然設計外**だが、CHG-B5 の version 埋め込み fail-closed＋C 検知により「**更新が無検証で危険側に漏れない**」型は入った。オフライン更新の供給運用（社内ミラー・媒体）は引き続きベンダ SE の段0 作業。

## 4. この構成で成立させるための条件（更新版）

前回条件 (a)〜(f) を、v2.3 を踏まえ更新する。

- **(a) remediation の二層運用を明文化**:日常 drift は §10.8 の schedule で **保守窓（CAB 承認済み時間帯）のみ auto・他は alert-only**。窓外は検知のみ。cause tag B の窓外自動修復は組織ポリシーで禁止。**schedule を「承認統制の代替」と誤解しないことを規程に明記**（新規条件）。
- **(b) Sakutei の役割定義**:「ドリフト検出器＋適合レポート＋4面構成一致検証器（plan/twin）」を主軸に据える。これは v1a〜v1b で成立し、4-eyes と衝突しない（前回同様、最も堅い価値）。
- **(c) 計画変更（手順書）の Apply は v1.5 の承認ゲート付き Workflow で**。直列＋不変条件＋手動承認ゲートで写像できる範囲（＝多相 Task・自動 canary を含まない手順書）に限る。**多相 Task・自動段階ロールアウトを含む手順書は v2 待ち**。
- **(d) 4-eyes／N-of-M・CAB 連携・職務分掌は上位プラットフォーム側で実装**（本体未解消・条件維持）。§10.5 の単一承認を、承認者 ID の二重取得・申請者除外・CAB チケット連携でラップする。**大量破壊ゲート（CHG-B6）も単一承認なので二人承認化のラップ対象に含める**（新規条件）。
- **(e) 監査アンカーは即時 push（§17.5・CHG-B6）を採用しつつ、独立性を社内 RFC3161 等で補強**。WORM＋別権限別プロセスで改竄窓は縮んだが、独立第三者アンカーの要求には社内タイムスタンプ局で対応。S4 永続化先は §26.1 A-4 に従い**第0スプリントで確定**。
- **(f) 監査エビデンス様式**:conformance＋last-seen 差分（§10.3）＋plan を「作業前後スナップショット」へ整形する**エビデンス生成器を追加実装**。素材は v2.3 で増えたが整形器は依然自作。
- **(g) Windows/Linux 400台の TrueObserve 経路（agent/WinRM）を確保**（検出器価値の要・条件維持）。Ansible ラップ縮退を避ける。
- **(h) 段0（エアギャップ）**:Vault-HA＋SecretRef 直結（broker は v2）で構築。依存ソフト・provider のオフライン調達／更新供給を段0 運用として設計。version fail-closed（CHG-B5）で更新の危険側漏れは型で防がれる。管理NWコアは v1 では観測のみ（§19.3）。

この範囲なら、v2.3 は前回の「継続的適合の自動証明＋4面構成一致証明」に加え、**保守窓限定の自動修復（schedule）と、手順書の直列部分の承認ゲート付き Apply（v1.5）**まで踏み込める。金融機関が手作業で苦しむ監査対応を、より広い面で堅く肩代わりできる——ただし 4-eyes とアンカー独立性という規制の芯は、依然として上位実装で埋める前提が残る。
