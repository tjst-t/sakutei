## 判定を ✗ → △ に変更した理由

前回 ✗ の**構造的破綻の中核(G1 段0過重)が CHG-D1 で解消**された。これが最大の変更である。前回レポートは「段0縮退形を埋めない限り正攻法では入らない」と明言しており、v2.3 はその縮退形を第一級で定義した。段0-minimal(単一ノード・file backend・Vault/broker なし)は本構成の「物理2台・予算極小・クラスタなし」とほぼ一致し、「入場料が管理対象より重い」という前回の倒立が解消される。

第二に、前回「最大の設計課題」とした UniFi の扱いが CHG-D2 で前進した。前回は「最小 provider に押し込むしかない」ことを設計ギャップとして挙げたが、v2.3 は `external_owner` で「触らない」を宣言的に固定でき、二重ループの綱引きと prune 事故を型で回避できる。これは前回結論(alert-only 可視化に留める)を設計として追認し、安全に実装する道を与えた。

第三に、前回 △ の条件だった「外部 git・軽量シークレット代替・1〜2台縮退」が、それぞれ §19.4(git 外部)・§19.8(file SecretBackend)・§19.8(単一ノード)として設計本文に載った。前回は「設計が定義していないから ✗」だったものが「設計が定義したので条件付き △」に変わる。

**△ に留まり ✓ にならない理由**:UniFi/QNAP/WinAD という SOHO インフラの実質過半が依然 provider 最小階級(G6)で、Sakutei の中核価値(原因区別・converging・prune 安全性)がそこには効かない。Apply の主戦場は前回同様 DNS/バックアップ/証明書など「壊れても局所的なコア provider」に限定される。「インフラ全体の自律収束」という本来の姿は本構成では成立しない。したがって「限定運用として成立(△)」であり「本来用途で成立(✓)」ではない。

## v2.3 で新たに気づいた問題・残存課題

1. **段0-minimal のトレードオフが1名運用と噛み合う一方、可用性天井は残る(G2 と表裏)**。§19.8 は「単一障害点を許容/復帰後に自然再収束」と明示するが、これは「制御面が止まる=新規障害の自己修復が止まる」を許容する構成である。1名運用の SOHO では夜間にノードが落ちても「既存 VM は動き続ける」ため実害は小さく、むしろ整合的。ただし file backend のシークレット保護強度低下(§19.8)を「ディスク暗号化+アクセス制御」で埋める運用は追加で必要。

2. **G5(PR 相手なし)が v2.3 で逆に強まった**。CHG-B6 で platform 破壊的大量変更が A タグでも承認必須になったため、1名運用では「自己承認」がさらに形骸化する。ただし本構成の主敵は「1コミットで全 VM 削除」(§19.5)であり、CHG-B1 の累積時間窓予算(24h/50 deletes・halt-all)は 1名運用の誤記1つ被害を確実に止める新防御として大きな価値がある。承認相手不在は運用回避(承認=自分の二段確認手順に読み替え)で凌ぐしかない。

3. **external_owner はまだ写像品質を上げない**。§11.4 は「除外宣言と協調 seam」を v1a で切るが、UniFi 固有の写像実装は v1b〜。したがって v1a 時点では「UniFi scope を Observe(可視化)して Apply 抑止」までで、UniFi の drift 自動修復という本来欲しい機能は依然得られない。前回指摘の「収束の主戦場にならない」は不変。

4. **§23.9 で QNAP/旧機器の unknown を台帳一級化できるが、運用は v1b**。型は v1a、実運用フローは v1b(§23.9 末尾)なので、可視化ツールとして初日から使うなら v1a の範囲(DNS/VM/FW + external_owner)に限られる。

5. **G4(Gitea 循環)は依然 v2.3 の手当て外**。段0-minimal でもローカルミラー全断耐性は効くが、復旧時 push 先問題への設計変更は無い。

## この構成で成立させるための条件(更新版)

前回の「収束エンジンでなく可視化ツールとして入れる」路線を維持しつつ、v2.3 の新機能で条件が緩む:

1. **段0-minimal(§19.8)を採る**:単一ノード・ローカルディスク・file ベース SecretBackend・Vault/broker なし。物理2台の片方を段0-minimal、もう片方をワークロードに。file backend はディスク暗号化+アクセス制御で保護。→ 段0過重が構造的に解消(v1a で成立)。
2. **UniFi/QNAP/WinAD を `external_owner`(§11.4)で除外宣言**:Observe(可視化)はするが Apply しない。二重ループ事故と prune 巻き添え・ロックアウトを型で封じる。observe 不可の機器は §23.9 の `observability: none`+`ledger_only` で台帳に置く。
3. **Apply は局所 provider に限定**:DNS・バックアップ構成・証明書など「壊れても局所的」なコア provider のみ auto。管理NWコアは §19.3 により v1 では強制的に alert-only(型で Apply 不可)。
4. **git は外部(GitHub private 等)へ**:段0-minimal でも Gitea 循環の復旧時 push 先問題(G4)は残るため、intent リポジトリを外部化するか別筐体に逃がす。
5. **安全機構を必ず設定する**:CHG-B1 の `destructive_budget`(24h 窓・halt-all)で全 VM 削除を封じる。グローバル freeze(§23.6)を1コマンドで叩ける状態に。lint 強制と golden path(§5.5/§24.1a)で 1名運用者の Schema 事故下限を下げる。
6. **導入順序は §23.7 に従う**:DNS/監視/証明書 → 可視化(全 VM Observe)→ 新規構築部分のみ auto。既存中核(UniFi/AD)は永久 alert-only で構わない。

この条件下では、前回 ✗ だった段0破綻が消え、UniFi 事故が型で防がれるため **△(条件付き成立)** に格上げできる。ただし「SOHO インフラ全体を Sakutei が自律収束する」姿は依然 ✗ であり、Apply の実質射程は局所 provider に限られる。予算極小・1名運用に対し「Ansible 定期実行+手運用」との総コスト比較は依然シビアで、Sakutei を選ぶ根拠は「drift 可視化と全 VM 削除防御に価値を見出すか」に絞られる。
