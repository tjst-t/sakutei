# 対象構成15: 通信事業者 NFV / テレコムクラウド Sakutei 適用可能性レポート(v2.3 再評価)

**新判定: ○ 条件付き成立(本来運用が v1.5 で射程に入った。最大ギャップの機構が新設され、無改造での限定運用も本来運用も設計上は成立する。残る律速は S4 証跡ストアの法対応具体化と SR-IOV/NUMA 境界の実装検証)**

**前回判定(v2.2 時): △ 大幅な拡張が必要**(alert-only 常用 + 可視化 + 承認付き保守窓実行に限れば ○ 条件付き成立に届く)

前回の総合判定を押し下げていた核心は「本構成の生命線である時間帯連動 mode 自動切替が設計に存在せず、新規設計を要する」ことだった。v2.3 はこの最大ギャップに正面から機構(§10.8 `remediation.schedule`)を新設し、しかも v2 送りではなく **v1.5** に配置した。これにより「本来運用に必要な機構が設計に無い」という △ の主因が消え、判定を ○ 条件付き成立へ一段引き上げる。ただし残存課題(S4 永続化先の法対応具体化・SR-IOV/NUMA 境界の脆さ)は「拡張が要る」から「実装検証と外部連携が要る」へ性質が変わったに留まり、無条件 ○ には至らない。

## 2. 判定変更の理由

△ → ○ 条件付き成立への引き上げは、主に **ギャップ #1 の完全解消**が牽引する。前回レポートは「本構成の生命線である時間帯連動 auto/alert-only 切替が設計に存在せず新規設計を要する」ことを △ の第一根拠に据えていた。v2.3 の §10.8 はこの機構を宣言的 API として過不足なく設計し、既定を alert-only(最保守)に置き、freeze との重畳優先順位まで規定した。特に **v1.5 配置**が効く——前回は「本来運用は要拡張(実装時期不明)」だったが、v1.5 は「無いと使い始められない導入形態がある」基準で前倒された枠であり、保守窓文化の構成(03/15/17)が名指しで根拠に挙がっている。つまり本構成の本来運用が「いつか作るかもしれない v2」ではなく「v1.5 の明示スコープ」になった。これは判定を実質的に動かす。

加えて #3 の `external_owner` 第一級化(CHG-D2)は、前回「vSphere 案件より難度が高い」と評した VNFM 境界に対し、フィールド単位 managed の一段上の scope 単位除外を与える。VNFM が所有する層(VF/CPU/ページの実割当)を scope ごと Observe 専用に固定でき、level-triggered の綱引き事故の主因を宣言で塞げる。境界を「引ける道具」が増えた分、残るのは Schema 設計という実装検証課題に縮退した。

一方で無条件 ○ に届かないのは、#4(法対応証跡ストアの具体化)が §26.2 B に未確定で残り、変更管理システム突合と auto 収束の plan 承認段が依然欠けるためである。通信事業法対応はこの構成の必須要件であり、ここが未充足である限り「条件付き」を外せない。

## 3. v2.3 で新たに気づいた問題・残存課題

- **§10.8 と段0 Vault sealed-on-restart の時間帯衝突**:§10.8 自身が「保守作業や段0 の Vault sealed-on-restart と窓を整合させよ」と注意喚起している(§26.3 の運用パラメータ扱い)。保守窓(深夜 auto 昇格)に段0 再起動や broker 断が重なると、auto に上げた周に収束が走れず(§19.7 の依存 unready 時待機)、「窓は開いたが直らない」空振りが起こりうる。窓カレンダーと段0 メンテの相互排他は運用設計の新たな要件。
- **schedule の tz と保守窓カレンダー(祝日・臨時窓)の乖離**:§10.8 は `window: "Sat 02:00-04:00"` の曜日×時間帯の静的宣言で、事前申請制の**臨時保守窓・窓の前倒し/延長・祝日運休**を宣言だけでは追随できない。実運用では「今夜だけ窓」を freeze/unfreeze の手動操作(§10.6)で重ねる必要が残り、ヒューマンエラー面が schedule 導入後も臨時窓に局在して残る。変更管理システム(申請番号)との連動が本来欲しいが #4(b)同様に未設計。
- **auto 昇格周の rate limit との相互作用**:窓が開いた瞬間、窓外に貯まった全 drift が一斉に「直す」対象になる。CHG-B1 の destructive_budget(24h 窓の累積予算・halt-all)と CHG-B6 の platform 破壊的大量変更=A でも承認必須が効くため、貯まった drift が SLA 99.999% のデータプレーンを一斉に潰す事故は構造的に抑止される。ただし逆に「窓は2時間しかないのに承認必須で捌き切れず、翌週へ持ち越し」の運用律速が新たに生じうる(機構としては安全側で正しい挙動)。
- **S4 の永続化先が A(着手前)でなく B(着手後)に留まる非対称**:CHG-A3/A4 は S2 の永続化先を A へ格上げしたが、**S4(監査 Event)の保存年限・可用性は §26.2 B のまま**。通信事業法の保存年限は「後から変えると痛い」性質で、本構成に限れば A 相当の重みを持つ。汎用設計では B が妥当でも、本構成適用時は着手前決定に引き上げる必要がある。
- **auto 収束の plan 承認段の欠落は未解消**:承認ゲート(§10.5)は Workflow 経路のみで、Resource の auto 収束(窓内で schedule が auto に上げた分)には「人が dry-run を確認してから適用」の段が無い。前回指摘のまま。窓内 auto を「schedule=auto だが承認ゲート付き Workflow 経由」に寄せれば埋まるが、それは Resource 収束でなく Workflow 運用への設計上の割り切りになる。

## 4. この構成で成立させるための条件(更新版)

**短期(v1a〜v1b・改造ほぼ不要)**:全域 alert-only 固定 + 承認ゲート付き Workflow 実行の「drift 検知器 + 承認付き実行基盤」限定運用。`external_owner`(§11.4・v1a で Apply 抑止として成立)で VNFM 所有 scope を除外宣言し、last-seen リング(§10.3)+ `sakutei status` で可視化価値を出す。§23 brownfield 戦略を厳格適用。この形なら ○ に十分届く。

**本来運用(v1.5 到達時)**:`remediation.schedule`(§10.8)で保守窓 auto 昇格を宣言。これが v1.5 スコープに入ったため前回のような「新規設計待ち」ではない。ただし以下を満たすこと。
- **S4 証跡ストアの法対応具体化**:§26.2 B の S4 永続化先を、本構成では着手前決定へ引き上げ、保存年限・可用性・WORM 即時 push(§17.5)を通信事業法要件に合わせて確定する。
- **変更管理システム連携**:申請番号 ↔ Apply/commit の突合を外部連携で実装(設計外)。臨時窓の追随もここに寄せる。
- **auto 収束の plan 承認**:窓内の破壊的変更は承認ゲート付き Workflow 経由に寄せるか、plan 承認段の追加を要件化する。
- **SR-IOV/NUMA 境界の検証**:`external_owner` + managed の線引きを devenv/twin(§22)でカオステスト検証してから本番へ。CHG-C3 の Schema lint 強制・golden path を活用。
- **窓カレンダー整合**:§10.8 の schedule 窓と段0 メンテ・Vault unseal(§19.7)・臨時窓を運用設計で相互排他にする。

**サイト冗長(v2 待ち)**:2サイトを shard 境界に一致させる理想形はシャーディング(v2・§24.2)待ち。当面は2独立単一デーモンで代替(規模的に各サイト数千 Resource で単一デーモン内)。fencing token(§12.2)は明文化済みだが本体は v2。
