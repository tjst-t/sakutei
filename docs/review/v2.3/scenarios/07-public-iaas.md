# 対象構成07:パブリックIaaSプロバイダ — Sakutei適用可能性 再評価(v2.3)

**新判定:△ 大幅な拡張が必要(v1では不成立。判定は据え置き)**
— ただし「v1のどこまで動くか」の解像度は上がり、v1a での価値実証範囲と、事業成立に必要な v2 完遂+上位基盤自作の切り分けが明確化した。

**前回判定(v2.2時):△ 大幅な拡張が必要(v1不成立)**

構成前提は前回§1のまま(約2,000テナント・VM約10,000、即時API駆動・ピーク毎秒数件、KVM 400台/Ceph 3クラスタ/EVPN-VXLAN、テナントVPC=VRF+VXLAN+SG+FWaaS+LBaaS+FIP、課金/quota/分離が事業要件、SLA 99.95%・24/365)。

## 2. 判定変更の理由(据え置きの理由)

総合判定は前回同様 **△**。理由は G1・G3 が判定の芯だから。

- **G1 未解消が支配的**:本構成は「設計として最有力ユースケース」である一方、必須の4機能(DBSource/シャーディング/分散Executor/intent UI)が v2.3 でも一つ残らず v2。v1 再スライスは Task/Workflow 依存構成(20構成中12)を救う設計判断であり、本構成のように「即時テナント書込+水平分割」を核とする帯には恩恵が薄い。v1a で作れるのは「触っていないのに戻る」の価値実証(DNS→VM→FW の数個Provider・単一デーモン・FileSource)までで、事業としてのマルチテナントIaaSは動かない。

- **allocation v1依存解消がテナントVPC採番に与える影響(精査結果)**:CHG-A2 で v1a=非採番の固定値展開のみと縮退したことで、**本構成の中核であるテナントVPCの採番展開(VNI/VMID/テナントIP/FIP)は丸ごと v1b 依存**になった。§7.5 の合成リソース `virtual_network → vxlan_segment(vni採番)+…` は、まさに `from_pool` を使うため v1a では展開不能。つまり「v1a で IaaS カタログ商品を1つでも出す」ことすらできず、最小価値実証と本構成の距離は v2.2 時より明示的に開いた(矛盾解消の代償として、本構成は v1b 到達が最低ライン)。ただし allocator interface に Reserve/Confirm/Release/逆引き再構築(§16.6)が揃い、大規模採番(毎秒十数回 read-write)を NetBox/Infoblox 実装へ差し替える seam は綺麗に切られている。

- **G3 への設計側応答は無い(最重要・未解消)**:v2.3 CHANGELOG 全体を精査したが、「委譲した先(quota admission・メータリング課金・認可・ポータル)がパブリックIaaSでは事業本体で、Sakuteiと同規模の別開発になる」という前回の最重要指摘に対する設計変更・注記・反論はいずれも存在しない。§24.3 は委譲リストを据え置き、CHANGELOG の「採用しなかった指摘」にも本件は現れない(製品ポジショニング助言 F M-7 は見送られたが、G3 は工数見積の構造問題でありポジショニングではない)。したがって「委譲=作らなくてよい、ではなく別途フルスクラッチ」という工数の非対称は v2.3 でも認識されておらず、Sakutei 単体で本構成を「管理できる」という表現が誤りである点は不変。

## 3. v2.3で新たに気づいた問題・残存課題

- **N1. v1b が本構成の実質的な最低ライン**:採番展開が v1b に固まったことで、本構成は「v1a では価値実証すらできない」構成として v2.2 時より下方に位置づく。ロードマップ上、本構成の PoC は v1b(import・allocator・ready_condition・capacity gate)完遂を待つ。段0で持つべき allocator(高可用)・DBSource本体・shard router 割当表(S2)は v2 機能に依存するため、段0の"中規模クラスタ化"(前回§6)は解消されていない。むしろ fencing token を持つ割当表・累積予算カウンタのS2永続化(§10.2)・監査WORM即時push(§17.5)が段0に追加要件として乗り、段0の重量はやや増した。

- **N2. tier別Observe頻度の最小形(v1b)は本構成に効くが天井は依然低い**:§12.2 で tier別頻度 seam が v1b に前倒されたのは前進。ただし watch併用(drift即知)は v2 のままで、10,000リソースを収束周期内で捌くにはシャーディング(v2)必須という構造は変わらない。CHG-C2 の実機表により、単一デーモンでは vCenter系 ~200台が上限と明示され、20シャード程度では足りず、より細粒度の分割前提になった。

- **N3. fencing はテナント跨ぎ整合を提供しない点が明確化**:CHG-B6 で platform シャードの単一writer保証(fencing)は得たが、§12.2 は「強い順序保証はシャード内に閉じたときのみ成立/シャード跨ぎは観測ready待ち=結果整合」を再確認。前回§5末の懸念(platform変更が全tenantシャードに結果整合で波及)は原理として残存。パブリックIaaSで求められがちな「テナント跨ぎのアトミックな一括操作」は原理的に提供不可。

- **N4. G4 の残り穴**:capacity gate はクラスタ物理容量のみで、テナント別 quota(VM数/vCPU/FIP/帯域)強制は依然 Sakutei 外。DBSource 書込前の admission が甘いと、Sakutei は quota 超過理想を忠実に収束する。§10.2 表がこれを再確認しており、v2.3 でも塞がっていない。

- **N5(有利側). 安全性は明確に前進**:CHG-B1/B2/B6 により「テナントAがテナントBに波及しない」保証(closed-world scope + DAG無エッジ + shared-nothing + fencing + 累積予算 + List急減halt)が多層化。本構成の分離要件・platform爆発半径抑制には v2.2 より確実に効く。

## 4. この構成で成立させるための条件(更新版)

前回4条件を、v2.3 の切り分けを反映して更新する。

1. **Sakutei v1b + v2 ロードマップを完遂する**(更新):v1b(allocator実装・採番連携展開・ready_condition・capacity gate)を PoC の最低ラインとし、その上で v2 の **DBSource・シャーディング+fencing・分散Executor・watch併用・intent UI(catalog)** を完遂する。v2.3 で fencing/累積予算/List完全性の設計は固まったため、v2 実装の設計リスクは v2.2 時より下がった。

2. **高スループット allocator を NetBox/Infoblox 等の実運用IPAM、またはシャード対応 allocator で用意する**(更新):§16.5 の SQLite 最小実装は本規模(毎秒十数回 read-write)でボトルネック/SPOF。interface seam(§16.5)と 1プール1権威の静的分割(§16.6)は切られているので差し替えは可能。

3. **上位テナントプラットフォームを Sakutei と同規模で別途フルスクラッチ構築する**(不変・最重要):quota admission(DBSource書込前に強制)・メータリング/レーティング/請求連携・RBACマルチテナント認可・非同期セルフサービスAPI+ポータル・SLA計測。v2.3 でも設計側の応答が無いため、この存在を工数見積に必ず織り込む。「委譲」は「作らなくてよい」ではない。

4. **twin(v2)で 1万リソース×ピーク負荷の収束周期・EVPN realizationラグ・Ceph/LB API rate limit を実測検証する**(不変):CHG-C2 の実機表は出発点であり、実測の代替ではない。

5. **ポータルUXを非同期provisioning前提で設計する**(不変):Sakutei は "provisioning is eventually consistent"。同期的な「作成APIが返った=VMがある」は提供しない(§12.2 シャード跨ぎ結果整合により、むしろ v2.3 で構造が明確化)。

**位置づけ**:これら5条件を満たせば ○(条件付き成立)に到達しうるが、条件3の存在により「Sakutei単体で本構成を管理できる」は依然として誤り。**Sakutei は事業システムの下半分(宣言的インフラ収束)を担う部品**であり、v2.3 でこの位置づけは変わっていない。
