## 2. 判定変更の理由

**△→○ に上げる根拠**は G1・G2 の解消に尽きる。前回レポートの総合判定は「段0-minimal クラスと単独運用者プロファイルという2つの拡張を加えて初めて ○ 条件付き成立」であり、「拡張なしの素の v2.2 では段0が組めず不成立寄り」だった。v2.3 は前者(段0-minimal)を**設計本体に第一級で取り込んだ**ため、この構成の成立を阻んでいた核心が消える。しかも段0-minimal は Vault を持たないため、前回2番目に痛かった G2(unseal 地獄)まで**副次的に根絶**する——これは前回想定した「単一ノード + auto-unseal で緩和」より上位の解決(そもそも sealed 状態が存在しない)である。

**無条件 ○ にしない理由**は G3 が未解消で残ること、および段0-minimal が可用性トレードオフ(単一障害点許容)を明示的に引き受ける構成である点。ただしこのトレードオフは本構成の物理現実(Proxmox 1台 = 元々 SPOF)と一致しており、設計が現実を正直に写し取った結果なので減点ではなく「条件付き」の条件として扱う。§19.8 自身が「観測 state レス + level-triggered なので復帰後に自然再収束、制御面が落ちてもデータ面は動き続ける」と、まさにこの構成のコア価値を可用性トレードオフの受け皿として説明している。

**G3(単独運用者の PR 儀式)を残す判断**:これは「不成立を招く核心」ではなく「運用上の摩擦」に留まるため、判定を △ に押し戻すほどではない。1名運用では platform プロファイルの PR 必須を自己 PR の儀式として回すか、tenant プロファイル(即時)を流用するワークアラウンドで実運用は回せる。ただし後述の通り v2.3 で**むしろ摩擦が増える方向の変更**が入った点は注意が必要。

## 3. v2.3 で新たに気づいた問題・残存課題

1. **CHG-B6 が単独運用者の摩擦を増やす方向に働く**(新規・要注意):§10.2 に「`ownership: platform` の破壊的大量変更は原因タグ A でも承認必須」が入った。本構成は**実質全リソースが platform**(テナント不在)なので、この新ゲートが**全破壊的大量変更に一律で掛かる**。侵害 reconciler 対策としては正しいが、1名・数十リソースのラボでは「自分で意図した VM 一括入れ替えのたびに自分の承認を要求される」形になり、G3 の空回りをさらに濃くする。段0-minimal / 単独運用向けに**このゲートの閾値を緩められる seam が欲しい**(現状 §10.2 は scope ごとに `on_exceed` を選べるが、「承認必須」自体の on/off は platform 固定に読める)。

2. **段0-minimal から標準段0への移行が「seam はあるが手順は未記述」**:§19.8 は「規模が育ったら Vault へ SecretBackend seam 経由で移行」と述べるが、file → Vault、単一ノード → 3ノード + Ceph の**移行手順(段0 の作り替え)は本書のスコープ外**(§1.5 の参照実装側)。ホームラボが育つ現実的パスなので、移行時に段0 全体を人手再構築する必要がある点は導入時に正直に提示すべき。

3. **file SecretBackend の保護強度**:§19.8 は「ディスク暗号化 + アクセス制御で緩和」とするが、単一ノードでディスク暗号鍵をどこに置くか(= unseal 問題の縮小版)は本書では未詳。ラボでは TPM か平文許容が現実だが、「シークレットの根が人間の金庫に着地」という原則(§19.4)からの後退である点は段0-minimal のトレードオフとして明示されるべき。CHANGELOG は §19.8 で可用性トレードオフは明示するが**秘匿強度トレードオフの明示は弱い**。

4. **OOB / Break Glass の不在は依然未カバー**:§19.8 の表に OOB 行が無い。標準段0は「OOB = 唯一の経路」を必須としているが、段0-minimal ではコンソールサーバも OOB 専用 NW も想定外。前回指摘どおり「Proxmox の物理コンソールが唯一の OOB」で成立するが、これは §15.6 の Break Glass L2.5 が段0-minimal では**物理アクセス前提に暗黙縮退**していることを意味し、設計上明文化されていない。

5. **残存(前回から不変)**:G4 の provider 階級縮退、G6 の canary(v2 送りで当面不問)は構造的に残る。ただしいずれも「成立を阻む」レベルではない。

## 4. この構成で成立させるための条件(更新版)

前回の3条件(①段0-minimal 明文化 ②Apply を alert-only 中心 ③PR 儀式を省く単独運用モード)のうち、**①は v2.3 本体が満たした**。更新版は以下。

- **[設計が満たした] 段0-minimal を採用する**(§19.8):単一ノード + ローカルディスク + file SecretBackend + SecretRef 直結。Vault/broker/Ceph/3ノードは持たない。v1a の範囲で構築できる。
- **[運用条件] 停電・再起動を前提に remediation を保守的側へ**:既定 `alert-only`、修復は §10.8 の `remediation.schedule` で明示窓に限定。起動直後の一斉収束は freeze(§10.6)で抑える。段0-minimal は unseal が無いのでコールドスタート順序制約(§19.7-1)は不要。
- **[運用条件] prune を厳格に**:`pruneable: false` 既定厳守、`destructive_budget`(§10.2)を絶対値小さめに、非管理 L2 スイッチや旧 NAS は `observability: none` + `ledger_only`(§23.9)で台帳化して巻き添え防止。
- **[要留意] platform 一律の「破壊的大量変更 承認必須」ゲート(§10.2)を運用でどう回すか決める**:1名運用では自己承認が儀式化する。scope ごとの `on_exceed` 選択で緩和するか、変更を小分けにしてゲートに掛からないよう運用する。
- **[未解消・ワークアラウンド] 単独運用者の書き込みポリシー**:PR 必須は自己 PR で回すか tenant プロファイル(即時)を流用する。設計側の単独運用者プロファイルは v2.3 でも無いため、実利面はワークアラウンド頼み。
- **[要留意] 秘匿強度と OOB**:file SecretBackend の鍵管理は物理保管 or TPM、OOB は Proxmox 物理コンソールで代替。いずれも段0-minimal の暗黙トレードオフとして受容する。

以上を満たせば、本構成は**素の v2.3 内で「drift 自己修復付き宣言的管理」として実用成立する**。前回「拡張なしでは不成立寄り」だった帯が、CHG-D1 一本で開いたことが最大の変化である。
