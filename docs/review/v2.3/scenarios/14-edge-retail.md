## 2. 判定変更の理由

**△ 据え置きの根拠は G1 に尽きる。** この構成の成立可否を握るのは「WAN 断が定常の 300 分断ドメインを、断中も自律収束する実行体(案 C の店舗 agent)で扱えるか」であり、その実行体 = **分散 Executor + lease/revision 縮退(§12.3)+ シャーディング(§12.2)は v2.3 でも一貫して v2**。CHG-C1 は「20 構成の 12 が Task/Workflow 依存」という別軸の最頻 △ 理由に応えた再スライスであって、**分断耐性の前倒しではない**。むしろ CHANGELOG は §24.2 で「分散 Executor + lease 縮退 / シャーディング + fencing」を v2 と再確認しており、この構成の核心が v2 であることが**より明確に確定**した。したがって「○ に上げる」判断は取れない。

**では何が良くなったか。** 前回レポートが「○ に到達する条件」として列挙した5項目のうち、**周辺の3項目が設計本体に取り込まれた**:(条件4)閉店 prune の多層防御 → G5 で解消、(条件5に近い)WAN 断中の Observe 継続 → G3 で部分解消(read-only 長 TTL 別枠)、(条件2の一部)割当表 fencing とサイト別プール → G6 で部分解消。これは「条件を満たす手段が設計側に揃ってきた」ことを意味し、**○ に至る道筋の確度は上がった**が、道の入口(v2 の分散実行体)が閉じたままなので判定は動かない。前回同様「案 C を前提にすれば ○ 条件付き」の構造は保たれる。

**段0-minimal の転用可能性(タスク指定の精査点)。** CHG-D1 の段0-minimal は「1〜2 台構成向けの縮退形」であり、案 C(agent だけ配る)の**分散トポロジそのものではない**。しかし本構成に対して**新しい選択肢を1つ開く**:各店舗を「段0-minimal(単一ノード・file SecretBackend・Vault/broker なし)を店舗内に置く」= **案 B の現実的縮退版(案 B-lite)**として読める。前回 案 B を却下した主因は「300 個の Vault sealed-on-restart を技術者ゼロで unseal」だったが、**段0-minimal は Vault を持たず file SecretBackend なので sealed-on-restart が構造的に消える**(§19.8「コールドスタートが単純」)。これは前回却下の**核心的前提を1つ崩す**。ただし (a) file SecretBackend の資格保護強度が店舗の物理セキュリティ(無人・施錠のみ)に依存する、(b) 段0-minimal は自律収束の**理想供給が単一ノードローカル**であり、§12.3 が警告する「stale な理想で削除を実行し続ける」暴走を 300 拠点分抱える、(c) 店舗ごとに理想を配布・更新する経路が結局 WAN 依存、という新たな問題が生じる。**結論:段0-minimal は案 B の Vault 問題だけは解くが、案 B の本質問題(stale 理想の分散暴走・300 拠点の理想配布)は解かない。**依然として案 C(制御面 DC・agent のみ店舗)が本命で、段0-minimal はその代替ではなく「小規模パイロット(数店舗)を DC なしで立てる」用途に留まる。

## 3. v2.3 で新たに気づいた問題・残存課題

1. **G8 の裏面 = 店舗 WAN 終端機器の自動化が v2 で固定された(新規に顕在化)。** CHG-C5 は commit-confirm を v1 で持たないため管理NWコアを alert-only に固定した。安全側として正しいが、この構成の `edge_router`(WAN 終端・commit-confirm 必須)は**そもそも v1 で Apply 収束の対象外**になる。前回は「高品質 provider を書けば実装工数で解決」と見ていたが、v2.3 は**型で v1 収束を禁止**したため、店舗ルータの構成自動化は v2 待ちが確定。ゼロタッチ開店の中核である WAN 終端設定が手動 or 外部ツールに残る。

2. **read-only 長 TTL キャッシュ(§19.7-4)は Observe を救うが「加算 Apply の資格」を救わない。** G3 が部分解消に留まる理由。台風数日断の間、店舗内 drift の自己修復(加算 Apply)に要る**書き込み権限つき資格**の供給は依然設計されていない。§12.3 の縮退表では「制御面と分断 = 加算のみ」だが、その加算に要る資格が数日供給できなければ実質 Observe のみに落ちる。**agent が持つべきキャッシュの範囲(理想 + read-only 資格 + write 資格 + render 済み理想)が §12.3 の 2 フィールド(revision/leaseUntil)では依然不足**という前回指摘は残存。

3. **ledger_only(§23.9)は WAN 断 unknown には効かない(タスク指定の精査点)。** §23.9 は「**恒久的に** Observe 不能な資産(API を持たない旧機器)」を台帳上 unknown で固定し prune から除外する型であり、対象は `observability: none`(そもそも Read/List を張れない)。一方 WAN 断の店舗は「**普段は Observe でき、断中だけ一時的に unknown**」= `observability` は有・transient unknown。両者は**質が違う** — ledger_only は「観測手段が構造的に無い」、WAN 断は「観測経路が一時的に切れた」。したがって **ledger_only を WAN 断店舗に付けるのは誤用**(断中に prune 除外できても、復帰後も台帳 unknown に固定され drift 検知が死ぬ)。ただし**副次的な効き目はある**:店舗内の「非管理 L2SW・古い AP・ドキュメントのみ配線」を ledger_only で持てば、閉店 prune や List 集合演算の**巻き添えを構造的に防げる**(G5 の prune 安全性を補強)。**結論:WAN 断 unknown の扱いには直接効かないが、店舗内観測不能資産の prune 巻き添え防止には有効。**両者を混同しない運用規律が新たに要る。

4. **destructive_budget の scope 設計が 300 拠点で非自明(新規)。** CHG-B1 の `max_scope_fraction`(単一 scope の実在リソースの X% 削除で escalate)は強力だが、本構成では「scope = 店舗」にすると閉店(1 店舗 = 20 削除 = その店舗の 100%)が**常に fraction 上限を叩く**。店舗単位では fraction 予算が無意味化し、window の `max_deletes`(24h 総数)に頼ることになる。**閉店を「正常な 100% 削除」として通しつつ、WAN 断誤認の巻き添え削除を止める** scope 粒度設計(店舗内 subsystem 単位 or 閉店 Workflow に approved-large-change を必須化)が新たな詰めどころ。

5. **段0-minimal を店舗に置く場合の理想配布経路が未設計(新規・§2 の (b)(c))。** 案 B-lite を採るなら「300 個のローカル理想をどう配布・整合させるか」が §13(FileSource git・PR)の想定外。git を 300 店舗へ pull させる経路が WAN 依存で、結局 §12.3 の分散問題に還る。

## 4. この構成で成立させるための条件(更新版)

前回5条件を v2.3 の進捗で更新する。**取り消し線相当 = v2.3 で設計本体に取り込まれ条件から降格したもの、太字 = 依然として構成側/実装側で満たす必要が残るもの。**

1. **案 C(ハイブリッド)を採る**(不変・本命)——店舗に軽量 agent(RemoteExecutor)、Vault/broker/reconciler/理想は DC 2 拠点。**この実行体(§12.3 分散 Executor)は v2.3 でも v2 のままなので、v2 実装を待つか先行実装するかの判断が構成成立の分水嶺**。段0-minimal は案 C の代替にはならず、数店舗パイロットの立ち上げ用途に限る。
2. **v2 の分散 Executor + シャーディング(site 軸)+ shard router を実装対象に含める**(不変・最重要残存)。ただし v2.3 で **割当表 fencing(§12.2)・サイト別静的プール(§16.6)・S2 永続化先の A 格上げ(§26.1 A-4)**が型・決定として整ったので、**実装時の設計負荷は前回より軽い**。agent の縮退キャッシュに **read-only 長 TTL 資格(§19.7-4 で新設)+ write 資格 + render 済み理想**を持たせる拡張は依然必要。
3. **段0 の店舗版最小核(ゼロタッチ立ち上げ・書き込み資格の TTL 供給)を新規に詰める**(不変・残存)。§19.7-4 で Observe 側は救えるようになったが、**加算 Apply の資格を数日断で供給する手当てと、BMC/PXE 核を現地ゼロで置く物理段(G7)は依然設計ギャップ**。
4. ~~閉店 prune を多層防御化~~ → **v2.3 で解消済み**(destructive_budget・§8.6 List 完全性・§16.4 Release を List 確認・§7.6 incomplete≠empty)。ただし **destructive_budget の scope 粒度**(§3-4)と **閉店 Workflow への approved-large-change 必須化**は構成側で設定する(条件から「防御機構を作る」は消え「機構を正しく設定する」に軽減)。
5. **WAN 状態を別入力として相関し unknown を分類する層を足す**(不変・残存)。CHG-B5(per-resource 帰属・last-seen リング)で「いつからズレたか」は答えられるようになったが、「**なぜ届かないか(回線断 or 故障)**」の分類は依然 Sakutei 外。回線監視との突き合わせは構成側の外付け。
6. **(新規)edge_router の Apply 自動化は v2(commit-confirm)待ちと割り切る。** v1 期は §19.3 に従い店舗 WAN 終端を alert-only(観測のみ)とし、config push は外部ツール/手動 + commit-confirm 手順で運用する。
7. **(新規)店舗内の観測不能資産(非管理 L2SW・旧 AP・配線)を `ledger_only`(§23.9)で台帳に持ち、prune 巻き添えから守る。** ただし WAN 断店舗を ledger_only にしてはならない(transient unknown と恒久 unknown の峻別を運用規律で担保)。

**総括:** v2.3 は「○ に至る道の周辺整備(prune 安全・Observe 継続・fencing・観測不能資産・原因帰属)」を大きく進め、成立条件のうち防御系(条件4)を1つ解消、資格系(条件3・G3)と割当系(条件2・G6)を部分前進させた。しかし**成立の分水嶺である分散実行体(§12.3)とシャーディング(§12.2)が v2 に据え置かれた**ため、総合判定は **△ 据え置き**。前回同様、**agent を配り段0 は配らない(案 C)** を前提に v2 機能を実装対象へ引き込めば **○(条件付き成立)** に届く。逆に v1 のまま・中央集中(案 A)では WAN 断で常時全盲となり ✗、店舗に完全自律収束を 300 個(案 B)は段0-minimal で Vault 問題は消えても stale 理想の分散暴走で ✗ という構造は不変である。
