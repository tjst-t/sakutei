# 対象構成05(再評価): Leaf-Spine SDN データセンターネットワークへの Sakutei 適用検討 — v2.3

**新判定: ○ 条件付き成立(v1.5 到達で「部分成立」の質が明確に改善。ただし SONiC 全断防御と疎通保証は依然 v2 依存)**
**前回判定(v2.2): ○ 条件付き成立**

判定シンボル自体は据え置きだが、内実は前進した。v2.3 は本構成の「全断事故防御」系ギャップ(累積削除・List 欠損・原因帰属・fencing)をコア(v1a)で塞ぎ、段階適用の骨格(直列+不変条件+手動承認)を v1.5 に前倒した。一方、本構成の価値の核である **SONiC の commit-confirm 合成**と **EVPN 疎通 canary** は v2 のまま据え置かれ、むしろ v2.3 は「commit-confirm 不在機器は型で Apply を禁じる」と**明示的に安全側へ縮退**した。結果、v1 の到達点は「可視化+テナント枠内即時収束」で変わらないが、その**防御品質と段0 の閉じ方が格段に堅くなった**。

## 判定変更の理由

シンボルは ○ 据え置きだが、**「部分成立」の中身が質的に改善**した。前回は「ファブリック本体は永久 alert-only、その間の全断防御は薄い」だったのに対し、v2.3 では:

1. **全断防御がコア(v1a)に降りた**:本構成最大の事故モデル(全 leaf 一斉 Apply / 漸進的全削除 / List 欠損による VLAN 巻き添え)を、v2 の段階適用を待たずに **v1a の rate limit 累積予算・List 完全性検証・per-resource 帰属**で塞げる。前回「段階適用(v2)が無いと全断防御が不十分」だった評価が、「v1a でも構造的全断はかなり止まる」に変わる。
2. **段0 の閉じ方が型で保証された**:前回の絶対条件「commit-confirm 未実装なら SONiC は alert-only 固定」が、v2.3 では**設計の既定挙動**(§19.3・§4.3 の Capabilities 強制)になった。管理NWコアを v1 で Apply 対象にしない=ロックアウト経路を型で塞ぐ、が明文化され、条件の一部が「運用努力」から「型による保証」へ格上げされた。
3. **段階適用の骨格が v1.5 に前倒し**:直列+不変条件+手動承認ゲートが v1.5 に来たことで、「canary 1 leaf → 手動承認 → broad」という**段階ロールアウトの手動運用**が v2 を待たずに可能になった。

一方で ◎ に上げられない理由は明確で、本構成の価値の核(SONiC 自動収束・EVPN 疎通保証)が **v2 のまま**だからである。したがって「防御は堅くなったが、自動収束の到達範囲は前回と同じ」= ○ 据え置きが正確。

## v2.3 で新たに気づいた問題・残存課題

1. **v1.5 の「最小 Workflow」は疎通 canary 要求に届かない**:v1.5 は**直列+不変条件+手動承認**まで。本構成が要求する「canary=能動的疎通テスト(テナント間/内の到達性を実測)+ health gate による自動判定 → 段階適用」のうち、**自動 canary 判定・動的 select・自動段階ロールアウトは §24.1.5 で明示的に v2 送り**。つまり v1.5 で書けるのは「1 leaf に適用 → **人が手で疎通を確認** → 承認 → broad」であり、`gate.health_check: required`(自動)は v2。SONiC の watchdog 合成も v2。→ **v1.5 で成立するのは「手動ゲート付き段階適用」まで**で、無人の疎通 canary+自動段階適用は依然届かない。これは前進だが、要求との差分が「自動化の有無」に凝縮された形で残る。

2. **SONiC commit-confirm 合成の扱いが「禁止」に振れた副作用**:§19.3 は commit-confirm 不在機器を型で Apply 禁止にしたが、これは**安全側だが SONiC 60 台(全 leaf の 6 割)が v1 で恒久的に観測専用**を意味する。前回「SONiC は permanent alert-only が安全側の結論」を設計が正式採用した形。合成 watchdog(§21.3「賢さは自前側」)の実装余地は残るが v2 provider の領分で、**本構成では v2 到達まで SONiC leaf の auto 収束価値は出ない**ことが確定した。EOS(Spine4+Leaf36)は CommitConfirm:○ なので先行 auto 化できる非対称が生まれる。

3. **NETCONF レイテンシ算術の精査(CHG-C2)**:§12.2 表は NETCONF/gNMI=1.5s、30s 間隔・並列度16・Observe 予算10s で **上限 ≈107 台**。本構成は Spine4+Leaf96=**100 台**で**この上限にほぼ張り付く**。さらに:
   - 表の「≈107」は**機器単位に並列度16 が効く前提**だが、§12.2 自身が「NW 機器は同時セッション2〜8制限」と注記。1 機器あたり複数リソース(BGP peer×config×VRF×VNI で数十〜数百 Read)を**逐次**引くなら、実効は機器数でなく**Read 総数**で律速する。100 台 × 数十リソース = 数千 Read を 1.5s 級で回すと、並列16 でも 10s 予算を**大幅超過**しうる。→ **v1b の tier 別 Observe 頻度(安定リソースは N 周に1回)が事実上の前提**になる。
   - gNMI subscribe(streaming)を使えば毎周 Read の 1.5s を回避できるが、これは watch 併用(v2)。v1 は毎周ポーリング前提なので、**100 台 × リソース展開でのポーリング設計が v1b の Observe スケジューラ seam に強く依存**する。
   - 1,500 VNI × 80 VRF の render フェーズ2 展開でオブジェクトが膨らむと、DAG 計算より先に Observe が刺さる(前回§7-4 の指摘)は**定量的に裏付けられた**。pod shard 分割(§12.2)は「将来」でなく**v1b 時点で見込むべき**と格上げされる。

4. **fencing の効きどころが本構成に直撃**:CHG-B6 の platform シャード fencing は、まさに本構成の「共有基盤(spine/アンダーレイ)を platform シャードが所有、tenant shard は read-only」設計に必要。ただし fencing は**分散化(v2)の実装契約**で、割当表の型定義時に持たせるのみが v1。単一デーモン運用の v1 段階では効かず、**pod shard 分割に踏み込む時点(v2)で初めて実効**。100 台上端で早期 shard 化が要るなら、fencing の v2 実装が shard 化の前提条件になる。

5. **List 完全性検証と NW の相性(好材料)**:CHG-B2 は本構成に特に効く。NW は「ACL ルール群・VLAN 群・VNI 群」を List で prune 判定するため、gNMI/CONFIG_DB のレプリカ遅延や部分応答での**大量誤 prune=通信断**が最悪級だった。件数急減 halt(−50%)+ `ListStatus` 三値が v1a で入るのは、前回§7 で未手当だった層を直接埋める。

6. **allocator の逆引き再構築(CHG-B6・§16.6)が VNI/RT 自作 allocator に効く**:前回「VNI/RT は自作最小 allocator」が現実解だったが、その state 喪失時の復旧が未設計だった。§16.6 の「現実逆引き再構築+1プール1権威の静的分割」が入り、二重払い出し=衝突(§16.4 最悪級)への防御が補強された。ただし NetBox(IP/ASN/VLAN)と自作(VNI/RT)の二本立てで、**1プール1権威**を跨いで守る運用規律は依然人手依存。

## この構成で成立させるための条件(更新版)

**v1(v1a+v1b+v1.5)で到達できること(前進した部分)**
- 全機器 import → alert-only で NetBox/git と現実を突合する**可視化**(v1b)。ここは即価値。
- テナント VRF/VNI/VLAN の**枠内即時収束**(採番済みレンジ・許可 leaf 集合内)。採番連携は v1b、枠外は platform 承認(§12.1)。
- 全断防御の主要層が **v1a で稼働**:累積削除予算・List 完全性・per-resource 原因帰属・halt-all。
- **手動ゲート付き段階適用**(canary 1 leaf → 人が疎通確認 → 承認 → broad)が v1.5 で可能。
- 保守窓連動の `remediation.schedule` で NW 文化に合わせた爆発半径管理(v1.5)。
- EOS 機器(Spine4+Leaf36)は `CommitConfirm:○` で**先行 auto 化**可能。

**依然 v2 を要する(auto 収束の完成条件)**
1. **SONiC commit-confirm 合成 provider**(watchdog/rollback)。無い間は SONiC 60 leaf は型により観測専用固定。
2. **疎通 canary(自動)+ 自動段階ロールアウト + 自動 health gate**。config 収束≠EVPN 到達性を無人で保証するのに必須。
3. **watch 併用(gNMI subscribe)/ tier 別 Observe 頻度の本実装**。100 台上端を毎周ポーリングで回すため。
4. **pod shard 分割 + fencing の実効化**。100 台上端かつ platform/tenant 分離を分散で安全に持つため。
5. **capability 抽象(§5.6 解禁)**。EOS/SONiC 二重 Schema の保守コストを構造的に下げるため(当面は具体型2つ+lint 強制で凌ぐ)。

**絶対前提(v2.3 で型により一部保証されたが、環境要件は不変)**
- **管理系(OOB/管理 VRF)がデータ系 EVPN から独立**していること(§19.3)。アンダーレイが管理系を兼ねると段0 が閉じない。この判定は環境依存で、設計変更では解消しない。
- 管理NWコアの**到達性最小核は段0(Ansible)**、残りは段1 alert-only(v1)。commit-confirm を持つ NW provider(v2)到達までコアは Apply しない。

**総括**:v2.3 は本構成の「事故防御」と「段0 の閉じ方」を型レベルで大幅に堅くし、手動段階適用を前倒した。到達可能な価値(可視化+枠内即時収束+手動段階適用+EOS 先行 auto)は v1 で確実に増えた。一方、**SONiC 自動収束と無人疎通保証という価値の核は v2 のまま**で、判定 ○ は据え置き。これらを満たせば ◎ に近づき、満たさない場合も「Ansible+手動レビューの現状より明確に前進」する構図は前回同様、かつ防御はより堅い。
