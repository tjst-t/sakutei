## 2. 判定変更の理由(△ 据え置きの内訳)

前回△の主因は「**中核機構が実装にも設計の一部にも無い二重の空白**」だった。v2.3 でこれは非対称に埋まった。

- **埋まった(設計側)**:割当表・単一 writer の **fencing 必須化**、**プールのサイト別静的分割**(§16.6=1 プール 1 権威で分断中も各サイト独立払い出し)、**allocator の現実逆引き再構築**、**S2 永続化先の quorum/同期レプリカ確定**(A-4)、**段0 SPOF・コールドスタート・自己収束自傷の確定**(§19.7)、**List 完全性検証**(B2)、**累積破壊予算 halt-all**(B1)。前回「安全機構の思想は正確だが機構が無い」と書いた領域に機構が足された。
- **埋まった(スライス側)**:**最小 Workflow が v1.5**、**段0-minimal が v1a**、**tier 別 Observe 頻度が v1b**。DR runbook を Workflow で書き、福岡を軽量段0にする経路が v1 系列で開いた。
- **埋まらない(核心)**:サイトシャーディング本体・RemoteExecutor・lease/revision・クロスサイト S2 **複製の実装**は §24.2 で **v2 のまま**。AD 整合は原理的に対象外、DR 自動判定は思想上不可(いずれも不変)。

**○ へ上げる 5 条件の設計上の裏付けはほぼ揃ったが、それを支える分散実装が v2 に残る**ためコードは据え置き△。前回「思想も実装も無い」→ v2.3「思想と着手前決定は固まったが実装待ち」で、**質は明確に前進**した。

## 3. v2.3 で新たに気づいた問題・残存課題

1. **DR 中の intent 書き込み経路が未設計**(G7 残り)。§19.4 の外部化+ミラーは**読み取り(pull)全断耐性**の話。東京全損時に大阪で intent を変更(PR マージ・承認)する経路は、承認者・ボット・署名(§26.3 C)が東京前提だと止まる。runbook に「intent 変更手段の確保」の明記が要る。
2. **fencing token 発行元が新たな単一性要求を生む**。token を単調増加で発行する主体(A-4 の quorum ストア)はクロスサイトで一貫が必要で、前回懸念の「裏口の分散合意」を完全には消さない。quorum ストアを東京集中に置くと分断中に fence 更新不可——設置サイトの選択が本構成固有の判断として残る。
3. **段0-minimal は DR の受け皿にならない**。福岡の可視化には使えるが、大阪 DR は基幹系を 4h で受けるため**標準段0(3+Ceph+Vault-HA)が必要**。§19.7 の Ceph SPOF(2 ノード同時障害で quorum 喪失=Break Glass L3)が大阪で顕在化し、障害ドメイン分散が人手運用要件に積まれる。
4. **Vault auto-unseal 再検討が 4h RTO に効く**。§19.7 が「段0 に限り auto-unseal(HSM/KMS)を選択肢として再検討」を追加。前回指摘「大阪 Vault の unseal 人手が MTTR に乗る」への設計側緩和が入った(哲学と両立)。ただし「再検討」段階で、採用しなければ RTO に人間 unseal 時間が残る。
5. **fencing・逆引きの実装も v2 側**。型は着手前(v1a)で確保するが、クロスサイトで効かせる**実装契約は v2**。型は早期でも実効は本構成が待つ。
6. **AD/DNS/監視のグローバル整合はこの構成の主目的の一部**であり続ける(G2 不変)。Sakutei に期待すると成り立たない点は前回同様に明示が要る。

## 4. この構成で成立させるための条件(更新版)

- **(a) 大阪に独立標準段0 + reconciler マルチサイト化**:必須。§19.7 の構築要件(Ceph 障害ドメイン分散・Vault 先行起動・自己収束除外)を流用できる。福岡は段0-minimal(§19.8)で可視化用途に留める。
- **(b) git の正を DC 外化 + 多拠点ミラー + DR 書き込み経路の runbook 化**:読み取りは §19.4 で確定。**追加で** DR 中の PR マージ・承認・署名の代替手段を runbook に明記(新課題1)。
- **(c) サイト別 allocator + グローバルプール静的分割**:§16.6 で設計裏付け確定。VLAN/IP はサイト分割、ASN/ループバック等のみ単一権威(分断中 reserve 不可を許容)、喪失時は現実逆引き。
- **(d) DR は人間トリガの手動 runbook(承認ゲート付き最小 Workflow)に限定**:§24.1.5 の最小 Workflow が v1.5 で書ける。`primary_confirmed_lost` は承認ゲート(§10.5)の人間入力、`replica_freshness`/`quorum` は invariant。
- **(e) AD/DNS のレプリ整合は Sakutei 外に委ね「サービス存在」までを収束対象に**:不変。
- **(f・新規) 分散実装(シャーディング/RemoteExecutor/lease/クロスサイト S2 複製+fencing)の v2 完成を待つ**:本構成は §26.4 D の再検討トリガが初日から発火する。この塊をこの構成のため前倒し実装するか、v2 到達まで「各サイト内の drift 自動修復と可視化」に価値を限定する(§23.7=DR 自動化は最後発)判断が要る。

(a)〜(e) は v2.3 で**設計上の裏付けがほぼ揃い**、(f) だけが実装待ちとして残る。◎(思想を曲げず完全自動化)に至れない構造的理由——観測 state レス・shared-nothing・分散合意を中枢に戻さない設計があえて避けた領域に正面から当たる——は不変である。
