## 判定変更の理由(据え置きの論拠)

前回 ○ の根拠(content-address参照・段階ロールアウト・rate limit+halt・managed field分離への一対一写像、テナント砂場が無く境界明快)は v2.3 でそのまま維持され、むしろ CHG-B1(累積削除予算)・CHG-D2(external_owner)・CHG-A4(§26.1 A-4 の S2 確定)で**この構成の安全性・境界設計が補強された**。一方、条件を格上げ・△化させるほどの新規欠陥も生じていない。

しかし ○ を格上げ(◎)できない理由も明確である。本構成の**事業の核はファーム更新=多相Task状態機械**であり、これは v1.5 前倒しの対象外(§24.1.5:「多相 Task 状態機械・自動段階ロールアウトは v2 のまま」)。v1.5 で書けるのは Workflow の骨格(drain→…→resume の直列順序・invariant・手動ゲート)までで、その内側の firmware-update step が要求する「リブート跨ぎの unknown≠absent 解釈・べき等な相再開・進行フェーズS2永続化」は多相Taskの機能そのものであり v2 を待つ。したがって「v1.5 で骨格は書けるが、この現場で価値を出すには依然 v2 の中核実装が必要」という前回の構図は不変。判定は据え置きが妥当。

### 精査項目への回答

- **v1.5 の単純Task+最小Workflowで drain→update→reboot→verify→resume がどこまで書けるか**:**外枠は書ける、中核は書けない**。最小Workflow(直列 one-at-a-time + invariant + 手動承認ゲート・§24.1.5)で `slurm_drain → wait(node_idle) → firmware-update → health-check → slurm_resume` の**順序・不変条件・ゲート**は表現可能。だが reboot を跨ぐ `firmware-update` step の実体は§9.1多相型(Rebooting相での unknown≠absent 待ち・Confirming での現実Observe照合・各相入口のべき等再開)で、これは v2。v1.5 では単純Task(一回実行して現実側に完了印)しか無く、リブート跨ぎ・中断不可の状態機械は表せない。→ **v1.5 では「多相相当を外部スクリプトに委譲し、Sakuteiは順序制御と版verifyゲートだけ担う」割り切りが必須**。
- **ファブリックレベルinvariantの語彙**:**未整備**。§9.2 は `min_active`/`quorum` 止まりで、IB経路の冗長性・ファブリック分断回避を表す述語は無い。IBスイッチ更新の「全ジョブdrain前提」を invariant として宣言する手段が依然欠けており、前回の「拡張が要る」指摘は生きている。
- **S2永続化先が週〜月寿命Taskに足りるか**:**質的には確定したが量的耐久は未検証**。A-4(§26.1)が S2 を quorum ストア+同期レプリカ+fencing と規定し、置き場の未定義は解消。ただしこれは主に「割当表・累積予算カウンタ」を念頭にした耐障害性の規定で、**週〜月にわたる進行フェーズの長期保持・複数メンテ窓跨ぎの再開・承認待ちの長寿命化**という時間軸の要件は明示的に扱われていない(§26.2 B も「相の途中death」の安全性であって寿命ではない)。長寿命Workflowの永続化耐久は残課題。

## v2.3 で新たに気づいた問題・残存課題

1. **多相Taskとv1.5のギャップが本構成では致命的**:他構成なら v1.5 の単純Task+最小Workflowで足りるが、GPU基盤は主戦場がまさに多相Task。v2.3 の v1.5 前倒しの恩恵が本構成には最も薄い(骨格だけ来て中身が来ない)。導入時期の判断で「v1.5 で部分導入→v2 で完成」の二段になる点を明示すべき。
2. **§26.2 B の「Applying=危険区間・人手ゲート」は VBIOS 文鎮化への正しい対処だが、多相Task(v2)前提**。v1.5 の外部スクリプト委譲では、この危険区間death検知を Sakutei が担保できず、スクリプト側の冪等性設計に依存が漏れる。
3. **external_owner の UFM 適用は Observe/Apply の線引きを鋭くする一方、IBファーム更新は「Sakuteiが Apply する領域」**(node_firmware Provider)。つまり UFM設定は external_owner で切り離せても、IBスイッチファーム版数統一は収束対象に残り、ファブリック瞬断invariantの欠如(①')が直撃する。切り分けと収束対象が交差する点に注意。
4. **remediation schedule(§10.8・v1.5)は本構成に好適**:四半期メンテ窓のみ auto、他は alert-only を宣言でき、前回§5の freeze 手動運用より安全。ただし「数日ドレイン待ち」が窓を跨ぐと、窓が閉じた後の周で修復が止まる挙動(level-triggered)と長寿命Workflowの相互作用は要検証。
5. **canary(⑤)未解消の影響が相対的に増大**:v2.3 で他の割り切りが設計化された分、NCCL疎通検証を外部スクリプトで代替する部分が「型に乗らない残余」として目立つ。段階ロールアウトの health_check gate(§10.5)が required でも、その中身は v2 の合成検証を待つ。

## この構成で成立させるための条件(更新版)

1. **多相Task(v2)の前倒し実装は依然必須**。v1.5 の最小Workflowは順序制御・invariant・手動ゲートの外枠として使い、reboot跨ぎのファーム更新中核は当面**外部スクリプト委譲**で割り切る(冪等性・危険区間death対策をスクリプト側で担保)。本格運用は v2 待ちと明示する。
2. **ファブリックレベルinvariant語彙の拡張**(①'・未解消)。IBスイッチファーム更新を「全ジョブdrain前提の別クラス手続き」として表す invariant(経路冗長性・分断回避)を設計語彙に足す。これは v2.3 でも手当されておらず、本構成固有の最優先拡張。
3. **UFM は `external_owner`(§11.4)で Observe-only に切り出す**一方、IBスイッチ**ファーム版数**は収束対象に残す線引きを明確化。converging 3層(§10.4)+ external_owner の併用で二重管理を防ぐ。
4. **S2 の長寿命耐久を別途検証**(A-4 は置き場を確定したが週〜月寿命は未検証)。承認ゲートtimeout(§10.5)・メンテ窓跨ぎ再開・進行フェーズの長期保持を運用試験で確認する。
5. **Slurm連携は drain/resume 2操作に厳格限定**(前回条件を維持)。§11.4(b) の「観測して待つ一方向連携」を `node_idle` の ready_condition に写像し、ジョブstateには触れない Schema規律を Schema lint(§5.2・ロード拒否強制)で担保。
6. **health/canary(⑤)の代替手当**。NCCL疎通・GPU健全性検証を外部スクリプトで health-check step 化し、v2 の合成検証(§17.3)移行を seam として想定。
7. **累積削除予算(§10.2)を version統一 scope に厳格設定**。「毎周数台ずつで全台リブート」の漸進破壊を halt-all で塞ぐ(v2.3 で新たに使える生命線)。
