# 対象構成19:ハイブリッドクラウド(オンプレ+AWS) — Sakutei適用可能性レビュー(v2.3再評価)

**新判定:オンプレ側=◎ 成立(v1a/v1bで到達可) / AWS側=△ 大幅な拡張が必要(ただし境界リソースの部分導入は○、v2.3で外堀が埋まった)**

（前回判定:オンプレ側=○ 条件付き成立 / AWS側=△ 大幅な拡張が必要）

v2.3はレビュー指摘を広範に反映し、本構成の緊張点(常時Observe×AWSレート、外部マネージドの縁切り、実機レイテンシ算術)に**直接効く変更**が入った。総合ベクトルは変わらないが、オンプレ側は「条件付き」の条件が設計側で解消され半段昇格。AWS側の△は残るが、その理由が「未定義ゆえの不安」から「v2機能待ちという既知の重み」へと質的に改善した。

## 2. 判定変更の理由

**オンプレ側 ○→◎**:前回の「条件付き」の条件(alert-onlyで信頼獲得、全platform相当ゆえDBSource不要)はv2.3でむしろ設計側の既定路線として固まった。§24.1aで**FileSource+alert-only+`external_owner`+last-seenリング+List急減halt**がv1aに、import/Sync Mode/ready_conditionがv1bに整理され、本構成のオンプレ要件(VM 200・drift常態化のimport・基幹DBの永久alert-only)は**v1a+v1bの範囲に過不足なく収まる**。§23.9(観測不能資産の`ledger_only`)も基幹DB周辺のprune巻き添え防止に効く。実機レイテンシ表でvCenter 0.8s→~200台という天井も明示され、VM 200が単一デーモンの現実的上限に収まることが数字で裏付けられた(§12.2)。不確実性が消え、条件付き→成立へ。

**AWS側 △維持(ただし内実改善)**:△の3本柱のうちG3が`external_owner`で境界レベル解消、G1がtier別頻度でv1b前倒し(部分)、G4/部分導入が第一級化。しかし**watch併用=v2・broker(STS)=v2・自前AWS provider群という「AWS全面をSakuteiで」のクリティカルパスがv2に残る**構造は不変のため、総合の△は据え置く。質は「未定義ゆえの△」から「既知のv2重み+境界導入は今すぐ可、の△」へ改善した。

## 3. tier別Observe頻度前倒しがAWSレート/課金問題に与える変化(精査)

- **レート制限**:前回試算「AWS 340リソース×10秒周期=毎秒34コール、8VPC短周期でRequestLimitExceeded」は不変。v2.3の**tier別頻度(§12.2・v1b)**で、安定リソース(VPC/Subnet/RTB/IGW=`tier: foundation`かつ低変化)をN周に1回に落とせば、実効コール数を1桁下げられる。EC2/RDS本体のみ毎周とすれば毎秒34→10コール前後に収まり、**スロットリング(§5.3 transient→§6.6 backoff)による自己律速を回避しやすくなる**。ただしこれはv1a初日には無く**v1b待ち**である点が構造的制約。
- **API課金**:前回同様Describe自体は概ね無料で直接課金は軽微。実害はCloudTrailノイズ(Describeが本当の変更を埋める)で、tier別間引きは**このノイズ量を直接削減**する二次効果を持つ(頻度低下=イベント生成減)。§10.3の**last-seenリング(S3・非永続)**が入ったことで、「actualがいつ変わったか」を観測stateレスを崩さず答えられ、AWS側のdrift調査(CloudTrail頼み)への依存を軽減できるのは新たな利点。
- **算術の再試算**:§12.2の実機表で**高速REST=0.15s → 30s間隔で上限~1,067台**が明記された。AWS 340リソースは毎周全ObserveでもObserve予算(10s×並列16)に対し 340×0.15s/16 ≈ 3.2s で理論上は1周に収まる。**つまりレイテンシ律速では収まるが、律速要因はレイテンシでなくAPIレート/トークンバケット**という前回の核心が数字で再確認された。tier別間引きはレイテンシ問題ではなくレート問題への対処として効く、と整理できる。

## 4. 外部オーケストレータ境界(RDS等マネージド内部収束器)のexternal_owner化(精査)

CHG-D2(§11.4)は本構成に最も効いた変更。RDS(`modifying`が数十分・メンテウィンドウでAWSが勝手に動かすフィールド)、および将来のASG/マネージドサービスを、`external_owner: rds`で**scope/種別単位で収束対象から除外(Observeはする=可視化は残る)**できる。前回G3の「managed宣言1つ間違えるとAWSと永久喧嘩」は、フィールド単位のmanaged fieldsに加えて**scope単位の粗い縁切り**という上位の逃げ道が入ったことで、事故時の被害を「Apply抑止で即座に止める」に閉じられる。協調は`ready_condition`のObserve待ち一方向(Sakuteiから外部へ指示を出さない)で、RDSフェイルオーバー完了やRoute53 INSYNCを下流gateにする用途にそのまま乗る。**v1aで`external_owner`が入る**ため、AWS部分導入時の安全弁が初日から使えるのは実務上大きい。

## 5. 「オンプレ=Sakutei / AWS=Terraform継続」推奨はv2.3で変わるか(精査)

**変わらない(むしろ設計が追認・補強)**。理由:(a) 自前AWS provider群+watch(v2)+broker STS(v2)というAWS全面のクリティカルパスがv2に残る(§24.2)。(b) §1.2でSakutei自身が差別化を「観測stateレス×オンプレ物理まで」に絞ると宣言し、AWSでTerraformと正面勝負しない方針を明示(F M-7見送り)。(c) Terraform側もrefreshで擬似stateレス化できる関係(G2)は不変。**ただし推奨の内実は前進**:`external_owner`(§11.4)とDNS provider v1a化(§24.4)により、「またがる依存(Route53←オンプレ、EC2←オンプレDB)をseam分割し、Route53だけSakutei管理」を**宣言的・第一級に実装できる**ようになった。前回は「書けば可能」だったものが「設計が用意した道具で綺麗に切れる」に昇格。結論のNo(全面)/Yes(境界のみ)は維持しつつ、Yes側の実現容易性が上がった。

## 6. v2.3で新たに気づいた問題・残存課題

- **N1(新規懸念):tier別間引きとAWSの結果整合の相互作用**。安定tierをN周に1回に落とすと、Route53伝播やSG参照変更のような**結果整合の収束途中(converging)を取りこぼす窓**が広がりうる。§10.4のconverging deadlineとtier頻度の整合(遅いtierほどsettle窓を伸ばす等)がv1b実装時に要調整。設計本文に明示なし=運用パラメータ(§26.3 C)行き。
- **N2(残存):external_ownerのObserveコストは残る**。§11.4は「Apply しないがObserveはする」ため、RDSを除外してもDescribe/List自体はレート予算を消費する。除外scopeにもtier別頻度(最低頻度)を適用できるか、が実装課題。
- **N3(残存・不変):broker STS=v2**。CHG-A2でv1はSecretRef直結・長命IAMキーと確定。AWSをv1で本格運用するなら攻撃面が残る。段0のreconciler配置(管理VPC内EC2でDX断時も自律収束・§19.7で段0 SPOF/自傷は補強されたが分散Executor自体はv2)も未成熟。
- **N4(新規・軽微):SG相互参照の循環検出**。前回指摘した「SG-A↔SG-Bの正当な相互許可を循環検出(§6.1)が誤って弾く」問題は、v2.3の§6.1がdepends_on統一(CHG-A5)に留まり参照種別の区別には踏み込んでいない。自前SG provider実装時に要注意(v2領域)。

## 7. この構成で成立させるための条件(更新版)

**オンプレ側(◎成立)**:
1. v1a(DNS/VM/FW providerで「触っていないのに戻る」実証)→ v1b(import→alert-only観察→scope昇格・§23.7)の順で導入。
2. 基幹DB/レイテンシ敏感VMは**永久alert-only**(§23.7)、観測不能な周辺資産は`ledger_only`(§23.9)でprune巻き添え防止。
3. VM 200はvCenter階級で単一デーモン上限~200台(§12.2)に収まる。超える場合はcluster軸シャーディング。
4. `destructive_budget`(§10.2)+List急減halt(§8.6)を初日から有効化し、Ansible時代のdrift放置からの一括収束事故を封鎖。

**AWS側(△・境界のみ○)**:
1. **全面移行はしない**。Route53のオンプレ発レコードのみをDNS provider(v1a)でSakutei管理、残AWSはTerraform継続。
2. RDS/ASG等マネージドは**`external_owner`(§11.4・v1a)で明示除外**(Observe=可視化のみ、Apply抑止)。
3. AWSシャードを立てる場合は**tier別Observe頻度(v1b)必須**:foundation系(VPC/Subnet/RTB)をN周に1回に落とし、EC2/RDSのみ毎周でレート予算内(毎秒~10コール)に収める。
4. 本格運用は**watch併用(EventBridge/Config・v2)とbroker STS(v2)を待つ**。それまでのAWS導入は「境界リソース+alert-only可視化」に留める。
5. またがる依存はseam分割:オンプレDBの`ready_condition`をAWSシャードがObserve gate、Route53はオンプレサービス実在Observe後にApply。**強い順序保証はシャード内のみ**(結果整合で足りる依存に限定)。
