## 2. 判定変更の理由

**オンプレ側 ◎維持(変化なし)**:v2.5の3テーマは本構成のオンプレ側に新条件を課さない。テーマ③(claim git配布・S2-freeシャード・§12.5)は300拠点エッジ向けで、単一DC・SRE5名の本構成には過剰。テーマ①(衛星の天井・§16.7)は「維持は衛星ゼロで回る」保証だが、本構成は全platform相当でchurnが低くallocator負荷がそもそも軽い。§5.8はvCenter PropertyCollector走査中のDRS移動をmanaged fields除外+converging/settleで吸収すると明記し、v2.4のBulkObserve天井拡張(VM200→数千)の**安全性の裏づけ**を足したが、判定は動かさない。◎据置。

**AWS側 △維持(据置・記号の重みは最軽量を維持)**:AWS側△の支配要因は前回同様「自前AWS provider群(約7種)+broker STS=v2の実装工数×5名SREの機会費用」という**経済判断**で、v2.5はここを一切動かさない(スコープ外・据え置き確認済み)。§5.8が答えたのは残る技術的懸念の最後の1本であり、これで「常時Observe×AWSの構造衝突」は**レート・課金・ノイズ(v2.4)+結果整合・ページング非一貫(v2.5)の全4面**が設計上片付いた。技術的障壁はほぼ消え、残る△は純粋に経済判断——という前回の結論が、より強固になった。

## 3. §5.8はAWS固有の結果整合問題への設計上の応答として十分か(精査)

**十分**。AWS Describe*の非一貫は2系統ある:(a)**結果整合**(直前の変更が反映されない/古い版が返る)、(b)**ページング途中の非一貫**(ページ1取得中の新規リソースがページ2に現れる/消える)。§5.8はこの両方を、正しさの問題ではなく**揺らぎの問題**と正しく位置づけた上で、危険な流用経路(prune・周期越え)だけを型で塞ぐという**過不足のない設計**を採る:

- (a)結果整合 → observed_at刻印+周期越え禁止で「古い版の持ち越し」を防ぎ、次周期の全量再観測(§6.2)で自然収束。converging/settle(§10.4)が一時不整合を吸収。
- (b)ページング非一貫 → complete-or-error(next token=nil完走をerror規律で強制)+prune非流用の型分離。**AWS Describeで最も危険な「ページング欠落IDが理想に無い=削除に直結」の事故**は、そもそもBulkObserveがpruneに渡らない型設計で構造的に不可能になる。prune安全は§8.6のList完全性検証(件数急減halt・ListStatus三値)に一元化され続ける。

前回「BulkObserveをList流用する際はpartial規律を守る」という**実装者の規律頼み**だった防御が、v2.5で**SDKの型強制+等価性テスト(`BulkObserve(scope)≡{Read(id)}`をCIで検証)**へ格上げされた点が実質的前進。AWS provider実装時に「バルク経路と個別経路が別の現実を返す」バグをCIで捕まえられる。

## 4. 「境界scope(Route53等)のみSakutei」推奨の実装確度は§5.8で上がったか

**上がった(判定記号は変えないが推奨の踏み込みが固まった)**。境界導入(Route53のオンプレ発レコードをDNS provider=v1aで管理、残AWSはTerraform継続、境界は`--claim`でgit宣言)という推奨自体はv2.4から不変だが、その手前の**「境界外の残AWSをBulkObserveで低コスト全量alert-only可視化する」運用**の安全確度が§5.8で上がった:

- v2.4で「可視化コスト1/25(340リソース→~12-15コール/周)」により可視化シャードの採用ハードルが下がった。v2.5はそこに**「その可視化がprune暴走を絶対に起こさない型保証」**を足した。alert-onlyなら本来prune側は問題になりにくいが、将来のscope昇格(alert-only→auto)を見据えると、BulkObserveとprune経路の型分離が効いているのは重要。
- 「境界のみSakutei/残はTerraform」の分割で、Sakutei側が触るのはRoute53等の少数リソースだが、そのDescribe/List経路も§5.8契約下に入る。境界を出し入れするPR(§12.4 claim-as-intent)のレビューで、「BulkObserveをprune根拠に使っていないか」が型で保証されるため、境界拡大の安全性が読みやすい。

## 5. 残存(v2.5でも未解決)

- **N-new3(据置・不変):broker STS=v2 / 自前AWS provider群約7種=v2の実装工数**。AWS側△の支配要因。v2.5はスコープ外で一切動かさない。全面移行の是非は依然「provider実装工数×SRE機会費用」の経済判断であり、技術的障壁ではない。
- **またぐ依存**:オンプレDB←EC2、Route53←オンプレの「観測ready待ち」はv2.4の§12.2 CHG-F4(シャード間協調は現実を介する)で確定済・v2.5変更なし。強い順序はシャード内のみ、で据置。
- **AWSシャードの自律収束(DX断時)**:管理VPC内EC2配置+RemoteExecutor実動作はv2。§12.5のS2-freeシャード階級はエッジ店舗向けで、AWSシャードには直接適用しない(AWSシャードはTask/Workflowを持てば中央claim側でS2が要る)。

**結論**:AWS側の技術的衝突は§5.8で最後の1本まで設計上片付いた。判定は据え置き(オンプレ◎/AWS△)だが、AWS境界導入は「安全に踏める」度合いが上がり、△の重みは最軽量を維持する。全面移行の壁は純粋に経済判断(provider実装工数=v2スコープ)として残る。
