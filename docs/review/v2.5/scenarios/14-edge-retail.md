## 2. 判定変更の理由(○→◎:残存の性質が「詰め」から「範囲外1点」へ)

**◎ 昇格の核心は「設計で解ける残存が全て解け、残るのが Sakutei 対象外の物理段1点だけになった」ことである。**
前回 ○(条件付き成立)を「無条件でない」に留めていたのは、claim 方式が**新たに生んだ4課題**(G3 資格・S2 耐久性・
git 二乗・順序ゲート進捗)が「詰め残し」として口を開けていたためだった。v2.5 はこの4つを**個別のパッチでなく
階級・規約・原則で構造的に**塞いだ:

- **S2 耐久性は "満たす" のでなく "要件から降りる" で解いた**(CHG-I3)。前回は「段0-minimal は quorum を
  持てないから S2 喪失時は Observe で再導出」という**緩和策**を条件4に積んでいた。v2.5 の S2-free シャードは、
  そもそも店舗 claim が S2 を持たない階級を第一級化する——耐久性要件をゼロにする。これは観測 state レス思想の
  最も純粋な帰結(「何も覚えないから何も失わない」)であり、緩和でなく**問題の消滅**である。§26.1 A-4 の未決も
  CHG-Z1 で連動消し込みされた。
- **順序ゲート進捗の中央移管が成立する**(CHG-I4)。前回最も慎重を要した「閉店 Workflow の順序ゲート進捗の
  S2 喪失が prune 安全性に直結」は、**手続き(S2 が要る)を中央プロビジョニング claim に、定常維持(Resource
  のみ)を店舗 S2-free に、claim 境界で分離**することで解ける。閉店の「回収完了 Observe→prune 解禁」の順序
  ゲートは中央 quorum S2 側に居るため、店舗ノード全損で飛ぶことがない。開店/閉店が **claim 変更 PR + fencing**
  という前回レポートの語彙(§12.4 再シャード Workflow)の**具体適用**として正式に書き下せる。
- **資格局所性が G3 を解いた**(CHG-G6)。前回「WAN 断中に write できる=資格が店舗に常駐する=盗まれたら
  店舗内を書ける、というトレードオフは claim 方式でも消えない」と断じた核心を、v2.5 は**トレードオフの構造を
  変えて**決着させた。破壊力の総量を消すのではなく、**爆発半径を当該店舗に局所化**する(中央の全店舗資格を
  配らない=1 店舗漏洩が全店舗に波及しない)。鮮度は中央 rotate 収束で維持。これは §16.7「維持は衛星ゼロで
  回る」の資格面への適用であり、前回「資格保護強度が店舗物理セキュリティ依存」だった弱点が「爆発半径が閉じて
  いるので 1 店舗物理セキュリティで十分」へと**受容可能なリスクに縮小**した。
- **git 二乗トラフィックが線形化した**(CHG-I1/I2)。前回「設計は全 intent を pull と書くが 300 規模では
  claim スコープ限定 pull が実質必須」という**設計と現実の乖離**を、v2.5 は §12.4 を否定せず精緻化する形で
  正式に埋めた。sparse checkout(パス接頭辞規約)+状態レスミラー2拠点で **5 fetch/s** に固定。二乗が消える。

**開店/閉店 Workflow のこの語彙での書き直し(前回レポート §2 の再構成)。** 前回は「開店月 5〜10 件を claim
デーモンが自律収束、断中開店は blocked」までしか書けなかった。v2.5 語彙では以下に精緻化される:

```
開店:
  1. 中央プロビジョニング claim 下で新店舗 scope を構築(中央が S2 付きで Task/Workflow=採番・初期 config を実行)
     ← allocator 到達が要るのはこのフェーズ。WAN 断中は waiting-allocation で保留(§16.8)
  2. 安定後、claim 変更 PR で当該 scope を店舗デーモン(S2-free)へ引き渡す(drain→PR→fencing 世代更新)
  3. 以降、店舗は「pull した intent(sparse)+ 局所資格(§15.7)」だけで WAN 断中も自律維持収束(§16.7)
閉店:
  1. claim 変更 PR で店舗 claim から外し中央へ戻す(店舗デーモンを drain・fencing 世代更新)
  2. 中央 claim 側で回収 Workflow(順序ゲート付き・S2 は中央 quorum)を実行し prune 解禁
```

**残るものの明確化。** 設計で解けるものが全て解けた結果、最後に残るのは **G7(ゼロタッチ物理段)のみ**である。
これは「段0-minimal を店舗に物理的に置くまで」——素の OS 起動・claim デーモンの初回配布・BMC/PXE 核を現地
作業ゼロで踏む段——であり、**Sakutei の責務境界の外**(段0 は「人が Ansible + 金庫で構築する不変の土台」・
CLAUDE.md ブートストラップ節)である。したがって G7 は「Sakutei 設計の穴」ではなく「Sakutei が委譲する範囲」
であり、◎(Sakutei 責務内での成立)を阻まない。G8(edge_router commit-confirm)は v2 固定で許容済み。

## 3. 残存(v2.5 後)

1. **G7 ゼロタッチ物理段(範囲外・唯一の本質的残存)。** 段0-minimal 到達までの物理立ち上げは Sakutei 対象外。
   実運用では外部の provisioning(ベンダキッティング/ZTP スイッチ/USB イメージ)に委譲する。**Sakutei は
   「物理が立ち上がった後」を ◎ で担う**が、物理段は別途手当てが要る——これは設計の欠落ではなく責務分界。
2. **G8 edge_router の commit-confirm(v2 待ち・許容)。** 店舗 WAN 終端の Apply 自動化は v1 期 alert-only。
   claim 方式で自ホスト側 IF 経由の緩和は効くが commit-confirm は必須で v2。
3. **二重 claim / fencing 世代更新の運用規律(軽微・不変)。** 店舗ノード交換(故障→新品)時に旧ノードが
   ゾンビ収束しないよう fencing 世代を確実に更新する運用規律は残る(CHG-I4 で PR+fencing に載ったので
   監査・検知はしやすくなった)。
4. **閉店 100% 削除の破壊予算(CHG-Z3 で claim 境界化済み・運用設計残)。** 「1 店舗閉店=その claim の 100%
   削除」に approved-large-change 必須化+`max_deletes`=「同時閉店店舗数」で引く運用設計は不変(claim 単位で
   設計しやすくはなった)。S2-free 化で閉店の順序ゲート S2 が中央に移ったため prune 安全性の土台は強化された。
5. **資格 rotate 収束の WAN 復帰依存(軽微・受容)。** §15.7 の鮮度維持は「再接続時に中央 rotate」なので、
   長期 WAN 断店舗は資格が古いまま常駐する。爆発半径が当該店舗に閉じているため受容可能だが、超長期断の店舗は
   物理巡回時の手動 rotate をフォールバックに持つのが安全。

## 4. この構成で成立させるための条件(v2.5 更新版)

v2.4 の8条件を v2.5 の解消で更新する。**取り消し線相当=v2.5 で解消し条件から降格、太字=残存。**

1. ~~claim スコープ限定 pull を成立条件に加える(二乗トラフィック回避)~~ → **CHG-I1/I2 で設計本体に格上げ・降格。**
   `intent/<scope>/...` レイアウト規約 + sparse checkout + 状態レスミラー2拠点で標準化された(5 fetch/s)。
   もはや「構成側が工夫すべき条件」でなく「設計が提供する規約に従う」だけ。
2. ~~WAN 断中の write 資格供給を新規に詰める(G3)~~ → **CHG-G6(§15.7)で解消・降格。** 店舗ローカル file
   SecretBackend に当該店舗分のみ局所常駐 + 中央 rotate 収束。**残る要件は「店舗ディスク暗号化+アクセス制御」
   のみ**(爆発半径が閉じているので 1 店舗物理セキュリティで足りる)。
3. ~~店舗ローカル S2 の耐久性を設計する~~ → **CHG-I3(S2-free シャード)で消滅・降格。** 店舗は Resource 収束
   のみ・S2 を持たない。**残る要件は「店舗 claim に手続き(Task/Workflow)を置かない」規律**——手続きは中央
   プロビジョニング claim へ(CHG-I4)。
4. **開店/閉店を claim 変更 PR ハンドオフで組む(新規に明文化・成立条件へ)。** 手続き=中央 S2 付き claim、
   定常維持=店舗 S2-free claim を claim 境界で分離。開店=中央構築→安定後 PR で店舗へ、閉店=逆順。fencing
   世代更新を必ず伴わせる。
5. **段0-minimal を店舗に置くまでの物理段(ゼロタッチ立ち上げ)を外部委譲で手当て(不変・残存=G7)。**
   Sakutei 責務外。ZTP/キッティング/USB イメージ等の外部 provisioning に委譲する前提を運用に明記。
6. **edge_router の Apply 自動化は v2(commit-confirm)待ちと割り切る(不変=G8)。** v1 期 alert-only。
7. **閉店 claim に approved-large-change を必須化**し破壊予算は「同時閉店店舗数」で引く(CHG-Z3・不変)。
   店舗内観測不能資産は `ledger_only`(§23.9)で prune 巻き添えから守る(transient unknown を ledger_only に
   しない運用規律は不変)。
8. **中央↔店舗依存は「観測 ready 待ち」で組む**(CHG-F4・不変)。RPC でなく Observe gate。分散合意も状態交換も
   持ち込まない。§16.7 でこれが「衛星コールゼロで回る維持」として設計保証に載った。

**総括:** v2.5 は本構成の残存4課題(G3 資格・S2 耐久性・git 二乗・順序ゲート進捗)を、それぞれ **資格局所性
(§15.7)・S2-free シャード階級(§12.5)・sparse checkout+ミラー中継(§12.5)・claim 変更 PR ハンドオフ
(§12.5)** で構造的に塞いだ。加えて §16.7「衛星の停止は変化を止めるが維持を止めない」が、300 拠点の常時
どこか WAN 断という本構成の定常を **設計保証内**に収めた。前回 ○ を「条件付き」に留めていた「claim 方式が
生んだ新課題」が全て解消し、**設計で解けるものは全て解けた**。最後に残るのは **G7 ゼロタッチ物理段**——
段0-minimal を店舗に物理的に置くまでの一段——のみであり、これは Sakutei が明示的に外部委譲する責務境界の外
(ブートストラップ段0)である。したがって **Sakutei 設計の責務範囲内で本構成は ◎(成立)** に到達する。
残る条件(上記5〜8)は「動かせない分水嶺」でも「設計の詰め残し」でもなく、外部委譲の明示と運用規律であり、
本構成は v2.5 の最大受益者として ○→◎ を達成する。
