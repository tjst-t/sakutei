# 対象構成20:ベアメタルホスティング/専用サーバプロバイダ — Sakutei適用可能性 再評価(v2.5)

**新判定:○ 条件付き成立(判定据え置き。ただし v2.4 で唯一の実質的な新論点だった N-1「速い経路の allocator/Vault 可用性が割当 UX に直結」が、v2.5 の§16.7/§16.8/§19.9 で原則・状態・可用性要件の 3 層から正面回答され、運用前提の不確実性が構造的に縮んだ)**
— v2.4 は早期収束(§6.8)で「割当の起動レイテンシを周期非依存」にした反面、その速い経路が render フェーズ1 の採番(allocator)と Vault 解決に律速され、**衛星可用性が UX 品質そのものになる**という新論点(N-1)を露出させた。v2.5 は「衛星の停止は変化を止めるが維持を止めない」(§16.7)を設計保証に格上げし、`waiting-allocation` 縮退(§16.8)と衛星停止影響表(§19.9)で N-1 を型と運用根拠の両面から回収した。本構成にとっての効き所はこの一点で、多相Task(§9.1・v2)/provisioner(§1.3・Sakutei 外)/credential-broker(§15・v2)という上限規定要因は不変。

**判定推移:v2.2 ○ → v2.3 ○(据え置き・確度前進) → v2.4 ○(据え置き・G2 起動側解消) → v2.5 ○(据え置き・N-1 が原則で解消・運用前提の不確実性縮小)**

## 2. 判定理由(据え置きだが N-1 が原則で解消)

- **N-1 の性格が「段0前提に織り込む宿題」から「原則で保証済み」へ**:v2.4 では「速い経路を秒オーダーにするほど allocator/Vault 可用性が UX 品質に直結し、段0の可用性(§19.7)を運用前提に明記すべき」という**運用側の宿題**として残った。v2.5 は §16.7 でこれを**設計保証に格上げ**した。維持(定常収束)は衛星コールゼロで回り、衛星可用性が守るのは変化(新規採番)だけである、と役割を分離した。日次5-10件割当という本構成の低 churn では、allocator 断の影響は「既存850台は無傷、新規割当だけが `waiting-allocation` で allocator 復帰まで保留」に限局し、**在庫プール全体が止まるという最悪シナリオが型レベルで排除**された。

- **QPS 算術が本構成の sizing 不安を数値で潰す**(§16.7・CHG-G2):在庫1,000台という規模を見て「allocator が捌けるか」と身構える直観を、churn ベース sizing(日次採番 ~100件/日規模でも無負荷)が明示的に否定する。本構成の割当バースト = ポータル申請レート(人の操作/秒)で上限され、定常収束はバーストを生まない。**allocator HA は「変化の可用性」への投資**であって生存条件ではない(§16.5)ことも明記され、段0 の HA 投資判断が軽くなった。

- **上限規定要因は不変**:v2.5 は「衛星が落ちても維持が回る」ことに応答したが、**「どう遷移するか」の多相Task状態機械(§9.1・v2)/「誰が焼くか」の provisioner(§1.3・Sakutei 外)/1,000台個体別 BMC 資格の credential-broker(§15・v2)には触れていない**。よって完全自動化の到達点は v2.2 以来不変で、判定を○より上げる材料はない。

## 3. 残存(据え置き確認)

- **多相Task状態機械は v2**:ワイプ/ファーム更新のリブート跨ぎ・べき等再開は §24.2 で v2 据え置き。安全骨格(pruneable:false・Workflow明示トリガ・invariant・手動承認ゲート・remediation schedule)は v1.5 で立つ点も不変。着火は秒(§6.8)・遷移は物理作業時間律速という二段構えの誤解防止(v2.4 N-2)も継続課題。
- **provisioner 実体は Sakutei 外**:Metal³/MAAS 相当の 10モデル混在 BIOS/RAID/UEFI・ベンダー固有Redfish吸収層は §24.3 で委譲。本構成の商品価値の半分を担う最大の実装ギャップは不変で、**判定の上限を規定するのは引き続きこの Sakutei 外実装**。
- **credential-broker は v2**:1,000台 BMC 個体別資格の JIT 発行(§15.2 層B)は v2 据え置き。v1 は SecretRef 直結(Vault 保存)+ 定期 rotate の static 運用で、v2.5 の §16.7(Vault 断でも last-resolved で継続)がその運用を可用性面で補強した。1,000台一斉 rotate の自動段階ロールアウト+canary は依然 v2。

**総括**:本構成は依然 Sakutei に最も素直に噛み合うシナリオの一つで、v2.5 でも判定 **○** は据え置き。v2.5 の効果は v2.4 で露出した唯一の実質的新論点 N-1 に限局し、§16.7/§16.8/§19.9 が「低 churn ゆえ allocator は詰まらず、落ちても既存インフラの維持収束は回り、止まるのは新規割当だけ」を原則・状態・可用性要件の三層で保証した。BMC 資格ローテーションも §16.7 の secret last-resolved で Vault 断耐性が付いた。BulkObserve 一貫性契約は BMC バルク非対応で本構成には無関係(数値不変)。多相Task(v2)・provisioner(Sakutei 外)・credential-broker(v2)という上限規定要因は不変。
