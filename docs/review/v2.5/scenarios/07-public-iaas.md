## 2. 判定理由

### 2.1 §16.7 QPS 算術は「churn が高い側の極」でも成り立つ — 実負荷試算

§16.7 の「QPS は churn 比例、フリート規模非比例」の論理は、本構成のような**毎分数件〜ピーク毎秒数件の新規採番**という churn が高い極でこそ真価が問われる。試算する:

```
・定常 9,900VM 相当:Lookup キャッシュヒット → allocator QPS = 0(§16.7 の核心)
・ピーク新規:5 VM/s(毎秒数件)× 採番数件/VM(VMID + IP + FIP + VPC 内 VNI/VLAN ≈ 4)
   = 20 alloc-ops/s(Allocate/Reserve のバースト)
・平常:毎分数件 = 0.1〜0.5 ops/s ≒ 無負荷
```

要点は **20 ops/s は「フリート 10,000」から来るのではなく「ポータル申請ピーク 5 req/s」から来る**こと。§16.7 の宣言どおり、負荷は人の操作レートで上限され、10,000VM が定常維持しても allocator には触れない。**20 ops/s の単純アトミック払い出し(INSERT + 一意制約)は SQLite の得意域**(数千 tx/s 級)であり、段0 VM-HA 上 active/standby + fencing(§16.5)で HA も満たす。→ **v2.4 で「SQLite 最小実装は不足」とした指摘は、sizing 基準の付け替えにより本構成でも成立側へ反転**した(NetBox/Infoblox 実 IPAM は選択肢として残るが**必須ではなくなった**)。ただし twin での実測条件へは移す(下記成立条件4)。

### 2.2 §16.8 waiting-allocation の UX 評価 — 「エラーでなく待ち」は本構成に最適合

allocator 瞬断時、v2.4 では「新規 VM 作成が止まる=事業インパクト」が懸念だった。§16.8 は瞬断を **`waiting-allocation`(converging 類似・エラーでも halt でもなく下流 skip のみ)** として型で表現し、(1)既存 10,000VM の収束は Lookup キャッシュで無停止、(2)新規申請は「キュー保持→allocator 復帰後の周期で払い出し」へ縮退、(3)Release は元々遅延前提で安全側に保留、とする。**IaaS の UX として「申請が即エラー返却」より「申請受付済み・provisioning 遅延中」の方が桁違いに良い**(ポータルが元々非同期 provisioning=「受付→provisioning→ready」前提・成立条件5)。§19.9 の停止影響表が「allocator 停止=新規採番リソースの作成のみ停止・定常収束は無停止」と非対称を明示し、**allocator の HA 投資は「変化の可用性」限定で足りる**(SLA 99.95% の分母は定常維持であって新規 provisioning ではない)ことが読める。→ UX 評価は**明確にプラス**。

### 2.3 プール分割 by claim — サイト軸には効くがテナント軸には限界(正直な指摘)

§16.5 のプール分割 by claim は「intent で disjoint レンジ宣言」により中央 allocator 依存を「全シャード共有プールのみ」に縮める。**本構成での適合を層別に評価する**:

- **効く軸(サイト/クラスタ/物理)**:VLAN/VNI・管理 IP のように**サイトごとに静的に切れるプール**は disjoint 宣言が回る(site-a=VLAN 100-199 等)。20 クラスタ・3 Ceph クラスタの物理境界に沿うシャード間干渉は切れる。
- **回りにくい軸(テナント)**:本構成の分割は本質的に**テナント軸の動的作成**であり、2,000 テナントが動的増減する。テナントは**どのサイトにも VM を置きうる**ため、テナント単位で disjoint プールを**事前宣言**する前提が崩れる(新規テナント=新レンジの PR が申請ごとに要る=動的作成の即時性と衝突)。→ **テナント跨ぎで共有される FIP プール・グローバル ASN・共有 VXLAN VNI 空間は「全シャード共有プール」として中央 allocator に残る**。ここは §16.7 の churn 算術(共有プールでも QPS は churn 比例)で救われるが、**disjoint 分割による干渉遮断は効かない**。§12.4 の「全域不変条件・全域 quota はシャード単体で強制不可・外部集約へ」がここに直撃する。CHG-I1〜I4(sparse checkout・S2-free シャード・開店/閉店ハンドオフ)は主に地理分散(拠点=サイト軸)を想定した精緻化であり、**テナント軸の動的 IaaS には部分適用**に留まる。

→ **プール分割 by claim は「シャード間干渉を物理/サイト軸で切る」には成功、「テナント軸で切る」には原理的限界**。ただしこの限界は §16.7 の churn 算術が緩和するため、**律速としては解消・アーキテクチャの純粋な分割としては未達**という二重の位置づけになる。

### 2.4 G3 は不変 — 総合が ○ に届かない唯一の理由(据え置き確認)

v2.5 CHANGELOG 全体を精査したが、quota admission・メータリング課金・RBAC 認可・ポータルという**委譲先が事業本体**という最重要指摘への設計変更・注記・反論はいずれも無い(§24.3 委譲リスト据え置き、採用しなかった選択肢にも現れない)。むしろ §12.4/§16.7 で「全域 quota はシャード単体で強制不可・外部集約へ」が再確認され、**Sakutei が全域 quota を担わない立場が確定**した。→ G3 は据え置きが確認された。

**「Sakutei 側の技術ギャップは全て解消し、残りは外部要素のみ」と言い切れる段階に達したか**:**達した(条件付き)**。v2.4 で残っていた技術ギャップ(周期律速→§6.8、単一天井→§5.7/§12.4、そして v2.4 が新規に立てた衛星 QPS→§16.7/16.8/16.5、BulkObserve 一貫性→§5.8)は v2.5 で**すべて設計上の解を得た**。残る △ の芯 G3 は**Sakutei の設計スコープ外(事業システムの上半分)**であり、Sakutei の技術的欠落ではない。ただし「言い切れる」には (a) DBSource 連動 Watch=v2、(b) 完全な tenant 即時 API は v2 待ち、という**実装フェーズの留保**が付く(下記残存 R1・R2)。

## 3. 残存(v2.5 でも残るもの)

- **R1. DBSource 本体が依然 v2**:tenant セルフサービス即時反映の本命は DBSource 連動 Watch=v2 でしか実らない。v1a/v1b で動くのは FileSource webhook 経路(疑似即時=PR ベース)のみ。§6.8 の seam(Watcher/ChangeHint)は v1a で確定しているが、本番 IaaS の tenant plane は v2 待ち。v2.5 はこの点に触れず(スコープ外)、v2.4 からの前進なし。
- **R2. テナント軸の分割は原理的に未達**(2.3):disjoint プール宣言はサイト軸専用で、テナント跨ぎ共有プール(FIP・ASN・グローバル VNI)は中央 allocator に残る。churn 算術で律速は救われるが、blast-radius の完全なテナント分離は Sakutei 単体では提供不可(§12.4 の全域制約と合流)。
- **R3. G3(quota/課金/認可=事業本体)**:総合 △ の芯。v2.5 スコープ外・据え置き確定。上位テナントプラットフォームを Sakutei と同規模で別途フルスクラッチする工数非対称は不変。
- **R4. テナント跨ぎアトミック性の原理的不在**(v2.4 N3 の継続):§5.8 で「BulkObserve も結果整合」が明文化され、全テナント一括操作・全域 quota 強制は Sakutei 単体で提供不可が再確定。上位プラットフォーム負担がここでも増える(G3 と合流)。

## 4. この構成で成立させるための条件(更新版)

1. **PoC は v1b で成立(不変・v2.5 で HA/縮退が v1b へ集約され補強)**:CHG-Z2 で allocator HA 最小形 + Lookup キャッシュ + waiting-allocation 縮退 + プール分割 by claim + BulkObserve 等価性テスト + claim git 配布 が **v1b に集約**。platform=FileSource/tenant=FileSource 疑似即時の縮小版マルチテナント IaaS が v1b で動く。tenant 即時 API の完全形(DBSource 連動 Watch)のみ v2。
2. **高スループット allocator の要件が緩和(v2.5 で前進)**:v2.4 で「筆頭級・NetBox/Infoblox 必須」としたが、§16.7 の churn 算術と §16.5 の HA 最小形により、**自作 SQLite + active/standby + fencing でピーク 20 ops/s 域を満たせる見通し**が立った。NetBox/Infoblox は選択肢に格下げ(必須→任意)。ただし FIP/ASN/共有 VNI の全シャード共有プールは中央権威に残るため、その QPS を twin で実測(条件4)。
3. **上位テナントプラットフォームを Sakutei と同規模で別途フルスクラッチ(不変・最重要)**:quota admission(書込前強制)・メータリング/課金・RBAC 認可・非同期ポータル・SLA 計測・全域 quota 集約。v2.5 でも設計側応答が無く工数非対称は不変。「委譲」は「作らなくてよい」ではない。総合 △ の芯。
4. **twin(v2)で 1万リソース×ピーク・共有プール allocator QPS・EVPN realization ラグ・BulkObserve 走査窓非一貫を実測(拡充)**:§16.7 の churn 算術と §16.8 の waiting-allocation 縮退キューの合流挙動、§5.8 の PropertyCollector 走査窓揺らぎを twin で検証。天井表(§12.2)と QPS 算術は理論値。
5. **ポータル UX を非同期 provisioning 前提で設計(不変・§16.8 で補強)**:制御プレーン起床は秒オーダー。「受付→provisioning→ready」の非同期 UX に §16.8 の「allocator 復帰までの遅延」も自然に吸収される(エラーでなく遅延)。

**位置づけ**:v2.5 は v2.4 が自ら立てた「次の壁=衛星 QPS」を原則(§16.7)・算術(churn 比例)・縮退(§16.8)・HA(§16.5)・BulkObserve 契約(§5.8)で塞ぎ、**Sakutei が担う下半分の技術ギャップを打ち止めにした**。本構成は churn が高い側の極でありながら、負荷がポータル申請レートで上限される構造ゆえ QPS 算術が成立する。総合が △ に据え置かれるのは、条件3(上位基盤=事業本体の別途フルスクラッチ)という**外部要素**が残るためだけであり、これは v2.5 のスコープ外・Sakutei の技術的欠落ではない。**「Sakutei 側の技術ギャップは全て解消・残りは外部要素のみ」は(実装フェーズ留保 R1/R2 付きで)言い切れる段階に到達した**——ただしテナント軸の完全な blast-radius 分離(R2)だけは原理的限界として残る。
