## 全 20 構成の現在地(v2.4 時点)

**◎=2**(03 中堅仮想化, 11 DBaaS。加えて部分◎: 18 可視化, 19 オンプレ) / **○=13**(01, 04, 05, 08, 09, 10, 12, 13, 14, 15, 16, 17, 20) / **△=3**(02, 06, 07。加えて部分△: 18 収束, 19 AWS) / **✗=0**。

**△として残る 3 構成の芯はすべて特定済みかつ性質が異なる:**
- **02 スモールオフィス**: 機器側 API の貧しさ(設計では解けない)
- **06 マルチサイト DR**: RemoteExecutor・lease 縮退・S2 複製の実装(v2 到達で解ける見通しが立った)
- **07 パブリック IaaS**: 委譲先の上位テナント基盤が事業本体という工数非対称(Sakutei の外の問題)

## v2.4 で確認された効果

1. **claim-as-intent が予想以上に効いた** — 特に 14(エッジ)は「分散 Executor が必要」という前提自体を無効化する構成転換(中央リモート収束→各拠点自律収束)を生み、v2 待ちだった分散型ユースケースの過半が v1b 圏内に入った。06 の DR 手順も claim 変更 PR という自然な語彙で書けるようになった。
2. **BulkObserve は算術を桁で書き換えた** — vCenter 8,000VM・AWS 340 リソース・Proxmox 3,500 リソースがいずれも単一デーモン圏に復帰。「シャーディングは v2」の制約が実質的に痛くなくなった(シャードが要る規模自体が一桁上がった)。
3. **早期収束パスは周期律速の問題を全域で解消** — 07 の核心だった「毎秒級 API と構造的に非互換」の議論は消滅。04/11/20 でも人の操作→反映の体感が周期非依存に。

## 新たに顕在化した共通課題(次回改訂の候補)

1. **allocator / Vault の QPS・可用性が次の天井** — 早期収束(採番が UX 直結)と claim 分割(全シャードが共有)の両方がここに合流する。04/07/11/20 が共通指摘。allocator の HA 設計・キャッシュ戦略が v1b の実質要件になりつつある。
2. **BulkObserve の一貫性** — バルク走査窓内のスナップショット非一貫(DRS 稼働中の PropertyCollector、AWS Describe の結果整合+ページング)。Observe 側は converging/settle で吸収可、prune 側は §8.6 が主防御という整理は付いたが、SDK での明文化が要る(04/19 指摘)。
3. **claim 方式のスケール詰め** — 300 拠点の git pull トラフィック(claim 軸スパース pull が実質必須)、店舗ローカル S2 の耐久性(段0-minimal は quorum なし)(14 指摘)。
4. **据え置きの既知課題** — 多相 Task(12/20)、自動段階ロールアウト/canary(05/09/11/16)、credential-broker(v2)、4-eyes(17)、大量正当作業と累積予算の衝突(11/13)は v2.4 でも未着手。
