## 2. 判定変更の理由(据え置きだが G2 の性格が変わった)

総合判定は前回同様 **○ 条件付き成立**。v2.4 の効果は G2 に集中しており、以下のとおり「据え置きだが確度前進」となる。

- **割当〜プロビジョニング開始が周期非依存に(§6.8 の効き所)**:v2.3 では「reconcile間隔を在庫向けに分オーダーで置くと、割当が入っても最悪その周期分プロビジョニング開始が遅れる」というトレードオフが残っていた(分オーダー間隔と即応性の板挟み)。v2.4 では**割当 PR マージ = ChangeHint 発火 → その scope だけ scoped reconcile** となり、**分オーダーの定期周期を在庫drift検知向けに据え置いたまま、割当だけは秒オーダーで起き上がる**。日次5-10件の割当は「PR マージ即着火」で体感が改善し、周期待ちが消える。level 保証(取りこぼしても次の定期周期が拾う)も無傷で、観測 state レス思想を崩さない。

- **日次5-10件割当・3-5件解約ワークフローの体感**:低頻度ゆえ scoped run の同時実行上限(§6.8 安全柵)には全く当たらない。**割当=A/E タグ(desired 変更)のみを速い経路で扱い、prune は速い経路禁止**(§6.8)なので、解約の**IP/VLAN 回収(集合差 prune・§16.4)は定期周期に残る**——これは本構成の急所(誤配送防止・Release非対称)にとってむしろ正しい設計で、速い経路が List 完全性検証をバイパスする穴を作らない。解約の即時削除が要るなら DBSource tombstone=明示 absent(§6.8/§8.2)で表現するが、本構成は FileSource+承認ゲート寄り(前回§3.4)なので、解約は「承認→定期周期で安全に回収」が素直。

- **多相Task/provisioner が未解消のため上限は不変**:v2.4 は「いつ・どれだけ」に効いたが「どう遷移するか」(多相Task・§9.1)と「誰が焼くか」(provisioner・§1.3)には触れていない。よって**完全自動化の到達点は v2.3 と同じく v2**であり、判定を○より上げる材料はない。

- **BulkObserve は本構成では実質不発(確認結果)**:Redfish に標準バルクがないため BMC は per-resource fallback のままで、**前回の 31-62.5秒/周は数値変化なし**。1,000台は単一デーモンで成立・シャーディング不要という前回結論も維持。§12.4 の静的シャーディング(`--claim`)も 1,000台規模では出番がない(数万〜が対象・§12.2 規模表)。よって提案2は本構成にはほぼ無関係で、効いたのは提案1(§6.8)のみ。

## 3. v2.4で新たに気づいた問題・残存課題

- **N-1. 速い経路の allocator/Vault 依存が割当 UX に直結(CHG-E4 の帰結)**:早期収束で割当を秒オーダーにするほど、**render フェーズ1 の採番(IP 払い出し)と Vault メタデータ解決が体感レイテンシの律速**になる(§6.8 注意点)。日次5-10件なら QPS は問題にならないが、**allocator/Vault が落ちていると「割当が周期に落ちて遅延」ではなく「速い経路が allocator 応答待ちで固まる」**形で現れる。§7.3 の不達時=前回保持で安全側だが、割当は新規払い出しなので前回保持が効かず、UX として遅延が露出する。段0の allocator/Vault 可用性(§19.7)が UX 品質に直結する点を運用前提に明記すべき。

- **N-2. scoped run の「起動」と多相Task の「実行」の責務境界**:§6.8 の scoped reconcile が起こすのは Observe→Diff→Apply の1回であって、**リブートを跨ぐ多相Task の全フェーズを駆動するものではない**。割当着火は速くなるが、その後の BIOS→PXE→OS→NW の10フェーズ遷移は多相Task(v2)が定期周期(または後続 ChangeHint)で1フェーズずつ進む。**「着火は秒・遷移は周期(かつ多相Taskはv2)」**という二段構えを運用が誤解しないよう、30分予算の内訳(着火≒0・遷移=物理作業時間律速)を明示する必要がある。

- **N-3. platform 破壊的大量変更の承認必須(v2.3 CHG-B6)× 早期収束の合成が未整理**:v2.4 で platform 層は「PR マージ=ヒント発火」(§6.8)で承認直後に収束するが、CHG-B6 の「platform 破壊的大量変更は承認必須」との合成(承認ゲート通過後にヒントが着火し、rate limit/累積予算は速い経路と共有・CHG-E3)は本構成の在庫プール一括操作(500台再イメージ等)で要検証。速い経路がバイパスにならない設計(§6.8 安全柵)は入ったが、**「承認済み大量作業」を累積破壊予算がどう解除するか**は v2.3 の宿題(README 3-②)のまま残る。

- **N-4. provisioner(G4)未解消が判定の上限を規定**(v2.3 から不変):Sakutei が v1a(早期収束)+v1.5(安全骨格)+v2(多相Task)を完遂しても、**provisioner を別途実装・統合しない限りプロビジョニング自動化は動かない**。上限を規定するのはこの Sakutei 外の実装ギャップである点は v2.2 以来不変。

## 4. この構成で成立させるための条件(更新版)

1. **【v2.4 で前進】割当の起動レイテンシは早期収束で周期外しする**:割当 PR マージ=ChangeHint 着火→scoped reconcile(§6.8・v1a)で、在庫drift向けの分オーダー定期周期を据え置いたまま割当だけ秒オーダー着火。解約の IP/VLAN 回収(集合差 prune)は**意図的に定期周期に残す**(§6.8 安全柵=速い経路 prune 禁止)——Release非対称(§16.4)の急所を守る正しい設計。

2. **【前倒し済み・v1.5】安全骨格**:pruneable:false・ワイプはWorkflow明示トリガ・invariant・手動承認ゲート・remediation schedule。§10.2 累積破壊予算+§8.6 List急減halt+§7.6 incomplete≠empty で「CMDB読み損ね全ワイプ」を塞ぐ(v1a)。

3. **【依然 v2】自動化本体**:ワイプ/ファーム更新の**多相Task状態機械**(リブート跨ぎ・べき等再開)、**1,000台BMC資格の credential-broker**、1,000台一斉rotateの自動段階ロールアウト+canary。v2.4 では未着手。

4. **【Sakutei外・不変】provisioner を実装/統合する**(最大の実装ギャップ・§1.3 は名前のみ)。

5. **【Sakutei外・強化】消去証明の外部ツール連携**:証明書PDF生成・署名検証は外部。Sakutei 側は §17.5 の即時push監査証跡で NIST SP 800-88 実行記録側を担保(v2.3 で強化済み)。

6. **【新規・v2.4】速い経路の衛星可用性を段0前提に織り込む**:早期収束で割当 UX を秒オーダーにするなら、その律速となる allocator/Vault の可用性(§19.7 段0)が UX 品質そのものになる(CHG-E4)。BulkObserve は BMC 非対応のため本構成では不発——1,000台 BMC は per-resource で 31-62.5秒/周・単一デーモン成立(§5.7/§12.2)、シャーディング(§12.4)も規模的に出番なし。

**総括**:本構成は依然 Sakutei に最も素直に噛み合うシナリオの一つで、v2.4 でも判定 **○** は据え置き。v2.4 の効果は G2 に限局し、**「割当の起動レイテンシが周期非依存になる」ことで、在庫drift向けの分オーダー周期と割当の即応性の板挟みが解け、日次5-10件割当の体感が改善**した。ただし遷移本体の多相Task(v2)と provisioner(Sakutei 外)は不変で、完全自動化の到達点は動かない。BulkObserve/静的シャーディングは BMC バルク非対応・規模不足で本構成にはほぼ無関係。上限を規定するのは引き続き Sakutei 外の provisioner(G4)である。
