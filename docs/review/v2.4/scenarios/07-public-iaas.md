# 対象構成07:パブリックIaaSプロバイダ — Sakutei適用可能性 再評価(v2.4)

**新判定:△→○ 手前(条件付き成立が視界に入った。ただし v1 では依然不成立)**
— 早期収束パス(§6.8)と BulkObserve+claim-as-intent(§5.7/§12.4)により、前回「据え置き」の芯だった **周期律速** と **単一デーモン天井** の2つが構造的に解け、本構成は両提案の**最大受益者**として明確化した。総合が △ のままなのは G3(委譲先=事業本体)が不変だから。ただし「v1では不成立」の中身は **v2 全体依存 → v1b で PoC 成立**へと大きく前進した。

**判定推移:v2.2 △(v1不成立)→ v2.3 △(据え置き・v1b が最低ライン)→ v2.4 △(芯の2ギャップ解消・v1b で成立見通し・○ は上位基盤自作が条件)**

構成前提は前回§1のまま(約2,000テナント・VM約10,000、即時API駆動・ピーク毎秒数件、KVM 400台/20クラスタ/Ceph 3クラスタ/EVPN-VXLAN、テナントVPC=VRF+VXLAN+SG+FWaaS+LBaaS+FIP、課金/quota/分離が事業要件、SLA 99.95%・24/365)。

## 2. 判定変更の理由

### 2.1 芯だった G2(周期律速)は解けた — E2E レイテンシ試算

前回「level-triggered=周期律速で毎秒級 API と構造的に相性が悪い」とした核心が、§6.8 の DBSource 書込通知→scoped reconcile で解ける。VM 作成の制御プレーン E2E を試算する(Apply 完了=VM clone の分単位は非同期のまま。ここは制御プレーン**起床〜Apply 開始**まで):

```
① API → DBSource 行書込 + tombstone なし          : ~数十ms
② DB 書込通知 → ChangeHint(intent_rev + scope)    : ~数十〜数百ms
③ scoped render:新旧 desired diff(リアル非接触)  : ~数十ms(決定的)
   + フェーズ1 採番(VMID/IP/FIP を allocator へ)   : ~数十〜数百ms(★allocator 律速)
④ 影響サブ DAG だけを Observe(BulkObserve なら1コール): ~0.3〜0.8s
⑤ Diff → Apply 開始                                 : ~数十ms
  ───────────────────────────────────
  制御プレーン追加レイテンシ ≈ 1〜2 秒オーダー(§6.8 の宣言通り)
```

周期待ち(30s 間隔なら平均15s・最悪30s)が **秒オーダー**へ短縮される。トリガ喪失時は次周期が拾う(正しさ無傷・遅延のみ)。**テナント削除**は §6.8 の安全柵通り、集合差 prune を速い経路で禁止し、**DBSource 側 tombstone=明示 absent(`ExplicitAbsentOnly`)**として個別リソース削除で表現するため、即時削除が成立する(List 完全性検証をバイパスしない)。DBSource 連動 Watch は v2 だが、**seam(§13.5 Watcher / ChangeHint)は v1a で確定**しており、FileSource webhook では v1a から動く。

### 2.2 芯だった単一天井 — BulkObserve でシャード数が激減、claim で静的分割成立

**BulkObserve による天井書き換え**:v2.3 では vCenter 系 ~200台/周が単一天井で、10,000VM に **~50シャード**必要だった。§5.7/§12.2 の BulkObserve 列では、KVM/libvirt を Proxmox `/cluster/resources` 相当のバルクで畳めば **1コール/クラスタ**。20クラスタ=20コール、0.3s×20 / 並列16 ≈ 0.4s/周で 10,000VM が単一デーモン圏内に入る。**シャード数試算:BulkObserve 前提なら 2〜4シャード**(可用性・爆発半径分割のための最小限)で足り、v2.3 の「20では足りず細粒度分割」から一桁改善。

**claim-as-intent での静的構成(§12.4)**:2,000テナントを `shards/*.yaml` の `claim:{tenant-hash-range}` で静的分割。各デーモンは全 intent を pull し自 claim 分のみ収束。platform 層は専用 platform シャード1つが所有・fencing token 必須、tenant シャードは read-only 参照。二重 claim は既存 fencing で検知。**新ルーター/新 S2 を増やさず**、割当が PR レビュー・監査対象になる。再シャードは drain→claim PR→fencing 更新の最小 Workflow(v1.5)。これは「単一デーモン+バルク」(平常)と「クラスタ/テナント群単位の静的 claim」(スケール時)の**両構成が同一設計で連続**することを意味する。

### 2.3 G3 は不変 — 総合が ○ に届かない唯一の理由

v2.4 CHANGELOG 全体を精査したが、quota admission・メータリング課金・RBAC 認可・ポータルという**委譲先が事業本体**という前回最重要指摘への設計変更・注記・反論はいずれも無い(採用しなかった選択肢にも現れない)。§24.3 は委譲リスト据え置き。むしろ §12.4 で「全域 quota はシャード単体で強制不可・外部集約へ」と明記され、**Sakutei が全域 quota を担わない立場が確定**した(G4 側は明確化=悪化ではないが、G3 の工数非対称は不変)。

## 3. 新たな懸念(v2.4 で顕在化)

- **N1. allocator が UX 直結の新律速(§6.8/§12.4 が明記)**:早期収束で render フェーズ1 の採番が**速い経路に乗る**ため、VM 作成 E2E の秒オーダーは **allocator 応答が律速**になる(2.1 の③)。かつ静的シャーディングでシャード数を増やすと「次の天井=allocator・Vault の QPS」(§12.4 正直な限界)。**周期律速を解いた代償として、共有衛星の可用性・QPS が UX と分散の共通の壁**に移動した。§16.5 の SQLite 最小実装は毎秒十数回 read-write の本規模で不足、NetBox/Infoblox 等 or シャード対応 allocator が必須(v2.3 の条件2を継承・強化)。

- **N2. DBSource 本体が依然 v2**:早期収束の恩恵の本命(tenant セルフサービス即時反映)は DBSource 連動 Watch=v2 でしか実らない。v1a/v1b で動くのは FileSource webhook 経路のみ。**PoC(v1b)では tenant 即時 API の完全形は出せず**、FileSource+PR ベースの疑似即時に留まる。seam は切れているが本番 IaaS の tenant plane は v2 待ち。

- **N3. テナント跨ぎアトミック性の原理的不在が確定(§12.2 格上げ原則)**:CHG-F4 で「観測 ready 待ち=結果整合」が思想の必然として格上げされ、パブリック IaaS が求めがちな全テナント一括操作・全域 quota 強制は Sakutei 単体で提供不可が**確定**した。上位プラットフォームが担う範囲がここでも増える(G3 と合流)。

- **N4. 段0 の重量は微増方向を継続**:fencing 世代番号(S2)・累積予算カウンタ(quorum ストア+fencing、§26.1 A-4)・claim 割当 intent が段0 要件に乗る。v2.4 は動的ルーター(v2)を避けた分**新 S2 は最小(fencing 世代のみ)**だが、段0-minimal(1ノード縮退)からの立ち上げでは quorum ストア要件が引っかかる可能性。

## 4. この構成で成立させるための条件(更新版)

1. **PoC は v1b で成立する(更新・前進)**:v2.3 では「v1b 最低ライン+v2 完遂」だったが、v2.4 で**シャーディング(静的・claim-as-intent)・BulkObserve が v1b へ降下**。v1b(import・allocator 実装・採番連携・capacity gate・BulkObserve 実装・claim フィルタ+fencing)で、**platform=FileSource/tenant=FileSource 疑似即時**の縮小版マルチテナント IaaS が動く。tenant 即時 API の完全形(DBSource 連動 Watch)のみ v2。

2. **高スループット allocator を最優先で用意する(強化・格上げ)**:v2.3 の「条件2」から**筆頭級**へ。早期収束(§6.8)と静的シャーディング(§12.4)の**両方の次の天井が allocator/Vault QPS**に収束したため、ここが UX と分散の共通の律速。NetBox/Infoblox 実 IPAM か 1プール1権威の静的分割(§16.6)+シャード対応が前提。

3. **上位テナントプラットフォームを Sakutei と同規模で別途フルスクラッチ(不変・最重要)**:quota admission(DBSource 書込前に強制)・メータリング/課金・RBAC 認可・非同期ポータル・SLA 計測・**全域 quota 集約**(§12.4 で外部集約に確定)。v2.4 でも設計側応答が無く、工数非対称は不変。「委譲」は「作らなくてよい」ではない。

4. **twin(v2)で 1万リソース×ピーク・EVPN realization ラグ・Ceph/LB API rate limit・BulkObserve 実測を検証(不変・拡充)**:天井表(§12.2)は BulkObserve 込みの理論値。PropertyCollector/`/cluster/resources` の実レイテンシと、scoped reconcile の合流キュー溢れ挙動を twin で実測。

5. **ポータル UX を非同期 provisioning 前提で設計(不変・ただし緩和)**:制御プレーン起床は秒オーダーに短縮されたが、Apply 完了(VM clone=分単位)とシャード跨ぎ結果整合(§12.2)は残る。「受付→provisioning→ready」の非同期 UX は不変だが、**"受付→provisioning 開始" の体感は秒オーダーへ改善**する。

**位置づけ**:v2.4 で条件1・2・4・5 が前進し、**5条件を満たせば ○(条件付き成立)へ到達しうる見通しが明確化**した。条件3(上位基盤=事業本体の別途フルスクラッチ)の存在により「Sakutei 単体で本構成を管理できる」は依然誤り。Sakutei は**事業システムの下半分(宣言的インフラ収束)を担う部品**であり、v2.4 はその下半分を**周期律速なく・単一デーモン圏で・静的分割で**実現する道筋を与えた。「v1では不成立」判定が**成立に変わるのは v1b(疑似即時の縮小版)/ 完全な tenant 即時 API は v2(DBSource 連動 Watch)**という二段の見通しになった。
