**新判定: ○ 条件付き成立(前回 △ から昇格)**
**判定推移: v2.2 △ → v2.3 △(据え置き)→ v2.4 ○(条件付き成立)**

前回(v2.3)△ 据え置きの分水嶺は「この構成の成立に必須な **分散 Executor(§12.3)/ シャーディング(§12.2)/
lease・revision 縮退** が全て v2 のまま=判定を動かせない最大要因(G1)」だった。v2.4 は **CHG-F2(claim-as-intent)**

○ に上げる根拠はここに尽きる。ただし claim 方式は新たな課題(300 リポジトリ pull の git 負荷・WAN 断中の

## 2. 判定変更の理由(claim 方式による分水嶺の付け替え)

**○ 昇格の核心は「分散 Executor の不要化」である。** 前回 △ の全重量は G1、すなわち「WAN 断が定常の 300
分断ドメインを、断中も自律収束する実行体で扱えるか。その実行体=分散 Executor(§12.3)は v2」に載っていた。
v2.4 の CHG-F2(claim-as-intent)は、この前提そのものを組み替える:

- **前回の案 C の含意**:制御面(reconciler+render+理想)は DC、店舗には **RemoteExecutor(agent)** を置き、
  DC の reconciler が WAN 越しに店舗を **リモート収束**する。この「WAN 越しリモート収束」こそが §12.3 の
  分散 Executor + lease 縮退を要求し、それが v2 だから △ だった。
- **claim 方式の含意**:各店舗に **段0-minimal + `sakutei --claim {store: 0042}`** を置く。各デーモンは
  git(ローカルミラー・§19.4)から全 intent を pull し、**自 claim にマッチする自店舗分だけを LocalExecutor で
  収束**する。DC は「制御面」ではなく「git の一元管理・PR レビュー・fencing 世代の発番」だけを持つ。
  **収束の実行体は各店舗ローカルに閉じ、WAN 越しのリモート収束が発生しない。** したがって **RemoteExecutor /
  lease 縮退(§12.3)は本構成の必須経路から外れ、v2 待ちが解消する。**

これが「300 拠点×独立デーモン(各自が git から自 claim 分を pull)」の成立性である。CHG-F2 は「git が落ちても
ローカルミラーで claim は読める」と明記しており、**WAN 断中も店舗ローカルで収束が回り続ける**(直近 pull の
intent を理想として LocalExecutor が自律収束)。前回案 B(店舗完全自律)を却下した2大理由——(i) 300 個の
Vault sealed-on-restart、(ii) stale 理想の分散暴走——のうち、(i) は段0-minimal(file SecretBackend で
sealed-on-restart 構造的消滅・v2.3)が、(ii) は「claim 方式では店舗が破壊的操作を**自 claim scope 内でしか
実行できず**、越境削除が構造的に不能」+「§12.3 の非対称縮退(制御面=git 断中は加算のみ)を店舗デーモンに
適用」で抑える。案 B の弱点が両輪(段0-minimal + claim)で塞がれた結果、**前回「案 C が本命・案 B は却下」
だった構図が、「claim + 段0-minimal による店舗ローカル自律(案 B の正統な再構成)が本命」へ反転**する。

**「シャード間協調は現実を介して行う」原則(CHG-F4)による中央↔店舗依存の整理。** 中央(platform claim)と
店舗(store claim)の依存はこの原則で綺麗に片付く:

- **共有物は既に衛星へ外出し済み**(採番=allocator、秘密=Vault/file、intent=git)。店舗デーモンと中央
  platform デーモンは **互いに RPC で問い合わせない**。店舗が platform リソース(例:WAN 側 IP プール・
  DC のバックホール)に依存するときは、**platform が作った現実を店舗が Observe して gate する**(観測 ready 待ち)。
- これは §12.2 の格上げ原則「シャード間 RPC/状態交換は正しさに一切関与しない(交換した状態を信じることは
  観測 state を持つのと同じ罠)」の適用。**中央↔店舗間に分散合意も状態交換も要らない** ため、WAN 断が
  定常でも「協調が壊れて誤動作する」経路が原理的に存在しない。店舗は自 claim を独立収束し、跨る依存だけを
  Observe で待つ。**この構成が WAN 断に強い理由が、v2.4 で "妥協" から "思想の必然的帰結" へ格上げされた。**

**allocator が UX/収束に直結する点(CHG-E4/F5)。** ただし店舗の新規払い出し(開店時 IP/VLAN)は render
フェーズ1 の副作用で allocator(DC)への到達を要する。WAN 断中は §7.3 で「前回割当保持・新規は保留」に
落ちるため、**断中の開店は blocked、断中の既存店 drift 加算修復は claim デーモンが自律継続**、という
安全側の切り分けになる。サイト別静的プール(§16.6・v2.3)で各店舗プールが独立しているのが効く。

## 3. 新たな懸念(claim 方式が生む課題)

1. **300 リポジトリ pull の git 負荷(新規・最重要)。** claim 方式は「全 intent を pull した上で自 claim 分だけ
   収束」する。300 店舗が中央 git を**毎周 pull** すると、pull 頻度×300 が git サーバ(DC)への集中負荷になる。
   §6.8 の Watch(webhook トリガ)で「変更時だけ pull」に寄せれば毎周 fetch は避けられるが、**webhook を
   300 拠点へ WAN 越しに配送する経路自体が WAN 依存**で、断中は定期 pull にフォールバックする。緩和策:
   (a) 店舗は**自 claim に触る変更のみ**を pull すれば済むよう、**リポジトリを claim 軸で分割**(`stores/0042/`
   をスパースチェックアウト or per-store サブリポジトリ)して pull コストを店舗ローカル差分に限る、
   (b) 中間 git ミラー(リージョン単位)を挟んで DC 集中を散らす。**「全 intent を pull」の字義どおりだと
   300×全店舗 intent = 二乗的トラフィックになる**ため、claim 軸でのスパース pull が実質必須。設計は
   「全 intent を pull」と書くが、300 規模では **claim スコープ限定 pull への最適化が成立条件**になる。

2. **WAN 断中の write 資格供給(G3・残存の最重要)。** claim 方式で「誰が収束するか」は解けたが、店舗デーモンが
   加算 Apply(店舗機器の config push・VM 再作成)に使う **write 資格**を、WAN 断中どう持つかは未設計のまま。
   選択肢:(a) 段0-minimal の **file SecretBackend に店舗機器資格を平文寄りで置く**——断中も write できるが、
   無人・施錠のみの店舗で**資格がディスクに常駐**する物理セキュリティリスク(ディスク暗号化+アクセス制御で
   緩和・§19.8 の但し書きどおり)、(b) DC Vault 発行の**短命資格を長め TTL でキャッシュ**(§19.7-4 は
   read-only 用。write 用の長 TTL は破壊力を店舗に常駐させるジレンマ)。**「WAN 断中に write できる=資格が
   店舗に常駐する=盗まれたら店舗内を書ける」というトレードオフは claim 方式でも消えない。** むしろ店舗
   ローカル収束を強めるほど、店舗に常駐させる資格の破壊力が上がる。ここは v2.4 でも解けていない核心課題。

3. **S2(進捗)の店舗ローカル置き場(新規)。** 開店/閉店 Workflow のフェーズ・承認ゲート待ちは S2(外部永続
   必須・喪失=事故)。claim 方式では **その店舗の Workflow S2 は店舗ローカルに置くのが自然**(DC 集約だと
   WAN 断中に進捗を書けない)。しかし段0-minimal は単一ノード・ローカルディスクで **quorum ストアが無い**
   ——§26.1 A-4 が要求する「S2=quorum ストア+fencing」を店舗が満たせない。店舗ノード全損で進行中 Workflow の
   S2 が飛ぶ。緩和:店舗 Workflow は**冪等な再開可能設計**にし、S2 喪失時は Observe から現実状態を再導出して
   Workflow を安全な地点から再起動する(観測 state レスの利点がここで効く——履歴は飛んでも現実は Observe で
   拾える)。ただし「回収完了 Observe 確認後に prune 解禁」のような **順序ゲートの進捗**は再導出しにくく、
   閉店 Workflow の S2 喪失は prune 安全性に直結する。**店舗 S2 の耐久性は claim 方式の弱点**。

4. **破壊予算の claim 境界化は前進だが閉店の 100% 問題は残る(CHG-Z3)。** rate limit/破壊予算が claim(=店舗)
   単位で閉じる(CHG-Z3)ため「隣店舗を巻き込む削除」は claim 越境=構造的に不能になり、前回 §3-4 の懸念の
   半分は解消。だが「1 店舗閉店=その claim の 100% 削除」が常に fraction 上限を叩く問題は残る。閉店 claim に
   **approved-large-change(承認ゲート)を必須化**し、window の `max_deletes` は「同時に閉じてよい店舗数」で
   引く運用設計が要る(claim 単位化で設計はしやすくなった)。

5. **二重 claim と fencing の運用(新規・軽微)。** 開店/閉店で claim 集合が月 10 件前後変わる。CHG-F2 の
   再シャード Workflow(drain→claim 変更 PR→fencing 世代更新)を**店舗の開廃店ごとに回す**ことになる。
   設定ミスで2デーモンが同一 store claim を掴む二重 claim は fencing token(§12.3)が検知するが、
   **店舗ノード交換(故障→新品)時に旧ノードがゾンビ収束しないよう fencing 世代を確実に更新**する運用規律が要る。

## 4. この構成で成立させるための条件(更新版)

v2.3 の7条件を v2.4 の進捗で更新する。**取り消し線相当=v2.4 で解消し条件から降格したもの、太字=残存。**

1. ~~案 C(店舗 agent + DC リモート収束)を採り、v2 の分散 Executor を実装対象に引き込む~~ →
   **claim 方式で置換・降格。** 本命は **「各店舗に段0-minimal + `sakutei --claim {store: N}` を置き、git から
   自 claim 分を pull して LocalExecutor で自律収束」**(v1b の語彙で成立)。RemoteExecutor / lease 縮退(§12.3)は
   **不要**になった(§2)。前回の分水嶺「v2 の分散実行体待ち」は消えた。
2. **claim スコープ限定 pull を成立条件に加える**(新規・最重要)。設計の「全 intent を pull」を字義どおり
   300 拠点でやると二乗トラフィック。**リポジトリを claim 軸で分割 or スパースチェックアウト**し、各店舗が
   自 claim 差分だけ pull する構成にする。§6.8 の Watch(webhook)で pull を変更時に限る。
3. **WAN 断中の write 資格供給を新規に詰める**(不変・最重要残存=G3)。段0-minimal の file SecretBackend に
   店舗機器資格を置く場合の**物理セキュリティ(ディスク暗号化+アクセス制御)を必須要件化**。write 資格を
   店舗に常駐させる破壊力と、WAN 断中の自己修復可能性のトレードオフを運用で明示的に受容する。
4. **店舗ローカル S2 の耐久性を設計する**(新規=§3-3)。段0-minimal は quorum ストアを持てないため、
   店舗 Workflow は**冪等・再開可能**に設計し、S2 喪失時は Observe から現実を再導出して安全地点から再開。
   **閉店 Workflow の順序ゲート進捗だけは特に慎重に**(S2 喪失が prune 安全性に直結)。
5. **段0-minimal を店舗に置くまでの物理段(ゼロタッチ立ち上げ)を詰める**(不変・残存=G7)。素の OS 起動・
   claim デーモンの初回配布・BMC/PXE 核を現地作業ゼロで踏む手当ては v2.4 でも設計外。
6. **edge_router の Apply 自動化は v2(commit-confirm)待ちと割り切る**(不変=G8)。v1 期は店舗 WAN 終端を
   alert-only。ただし claim 方式で店舗デーモンが自ホスト側から触れるため WAN 越しロックアウトリスクは軽減。
7. **閉店 claim に approved-large-change を必須化**し、破壊予算は「同時閉店店舗数」で引く(CHG-Z3 で
   claim 境界化・降格軽減)。**店舗内の観測不能資産は `ledger_only`(§23.9・v2.3)で prune 巻き添えから守る**
   (transient unknown な WAN 断店舗を ledger_only にしない運用規律は不変)。
8. **中央↔店舗依存は「観測 ready 待ち」で組む**(CHG-F4・新規に明文化)。店舗が DC 側 platform リソースに
   依存するときは RPC でなく Observe gate。分散合意も状態交換も持ち込まない。

**総括:** v2.4 の CHG-F2(claim-as-intent)は、前回 △ を固定していた「分散 Executor が v2」という分水嶺を
**構成の付け替えで無効化**した——「中央から 300 拠点をリモート収束(=分散 Executor 必須)」から「各店舗が
自 claim を自律収束(=分散 Executor 不要)」へ。段0-minimal(v2.3)との合成で案 B の Vault 問題と理想配布
問題が同時に解け、CHG-F4 で中央↔店舗の協調が「現実を介して」思想的に整理され、CHG-Z1/Z2/Z3 で ID・
rendered_revision・破壊予算が scope(=store claim)単位に確定した。**G1(最大要因)・G2・G6 が解消**し、
本命構成が **v1a/v1b の語彙だけで組める**ようになったため、総合判定を **△ → ○(条件付き成立)** へ昇格する。
残存は **write 資格の WAN 断供給(G3)・店舗 S2 の耐久性・300 拠点 git pull 負荷・ゼロタッチ物理段(G7)・
edge_router の commit-confirm(G8)** であり、いずれも「動かせない分水嶺」ではなく「成立のための詰め」に
性質が変わった。逆に、これらを詰めずに「全 intent を素朴に 300 拠点 pull」「write 資格の常駐リスクを無視」
すれば運用が破綻する——○ は無条件ではなく、上記8条件を満たす前提での条件付き成立である。
