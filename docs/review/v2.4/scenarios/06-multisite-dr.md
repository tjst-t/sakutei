**新判定:△→○ 寄りの △(条件付き成立の骨格が v1b で実装到達。DR 完全自動化のみ残置)**

## 2. 判定変更の理由(△ の中身が「実装待ち」から「導入設計待ち」へ)

前回△の主因は「**中核(サイトシャーディング本体)が v2 で、DR/分断耐性の骨格が実装スケジュール上存在しない**」ことだった。v2.4 でこの芯が外れた。

- **サイト=claim の静的シャーディングが v1b で動く(CHG-F2)**。本構成が必要とするのは「東京/大阪/福岡の**静的**なサイト分割」であり、**動的リバランスは要らない**。v2.4 はまさに静的部分だけを前倒し、動的部分(v2)と分離した。3DC への写像は素直:各サイトに独立 claim デーモン(`shards/tokyo.yaml`: `claim: {site: tokyo}` 等)+ サイト段0。共有基盤は platform シャードが1つ所有・テナントシャードは read-only 参照——これがそのまま「東京 platform が共有 NW/ストレージを持ち、各サイト tenant が VM を持つ」に一致する。
- **「新しい可用性部品を増やさない」設計が本構成の G4 を直接殺した(CHG-F2/CHG-Z3)**。v2.3 時点で最も苦しかったのは「shard router/割当表をクロスサイト複製すると裏口で分散合意が要る」だった。claim-as-intent は割当を git(既に外部化・多拠点ミラー化する対象)に載せるため、**新 S2 は fencing 世代番号のみ**。合意対象が消えた。
- **東京全損時の DR 手順が設計語彙で書けるようになった(CHG-F2 再シャード Workflow)**。「大阪が東京の scope を引き継ぐ」= **claim 変更 PR(大阪 claim に東京 scope を足す)→ fencing 世代更新** という再シャード Workflow(§12.4)そのもの。drain 手順は東京全損時は自明にスキップ(旧 writer が物理的に不在)、fencing 世代更新が「旧東京 writer が復活しても古い世代として fence される」split-brain 防護を担う。これは最小 Workflow(v1.5・直列+invariant+承認ゲート)で表現でき、`primary_confirmed_lost` は承認ゲートの人間入力、fencing 世代は S2 更新。**git 外部化(§19.4)との組み合わせで、大阪ローカルミラーの claim を PR で書き換える経路が理屈上は閉じる**。
- **CHG-F4(協調は現実を介して)が分断常態(G6)の性質を変えた**。シャードは互いに問い合わせないので、東京不達は大阪シャードの収束を止めない——大阪は自 scope を独立収束し、東京 AD/DNS の readiness gate が「開かない」だけ。分断が「協調破綻」から「gate 待ち」へ格下げされ、§6.2 の「分断は稀」前提への抵触が緩む。

**結論**:(a)〜(e) の成立条件のうち、v2.3 で「設計裏付けは揃うが実装が v2」だった (c) サイト別シャーディングと (f) 分散実装の**大半(静的部分)が v1b 実装到達**。判定コードは △ のままとするが、**中身は「○ 直前」**であり、v2.3 の△(実装待ち)とは質的に異なる。純粋に v2 に残るのは分散 Executor(福岡遠隔管理)・lease 縮退・クロスサイト S2 の**同期複製実装**の3点に縮小した。

## 3. v2.4 で新たに気づいた問題・残存課題

1. **DR 中の PR マージ・承認・署名経路の東京依存(G7 残り)**。claim 変更を PR で行う設計は正しいが、**PR をマージ・承認・署名する主体(承認者・bot・署名鍵)が東京前提だと DR で止まる**。§26.3 C(Sync Mode commit 主体・署名)が未決のまま。runbook に「東京全損時の claim 変更承認の代替経路(大阪側承認者・オフライン署名)」を明記する必要が残る。claim-as-intent は経路を git に一本化したぶん、**この一本が切れると DR 操作そのものが止まる**というトレードオフを持つ。
2. **fencing 世代の発行・単調増加の一貫性がクロスサイト単一性要求を残す**。CHG-Z3 で予算カウンタはシャード単位に閉じたが、**fencing 世代番号(S2・§26.1 A-4)は「古い東京 writer を fence する」ために大阪と東京で一貫が要る**。A-4 は「quorum ストア or 同期レプリカ+fencing」を必須要件としたが、その quorum ストアを東京集中に置くと分断中に fence 更新不可——**設置サイト選択が本構成固有の判断として残る**(v2.3 懸念2と同型、規模は縮小)。fencing 世代の実効クロスサイト複製は S2 複製の一部として v2 に残る。
3. **allocator の可用性が DR/早期収束の UX に直結(CHG-E4/CHG-F5 合流論点)**。§12.4 が「次の天井=allocator/Vault の QPS」を明記、§6.8 が「速い経路の採番が allocator 応答律速」を明記。DR で大阪が新規リソースを作る局面では**大阪 allocator の生存が RTO に効く**。サイト別 allocator(§16.6 の静的プール分割)で各サイト独立払い出しにするのが必須で、これは v2.3 の (c) と整合。グローバル空間(ASN/ループバック)は分断中 reserve 不可を許容。
4. **早期収束(§6.8)は DR には効かないが平常運用の価値を上げる**。CHG-E1〜E4 は「人の意図変更の即時反映」であり DR(人間トリガ)には直接効かないが、**平常時の各サイト内 drift 修復+セルフサービス反映の UX**を秒オーダーにする。本構成の「まず各サイト内の drift 自動修復と可視化に価値を限定」(§23.7)フェーズの価値が上がった。ただし速い経路の採番副作用でサイト allocator 依存が増す点は注意。
5. **分散 Executor・lease 縮退・クロスサイト S2 同期複製は v2 のまま(残置の芯)**。福岡を大阪から遠隔管理する構成(§4.4 RemoteExecutor)、分断段階縮退の lease 失効→Observe のみ縮退(§12.3)、fencing 世代/累積予算の**同期複製実装**は v2。**回避策**:福岡を独立 claim デーモン+段0-minimal にすれば RemoteExecutor 不要(各サイト自立)。lease 縮退が無い間は「分断中の破壊保留」を fencing+`unknown≠absent`+rate-limit halt で代替(v2.3 と同じ緩和が有効)。
6. **AD/DNS のグローバル整合は主目的の一部であり続ける(G2 不変)**。CHG-F4 で「現実を介した gate」が原則化されても、AD のマルチマスタ・レプリ状態そのものは収束対象外。Sakutei に期待すると成り立たない点は前回同様に明示が要る。

## 4. この構成で成立させるための条件(更新版)

- **(a) 各サイトに独立 claim デーモン + サイト段0**:大阪は標準段0(Ceph+Vault-HA、基幹系 4h RTO 受け)、福岡は段0-minimal(§19.8・可視化用途)、東京は標準段0。各デーモンは `shards/<site>.yaml` の `claim` で担当 scope 宣言(§12.4)。**v1b で実装到達**。
- **(b) 割当=git の claim-as-intent + git の正を DC 外化 + 多拠点ミラー + DR 承認経路の runbook 化**:読み取りはローカルミラーで全断耐性。**追加で**東京全損時の claim 変更 PR のマージ・承認・署名の代替手段を runbook に明記(新課題1)。§26.3 C の署名主体決定が前提。
- **(c) サイト別 allocator + グローバルプール静的分割**:§16.6 で裏付け確定。VLAN/IP はサイト分割で各サイト独立払い出し、ASN/ループバック等のみ単一権威(分断中 reserve 不可を許容)。DR の新規作成が大阪 allocator 生存に依存する点を RTO 見積に含める(新課題3)。
- **(d) DR = 再シャード Workflow(承認ゲート付き最小 Workflow)に限定**:「大阪 claim に東京 scope を足す PR → fencing 世代更新」を §12.4 の再シャード手順に沿って runbook 化。`primary_confirmed_lost` は承認ゲート(§10.5)の人間入力、`replica_freshness`/`quorum` は invariant。最小 Workflow(v1.5)で表現可能。**自動判定は不可(§18 不変)で人間トリガ前提**。
- **(e) AD/DNS のレプリ整合は Sakutei 外に委ね、シャード間は「現実を介した Observe gate」で扱う**:CHG-F4 で思想的に確定。「サービス存在・起動」までを収束対象に。
- **(f・縮小) 残る v2 塊は福岡遠隔管理・lease 縮退・S2 同期複製の3点**:(a) の各サイト自立化と (b)(c) のサイト別権威で**大半は回避可能**。lease 縮退の穴は fencing+`unknown≠absent`+rate-limit halt で当面代替。§26.4 D の再検討トリガ(§6.2 早期警戒線)が本構成では早期発火し得るが、静的シャーディングが v1b で足りるため「動的化 v2 を待つ」圧は v2.3 より大幅に下がった。

**総括**:(a)〜(e) は v2.4 で**設計裏付け+実装スケジュール(v1a 型切り/v1b 実動作/v1.5 Workflow)がほぼ揃った**。(f) だけが縮小した形で残る。◎(思想を曲げず完全自動 DR)に至れない構造的理由——観測 state レス・shared-nothing・分散合意を中枢に戻さず、DR 判定を人間に委ねる設計——は不変だが、v2.4 は「思想を曲げずにサイト分割をスケールさせる」(claim-as-intent)ことで、△の芯を実装到達させた。**判定は据え置き △ ながら、○(条件付き成立)の一歩手前まで前進した**。
