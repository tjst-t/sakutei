## 2. 判定理由

### 2-1. §8.6 scope 単位閾値 + §10.9 planned_change 連動の効果(本ラウンドの核心)

v2.3 の新規懸念4は「operator が正常にオブジェクトを増減する」k8s 特有の高流動性と、単一固定 −50% 閾値の不整合だった。v2.6 はこれを**二方向**で閉じた:

- **静的な流動性差の吸収(CHG-K4)**:k8s は scope によって流動性が桁違い(operator 派生の短命 CR 群 vs. クラスタ本体・PVC)。`list_drop_threshold` を scope 単位で宣言でき、「流動 scope は緩く/致命 scope は厳しく」を型で表現。単一閾値が全 scope を律する構造欠陥そのものが消えた。
- **動的な意図された減少の除外(CHG-J1)**:棚卸し削除・テナント一括退去のような**大量正当作業**は planned_change(scope/種別/`max_count`/window/承認)を宣言すれば急減とみなさない。しかも**バイパスではなく専用予算レーン**——上限件数まで別枠計上し、宣言外の暴発(別 scope・上限超過)は通常予算で止まる。「意図された削除は通す/意図せぬ暴発は止める」の分離が、コミットタグでなく intent 内の機械可読宣言で達成される。

この2つは v2.3 レポート §7 の成立条件2(「prune scope と List 完全性検証 scope の整合設計」)に**設計側から直接応える**。前回は「利用側が scope を注意深く合わせる運用規約」に依存していた誤発火回避が、設計書の宣言機構で裏打ちされた。よって懸念4は**解消**。

### 2-2. v2.4/v2.5 副次効果の本構成への波及(再評価対象外だが確認)

- **早期収束(§6.8)がクラスタ作成申請に効く**:tenant セルフサービス経由の「クラスタ作りたい」申請が周期待ちにならず、PR マージ/claim 発火で秒オーダー反映。マネージド PaaS の作成 UX に直結。ただし render フェーズ1 の採番(CIDR 等)が速い経路に乗るため allocator 可用性が UX に直結(§12.4)——CHG-G 群で「churn ベース sizing・維持は衛星ゼロ」と緩和済み。
- **BulkObserve(§5.7)+ 一貫性契約(§5.8)が k8s List 系に効く**:k8s API は本質的に集合列挙(`kubectl get`/informer)。1リソース1コールの Observe より BulkObserve で scope 一括取得する方が k8s の API モデルに素直で、単一デーモンの Observe 天井を 1 万規模へ押し上げる(§12.2)。**ただし型分離が重要**:BulkObserve は Observe 専用で **prune の根拠にできない**(§5.8-(3))。prune は依然 `Lister.List`+§8.6 完全性検証。k8s の list-watch を prune 根拠に流用しない規律は、operator 派生物の誤 prune 防止と整合的。
- **衛星停止原則(§16.7「変化を止めるが維持を止めない」)**:50→200 クラスタで allocator/Vault が停止しても、既存クラスタの定常収束は Lookup キャッシュ(S3)で継続、新規採番リソースのみ `waiting-allocation`(§16.8)で保留。全クラスタ全盲(v2.3 §6-6 の芯)を「変化だけ止まる」に縮退させ、多クラスタ規模での可用性論点を緩和。

### 2-3. 商品中核の v2 依存は据え置き(想定どおり)

自動段階ロールアウト/自動 canary(§24.2 v2)は v2.6 で**動いていない**。CHG-J2(N-of-M)は承認者要件の表現力を足すが**承認自体は依然手動**であり、canary→broad の自動刻みには寄与しない。よって「マルチクラスタ自動運用商品」としての v2 条件付きは不変。判定階級を ○(そのまま成立)へ格上げする根拠は生じていない。

## 3. v2.6 の新ギャップ有無

**本構成に固有の新ギャップは生じていない。** 4新機能の波及を点検した結果:

- **planned_change(§10.9)**:専用予算レーンは「別枠計上・宣言外は通常予算」で非対称原則と整合し、穴を作らない。k8s では「reimage/recreate 種別」がノード入替・クラスタ再構築の大量正当作業に素直に効く。**懸念というより追加の適合点**。
- **N-of-M(§10.5)/ DR モード(§18.1)/ 運用プロファイル(§10.10)**:いずれも既存機構(ゲート API・Break Glass・planned_change の cooling-off)の拡張で、新プリミティブを増やさず。本構成はチーム運用(SRE 6名)なので team〜enterprise プロファイル。マネージド PaaS が規制テナント(金融向け専用クラスタ)を抱える場合、enterprise の 4-eyes 既定が有効に働く**適合点**であり、ギャップではない。DR モードは本構成の主論点(単一 DC 内マルチクラスタ)には直接絡まないが、副次的に破綻要因も足さない。
- **§8.6/§10.9 の相互作用**:scope 単位閾値と planned_change 連動は同一 scope 語彙(§4.6 で `Scope` 正準形確定)で結ばれており、閾値宣言 scope と planned_change scope と prune 境界 scope が同じラベル集合/パス形式で表現される。**v2.3 で残った「3つの scope を利用側が整合させる」負担を、共通 scope 語彙が構造的に軽減**——これは新ギャップの逆で、既存懸念の縮小方向。
- **注意点(ギャップではないが記録)**:planned_change を「急減 halt 抑止」に使う場合、宣言 scope と List 完全性検証 scope の**種別一致**が要件(§8.6-b「種別一致の宣言済み削除のみ抑止」)。k8s で「CR 削除を宣言したが operator が派生 Pod も連鎖削除」した場合、派生物側 scope は宣言外なので通常の急減判定に戻る——これは設計として正しい(意図した CR 削除のみ通し、想定外の連鎖は止める)が、利用側が「連鎖削除される派生物 scope」の閾値も別途 `list_drop_threshold` で調整する運用理解を要する。設計欠陥ではなく運用規約の範疇。

## 4. 残存(v2.6 でも動かない・本構成の芯に残る依存)

1. **自動段階ロールアウト/自動 canary が v2 据え置き**(§24.2):canary→broad の自動刻みが無く、200→400クラスタで手動承認ゲート(N-of-M でも手動)が律速。商品中核の v2 依存の芯は不変。
2. **canary(能動検証)v2 据え置き**:削除経路・schedulability の能動検証は Observe ベース外形確認に留まる。「作成は動くが削除が権限不足」型の検出は弱い。
3. **`external_owner` の namespace 内混在境界**:operator の Deployment/版は収束・CR runtime は除外、の切り分けは v2.6 でも利用側判断。
4. **credential-broker / DBSource が v2**:JIT 全盲回避と tenant 即時払い出しは将来依存(v2.4/v2.5 で規模運用の器=BulkObserve/シャーディング/衛星停止縮退は前進したが、broker/DBSource 本体は未着)。
5. **drain timeout→承認昇格の自動接続欠落**:N-of-M ゲートへ「上げられる」が「自動で上がる」機構は未明文。運用手順依存。

## まとめ

v2.6 は本構成の判定階級を動かす改訂ではないが、**v2.3 が残した唯一の新規懸念(List 急減 halt の k8s 正常変動での誤発火)を §8.6 scope 単位閾値 + §10.9 planned_change 連動で構造的に解消**し、○条件付き成立の**確度を上げた**。共通 scope 語彙(§4.6)により「3つの scope の整合」という運用負担も縮小方向。v2.4/v2.5 の副次効果(早期収束=クラスタ作成 UX / BulkObserve=k8s List 系 / 衛星停止原則=多クラスタ可用性)も本構成に有利に波及する。**本構成固有の v2.6 新ギャップは無し**。据え置きは自動段階ロールアウト/canary(v2)を芯とする商品中核の v2 依存であり、「殻のライフサイクル運用基盤=○/マルチクラスタ自動運用商品=v2条件付き」の二段判定は維持される。
