## 2. 判定理由(○→◎)

**◎ に上げる根拠は G3 と B6 摩擦の同時解消に尽きる。** v2.3 は段0-minimal(CHG-D1)で成立核心を満たしたが、判定を無条件◎に上げられなかった唯一の実質障害が「1名運用に承認儀式が空回りし、しかも CHG-B6 でむしろ濃くなった」点だった。v2.6 の solo プロファイルは、この摩擦を **(a) 自己マージ可(他者承認の強制解除)** と **(b) cooling-off による承認代替(時間差+自己中断機会で他者レビューを置換)** の二段で正面から潰す。さらに §10.10 が「段0-minimal では solo を既定とする」と明記したため、本構成では**設定を書かずとも既定で摩擦ゼロ**になる——ワークアラウンド(自己 PR / tenant 流用)が不要になった点が○→◎ の質的転換である。

**安全が後退しない**点も◎の条件を満たす:cooling-off は監査を team と同等に残し(誰がいつ宣言・実行を S4)、宣言中いつでも halt 可能。「他者レビューの喪失」を「時間差+中断機会」で置換する設計判断は、1名運用では後者の方が実効的(そもそも他者が居ない)という現実に整合する。段0-minimal の可用性トレードオフ(SPOF)は残るが、これは Proxmox 1台=元々 SPOF という物理現実と一致し、収束コアが復帰後に自然再収束するため受容可能——v2.3 で既に「条件」として整理済みで、◎を妨げない。

## 3. v2.6 の新ギャップ有無(明示)

**本構成に効く新ギャップは発見されなかった。** 以下の観点で厳しく確認した:

1. **solo の cooling-off と most-restrictive-wins(CHG-K3・§10.8)の干渉なし**:cooling-off は「承認の代替」であって mode 決定源ではない。freeze/schedule/ownership の mode 解決は最も制限的が勝つまま働き、cooling-off 中でも freeze を掛ければ止まる。両者は直交し、solo が安全側解決を弱める経路は無い。

2. **solo が監査/List 完全性を弱めない**:§10.10 は「監査記録は team と同等」と明記。CHG-B2/B4(incomplete≠empty・List 完全性)や §8.6 の急減 halt は solo でも無効化されない(solo が緩めるのは**事前承認の要否**のみ)。1名運用で最も怖い「歯抜け inventory で全消し」は依然厚い。

3. **planned_change の PR 承認要件が solo で空回りしないか**:§10.9 は「planned_change 自体が PR 承認を経る」とするが、solo は自己マージ可なので**自己宣言→自己マージ→cooling-off→自動実行**で一貫し、儀式化しない。宣言という「人の意図の明示」自体は cooling-off の中断判断の起点として意味を持つため、無駄な儀式ではない。

4. **プロファイルの上書き自由度が穴を作らないか**:solo でも特定 scope に N-of-M を明示可(§10.10)。逆に「solo だから」と全 scope を無条件に緩める強制は無く、糖衣であって既定の束に過ぎない。破壊的型の `pruneable:false` 既定などコア安全は profile 非依存で残る。新たな緩和穴は生じていない。

## 4. 残存(◎の下でも留意)

いずれも「成立を阻む」レベルではなく、v2.3 から構造的に不変または軽微:

- **秘匿強度トレードオフ(file SecretBackend の鍵管理)**:§19.8 は「ディスク暗号化+アクセス制御で緩和」に留まり、単一ノードでの暗号鍵の着地先(TPM か平文許容)は本書スコープ外。v2.6 でも明文の強化は無し。ラボでは受容可だが原則(§19.4)からの後退である点は導入時に正直に提示する。
- **段0-minimal→標準段0 の移行手順が seam のみ・手順未記述**:規模が育つ現実パスで、file→Vault・単一→3ノードの作り替えは参照実装側。solo→team のプロファイル切替は宣言一語だが、その土台の段0 再構築は人手を要する。
- **OOB/Break Glass の物理縮退が暗黙**:段0-minimal では Proxmox 物理コンソールが唯一の OOB。§15.6/§18.1(DR モード)はマルチサイト前提で本構成には過大——単一サイトラボでは DR intent プリステージも書込 break-glass も不要(適用対象外であって欠落ではない)。
- **provider 階級縮退(G4)/ canary(G6, v2 送り)**:構造的に残るが成立を阻まない。BulkObserve 一貫性契約(§5.8)が縮退階級でも prune 誤根拠を型で封じたため、むしろ安全側は厚くなった。
