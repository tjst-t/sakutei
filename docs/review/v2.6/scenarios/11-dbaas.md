## 判定変更の理由

4ラウンドを通じ、この構成の無条件`◎`を阻む筆頭は一貫して残存#1、すなわち **「計画的大量変更(800台一斉VerUp・大量縮退)は自動段階化(v2)が来るまで手動 `approved-large-change`+段階分割でしか通せず、運用3名が毎回手作業で組む」** だった。v2.4 では CHG-E3 が「早期収束パスも予算・List完全性を共有(バイパス不可)」と念押ししたため、むしろ**回避不能が確定**していた。

v2.6 の CHG-J1(§10.9)は、この衝突を**自動段階化を待たずに**解いた点が本質的である。従来 v2 の canary ゲートに預けていた「正当な大量変更を安全機構に通す」問題を、**v1a の宣言機構**に引き下ろした。具体的には、`planned_change` が3つの安全機構すべてに同時接続する:(1)§10.2 の累積時間窓予算に対しては**別枠計上**(800台VerUpの delete 相当が`max_deletes`を食わない)、(2)§10.2 の halt-all 凍結に対しては**解除条件**(既存 `approved-large-change` タグを統合・置換し、機械可読な対象/種別/上限/窓/承認を持つ)、(3)§8.6-b の List 急減 halt に対しては**抑止連動**(宣言済み件数減は急減とみなさない)。800×2一括削除も `kind: delete`+`max_count: 1600`+`window` で宣言すれば、−50% halt を誤発火させずに通る。

決定的なのは「**バイパスではなく専用レーン**」の設計である。宣言上限を超えた分・宣言外 scope の delete・別種別の破壊は引き続き通常予算で止まる(§10.9「宣言中でも宣言外の暴発は止まる」)。したがって「予算を恒常的に緩めて暴発を野放しにする」危険側に倒れない。運用3名は「毎回コミットタグを打って段階分割を手で組む」から「メニュー変更ごとに planned_change を1宣言 PR にする」へ移行でき、**商品運用の日常が設計内で回る**。

以上で `◎` は据え置きだが、無条件`◎`に至らないのは残存#2(PITR人手ゲート)・#3(health/canary/DBSource=v2)・#4(claim跨ぎ invariant)が v2.6 のスコープ外で不変のため。据え置きが正しい。

## 800台一斉VerUp を planned_change で通す通し(v1.5 Workflow との組み合わせ)

商品「MySQL DBaaS」のマイナーVerUp(例 8.0.36→8.0.37)を 800インスタンスに適用する運用を具体化する:

1. **宣言**:運用者が intent に `planned_change: { scope: {cluster: db-shard-a}, kind: update, max_count: 800, window: "土 02:00..04:00", approval: {pr: NNNN, approvers: [a,b]} }` を書き、PR を出す。宣言自体が §10.5 承認を経る(=人の意図の明示)。team プロファイルなら単一承認、規制テナント向けに enterprise を張れば §10.5 N-of-M(separation)で申請者≠承認者を強制できる(CHG-J2 の副次利得)。
2. **予算レーン**:窓が開くと、db-shard-a・update・上限800の変更に専用レーンが割り当たり、§10.2 累積予算を消費しない。VerUp が delete+create に見えて破壊予算を食う懸念は、`kind` 宣言で「純粋な削除ではない」と分類され解消(§10.9・13指摘と同型)。
3. **段階適用**:実際の刻み(canary 1台→health確認→broad)は **v1.5 最小 Workflow の手動承認ゲート**(§10.5 `rollout.stages`)で組む。planned_change が「予算上 800台まで許す」を保証し、Workflow が「どう刻んで人が承認しながら進めるか」を担う——**「いつ/どれだけ許すか=planned_change、どう刻むか=Workflow」**と役割が綺麗に分離する。health_check の**自動**判定は v2 なので、各ステージのゲートは当面**手動承認**(lag/レプリカ健全性は外部監視を見て人が承認)。
4. **暴発防御は生きたまま**:同じ窓で誤って db-shard-b の 200台を消す intent が混入しても、宣言外 scope ゆえ通常の急減 halt / 破壊予算で止まる。窓経過後は自動失効。

この組み合わせで、v2 の自動canaryが来る前でも **800台VerUp・800×2縮退が3名運用で回る**。手作業は「段階分割の Workflow を書く」ことに残るが、「安全機構と正面衝突して毎回止まる/タグで無理やり通す」状態からは脱した。

## v2.6 の新ギャップ有無(敵対的確認)

**新規の設計ギャップは検出せず。**ただし planned_change の宣言粒度・乱用面に、実装時に閉じるべき**運用上の注意点(ギャップではなく C カテゴリの運用パラメータ)**を3点特定した:

1. **宣言の粒度と種別判定の一致(要 SDK 契約化)**:`kind: reimage`/`recreate`/`update` の「これは純粋 delete ではない」判定を**誰が保証するか**。provider が update と申告する変更が内部実装で全レコード drop→再作成なら、宣言 `kind: update` の下で 800台ぶんの実破壊が専用レーンを素通りしうる。§10.9 は「変更種別を宣言」と書くが、**宣言 kind と `Plan` の destructive flag(§4.6)の整合検証**が明文化されていない。悪意より「provider の内部が破壊的なのに update を名乗る」事故側が現実的。→ 実装時に「宣言 kind が `Plan.destructive` と矛盾したら宣言を無効化(fail-closed)」を SDK 契約に入れるべき(構造は §4.6 で確定済みなので実装可能・ギャップではない)。

2. **max_count の乱用面(恒常宣言による予算空洞化)**:悪意/怠慢の運用者が `max_count: 100000`・`window` を毎日更新する宣言を常設すれば、専用レーンが事実上の無制限バイパスに堕する。§10.9 は「窓経過で自動失効=恒久緩和にならない」と一応封じるが、**「常時更新される宣言」を検出する仕組みは無い**。ただし宣言自体が PR 承認を経る(=人の意図)ため、これは「承認プロセスの腐敗」であって planned_change 機構の穴ではない。§17.5 S4 に全宣言が append される(§10.10 solo でも監査同等)ので**事後検出は可能**。→ ギャップではないが、運用プロファイル enterprise 側で「planned_change の max_count/window に上限ポリシー」を IdP 委譲で被せる余地を運用手順に残すべき。

3. **scope 境界と rendered_revision 単位の一致依存**:planned_change の `scope` が §26.1 A-3(scope 単位 rendered_revision)・claim の scope-selector と**同一語彙**であることに機能が依存する(CHG-K1 で `Scope` = ラベル集合+パス形式に正準化され担保された)。db-shard-a の宣言が別 shard の観測に漏れない前提は、この語彙統一が守られる限り成立。→ CHG-K1 で型が確定したため**むしろ塞がれた**方向。新ギャップではない。

総じて、planned_change は「新しい可用性部品・新プリミティブを増やさず、既存の予算計上経路の別枠として実装」(CHANGELOG 波及確認)する筋の良い設計で、収束コアの不変条件(観測 state レス・非対称原則・バイパス禁止)を崩していない。上記3点はいずれも **C カテゴリ(運用前に決める)** に属し、A(着手前決定)を再オープンさせるものではない。

## 残存(v2.6 でも動かなかったもの)

1. **PITR/大容量リストアの途中death人手ゲート(§26.2 B)**:多相Taskがv2のため不変。planned_change は desired 予算の話で長時間Taskに無関与。
2. **health(lag監視)/canary(PITR復元可能性証明)の自動判定/DBSource連動即時DB反映**:v2 or 外部監視委譲。§10.5 N-of-M は**手動**ゲートの拡張であり health 自動判定ではない。800台VerUp の各ステージゲートは当面手動承認。
3. **claim跨ぎfailoverのinvariant非強制**(4シャード採用時):§18.1 DRモードは別軸で直接効かない。全域 writable 数の集約は外部委譲のまま。
4. **planned_change の kind 整合検証・max_count 乱用検出**(v2.6 新規・上記新ギャップ確認の1・2):ギャップではなく C カテゴリの実装/運用パラメータ。実装時に fail-closed 契約と監査運用で閉じる。
