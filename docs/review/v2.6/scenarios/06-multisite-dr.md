## 2. 東京全損シナリオの通し再演(手順が設計語彙だけで閉じるか)

1. **検知**:東京全損。大阪デーモンは **ローカルミラー(§19.4)**で intent を読み続ける(中央 git 不達でも収束継続=稼働必須依存にしない)。読み取りは v2.5 で全断耐性が確定済み。
2. **判断**:DR 発動可否は **人間**が下す(§18・不変)。判断は **DR Workflow の承認ゲート**(§9.2・v1.5)の入力として設計内に位置づく。
3. **claim 切替発動**:DR 構成は **§18.1(a) でプリステージ済み**(平時に PR 承認済み)。発動は `on_activation.enabled: true`(または claim 切替)1 点のみで**新規レビュー不要**。中央 git 到達可なら通常 PR フロー、**不達なら §18.1(b) の署名付き break-glass コミット**で大阪ローカルミラーへ書く。→ **東京の承認者・署名鍵に一切依存しない**。
4. **大阪収束**:claim 切替後、大阪デーモンが東京 scope を claim し次周収束。**fencing 世代更新(§12.4 手順3)が(GC pause 等で部分生存しうる)旧東京 writer を fence** する。既存資産の維持収束は **allocator 断でも Lookup キャッシュ(§16.7)で衛星ゼロ**。新規採番は大阪の **disjoint プールレンジ(§16.5)**から独立払い出し(中央依存なし)。
5. **復旧後合流**:break-glass コミットは `BreakGlassWriteUsed` Event → sink → S4(§17.5)で**必ず発覚**。中央の正が復旧したら**事後合流 PR として起票し事後レビュー**、書込鍵を rotate。「DR 中に緊急で書いた変更」が正の履歴に正規取り込みされ、分岐放置されない。

→ **手順 1〜5 の全てが設計の語彙(claim ハンドオフ・Break Glass・fencing 世代・Event/S4・DR Workflow ゲート)で表現でき、v2.5 で runbook に落ちていた「東京全損時の代替承認者・オフライン署名鍵・fencing 世代の手動発行」が §18.1 の第一級機構に吸収された。**

## 3. v2.6 の新ギャップ有無(敵対的確認)

**結論:設計思想を崩す新ギャップは検出されなかった。ただし §18.1 は運用設計上の要注意点を2つ内包し、いずれも「実装/運用前に閉じるべき既知事項」で設計欠陥ではない。**

- **(悪用面・要注意①)書込 break-glass の悪用**:git 正への「到達不能」を偽装/誤判定すれば、レビューなしで正へ書ける経路が開く。設計は §15.6 の封じ込め(オフライン相当鍵・使用後 rotate・確実な発覚)を継承し、**発覚(Event+S4)+事後合流の強制**で抑止する立て付けで、「事前チェック最小・事後監査最大」の一貫適用として妥当。**残る運用判断**は「到達不能をどう機械判定/誰が宣言するか」(誤判定・悪意ある宣言の防止)——これは §18.1 が明示していない運用パラメータで、runbook/実装で閉じる範囲(思想の穴ではない)。
- **(競合面・要注意②)事後合流時の競合**:DR 中に break-glass で書いた変更と、復旧した中央の正が分岐しうる。設計は「PR 起票→事後レビュー」で正規取り込みを規定するが、**マージ競合の解決責任・順序**(DR 中に大阪が変えた scope を東京復旧後にどちらが正とするか)は §18.1 が具体化していない。ただしこれは git の通常マージ競合であり、claim 境界(東京 scope は大阪所有に移っている)+ fencing 世代で**二重所有は検知される**ため、収束の安全性(暴発)は損なわれない。UX/運用手順の課題であって設計思想の破れではない。
- **(スプリットブレイン面)DR 発動と旧 writer 生存の同時性**:東京が部分生存のまま大阪が claim すると二重 writer になりうるが、**fencing 世代更新(§12.4/§12.2)が旧世代の Apply を拒否**する。§18.1 の claim 切替がこの fencing 更新と一体なので、DR モードは既存の単一 writer 保証を継承する。新ギャップなし。
- **横断整合**:CHG-J1(planned_change 別枠予算)/ CHG-K3(most-restrictive-wins)/ CHG-J4(solo cooling-off)は本構成(3DC・チーム/enterprise 運用)に直接は効かないが、**DR 発動時の大量再収束が累積破壊予算に誤衝突しないか**は敵対的に確認した——大阪が引き継ぐのは主に**既存資産の維持収束**であり破壊的変更ではないため、通常予算で止まらない。真に破壊を伴う DR(旧構成の一括退去等)を要するなら `planned_change`(§10.9・種別 delete/recreate の専用レーン)で宣言でき、v2.6 は**むしろこの衝突リスクを塞ぐ道具を新たに与えた**。新ギャップを生むどころか閉じる方向。

## 4. 残存(◎にしてなお残る条件・v2 塊)

1. **fencing 世代のクロスサイト同期複製は依然 v2**(v2.5 R4 から規模不変)。DR 発動時の fencing 世代更新は claim ハンドオフ(v1b)で表現できるが、その世代情報の**クロスサイト一貫(quorum を東京単独に置かない設置)**は S2 複製の一部として v2。**quorum 設置サイト選択が本構成固有の残判断**(導入設計で閉じる)。
2. **書込 break-glass の「到達不能」判定基準**は §18.1 が具体化していない運用パラメータ(新ギャップ③ に対応)。誤判定・悪用防止の宣言主体/機械判定条件を実装で定義する必要がある。
3. **事後合流のマージ競合解決手順**は git 通常競合として残る(新ギャップ②)。収束の安全性は fencing+claim 境界で守られるが、運用手順の明文化が要る。
4. **AD/DNS のマルチマスタ整合は収束対象外(§20.1・不変)**。「サービス存在・起動」までしか保証しない。主目的の一部であり続けるため、Sakutei に期待しない切り分けの明示は引き続き必要。
5. **DR 後の新規大量作成は allocator 復帰まで `waiting-allocation` で遅延**(v2.5 R1'・不変)。既存資産の引き継ぎには効かない点を RTO 定義で分離すること。

**総括**:v2.6 の §18.1 は、v2.5 で「○の最後の芯」だった DR 書込経路の東京依存を、新プリミティブを増やさず(claim ハンドオフ+Break Glass の書込版+Event/S4 の再利用で)設計内に閉じた。東京全損の通し再演が設計語彙だけで完結し、runbook に残っていた代替承認・オフライン署名・fencing 手動発行が第一級機構に吸収された。敵対的確認では書込 break-glass の悪用面と事後合流の競合という**運用設計上の要注意点**を検出したが、いずれも fencing+claim 境界+発覚強制で収束の安全性は保たれ、**設計思想を崩す新ギャップではない**。判定を **◎(思想を曲げずに成立)** に進める。◎にしてなお残るのは fencing 同期複製(v2)と 2 つの運用手順明文化であり、いずれも導入設計/実装の範囲で閉じる。
