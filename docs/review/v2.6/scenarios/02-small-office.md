## 判定を △ 据え置きとした理由

第一に、**G5 は solo プロファイルで構造的に解消した**。v2.3 レポートは G5 を「未解消(むしろ要求増)」とし、運用回避(承認=自己二段確認)で凌ぐしかないと結論していた。v2.6 の solo は cooling-off を「1名運用における実効的な安全弁」として第一級で定義し、段0-minimal に既定で紐づけた。これは本構成にとって最も摩擦の大きかった非機能ギャップを、設計の糖衣層で正しく吸収した優れた応答である。

第二に、**しかし G5 の解消は判定を △→✓ に押し上げない**。△ の芯は G5(運用摩擦)ではなく **G6(機器 API の貧しさ)** だからである。SOHO インフラの実質過半(UniFi/QNAP/WinAD)は Observe すら CLI scrape 相当か observe 不能で、external_owner/ledger_only で「触らない・台帳に置く」ところまでしか行けない。Sakutei の中核価値(原因区別・converging 検知・prune 安全性・drift 自動修復)がここに効かないのは、Sakutei 側の設計不足ではなく**相手機器の API 表現力の問題**である。**したがってこれは設計では解けない見込みが正しく、△ が本構成の到達上限で確定する。** Apply の主戦場は v2.3 同様「壊れても局所的なコア provider(DNS/バックアップ/証明書/新規構築 VM)」に限られる。

第三に、solo が破壊予算防御を弱めないことを確認した。solo cooling-off は planned_change の遅延実行であり、累積破壊予算・halt-all・List 急減 halt を素通りしない(§10.9「バイパスではなく別枠」)。本構成の主敵「1 commit で全 VM 削除」への防御は維持されている。

## v2.6 の新ギャップ有無

**本構成に対する新規の設計ギャップは検出されなかった。** 精査した観点:

1. **solo が承認・監査を省いていないか** → 省いていない。監査は team と同等に S4 へ残り、破壊予算防御も維持(CHANGELOG 見送り欄「solo で承認・監査そのものを省く=棄却」と一致)。**新ギャップなし。**
2. **cooling-off の実効性が 1名運用で担保されるか** → cooling-off は「宣言から N 時間後に自動実行・その間 halt 可能」。1名運用者が就寝中など不在の窓に自動実行が走る懸念はあるが、これは planned_change を「気づける時間帯に宣言する」運用で吸収でき、かつ破壊予算 halt が最終防波堤として残るため設計ギャップには当たらない(運用パラメータ=カテゴリ C の話)。
3. **N-of-M(CHG-J2)/DR モード(CHG-J3)が solo と衝突しないか** → いずれも上書き可能な既定値であり(§10.10「プロファイルは糖衣・個別宣言が常に優先」)、本構成は単一サイト・1名なので N-of-M/DR は対象外。solo と排他せず共存する。**新ギャップなし。**
4. **§26 カテゴリ A 消し込み(CHG-K)の波及** → コア型正準形(§4.6)・S4 永続化先(§17.5)確定は本構成に有利(実装着手ブロッカーの解消)で、負の波及はない。

## 残存課題

- **G6(機器 API の貧しさ)= △ の恒久的な芯**。v2.6 で確定した本構成の到達上限。UniFi/QNAP/WinAD は external_owner による alert-only 可視化 + ledger_only 台帳化が上限で、自律収束は成立しない。**設計改訂では解けない**(機器側の問題)。
- **G4(Gitea 循環)**。v2.6 でも単一サイト向けの手当てはなく、外部 git 化 or 別筐体退避の回避策が必要。
- **cooling-off の時間帯設計(運用パラメータ)**。solo の自動実行窓と 1名運用者の稼働時間の噛み合わせは運用で詰める(カテゴリ C・設計ギャップではない)。
- **総コスト比較は依然シビア**。予算極小・1名運用に対し「Ansible 定期実行 + 手運用」との比較で Sakutei を選ぶ根拠は「drift 可視化 + 全 VM 削除防御 + solo による低摩擦運用」に価値を見出すかに絞られる。運用摩擦(G5)が下がった分、v2.3 時点より選好理由はわずかに強まった。
