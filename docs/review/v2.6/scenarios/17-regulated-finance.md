## 2. 判定理由(◎ 到達の核心=承認直前性の証明が v2.6 語彙で完結するか)

FISC 監査が求める中核は「**人間の承認が、変更の直前にあることの証明**」である。v2.6 でこれが Sakutei 単体の語彙で完結するかを検証する。

- **承認直前性**:v1.5 の承認ゲート付き Workflow は step ごとに `StageAwaitingApproval` → 人が承認 → 次 step で進む。承認が実行の直前に構造的に挟まる。これは v2.3 時点で既に満たしていた。
- **職務分掌(申請者≠承認者)**:v2.6 の `separation: applicant_ne_approver` が `planned_change`／PR の申請者 ID と承認者 ID の不一致を**型で強制**。自己承認が塞がれる。これが前回の欠落。
- **複数承認(N-of-M)**:`quorum:{n:2, of:3}` で 3 人中 2 人の署名が揃うまでゲートが S2 に留まり、揃った瞬間に進む。4-eyes の一次要件を本体が担う。
- **承認の恒久記録**:全承認者を S4 に append し、原因タグ帰属と一体で「どの承認ゲートを誰が通したか」が追える。S4=WORM/外部即時 push が正式決定されたことで、この記録の改竄耐性がストレージ層で保証される。

以上4点で「承認直前性＋職務分掌＋複数承認＋改竄耐性ある恒久記録」が **§10.5＋§10.10＋§17.5 の宣言と API のみ**で表現でき、FISC の中核要件が Sakutei の語彙で閉じる。enterprise プロファイル1語で platform 破壊的変更にこれらが既定化される点も、規制現場の「例外なく全変更に 4-eyes」運用と噛み合う。したがって ○＋ → **◎** に到達する。

◎ に「無条件」でなく「条件付き」を付す理由:監査様式の整形器・外部アンカーの第三者性・Windows TrueObserve が本体外に残るため。ただしこれらは 4-eyes のような**構造的律速ではなく実装/運用の埋め合わせ**であり、判定記号を ○＋ に押し戻す性質ではない。

## 3. v2.6 が新たに生んだ設計ギャップの有無(明示)

**結論:本構成に効く新規の構造的ギャップは無い。**個別に確認する。

1. **N-of-M の役割判定を上位 IdP へ委譲**する設計は妥当だが、「上位 IdP が停止したとき承認ゲートがどう縮退するか」は §10.5 で明示されていない。ゲートは requirements 未充足で S2 待ちに留まる(=安全側 halt)ので**危険側の穴ではない**が、IdP 断が全承認ゲートの停止に直結する可用性依存は運用条件として意識すべき(新ギャップではなく運用注記)。
2. **cooling-off(§10.10 solo)は本構成に非該当**。400VM・4面・規制環境は enterprise プロファイルであり、solo の「遅延実行で承認代替」は使わない。solo と enterprise が同一 §10.10 に同居するため、**プロファイル取り違え(規制環境に solo を張る)は致命的**だが、これは most-restrictive-wins(§10.8)とは別軸の設定ミスであり、組織ポリシーで enterprise 固定を強制すればよい(新ギャップというより運用ガードレール要件)。
3. **planned_change(§10.9)の approval が §10.5 requirements を満たす**と明記され、大量正当作業(棚卸し削除等)も 4-eyes を通せる。前回懸念した「schedule を承認統制の代替と誤解」の火種は、planned_change が承認情報を構造化して持つことで**むしろ縮小**した。新ギャップ創出はない。
4. **DR モード(§18.1)の書込 break-glass** は本構成の主論点ではないが、緊急ローカル書込が `BreakGlassWriteUsed`(最高 severity)＋S4＋事後合流 PR で必ず検出・監査される設計は、規制環境の「例外書込も監査に必ず載る」要求と整合する(むしろ追い風)。

以上より、v2.6 は本構成に対して**新たな設計ギャップを生んでいない**。むしろ前回の残存を減らし、逆指摘(大量破壊の単一承認)まで解消している。

## 4. 残存(簡潔)

- **エビデンス様式整形器**:S4 の承認記録・conformance・last-seen・plan は素材として完備。FISC 様式への整形・保管器は追加実装(本体外・自作)。
- **Windows 400台の TrueObserve 経路**:agent/WinRM 確保が前提。Ansible ラップ縮退(cause tag A/B 区別喪失)を避ける(条件維持)。
- **外部アンカーの第三者性**:S4=WORM/外部即時 push で改竄耐性は正式決定。「独立第三者」の厳格要求には社内 RFC3161 タイムスタンプ局等で補強(残差は縮小)。
- **手順書の全 Workflow 化**:多相 Task・自動段階ロールアウト・自動 canary は v2 待ち。v1.5 は直列＋N-of-M ゲートの範囲。
- **運用条件**:enterprise プロファイルを組織で固定(solo 取り違え防止)、承認ゲートの IdP 依存を可用性設計に織り込む。
