## 総評

設計としての完成度は高い。抽象(Provider/Lister 二層・Observation/ConvergenceStatus 分離・
Capabilities による機械的縮退・原因タグ・seam 群)は一貫しており、大半の判断に納得できる根拠がある。
一方で**「v1 スコープが MVP としては大きすぎる」**という一点が、実装可能性・運用性の両面で最大の
リスクである。§24.1 の v1 リストは「後付け不可のコア型」に留まらず、SDK 一式・import・Sync Mode・
capacity gate・ready_condition・テンプレート展開・render 2フェーズまで含んでおり、
「数百行のオーケストレータ + provider 数個で体験を作れる」(§24.4)という自己申告と実際の v1 定義に
乖離がある。

スケール算術(§12.2)は**代入は正しいが前提レイテンシが楽観的**で、実オンプレ機器では天井が1桁下がる。
Provider SDK の「4関数書くだけ」は Read/Apply については概ね正しいが、**Schema 設計が実質的な障壁**で
あることは設計書自身が §5.5 で認めており、そこが普及の律速になる。

指摘は以下のとおり(重大度:高6 / 中7 / 低4)。

## 重大度[高]

### H-1. v1 スコープが MVP として過大 — 「コア型」と「MVP 機能」が混ざっている

**内容**:§24.1 の v1 は、(a) 後付け不可のコア型10個(これは妥当に v1)と、(b) それとは独立に実装量の
大きい機能群——プロバイダ SDK フルセット(Schema 駆動 diff・secret マスキング・managed 除外・エラー
分類・**テストハーネス・Schema lint**)、`import`、**Sync Mode(別ループ)**、capacity gate、
`ready_condition` + 複数 Cycle 依存、render 2フェーズ + テンプレート展開 + カスタム関数——を同列で
「v1」に積んでいる。

**根拠**:
- §24.4 は「数百行のオーケストレータ + provider 数個」で最初の体験が作れると述べる。これは正しいが、
  それは §24.1 の v1 全体ではなく**収束ループ + FileSource + provider 1個**の話である。両者の規模が
  1桁違う。
- SDK の「Schema 駆動汎用 diff エンジン」は、順序付きコレクション(§8.5 全置換 + 表示粒度展開)・
  managed/computed/secret/identity の全属性・content-address 型・SecretRef 型を横断的に正しく扱う
  必要があり、これ単体で相当な設計・実装・テスト量になる。「作者に Diff を書かせない」ための
  肩代わりコストは**コア側に全部乗る**——負担の総量は減っていない、移動しているだけ。
- Sync Mode(§23.8)は「収束サイクルとは別ループ」であり、commit 主体・generated/ 規律・
  正当性判断の非接続を含む独立サブシステム。import(§23.3)とロジック共通とはいえ、
  継続ループ・スナップショット差分・commit 間引きは追加実装である。

**提案**:v1 を2段に割る。
- **v1a(歩けることの証明)**:コア型10個 + 収束ループ + FileSource + rate limit/halt +
  最小 SDK(Schema 駆動 diff・secret マスク・managed 除外のみ)+ provider 2〜3個。
  ここで「触ってないのに戻る」体験と爆発半径制御を実証する。
- **v1b(brownfield 導入可能にする)**:import + alert-only 昇格 + Sync Mode + Schema lint +
  テストハーネス。**import を「v1 必須」とする §24.1 の主張(brownfield では使い始められない)は
  正しいが、それは v1a では不要**——v1a は greenfield/devenv で価値実証できる(§23.7-3 が既に
  「新規構築部分から」を推奨している)。
capacity gate・ready_condition は最初の実インフラ provider(VM/物理)を書く段で入れれば足りる。

### H-2. スケール算術の前提レイテンシが実オンプレ機器で楽観的 — 天井が1桁下がる

**内容**:§12.2 は「1万リソース × 200ms / 並列度16 ≈ 125秒/周」「実用上限は数千〜1万リソース」とする。
**代入は正しい**(10000 × 0.2 / 16 = 125s)。問題は **200ms/Observe という前提**が、設計書が主対象と
宣言するオンプレ実機(NW 機器・vCenter・レガシー CLI・Ansible)では成立しないことである。

**根拠(計算過程)**:1リソースの Observe レイテンシを実機ごとに置くと、10,000 リソース・並列度16 で:

| Observe 手段 | 1回のレイテンシ | 10,000 台の1周 | 30s 間隔に収まる上限台数 |
|---|---|---|---|
| 高速 REST(クラウド的) | 0.15s | 1.6 分 | ~1,067 |
| vCenter / govmomi(重い SOAP) | 0.8s | 8.3 分 | ~200 |
| NETCONF / gNMI(NW 機器) | 1.5s | 15.6 分 | ~107 |
| CLI scrape(旧機種) | 4.0s | 41.7 分 | ~40 |
| Ansible module(fork+SSH) | 6.0s | 62.5 分 | ~27 |

（「上限台数」= §6.2 の早期警戒線「間隔30sに対しObserve 10s超で破綻」に基づき、
Observe 予算10s = 10 × 16 / レイテンシ）

- §12.2 の「200ms」は**表の最上段(高速 REST)にしか当てはまらない**。設計書自身が §11.1・§21.3 で
  「実装の8割は泥臭い層(生 NW 機器・FW・guest OS)」「その多くは Ansible ラップ = check mode で
  fork+SSH」と述べている。その泥臭い層こそ 1.5〜6s 側であり、そこでは**単一デーモンの実用上限は
  数百リソース**まで落ちる。
- 並列度を上げる逃げ道は §12.2 自身が「相手 API が rate limit で音を上げる」として封じている
  (§6.2 の sem=16 は「相手 API への礼儀」)。NW 機器は同時セッション数が2〜8程度に制限される機種が
  多く、機器単位では並列度を上げられない。
- Ansible module は fork プロセス起動コストがあり、goroutine 並列の恩恵が I/O 待ちほど効かない
  (CPU/メモリが先に律速する可能性)。「Observe は I/O バウンドで goroutine で足りる」(§4.4)は
  自前 provider には正しいが Ansible executor には当てはまりにくい。

**提案**:
- §12.2 の見積もりを「**provider の階級別**」に書き分ける。「完全/標準階級(REST・自前)= 数千〜1万」
  「Ansible/CLI ラップ = 数百〜千」と明示し、単一の「数千〜1万」を撤回する。
- 早期警戒線(§6.2)を数値で具体化し、**tier 別 Observe 頻度と間引きを v1 の設計余地として型に残す**
  (現状 §24.2 で v2 送り)。泥臭い層を主対象と宣言する以上、間引きは「破綻してから」では遅い。
- ready_condition による複数 Cycle 依存(§6.7)で「物理サーバ立ち上げが数十 Cycle に跨る」なら、
  1 Cycle が数分〜数十分になる規模では**依存解放に数時間かかる**。この体感を運用ドキュメントで
  明示すべき(遅いこと自体は設計上正しいが、期待値管理が要る)。

### H-3. Schema 設計が普及の実質的障壁 — 「4関数書くだけ」は Read/Apply に限った話

**内容**:§5.1 は「作者が書くのは4関数」と謳うが、§5.5 は**同じ設計書内で**「実装の重さの本体は
Schema を正しく書くこと」「間違えると設計書が積み上げた安全性が無効化される」と述べている。
この2つは矛盾ではないが、**対外的な訴求(4関数)と内部的な真実(Schema が最難関)がずれている**。
これは Terraform の教訓(§21:プロバイダエコシステムが勝敗を決めた)に照らして重大である。

**根拠**:
- proxmox 例(`docs/examples/`)の Schema は、`vmid`(identity + computed + allocator 連携)・
  `current_node`/`ip_address`(managed + computed)・`power_state_actual`(managed:false で
  drift 対象)・`cloud_init_password`(SecretRef + secret)・`image`(content-address format)を
  正しく宣言し分けている。**この分類を誤ると、別 VM を消す/DRS と永久に喧嘩する/資格情報が平文で
  ログに出る**(§5.5 が列挙)。これは「4関数を書く」より遥かに高い専門性を要求する。
- identity を「運用上の変更頻度で選ぶ」(§5.5:シリアルでなくトポロジ座標)という指針は正しいが、
  **これは provider 作者がドメインの運用実態を深く理解していないと書けない**。Ansible/Terraform の
  provider 作者が「モジュールを1本ラップする」感覚で入ってくると、必ず identity/managed を誤る。
- Terraform provider が普及したのは schema 記述が**宣言的で局所的**(1フィールド1行、意味論は
  Terraform コア + プロバイダ SDK が広く examples 化)だったから。Sakutei の Schema は意味論の
  射程が広い(diff・prune・監査・爆発半径・secret 漏洩がすべて Schema に依存)ぶん、
  **1つの誤りの爆発半径が大きい**。

**提案**:
- Schema lint(§5.2)を「あると良い」ではなく**「Schema 検証が通らない provider はロードを拒否する」
  レベルの強制**にする。特に (a) content-address format のフィールドに identity を許さない、
  (b) List:true なのに identity 未指定を拒否、(c) secret フィールドが平文 String 型を拒否、
  を静的に強制。
- **golden path テンプレート**を SDK に同梱する。「REST API の CRUD provider」「Ansible ラップ
  provider」の2雛形を、Schema の正しい書き方の実例(proxmox 例のレベル)込みで提供し、
  作者が「埋めるだけ」にする。§5.2 のテストハーネス(契約テスト自動生成)はこの雛形と一体化させる。
- 「4関数書くだけ」という訴求を**「4関数 + Schema。Schema が肝で、SDK と lint が支える」**に
  正直化する。過小訴求で入ってきた作者が事故を起こすほうが、エコシステムには有害。

### H-4. 「なぜこの差分が出たか」の追跡は原因タグ B(drift)が構造的に弱い

**内容**:運用者の最頻の問い「**なぜ Sakutei はこれを変えようとしているのか**」に対し、原因タグ
(§10.3)は良い枠組みだが、**B(drift = 現実が乖離)を「消去法」でしか判定できない**。観測 state を
持たない代償として、「actual がいつ・何によって変わったか」を Sakutei は原理的に言えない。

**根拠**:
- §10.3 明記:「観測 state を持たないため『actual が変化した』こと自体は観測できない(前回の actual を
  保持していない)。diff が存在し、他の3つの revision がいずれも動いていなければ現実側が動いたと結論」。
  つまり B の証拠は「**A/C/E のどれでもない**」という否定形でしかない。
- 運用者のデバッグは「いつからズレた? 誰が触った?」から始まるが、Sakutei は「今ズレている」しか
  言えない。**手で触った犯人の特定は Sakutei の外**(機器の監査ログ・§17.5 の外部監査)に依存する。
  これは観測 state レスの正しい帰結だが、**運用者の期待とギャップがある**(Terraform の state diff は
  「前回の記録との差」を見せてくれる)。
- タグ C(幽霊 diff)は「provider version を diff 入力に含める」で検知するが、**provider の正規化
  ロジックのバグと正当な修正が同じ見た目**(§10.3 自認)。運用者は ProviderUpgradeDiff Event を見ても
  「これは適用してよい修正か、バグか」を自力で判断できない——dry-run と目視に頼る。

**提案**:
- **軽量な "last-seen" リング(S3・インメモリ・非永続)を許す**。観測 state の永続化は原則違反だが、
  「直近 N 周の actual スナップショットをメモリに保持し、drift 検知時に『前周は X だった』を Event に
  添える」ことは、喪失しても安全側(S3 の定義通り、数周鈍るだけ)であり原則と両立する。
  これで B の「いつから」に近い情報が運用者に出せる。**永続化しない限り観測 state レスの看板は守れる**。
- `sakutei status`(§1.3)に「なぜ変わるか」の**原因タグ + 直近スナップショット差分 + 影響下流
  (タグ D の波及)**を1画面で出す。デバッグ体験の設計を v1 のスコープに明示的に入れる
  (現状 §24.1 の conformance レポートは「drifted 一覧」止まり)。

### H-5. render 2フェーズ + テンプレート展開が v1 の隠れた複雑性ホットスポット

**内容**:§7 は render を「収束ループと同格の複雑さ」と位置づけ、§24.1 で v1 に含めている。だが
render フェーズ1は**外部権威(Vault metadata・allocator・CMDB)への副作用ある呼び出しを毎周**行い、
フェーズ2は**テンプレート展開 + カスタム関数**(§7.5:プール採番・CIDR 計算・tier 別割り当て)を
含む。これは「合成リソースを DAG に実在させる」ために必須だが、v1 の allocator が「不要」(§3.4 の
seam 表)とされていることと緊張する。

**根拠**:
- §7.1 のフェーズ1は allocation 解決を含むが、§3.4 は `AllocationAuthority` を「v1 不要」とする。
  proxmox 例(§2.2)は `vlan_tag: 573` を「allocator が払い出した具体値」として展開しており、
  **合成リソース(mysql_database)を v1 でまともに動かすには allocator が要る**。v1 で allocator 無しなら、
  合成リソースの採番フィールドは手書き固定になり、§7.5 の「カタログの商品 = 合成リソース」の価値が
  出ない。→ v1 の「render 2フェーズ + テンプレート展開」と「allocator は v2」が噛み合っていない。
- テンプレートのカスタム関数(§7.5:「単純な変数展開を超える処理」)は、決定性(§7.1:同じ入力→同じ
  出力)を保ちながら CIDR 計算・プール割り当てを行う必要があり、**テンプレートエンジン選定 + カスタム
  関数フレームワーク**という独立した設計課題。§26 未決事項にも `rendered_revision` の算出定義
  (TTL キャッシュのヒット/ミスで値が変わらない担保)が残っている——**決定性が未証明のまま v1 に
  入れている**。

**提案**:
- **v1a では合成リソース(render フェーズ2 の展開)を外す**。単一 provider の直接収束(DNS/VM 個別)で
  価値実証し、合成リソース + テンプレート展開は allocator と**同時に**v1b で入れる(依存関係が実在する)。
- `rendered_revision` の算出定義(§26.2 B)を**フェーズ2 実装の着手前に確定**する。決定性が
  原因タグ E の判定基盤である以上、これは「動かしながら決める」項目ではない。

### H-6. 自己運用の鶏卵構造は成立するが、段0 の運用負荷が「年数回〜月1回」に収まらないリスク

**内容**:§19 の段0(Proxmox 3ノード + 統合 Ceph + VM-HA + Vault + broker + reconciler)は
ブートストラップとしては定石で妥当。しかし §19.6 は人手運用を「年数回〜月1回レベル」と見積もるが、
**Ceph + Vault(sealed-on-restart)+ VM-HA + OOB という4つの有状態/物理要素を同居させた段0 は、
実際には常時の目配りを要する小規模プラットフォーム**であり、この見積もりは楽観的である。

**根拠**:
- §19.4・§14 が正直に認める通り、**Vault は再起動で sealed に戻り、MTTR に人間の unseal 時間を含む**。
  段0 ノード障害 → VM-HA で Vault VM が別ノード再起動 → sealed → **人が unseal するまで新規/rotate
  シークレットを要する Apply が止まる**。これは「年数回」ではなく「ノード障害・保守再起動のたび」に
  発生し、頻度はハード信頼性次第。3ノードなら年数回のハード事象は現実的にあり得る。
- Proxmox 統合 Ceph は「運用重量が下がる」(§19.4)とされるが、3ノード Ceph は**最小構成で冗長性が
  薄い**(1ノード障害で degraded、2ノードで read-only リスク)。Ceph 健全性監視(§19.6)は
  「たまに UI を見る」では済まない場合がある。
- reconciler が「本番中枢」でありながら段0 は Ansible 手管理(§19.2)。**段0 の Ansible playbook 自体の
  drift・保守は誰も収束しない**(§19.6 の「たまのバージョンアップ」に含まれるが、段0 が育つほど
  Ansible 資産の保守が重くなる)。

**提案**:
- **auto-unseal を「思想的ねじれ」として一律排除せず、段0 に限り選択肢として再検討**する
  (§19.4 は auto-unseal を避けたが、その代償が MTTR に人手が入ること)。段0 の可用性要求
  (broker 断 = 全盲、§15.1)を考えると、Vault の sealed-on-restart は運用上の実害が大きい。
  Transit auto-unseal を別の最小 Vault に置く等、ねじれを局所化する設計を検討余地として残す。
- §19.6 の「年数回〜月1回」を**根拠つきで再見積もり**する(ハード MTBF・Ceph リバランス頻度・
  Vault unseal 頻度を積む)。運用チームへの導入時に「段0 は片手間では回らない」ことを正直に
  提示しないと、H-4/ブラウンフィールドで得た信頼を段0 の運用破綻で失う。

## 重大度[中]

### M-1. Go での実装可能性は現実的だが、v1 一括では見積もりが伸びる

**内容**:Go は本用途に適する(goroutine 並列 Observe・interface による seam・単一バイナリ配布・
govmomi/各種クライアントの成熟)。実装可能性そのものに疑義はない。工数は**v1 の切り方に強く依存**する。

**根拠と人月概算**(シニア Go エンジニア基準、テスト・レビュー込み):

| 塊 | 内容 | 人月 |
|---|---|---|
| コア型10個 + 収束ループ | Provider/Lister・Observation・DAG/wave・非同期 Apply・in-flight・backoff | 3.0 |
| 安全機構 | rate limit/halt・原因タグ5分類・振動検知・capacity gate・remediation mode | 2.0 |
| Provider SDK | Schema 駆動 diff(順序付き含む)・secret マスク・managed 除外・エラー分類・version 埋め込み | 2.5 |
| SDK 周辺 | Schema lint・テストハーネス(契約テスト自動生成)・フェイク provider 基盤 | 1.5 |
| render パイプライン | 2フェーズ・TTL キャッシュ・障害時前回値保持・テンプレート展開 + カスタム関数 | 2.5 |
| FileSource + Loader | YAML/JSON・JSON Schema 検証・循環検出 | 1.0 |
| SecretBackend(Vault)| SecretRef 型・遅延展開・世代解決 | 1.0 |
| import + Sync Mode | reverse-render・継続ループ・generated/ 規律 | 1.5 |
| ready_condition + 複数 Cycle | Observation.Ready・canApply 拡張 | 0.5 |
| provider 2〜3個(DNS + VM + FW/order) | 実 provider の泥臭さ込み | 2.0 |
| devenv(フェイク中心)+ E2E | §22 の層A + カオステスト基盤 | 1.5 |
| 未決型5個の確定 + 統合・安定化 | §26 A、結合バグ、ドキュメント | 1.5 |
| **合計(§24.1 の v1 全部)** | | **約22.5人月** |

- これは**1人なら約2年、3人チームで8ヶ月**。「MVP」としては重い。
- H-1 の v1a(コア + ループ + 安全機構 + 最小 SDK + provider 2個 + devenv)だけなら**約10〜11人月**で
  「触ってないのに戻る」+「爆発半径で止まる」体験に到達できる。**差別化の核はこの範囲で実証できる**。

**提案**:見積もりを v1a/v1b で分け、**先に v1a を出して市場/組織の反応を見る**。SDK フルセット・
import・Sync Mode を v1a に入れないことで、価値実証を10人月前後に圧縮できる。

### M-2. Ansible executor での「保証の落ち込み」が主対象領域と衝突する

**内容**:§21.3 は「Ansible provider では横断保証の多く(Diff・原因タグ A/B・converging・破壊的重み付け)が
機能しない」「保証群は当面少数派のコア provider にしか完全には効かない」と正直に認めている。だが
§11.1 は「実装の8割は泥臭い層 = Ansible 担当」とも述べる。**= Sakutei の価値の8割の領域で、
Sakutei の差別化(安全機構・原因タグ)が効かない**という構造的緊張がある。

**根拠**:TrueObserve:false → タグ単一化 `changed`・rate limit 破壊側倒し(§4.3)。これは「安全側で
正しい縮退」だが、運用者から見ると「泥臭い層では Sakutei はただの冪等 Ansible ラッパーで、
賢い drift 追跡は効かない」に映る。差別化(System Initiative 的な「なぜ変わるか」の可視化)が
**効く領域と効かない領域が provider 階級で割れる**ことを、運用者は導入前に理解しにくい。

**提案**:`sakutei status` で provider ごとに**「この provider は完全/標準/最小階級。効く保証はこれ」**を
明示表示する。期待値管理をツール内で行い、「なぜこの機器では原因タグが `changed` しか出ないのか」を
運用者が自己解決できるようにする。§21.3 の `*_info` 部分昇格を**積極的に推奨パターン化**し、
Ansible 層の縮退を可能な限り部分回復させる。

### M-3. ブラウンフィールド導入戦略は現実的だが「N日間 diff ゼロ」の運用が回りにくい

**内容**:§23 の import → alert-only → scope 昇格は戦略として優れており、Terraform import より楽
(観測 state レスゆえ state ズレが原理的に無い・§23.3)という主張も正しい。ただし昇格基準
「N 日間 diff ゼロ or 全て説明可能な diff」(§23.4)は、**実基盤では diff がゼロになりにくい**。

**根拠**:既存基盤は managed fields(DRS 配置・動的 IP・NW 機器の counter/timestamp)を常時動かしており、
import 直後の生スナップショットではこれらが毎周 diff として出る。§23.3 は「import 時に managed の
切り分けが必要」とするが、これは**人が全 provider・全フィールドについて managed 判定を手で行う**という
重い前工程を意味する。切り分けが不完全なまま alert-only にすると「説明可能な diff」が大量に出続け、
運用者が**本物の drift を見落とす**(アラート疲労)。

**提案**:
- import 出力に**「managed 候補の自動サジェスト」**を付ける(N 周観測して毎周値が変わるフィールドを
  「managed 候補」としてマーク)。人の切り分け作業を「ゼロから」から「サジェストの承認/却下」に下げる。
- 昇格基準を「diff ゼロ」から**「意味のある diff がゼロ(managed 除外後)」**に緩め、
  ノイズと本物を分離する仕組みを Sync Mode の commit 間引き(§23.8)と共通化する。

### M-4. commit-confirm を「管理NW機器で必須」とするが v1 に無い

**内容**:§19.3 は「管理NW機器では `Capabilities.CommitConfirm` を必須とする」と定めるが、
§24.1 の v1 スコープに commit-confirm(Apply 契約の transactional/candidate-commit)が**入っていない**
(reconciler-design-v1 のバックログでも「NW 機器プロバイダを書くとき」= 実質 v2)。

**根拠**:管理NW コアの自傷ロックアウト(§19.3 の DC 規模版ロックアウト)を防ぐ3層のうち1つが
commit-confirm。これが無い v1 で管理NW を触ると、**commit-confirm 抜きの platform 層 config push で
自分を締め出す**リスクが残る。§19.5 は「rate limit + halt と remediation mode は v1 必須」とするが、
commit-confirm はそこに含まれていない。

**提案**:v1 では**管理NW コアを収束対象にしない**(§19.3 で「到達性の最小核は段0 = Ansible」と
既に切っているので、v1 の Sakutei は管理NW を alert-only 限定とする)ことを明示する。
commit-confirm 未実装の間、NW 機器 provider は**「Apply 不可・観測のみ」を Capabilities で強制**し、
ロックアウト経路を型で塞ぐ。

### M-5. 学習コストが高い — 概念数が Terraform/Ansible より多い

**内容**:運用者(自組織 社内インフラ運用チーム想定)が習得すべき概念:3プリミティブ・DeletionPolicy 2種・
pruneable・ownership 2層・原因タグ5分類・Capabilities 4項目 + 階級3種・ScopeMode 2種・
remediation mode・rate limit/capacity gate・tier: foundation・managed/computed/identity/secret/ordered・
ready_condition・SecretRef・render 2フェーズ。**Terraform(resource/state/plan/apply)や Ansible
(playbook/task/idempotent)より概念負荷が明確に高い**。

**根拠**:設計書自身が「CLI 動詞は業界標準を用いる(学習コストが生じないことに価値)」(§1.3)と
述べる一方で、その下の**データモデルの概念数は業界標準を大きく超える**。運用者が最初に触るのは
CLI だが、事故を防ぐには Schema 属性・pruneable・ownership を理解する必要があり、
**「使い始めは簡単、正しく使うのは難しい」**構造になっている。

**提案**:
- **段階的開示**の運用ドキュメントを用意する。「読むだけ(status/plan)」→「alert-only で観察」→
  「auto に昇格」の各段で必要な概念だけを提示し、全概念を最初に要求しない(§23 の導入戦略が
  そのまま学習パスになる)。
- 危険な概念(pruneable・prune・ownership: platform)は**既定で最も安全な側**に倒っており
  (pruneable:false・alert-only)、これは学習コストを事故に直結させない良い設計。この
  「安全既定」を運用ドキュメントの前面に出す。

### M-6. `ID` 名前空間・`Plan` 型が未定義のまま v1 スコープに全機構が乗っている

**内容**:§4.6・§26.1 が認める通り、`State`/`Plan`/`ID`/`Scope`/`Event` の5型が未定義。特に
**`ID` 名前空間と `Plan` の中身は「後から変えると全プロバイダに波及」**(§26.1)。これが未確定のまま
§24.1 の v1 機能群(rate limit は Plan の破壊性を読む・dependsOn は ID を読む・監査は Event を読む)を
設計している。

**根拠**:§26.1 明記:「`Plan` の中身:Apply の契約と rate limit の重み付けが両方これを読む。破壊性
フラグと原因タグを含めるかどうかで安全機構の実装が変わる」。**安全機構(v1 必須・§19.5)の実装が
未定義型に依存している**。ID 名前空間もマルチテナント境界(§12.1)と dependsOn の曖昧さに直結。

**提案**:§26.1 A の5型を**実装着手の第0スプリントで確定**する(設計書もそう位置づけている)。
特に `Plan`(破壊性フラグ + 原因タグ + 操作種別 + 変更フィールド)と `ID`(複合キー
`(provider, scope, id)` 推奨:テナント衝突を型で防げる)を先に決める。これは工数見積もり(M-1)の
「未決型確定 1.5人月」に含めたが、**最初にやる**ことが波及コストを最小化する。

### M-7. 差別化(観測 state レス + ループ)は実装後も維持できるが、System Initiative との差別化は薄い

**内容**:類似ツールとの差別化を実装可能性の観点で評価する。
- **vs Terraform**:観測 state レスで「三項差分(宣言/state/現実)」が構造的に消える(§1.2)——
  これは**実装後も維持できる本質的差別化**。import が state ファイルを作らない(§23.3)のも実利。
- **vs Ansible**:ループ型で drift 自己修復——維持できる。ただし泥臭い層は Ansible module を借りる
  (§21.2)ので、その層では差別化が薄まる(M-2)。
- **vs k8s operators/Crossplane**:etcd/apiserver を持たない単一デーモン——運用が軽い点は維持できる。
  ただし Crossplane の Composition(合成)/ Provider エコシステムは成熟しており、Sakutei の合成リソース
  (§7.5)+ provider は**後発でエコシステムを追う立場**。
- **vs System Initiative**:SI は「なぜ変わるか」の可視化・シミュレーションが売り。Sakutei も原因タグ・
  twin(§22.5)で近いことを狙うが、**H-4 で見た通り観測 state レスゆえ drift の "いつから" が弱い**。
  差別化の主張が最も競合と被り、かつ実装で弱い領域。

**根拠**:上記各項の設計書該当節。

**提案**:差別化の一本目を**「観測 state レス × オンプレ物理まで(電源〜guest OS)」**に絞る
(Terraform は state 地獄・k8s はアプリ層止まり・SI は可視化寄りで物理を扱わない)。
「なぜ変わるか」で SI と正面勝負しない——そこは H-4 の弱点があり、勝てない土俵。
**オンプレ物理を宣言的にループ収束する**という一点は、実装後も競合が薄い。

## 重大度[低]

### L-1. `sakutei` 単一バイナリのサブコマンドに `apply` を置かない判断は妥当だが運用者が探す

**内容**:§1.3 で `apply` を主動詞に置かず `reconcile` を使う判断は思想的に正しい(回り続けるもの)が、
Terraform 慣れした運用者は最初 `apply` を探す。**エイリアス `apply → reconcile` を用意**し、
実行時に「Sakutei は回り続けるもの。単発は reconcile」と教育メッセージを出すと親切。

### L-2. content-address 参照(`image@sha256`)の運用フローが未記述

**内容**:§20.3 で image を名前でなくハッシュ参照する判断は drift 検知の正しさに直結し妥当。ただし
**運用者がハッシュをどう取得・更新するか**のフローが無い。image を焼き直すたびに intent の sha256 を
書き換える運用は手間。golden image ビルド Task(§20.2)の出力ハッシュを intent に自動反映する経路を
（v2 でよいので)設計に残すべき。

### L-3. reconcile 間隔の既定値が未定(§26.3)で、スケール見積もり(H-2)と相互依存

**内容**:§26.3 で reconcile 間隔を「動かしながら決める」としているが、H-2 で見た通り**間隔と Observe
時間の比が破綻線**(§6.2)を決める。間隔既定値は「運用パラメータ」であると同時に「スケール上限を
決める設計値」でもある。既定値の決定を「動かしながら」に丸投げせず、**provider 階級ごとの推奨間隔表**を
用意すべき。

### L-4. devenv/twin のドッグフーディングは優れているが v1 の工数に効く

**内容**:§22 の「devenv 自体を Sakutei で構築する」(ドッグフーディング)・フェイク provider 中心の
テスト戦略は、実装可能性を大きく高める良い設計(seam の副産物でフェイク挿入が容易)。ただし
twin(§22.5:render 入力差し替え)は allocator seed・SecretBackend フェイクを要し、**v1 の allocator/
credential-broker 不在(v2 送り)と噛み合わない**。twin フル機能は v2 で正しい。v1 は層A(フェイク)+
層B(軽量本物)までと明示すべき(§22.4 のワークフロー1〜2)。

## まとめ:優先対応順

1. **v1 を v1a/v1b に分割**(H-1・M-1)——価値実証を10人月に圧縮、SDK フル/import/Sync Mode は後段。
2. **未決型5個を第0スプリントで確定**(M-6)——特に `Plan`/`ID`。安全機構がこれに依存。
3. **スケール見積もりを provider 階級別に書き直す**(H-2・L-3)——「数千〜1万」は高速 REST 限定。
4. **Schema lint 強制 + golden path 雛形**(H-3)——普及の律速を SDK で潰す。
5. **段0 運用負荷の再見積もり + auto-unseal 再検討**(H-6)——導入信頼を段0 破綻で失わない。
6. **`sakutei status` のデバッグ体験を v1 に明示**(H-4・M-2・M-5)——「なぜ変わるか」+ 階級表示 +
   軽量 last-seen リング。差別化と運用性の両方に効く。

**設計の骨格(3プリミティブ・観測 state レス・seam 群・ownership 貫通)は健全であり、上記は
"作り直し" ではなく "切り出しと期待値調整" の指摘である。**
