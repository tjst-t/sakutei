## 重大度[高]

### H-1. `Provider` interface のメソッド定義が §4.1 と §5.1 で食い違う(Diff の有無・戻り値の型)

**該当箇所**:§4.1、§5.1、§4.4、§6.1

**内容**:
同一の `Provider` interface が2章で異なる定義になっている。

- §4.1:
  ```go
  Observe(ctx, id string) (Observation, error)
  Diff(desired, current State) Plan     // ← Diff を持つ
  Apply(ctx, Plan) error
  ```
- §5.1:
  ```go
  Schema() Schema
  Capabilities() Capabilities
  Read(ctx, id string) (State, ObserveStatus, error)   // ← Observe でなく Read、戻りも別
  Apply(ctx, plan Plan) error
  // Diff は「書かせない」= Provider は Diff を持たない
  ```

§4.1 は「`Diff` は provider が実装する」形だが、§5.1 と §5.3(1)は「Diff を書かせない・コアが Schema 駆動で汎用実装」と明言し、Provider に `Diff` が無い。さらに §4.1 は `Observe`、§5.1 は `Read` とメソッド名すら違い、戻り値も `Observation` と `(State, ObserveStatus)` で不一致。§4.1 末尾に「§5 を正とする」注記はあるが、**§4.1 のコードブロックそのものが誤った実装契約を提示している**ため、実装者が §4.1 をコピーすると Provider に Diff を実装してしまう。§4.4 の `Executor.Observe` / §6.1 の `Observe` という呼称もこの揺れに乗っている。

**修正提案**:§4.1 のコードブロックを §5.1 と一致させる(`Read` に統一、`Diff` を Provider から削除しコメントで「Diff はコアが Schema 駆動で実装」と明記)。あるいは §4.1 を「概念モデル(実際の署名は §5)」と明示した上で、誤解を招く `Diff(desired, current State) Plan` の行を削除する。名称も `Observe`/`Read` のどちらかに全書統一する(用語集で確定させるのが望ましい)。

### H-2. `ObserveStatus` が §5.1 で使われているが未定義。§4.2 の `Availability` との関係も不明

**該当箇所**:§5.1、§4.2、§4.6、§5.3

**内容**:
§5.1 の `Read(ctx, id string) (State, ObserveStatus, error)` で `ObserveStatus` 型が戻り値に現れるが、**この型はどこにも定義がない**。§4.2 は Observe の戻りを `Observation{ Availability, State, Ready }` と定義しており、`ObserveStatus` に相当するのは `Availability`(ok/unknown/converging)と思われるが、明示的な対応づけがない。加えて §5.1 の `Read` は `Ready`(§4.2 / §6.7 で必須とされた ready condition)を返さない署名になっており、§6.7「provider は `Observation.Ready` に condition を返す」と矛盾する。§4.6 の「定義済み」表は `Observation(Availability/State/Ready)` を確定としているが、§5.1 の実際の provider 契約はこの3要素を返せない形。

**修正提案**:§5.1 の `Read` の戻り値を §4.2 の `Observation`(Availability・State・Ready を含む)に統一する。`ObserveStatus` を新設語として使うなら §4.6 の型表に加え定義を書く。いずれにせよ「provider が Ready を返す経路」を署名レベルで通す。

### H-3. allocation(採番)は v2 なのに、v1 スコープの render フェーズ1・合成リソース・reserve→confirm がそれに依存する

**該当箇所**:§24.1(v1)、§24.2(v2)、§7.1、§7.5、§16.3、§13.4、§20.3

**内容**:
§24.2 と §3.4 seam 表・§24.3 は `AllocationAuthority`(allocator)を **v2 以降 / v1 不要**と明記する。ところが v1 スコープ(§24.1)に含まれる機構がこれに依存している:

- §7.1:render フェーズ1 の3処理の1つが「**allocation 解決(AllocationAuthority への払い出し)**」。render パイプラインは §24.1 で v1。
- §7.5 / §24.1:「render フェーズ2 のテンプレート展開(合成リソースの展開)」は v1。§7.5 の例(virtual_network → vxlan/vds/dhcp)と §13.4「カタログ商品=合成リソース」は from_pool 採番を前提にしている。§7.6相当の §7.5 末尾も「プール採番・CIDR 計算」をテンプレート展開の処理として挙げる(§7.5 の展開ロジック節)。
- §16.3:reserve→confirm は「マージ後最初の render フェーズ1が confirm を実行」と、render(v1)に採番(v2)を織り込む。
- §7.3:render の障害時挙動表に「allocation authority 不達 → 前回割当保持」が v1 の障害設計として入る。

つまり **v1 の render / 合成リソースを実装するには allocation の口が要る**が、allocator 本体は v2。「v1 不要」の意味が「authority 実装は不要だが seam と呼び出しは v1 に要る」なのか「採番を使う合成リソースは v1 では from_pool を使わない」なのかが判別できない。§26 の未決リストにもこの矛盾は挙がっていない。

**修正提案**:v1 で「from_pool を使わない合成リソース(固定値展開)のみ v1」とするのか、「`AllocationAuthority` interface と最小実装を v1 に前倒す」のかを §24.1 で明示する。前者なら §7.1 の「allocation 解決」を「v2〜」と注記し、§7.5 の採番前提の例を v1 では非採番の例に差し替える。§16.3 の render 連動も v2 に紐づける。

### H-4. credential-broker は §14.5 で「v2 以降」とされるが、段0(§19.2)と依存図(§3.3)は broker を v1 稼働の前提に置く

**該当箇所**:§14.5、§3.2、§3.3、§19.2、§15、§24.2

**内容**:
§14.5 は「**credential broker は v2 以降のため、v1 では provider のターゲット認証を SecretRef で注入する**」と明記し、§24.2 も credential broker を v2 に列挙する。一方:

- §3.3 依存図:`reconciler ──(実行時に依存)──▶ credential-broker / Vault / allocator / git`。
- §3.2:credential-broker は「**core の依存先**(下位)…落ちると全ターゲット全盲」。
- §19.2:段0 構成に「credential-broker(VM-HA 保護)… reconciler の依存先」が**必須要素として**入る。
- §15.5:「broker 断 = システム全盲」を段0の可用性設計の柱にしている。

v1 に broker が無いなら、v1 では「reconciler → SecretRef(Vault)→ 機器」で到達し、broker への実行時依存は存在しない。にもかかわらずアーキ図・段0図・依存図が broker を常在の前提として描くため、**「v1 の段0に broker を建てるのか否か」が読み取れない**。§15.4 の「段階1(人向け短命発行)から作る」も broker=v2 と衝突する(段階1 で broker の一部を作るなら v2 全体が v2 とは言えない)。

**修正提案**:段0 図・依存図に「broker は v2 で追加。v1 は SecretRef 直結」の注記を入れるか、あるいは broker の最小機能(bastion+JIT の人向け発行)を v1 に含めると §24.1 で明示する。§15.4 の段階1が v1 に属するのかを確定させる。

### H-5. §26 の「実装着手前に決める」リストから、H-1〜H-4 の型・スコープ矛盾が漏れている

**該当箇所**:§26.1(A)、§4.6、§24.1

**内容**:
レビュー観点「§26 以外に実装前に決めないと詰む事項が漏れていないか」に対する中心的な指摘。§26.1(A)は未定義型として `State / Plan / ID / Scope / Event` の5つ(§4.6 の表)だけを挙げる。しかし本レビューで検出した以下は、いずれも**型を書き始めた瞬間に露呈し、後から変えると全 provider に波及する**にもかかわらず §26 に無い:

1. `Provider` interface の正となる署名(H-1)。§26 A は「interface は厳密に定義された」と書くが、実際は §4.1 と §5.1 で不一致で未確定。
2. `ObserveStatus` の定義と `Ready` を返す経路(H-2)。
3. allocation seam を v1 render に通すか(H-3)。
4. broker の v1 有無(H-4)。
5. `ready_condition` 名前空間は §26.2(B)に落とされているが、これは §6.7 で v1 必須とされた依存解決の中核であり、「dependsOn が壊れる」と自認している(§26.2)以上、A(着手前)相当。

**修正提案**:§26.1(A)に上記を追加する。特に「Provider 署名の一本化」は最優先(A の筆頭)に格上げすべき。`ready_condition` 名前空間は v1 必須機能(§24.1)の前提なので B から A へ移す。

### H-6. Release の発火根拠「下流削除を Observe で確認」が、観測 state レス原則および prune 判定と整合しない箇所がある

**該当箇所**:§16.4、§16.5、§8.4、§2-1

**内容**:
§16.4(a)は「desired から消えても Release せず、**下流リソースの削除完了を Observe で確認してから**返却」と定める。しかし「削除が**完了した**(= 現実から消えた)」ことの検知は、観測 state レス下では **`Observe` が unknown を返す状態と『本当に消えた』状態を区別できない**という §14.1/§5.3 で繰り返し警告されている問題そのものに直面する。§4.2 の三値では「absent(消えた)」を表す値が無く(ok/unknown/converging のみ)、Observation は「存在しない」を積極的に表現できない。つまり「現実から消えたことを Observe で確認」する具体機構が型に無い。§8.4 の削除判定3種とも接続が示されていない。

**修正提案**:「削除完了の観測」をどの型・どのステータスで表すかを定義する(例:List に現れなくなったことを根拠にする=Lister 前提にする、あるいは Observation に absent を表す第4値を足す)。§16.4 と §4.2 / §8.1 の集合演算を明示的に接続する。

### M-2. 依存宣言のキー名が `dependsOn`(§6.1)と `depends_on`(§6.7 YAML)で不統一

**該当箇所**:§6.1(L540, L542)、§6.7(L620 YAML)、§26.1

**内容**:散文・型議論では `dependsOn`(キャメル)、YAML 例では `depends_on`(スネーク)。Loader が両者を吸収する規約(camelCase↔snake_case 変換)が明示されていないため、実装者が別キーと誤認しうる。§26.1 の `ID` 名前空間議論も `dependsOn` 表記。

**修正提案**:設定ファイル上のキーを一つに定め(YAML 慣習なら `depends_on`)、コード内フィールド名との対応(変換規約)を Loader 節(§13.3)に一文追加。

### M-3. 上位ステータス集約の全順序に `stuck`/`blocked` が無い

**該当箇所**:§7.5(集約規則 `unknown > oscillating > drifted > converging > converged`)、§17.4、§6.6

**内容**:§7.5 の合成リソース上位ステータス集約は5値の全順序だが、§17.4 は Event 分類に `stuck`(permanent 失敗)・`blocked`(依存未達)を、§6.6 は `stuck` をリソース状態として持つ。子が `stuck`/`blocked` のとき上位に何を昇らせるかが未定義。fail-safe を謳う以上、permanent 失敗は最悪級に昇るべきだが順序に席がない。

**修正提案**:集約順序に `stuck`/`blocked` を位置づける(例:`unknown > stuck > oscillating > drifted > blocked > converging > converged`)か、これらは報告用 Event であり収束ステータス集約とは別軸だと明記する。

### M-4. §14.5 の暫定 SecretRef 注入と §14.2 の遅延展開・§14.5 本文の境界が緊張する

**該当箇所**:§14.5、§14.2

**内容**:§14.5 は「v1 では provider のターゲット認証を SecretRef を provider 設定として注入する」とするが、§14.5 冒頭は「CredentialProvider = engine がターゲットに到達する資格 = **desired の一部ではなく実行時の資格**」「SecretRef = desired の一部」と両者を明確に分離している。到達資格を SecretRef 経路で流す暫定は、この「desired の一部/実行時の資格」の分離を v1 で崩す。崩し方(desired に載るのか、Executor が実行時に Resolve するのか)が曖昧。

**修正提案**:v1 暫定でも「到達資格の SecretRef は desired 本体には載せず、Executor 実行時に Resolve する」等、注入点を明示する。§14.2 の「Apply 直前のみ実値化」と同じ規律で統一する。

### M-5. §12.2 のスケール移行策(Observe 間引き / watch / tier 別頻度)は v1 の「間引きなし」原則と衝突するがバージョン帰属が曖昧

**該当箇所**:§6.2、§12.2、§24.2

**内容**:§6.2 は「毎周全部・間引きなし」を観測 state レスの価値の源泉と断言。§12.2 は「Observe 間引き / watch 併用 / tier 別頻度」を延命策として提示。§24.2 は「Observe 間引き / シャーディング」を v2 に列挙するが、watch 併用・tier 別頻度がどのバージョンかは不記載。§6.2 の早期警戒線が「立つまで不要」なので設計上は整合するが、v1 実装者が「間引きなし」を絶対と読むと §12.2 の余地を型に残さないおそれ。

**修正提案**:§12.2 の各延命策のバージョン帰属を明記し、「v1 は間引きなしだが Observe スケジューラの seam を残す/残さない」を一文で確定。

### M-6. `credential-broker` の v1 稿呼称「credential broker」と新呼称、`allocator`/`allocation authority` 混在

**該当箇所**:§1.3、§16 全般、§3.4

**内容**:§1.3 でコンポーネント名を機能名へ改名(`allocator` / `credential-broker`)したと宣言しつつ、本文は §16 で「allocator」の語をほぼ使わず「allocation authority / authority」を多用、§3.4 seam 表も interface 名は `AllocationAuthority`。プロジェクト名以外は機能名という規約(§1.3)自体は守られているが、コンポーネント名(`allocator`)と interface 名(`AllocationAuthority`)と役割語(allocation authority)の3つが並走し、初読者がどれが「そのコンポーネントの名」か迷う。

**修正提案**:「コンポーネント=allocator、その interface=AllocationAuthority、役割=採番権威」の三者関係を §16.1 冒頭で一度定義する。

### M-7. §23.8 Sync Mode は v1(§24.1)だが、依存する continuous commit / attribution 機構の置き場が未定義

**該当箇所**:§23.8、§24.1、§26.2

**内容**:Sync Mode は §24.1 で v1。動作は「毎周 List → 前回スナップショットと比較 → intent ファイルへ commit(コミット者=システム)」。ここで (1) 前回スナップショットの保存先(S1 観測 state に見えるが §6.5 で S1 は「持たない」)、(2) システムによる git commit 権限(§13「git は単一書き込み経路・人がレビュー」と緊張)が要る。(1) は §6.5 の state 分類にも §26.2 の S2 永続化先にも明記なく、「観測 state を持たない」原則と表面的に矛盾。

**修正提案**:Sync Mode の「前回スナップショット」を state 分類(S1〜S4)のどこに置くか明示する(diff 検出専用で喪失しても再同期で復元可能なら S3 相当と位置づける等)。システム commit 権限を §13 の「単一書き込み経路」原則の例外として明記する。

### M-8. `Scope` 型が provider ごとに意味が違う(§4.6 未定義)のに、§8.2 / §12.1 / §23.8 が Scope を確定機構として多用

**該当箇所**:§4.6、§8.2、§12.1、§23.8

**内容**:`Scope` は §4.6・§26.1 で未定義(「型付きにすると provider 追加のたびにコア変更」と設計上のジレンマも未解決)。一方 prune の境界(§8.2)、テナント分離境界(§12.1)、Sync/Converge の単位(§23.8)、シャード分割キー(§12.2)がすべて Scope に乗る。**未定義の型に4つの安全機構が依存**しており、Scope の表現(zone/cluster/rack をどう1型で表すか)が決まらないと prune もテナント境界も実装できない。

**修正提案**:§26.1(A・着手前)における `Scope` の優先度を、`ID`/`Plan` と同格の最優先に位置づける(現状 §26.1 は ID と Plan のみ「特に優先」)。
