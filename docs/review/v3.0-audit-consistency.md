## 重大(矛盾・誤参照)

### 重大-1. backoff の参照先が §11 になっている(正:§8.5)

- **箇所**: §5.4(L581)、§5.5(L587)
- **内容**: backoff は §8.5「per-resource backoff」で定義されるが、2 箇所とも「§11 の backoff」と参照している。§11 は「多周期収束」であり backoff の記述は一切ない。v2.6 では §6.6 が backoff で、そこを指していた(v2.6 L512「§6.6 の backoff のため」)。再構成で §8.5 へ移った先を追えず、converging の移動先 §11 に誤って合流させたもの。
- **修正案**:
  - §5.4(L581): 「エラーを **transient / permanent に分類**して返す(backoff のため・**§8.5**)」に修正。
  - §5.5(L587): 「Apply のエラーは2種類に分類して返す(**§8.5** の backoff が読む)。」に修正。

### 重大-2. twin の参照先が §15 になっている(正:§26.2)

- **箇所**: §10.2(L1208、原因タグ C / ghost diff の説明)
- **内容**: 「twin(**§15**)への自動流し込みを既定運用に組み込み、ghost diff を本番前に観測する」とあるが、twin(縮景)は §26.2「devenv(坪庭)と twin(縮景)」で定義される。§15 は「隔離と防御」であり twin の記述はない。v2.6 では twin は §22.5 で、そこを指していた(v2.6 L1291「twin(§22.5)への自動流し込み」)。同節内の別箇所(L2629)は正しく「twin(§26.2)」と参照しており、L1208 だけが誤り。
- **修正案**: §10.2(L1208)を「解禁する(twin(**§26.2**)への自動流し込みを既定運用に組み込み、ghost diff を本番前に観測する)。」に修正。

### 重大-3. allocator HA の fencing 再利用参照が §18 になっている(正:§15)

- **箇所**: §19.8(L2049)
- **内容**: 「active/standby + fencing token(**§18** の fencing を再利用)」とあるが、fencing token の定義は §15.2「fencing token(単一 writer の保証)」。§18「分散の原則と将来」は §18.4 で動的ルーター割当表の fencing に触れるものの、そこ自体が §15 を参照しており、fencing を「定義」してはいない。v2.6 では fencing は §12.3 で、そこを指していた(v2.6 L2254「§12.3 を再利用」)。同節内の別箇所(L2051)は「§17 の単一 writer fencing と同型」と参照している。
- **修正案**: §19.8(L2049)を「active/standby + fencing token(**§15** の fencing を再利用)」に修正(§15.2 でも可。CHANGELOG は fencing の正準参照を §15.2/§17 と定義しており §18 は該当しない)。

### 重大-4. managed fields の参照先が §11 になっている(正:§7 / §7.2)

- **箇所**: §28.3 SDK 機能表「managed fields 除外」行(L2831)、§28.4(L2843)
- **内容**: 両箇所とも managed fields を「§11」と参照するが、managed fields は §7.2「managed fields —— 外部システムが動かす欄の diff 除外」で定義される。§11 は「多周期収束」で managed の記述はない。v2.6 では managed fields は §11.2-4 にあり、SDK 表も「§11.2-4」を指していた(v2.6 L491)。再構成で §7.2 へ移った際に「.2-4」だけを削り「§11」に丸めてしまい、無関係な §11 を指す結果になった。なお同一概念を §5.2 の Schema 属性表は正しく「(§7)」と参照している。
- **修正案**:
  - §28.3(L2831)の「関連」列を「**§7**」に修正。
  - §28.4(L2843)を「どのフィールドが **managed / runtime**(**§7**)→ 誤ると DRS と永久に喧嘩する。」に修正。

### 重大-5. `ChangeHint` 型のフィールド名が 2 箇所で不一致

- **箇所**: §4.6(L442-445)と §21.2(L2223-2226)
- **内容**: 同一の `ChangeHint` 型が異なるフィールド名で定義されている。
  - §4.6: `Revision string  // intent_revision(触られたことの目印)`
  - §21.2: `IntentRevision string  // どの intent 版か(合流時に最新を読むための目印)`
  `Scopes []Scope` は両者一致するが、revision フィールドの名前(`Revision` vs `IntentRevision`)が食い違う。コア型の正準形は §4 で固定する方針(本書 §4 冒頭)なので、両者を一致させる必要がある。
- **修正案**: §4.6 の `Revision` を **`IntentRevision`** に統一する(§21.2 側がより明示的で、コメントも intent_revision を指しているため §21.2 の名称を正とする)。§4.6(L443)を
  `    IntentRevision string  // intent_revision(触られたことの目印)`
  に修正。あわせて §4.6 本文・§21.2 本文の説明が両立していることを確認する(内容説明は既に一致)。

### 重大-6. 「全域予算は外部集約で見る」の参照先が箇所により §17 と §29 に食い違う

- **箇所**: §13.2(L1457)と §18.2(L1903)
- **内容**: 同一の決定「全域予算(全シャード合算予算)はシャード単位では閉じず外部集約で見る」を、
  - §13.2(L1457): 「全域予算は外部集約で見る(**§17**)」
  - §18.2(L1903): 「全域予算は外部集約で見る(**§29**)」
  と別々の節に参照している。実際にこの概念を展開しているのは §18.2/§15.4 であり、§17(claim シャーディング)には全域予算集約の記述がない。v2.6 では両者とも未決事項 §26.1 A-1 を指しており(v2.6 L1801)、その後継が v3.0 §29。したがって §29 を指す §18.2 側が v2.6 の意図を継いでおり、**§17 を指す §13.2 側が誤り**。
- **修正案**: §13.2(L1457)を「全域予算は外部集約で見る(**§29**)」に統一する(§18.2 と一致させる。あるいは概念の実体がある §18.2 を両者の参照先に揃えてもよいが、最小修正は §13.2 を §29 に合わせること)。

## 中(用語ゆれ・不正確参照・重複)

### 中-1. §28.3「エラー分類ヘルパー」の参照が §8(正準は §5.5)

- **箇所**: §28.3 SDK 機能表(L2833)
- **内容**: 「エラー分類ヘルパー | Apply のエラーを transient / permanent に型付け | **§8**」。エラー分類の定義は §5.5「エラー分類」で、SDK ヘルパもそこで言及される(L592)。§8.5 は分類結果を「読む」側。表の他行(diff=§5、version 埋込=§10 等)は定義節を指す慣例なので、ここも定義節 §5.5 が整合的。
- **修正案**: §28.3(L2833)の「関連」列を「**§5.5**」に修正。

### 中-2. §24.6「§26 の証明書 expiry と同型」——§26 に証明書 expiry の記述がない

- **箇所**: §24.6(L2547)
- **内容**: 「`last_verified` が古くなったら…health 述語(**§26** の証明書 expiry と同型)として上げる」とあるが、§26「検証と監査」に証明書(cert)expiry の記述は存在しない。時間ベース health 述語(鮮度述語)を実際に述べているのは §25.2(L2601「鮮度は時間ベースの health 述語」)。
- **修正案**: 「(**§25.2** の時間ベース health 述語と同型)」に修正するか、証明書 expiry の例に固執するなら observability(§22.2)を参照する。最小修正は参照先を §25.2 に変更。

### 中-3. `Observation` 型の Ready コメントの参照粒度が 2 定義で不一致

- **箇所**: §4.5(L419)と §10.1(L1176)
- **内容**: 同一の `Observation` 型を 2 箇所に掲載。Ready フィールドのコメント参照が
  - §4.5: `// 名前付き ready condition の充足状況(§6, §11)`
  - §10.1: `// 名前付き ready condition の充足状況(§8.3, §11.2)`
  と食い違う。ready_condition の正確な定義先は §11.2(依存条件は §8.3)なので §10.1 側の粒度が正確。矛盾ではないが、同一型の重複掲示で参照が揃っていないのは可読性上の傷。
- **修正案**: §4.5(L419)のコメントを `// 名前付き ready condition の充足状況(§8.3, §11.2)` に揃える(§10.1 に合わせる)。

### 中-4. プロバイダ階級表の完全重複(§5.6 と §28.5)

- **箇所**: §5.6(L598-602)と §28.5(L2857-2861)
- **内容**: 「完全/標準/最小」の 3 行 4 列の表が、内容・例まで含めて完全一致で 2 箇所に掲載されている。CHANGELOG-v3.0 の「圧縮した重複」一覧には capacity gate と observability 階級の 2 件のみが挙げられ、この階級表は列挙されていない。承認ゲート/CLI verb のような「短い定型 + 相互参照」ではなくフル表の重複であり、片方を要約 + 参照に圧縮する対象になりうる。
- **修正案**(任意): §28.5 を「階級の定義は §5.6 を正とする」+ SDK 文脈固有の一文(「作者は自分の階級を選べる/最小階級なら Apply だけで参入障壁が下がる」)に圧縮する。または「異なる読者文脈での意図的再掲」として CHANGELOG-v3.0 の重複一覧に明記して監査痕跡を残す。どちらでも可(内容自体は一致しているため矛盾ではない)。

### 中-5. identifier の表記ゆれ(underscore 形 vs 空白形)

- **箇所**: `provider version`(L590, L2724。他は `provider_version` 9 件)、`intent revision` / `rendered revision`(L2108。他は underscore 形が各 14 / 21 件)
- **内容**: 型・ハッシュを指す識別子はコード中では underscore 形が正準(`provider_version` / `intent_revision` / `rendered_revision`)。散文中の数箇所だけ空白形になっている。意味は同一だが、識別子として一貫させたい。
- **修正案**: L590「provider version が変わるまで」→「`provider_version` が変わるまで」、L2724「provider version を diff 計算に含める」→「`provider_version` を diff 計算に含める」、L2108「intent revision と rendered revision の差」→「`intent_revision` と `rendered_revision` の差」。

## 軽(体裁)

### 軽-1. 括弧幅(全角/半角)が部境界で切り替わる——執筆分担の痕跡

- **箇所**: 文書全体。分布は明確に 3 帯に分かれる。
  - 冒頭・目次(L1-91): **半角 `()`**
  - §1-3(第I部)(L92-324): **全角 `（）`**(全角 68・半角 0)
  - §4-18(第II〜V部)(L325-1947): **半角 `()`**(半角のみ・全角ほぼ 0)
  - §19-29(第VI〜VIII部)(L1948-2933): **全角 `（）`**(全角優勢・§28-29 に半角の混入あり)
- **内容**: 8 名分担執筆 + 統合の最も顕著な痕跡。CHANGELOG-v3.0「体裁の統一」は見出しレベル・文体・コードブロックを挙げるが、括弧幅の統一に言及がなく、実際に統一されていない。矛盾ではないが、通読時に「章ごとに書き手が違う」印象を与える最大の可読性上の傷。
- **修正案**: 括弧幅を全文どちらかに統一する(識別子・型・数式を多く含む技術文書では**半角 `()` への統一**が読みやすい。あるいは全角へ統一)。一括置換で対応可能だが、コードブロック内・URL・顔文字状の記号を壊さないよう機械置換の範囲に注意する。CHANGELOG-v3.0 の「体裁の統一」節に括弧幅の統一方針を追記する。

### 軽-2. §16.2 天井算術表:Proxmox 行「3.3 分」は「約 3.1 分」

- **箇所**: §16.2 実機レイテンシ階級表(L1673、Proxmox 行)
- **内容**: 「10,000 台の1周 = 1回のレイテンシ × 10,000 / 16」の式で、Proxmox(0.3s)は 0.3×10000/16 = 187.5s = **3.125 分 ≈ 3.1 分**。表は「3.3 分」。他の全 5 行(1.6 / 8.3 / 15.6 / 41.7 / 62.5 分)は式と正確に一致するため、この 1 行だけ丸めが合わない(「上限台数 ~533」は正しい)。
- **修正案**: §16.2(L1673)の Proxmox 行「3.3 分」を「**3.1 分**」に修正。
