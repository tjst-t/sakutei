## S-01【指摘】周期をまたいだ漸進的削除で rate-limit をすり抜ける

- **前提**: `max_changes_per_cycle: { absolute: 10 }`、`on_exceed: halt-destructive-only`。ある scope に
  破壊可能(`pruneable:true`)なリソースが 500 個ある。rate limit は「1 Cycle 内の同時変更数」と
  「in-flight を含む同時変更数」(§10.2)で評価される。
- **引き金**: 理想状態から 500 個が一斉に消えた(誤った一括削除 PR、または render バグ)。あるいは
  closed-world scope で List が徐々に「理想に無い」を返し続ける。
- **進行**: 1 Cycle 目、Diff は 500 件の delete を検出するが、rate limit が「一度に 10 件」に制限する。
  **halt-destructive-only は「超過分を止める」であって「削除意図そのものを止める」ではない**(§10.2
  「悪化を検知したらそこで halt、残りを保護」= reconciler-design-v1 L809)。10 件を削除して残り 490 は
  保留。次 Cycle、in-flight が捌けると再び 10 件が削除枠に入る。**理想状態は依然 490 件 delete のまま
  なので、毎周 10 件ずつ削除が進み、50 周(reconcile 間隔 30s なら約 25 分)で 500 件全消し**が完了する。
- **被害**: rate limit を「発動させたまま」全リソースが削除される。人間が気づく猶予は「1 周あたり 10 件」の
  Event だが、level-triggered の Event は firing/resolved 集約(§17.4)されるため、**同一 scope の削除は
  1 本の firing アラートに畳まれ、"じわじわ 500 件が消えていること" が量として見えにくい**。
- **設計上の防御は効くか**:
  - §10.2 の「異常検知(Diff が突然巨大化)」は **1 周目には効く**(500 件の巨大 Diff を検知しうる)。
    ただしこれが「halt-all で理想変更そのものを凍結する」のか「超過分だけ保留し漸進継続する」のかが
    設計上曖昧。文面「危険域に入ったら止める」だが、**"止める" が「その周の超過分」なのか「以後の削除
    意図全体」なのかが未定義**。halt-destructive-only の定義(超過分保留)を素直に読むと漸進継続になる。
  - freeze(§10.6)は人間が叩けば止まるが、**自動では止まらない**。25 分の間に人間が異常に気づき freeze
    する必要がある。
- **結論: 防御が不十分**。rate limit が「累積削除量 / 一定時間窓での削除総数」を見ていない。cycle 単位の
  瞬間量しか見ないので、周をまたいだ漸進的削除に対して構造的に無力。
- **提案**:
  1. **削除に対しては cycle 瞬間量ではなく "時間窓での累積削除量" と "同一 scope の削除進捗率" を見る
     halt を追加**。「halt-destructive-only 発動が M 周連続」または「ある scope の実在リソースの X% が
     削除進行中」で **halt-all(理想変更そのものを凍結し人へ)** にエスカレーションする。
  2. **異常検知の "止める" のセマンティクスを明文化**する。巨大 Diff 検知時は「超過分保留(漸進継続)」
     ではなく「その rendered_revision 全体を凍結し、`approved-large-change` が付くまで一切の破壊を保留」
     とするのが非対称原則に整合。§26.1 の `Plan` 定義で破壊性フラグを持つと決めた以上、ここまで規定すべき。

## S-02【指摘】cause tag 誤分類:E(外部入力)を A(意図)に誤帰属して破壊が通る / その逆

- **前提**: 原因タグは revision の消去法で判定(§10.3)。A = intent_revision 変化、E = rendered_revision
  変化 & intent_revision 不変、B = すべて不変で diff あり。rate limit の重みは A は「意図として通す」、
  E は「破壊的側に倒す」。
- **引き金 (a)**: render フェーズ1が inventory/allocation を解決した結果、**intent_revision は変わって
  いないのに大量のリソースが再構成**される(E-inventory / E-alloc)。ところが同時に人が小さな intent
  commit を1つ入れた(intent_revision が変化した)。
- **進行**: この Cycle の rendered_revision は「intent 変化 + 外部入力変化」の複合。**タグは
  intent_revision の変化を見て "A(意図的)" と判定**する(§10.3 の判定表は intent_revision 変化を A の
  十分条件にしている)。実際の 500 件の変更の大半は E 由来(CMDB が壊れた)だが、A としてマークされ、
  **rate limit は「意図なので通す」側に倒れ、承認済み扱いで破壊が進む**。
- **被害**: CMDB のバグ(E)由来の破壊的変更が、無関係な人間の小 commit に「相乗り」して A の緩い扱いで
  通過する。原因タグは per-diff だが、**1 Cycle 内に A と E が混在するとき、リソース単位で正しく分離
  できるかが設計上不明**。「intent_revision が変わった Cycle は全部 A」なら重大な穴。
- **引き金 (b)(逆方向)**: `rendered_revision` の算出に「何を含め何を含めないか」が未決(§26.2)。TTL
  キャッシュのヒット/ミスで rendered_revision が揺れると、**intent も現実も変わっていないのに E と誤判定
  → 破壊的側の重みで無用な halt**(可用性事故)。あるいは逆に、外部入力が変わったのに rendered_revision
  ハッシュに反映されない実装バグがあると、**E を B(drift)と誤判定 → auto remediation が現実を "古い
  外部入力の値" へ強制的に戻す**(rotate したシークレットを古い世代へ戻す等)。
- **設計上の防御は効くか**:
  - 原因タグを per-diff で持つ設計(§10.3、`Plan` に原因タグを含める・§26.1)は**正しい方向**。もし
    実装が「diff ごとに、その diff の入力ハッシュ差分の出自」を追えるなら (a) は防げる。しかし設計文面は
    「intent_revision が変化 → A」とグローバル revision で語っており、**per-resource の帰属アルゴリズムが
    未定義**。ここが実装依存の穴。
  - (b) は §26.2 で「TTL キャッシュのヒット/ミスで値が変わらないことの担保」を**未決と自認**している。
    つまり設計者も危険を認識しているが、**未解決のまま v1 の安全機構の判定根拠に使っている**。
- **結論: 防御が不十分**(判定根拠の未定義 + 混在時の帰属アルゴリズム欠如)。原因タグは安全機構の
  中核(rate limit 重み・監査帰属・レビュー前提が全部これに乗る)なのに、その計算根拠が §26 送りになって
  いる。「安全機構が原因タグに依存し、原因タグが未決に依存する」という依存の逆立ち。
- **提案**:
  1. **原因タグを Cycle グローバルでなく per-resource-diff で確定するアルゴリズムを設計に格上げ**する。
     各リソースの入力ハッシュを「intent 由来部分」「外部入力由来部分」「provider version 由来部分」に
     分解し、どの部分が動いたかでタグを決める。A と E の混在 Cycle で正しく分離できることを要件にする。
  2. `rendered_revision` を **decision-relevant な入力のみの決定的ハッシュ**として定義し(TTL ヒット
     /ミスや順序で揺れない)、§26.2 を v1 のブロッカーに昇格。ここが揺れると安全機構全体が誤作動する。

## S-03【指摘】render 失敗の "前回値保持" が部分成功で破れる(空 desired ではなく "歯抜け desired")

- **前提**: §7.3「どの外部権威が不達でも前回解決値を保持。空 desired を生成しない」。これは全削除事故の
  防止策。TTL キャッシュ(§7.4)が前回値を持つ。
- **引き金**: render フェーズ1は多段(inventory 合成 / Vault metadata / allocation)。**外部権威が
  "不達" ではなく "部分的に成功して部分的に欠損した値を返す"**。例: CMDB が 200 OK だが、内部の一部
  レコードだけ欠落した JSON を返す(バックエンド DB のレプリカ遅延・部分障害)。TTL キャッシュは
  「fetch 成功」とみなして新しい(歯抜けの)値でキャッシュ更新する。
- **進行**: §7.3 の防御は「**不達 = 前回保持**」の二値。「200 だが中身が縮んだ」は不達ではないので前回
  保持が発動しない。歯抜けの inventory で render すると、**欠落したリソースは "理想に存在しない" と
  展開され、closed-world prune で削除対象**になる。空 desired ではないので「全削除事故防止」もすり抜ける
  (全消しではなく "欠落した分だけ" 消える)。
- **被害**: CMDB の部分障害が、そのまま本番リソースの部分削除に翻訳される。S-01 と組み合わさると、
  漸進的に消えていく。
- **設計上の防御は効くか**:
  - §7.3 は「不達」しか想定しておらず、**"到達したが不完全" を検知する仕組みがない**。List の網羅性は
    prune 側(§5.3)で語られるが、**render 入力(desired 側)の網羅性チェックは設計に無い**。
  - rate limit(S-01 参照)は瞬間量には効くが、部分欠損が徐々に進むケースには弱い。
- **結論: 防御が不十分**。render 入力の障害モデルが「不達 / 到達」の二値で、「到達したが縮んだ」を
  扱えていない。observe 側の unknown≠absent と対をなす「**desired 側の incomplete≠empty**」が欠けている。
- **提案**:
  1. **render 入力に "期待基数 / 前回比の急減検知" を入れる**。前回 N 件だった inventory が今回 0.5N に
     なったら、それを「不達」と同じく前回保持側へ倒す(または halt + Event)。observe 側の
     unknown≠absent と対称に、desired 側にも「急減は疑う」を入れる。
  2. render 出力に対しても異常検知(§10.2 の巨大 Diff 検知)の**逆方向=「削除方向 Diff の急増」**を
     専用に監視する。

## S-04【指摘】観測 state レスの弱点:Observe が "部分的に嘘をつく" とき unknown≠absent が破れる

- **前提**: 非対称原則の起点は「到達不能 = unknown、存在しない = absent、両者を絶対に混同しない」
  (§4.2, §5.3)。prune は「List に無い = 消す」(§4.1, §5.3)。unknown は保守側に倒れるので安全。
- **引き金**: 問題は **`Read`(個別)は unknown を返せるが、`List`(集合)は "存在するものの部分集合"
  を成功として返しうる**こと。List の契約(§5.3)は「scope 内の全 ID を漏れなく返す。中途半端なら
  List:false にせよ」だが、**"漏れ" を List 実装が自己検知できるとは限らない**。API がページングの
  途中で 200 を返して打ち切る、フィルタ条件のバグで一部が抜ける、相手 DB のレプリカが遅延して古い
  (少ない)集合を返す——いずれも **"成功した List" として返り、欠けた ID は "理想に無い = 削除"**。
- **進行**: unknown≠absent は **Read の三値**で守られるが、**prune の判定は List の網羅性に全依存**する。
  List が静かに欠損すると、Read が幾ら正直でも prune は取りこぼしを削除する。§5.3 も「List の網羅性が
  prune の安全性を担保する」と明言=**網羅性が破れたら安全性も破れる**ことを自認している。
- **被害**: List の部分欠損 → 実在リソースの誤削除(volume=データ消失、VLAN=通信断)。unknown≠absent の
  哲学的防御が、集合演算の層では効いていない。
- **設計上の防御は効くか**:
  - §5.3「中途半端な List を返すくらいなら実装しない方が安全」は**規律としては正しいが、実装が自分の
    欠損を検知できる前提**に立っている。検知できない部分欠損(ページング打ち切り・レプリカ遅延)には
    無力。
  - `pruneable:false` 既定(§8.3)は破壊種別を守るが、**pruneable:true にした種別(まさに削除を許した
    もの)は List 欠損の直撃を受ける**。
  - Tier2 自傷猶予(§10.4)は Apply 直後の揺れを吸収するが、List 欠損は Apply と無関係に起きる。
- **結論: 防御が不十分**。unknown≠absent は Read(個別)の話で、prune の根拠である List(集合)の
  **サイレント欠損に対する防御が無い**。「List の網羅性」を実行時に検証する機構が設計に無い。
- **提案**:
  1. **prune 発火前に List 結果の健全性チェック**: (a) 前回 List との基数差が閾値超なら prune 保留 +
     Event(S-03 の desired 側と同じ思想を prune 側にも)、(b) 可能なら 2 経路で List して突き合わせ、
     (c) ページング完走の検証(next token が nil で終わったことの確認)を SDK ヘルパに入れる。
  2. **List にも "unknown" を返せる三値を導入**。「網羅を保証できない今回の List」を List 実装が申告
     できれば、その周の prune を保守側に倒せる。Read の三値と対称にする。

## S-05【防御あり(条件付き)】converging 3-tier 誤判定による発振・永久非収束

- **前提**: converging 検知は 3-tier(§10.4)。Tier1 ネイティブ、Tier2 自傷猶予(settle 窓)、
  Tier3 振動推定(M 回で Diff 縮まず → oscillating → auto alert-only 隔離)。deadline 必須。
- **引き金**: 相手が真に収束中なのに、settle 窓(例 30s)を超えて収束が続く長時間オペ(NSX の大規模
  realization、ストレージの再同期)。Tier2 窓を超えた不一致は drifted 扱いになり、reconciler が再 Apply
  → 相手の収束を撹乱 → 綱引き。
- **進行**: Tier3 が M 回で oscillating を検知し alert-only へ自動隔離する。**ここは効く**。ただし
  「M 回」に到達するまでは再 Apply が走り、その各回が相手にとって撹乱になる。相手が「realization に 5 分
  かかる」種別だと、M 回の再 Apply が 5 分の realization を毎回リセットさせ、**"検知はされるが、検知
  までに相手を stuck に追い込む"** 可能性。
- **被害**: 最終的には alert-only 隔離で止まるので**破滅的な暴走にはならない**(自動検疫が効く)。ただし
  収束対象が一時的に不整合状態(realization 途中)で放置される。
- **設計上の防御は効くか**:
  - **効く**。Tier3 の auto alert-only 隔離 + deadline が二重の安全網。非対称原則(綱引きは検疫)に整合。
  - 残る懸念は「M と settle 窓の値」で、これは §26.3 の運用パラメータ。Tier2 の settle が型ごとに
    静的固定(`30s / N サイクル`)なので、**realization 時間が可変な相手**(負荷で 30s〜10min)では
    固定窓が短すぎて誤 drifted を招く。ただし Tier3 が受け止めるので致命化しない。
- **結論: 防御は概ね効く(指摘としてカウントしない)**。ただし推奨として、Tier2 の settle 窓を静的固定
  でなく **Tier1 ネイティブ信号がある相手はそれを優先、無い相手は "前回の収束所要時間から適応的に
  延長"** すると、Tier3 到達前の撹乱を減らせる。converging deadline 超過時の昇格が確実に Event 化される
  ことも要確認(§10.4 は昇格すると明記=OK)。

## S-06【指摘】S2(進行 state)喪失時の実被害:シャードルーター割当表と Task フェーズ

- **前提**: S2 のみ外部永続化(§6.5)。中身は「Task/Workflow フェーズ・承認待ち・シャードルーターの
  割当表」。喪失時は「事故(割当表喪失 = 誤配送)」と自認。だが **S2 の永続化先は §26.2 で "未決"**
  (「外部永続化必須と決めたが、何に永続化するかが未定義」)。
- **引き金 (a) 割当表喪失**: シャードルーターの割当表(どのリソースがどのシャードか)が失われる/破損する。
  永続化先が未定義なので、実装次第で単一ファイル・単一 KV になり、それ自体が単一障害点になりうる。
- **進行 (a)**: 割当表が失われると、リソースが**どのシャードの所有か分からなくなる**。復元時に別シャードへ
  再割当されると、**2 つのシャードが同一リソースを両方 "自分の所有" と認識 → 両方が収束 → 綱引き or
  二重 Apply**。あるいは platform 基盤リソース(単一 writer 前提・§12.2)が複数 writer になる=
  スプリットブレイン(S-08 と接続)。
- **引き金 (b) firmware Task フェーズ喪失**: 多相 Task の Applying フェーズ永続化(§9.1、S2)が消える。
  再起動後、Task がどのフェーズにいたか不明。
- **進行 (b)**: §9.1 は「各相の入口で現実 Observe して二重実行を防ぐ」= べき等再開で守る、とする。だが
  **Applying の途中(firmware 書き込み中)にプロセスが死に、フェーズ state も消えた場合**、Observe で
  見えるのは「中途半端に書かれた firmware / リブートで unknown」。unknown≠absent で「リブート中」と
  解釈しタイムアウト待ちするが、**実際は書き込み途中で bricked(文鎮化)している**ケースを "リブート
  中" と区別できない。フェーズ state があれば "Applying で死んだ = 要人手確認" と分かるが、喪失すると
  この情報が消える。
- **被害**: (a) スプリットブレイン誘発、(b) 文鎮化した機器を "リブート待ち" と誤認して延々待つ / または
  再 Apply で二重書き込み。
- **設計上の防御は効くか**:
  - べき等再開(§9.1)は「相の境界で死んだ」場合は効くが「相の途中で死んだ」場合は Observe の
    解像度に依存。firmware 書き込み途中の観測可能性は provider 依存で、**保証がない**。
  - 割当表については §12.2 が「上位はルーター、状態=割当表=S2」とするが、**その S2 の可用性・整合性
    設計が §26.2 で未決**。事故になると自認しつつ永続化先未定は、安全設計として穴。
- **結論: 防御が不十分**。「S2 は喪失が事故」と正しく識別しながら、(1) 永続化先が未決(可用性・SPOF
  未設計)、(2) 割当表喪失時のスプリットブレイン防止機構が無い、(3) firmware Task の "相の途中death" が
  べき等再開の射程外。
- **提案**:
  1. **割当表に fencing token / 世代番号**を持たせ、復元・再割当時に古い世代の writer を fence する
     (§12.3 の `revision`/`leaseUntil` と同型を割当表にも適用)。割当表は「最も喪失が痛い S2」なので、
     単一 KV でなく **quorum を持つストア or 少なくとも同期レプリカ + fencing** を §26.2 の必須要件に。
  2. firmware 多相 Task の Applying を **"点" でなく "危険区間としてマーク"** し、区間内での death は
     Observe で Done を確認できない限り **auto 再開を禁止し人手ゲート**へ(bricked を待ち続けない)。

## S-07【指摘】credential-broker / Vault / allocator 障害時のカスケードと全盲

- **前提**: §15.1「broker 断 = 認証が要る全ターゲットの Observe が止まる = システム全盲」。緩和は
  §15.5(発行済み短命資格を TTL 内キャッシュ / broker 不達中は unknown 扱い / broker は VM-HA 保護)。
  Vault sealed-on-restart は unseal に人手が要る(§19.4)。
- **引き金**: 段0 の Proxmox ノード障害で Vault と broker が同時に VM 再起動 → Vault は sealed に戻る。
  broker も Vault 依存なら発行不能。同時に render フェーズ1 の Vault metadata 解決・allocation 解決も死ぬ。
- **進行**:
  1. broker 断で全ターゲット unknown → 全 Apply が unknown 相手で保留(非対称原則で破壊は止まる=安全)。
  2. だが **broker の短命資格 TTL キャッシュ(§15.5a)が満了すると、キャッシュ済みの資格も使えなくなり、
     Observe すら不能**。TTL は短命(=短い)なので、Vault の unseal に人手時間(§19.4「MTTR は人間の
     unseal 時間を含む」)がかかる間に **TTL 満了 → 完全全盲**が現実的に起きる。
  3. Vault unseal は Ansible + 人の金庫(§19.4)。夜間・休日・担当者不在なら unseal まで長時間。
  4. その間 render は前回値保持(§7.3)で desired は生きるが、**Observe が全滅しているので収束は
     何も進まない**(加算も減算も、現実が見えないと Apply の可否が判断できない)。
- **被害**: 「破壊はしない」は守られるが、**"何も直せない全盲状態" が人手 unseal 完了まで続く**。この間に
  本番で別の drift/障害が起きても reconciler は無力。緊急対応も broker 経由の到達が死んでいるので、
  L2.5 の OOB(§15.6)= シリアルコンソール手作業に落ちる。
- **設計上の防御は効くか**:
  - **破壊回避は効く**(unknown≠absent、非対称原則)。ここは設計の勝ち。
  - **可用性(全盲時間)は緩和が弱い**。TTL キャッシュは「短命」ゆえ人手 unseal MTTR より短い可能性が
    高く、§15.5a の緩和が **最も必要な "長時間 Vault 断" のときに先に切れる**。設計も §19.4 で
    「MTTR は人間の unseal 時間を含む」と正直に認めているが、**緩和策(TTL キャッシュ)の TTL < unseal
    MTTR という不等号を放置**している。
  - Break Glass L2/L2.5 はあるが、これは「人が手で機器に入る」であって reconciler の全盲は解消しない。
- **結論: 防御が不十分(可用性面)**。破壊安全性は堅いが、Vault/broker 同時断時の全盲時間が人手 unseal
  に律速され、TTL キャッシュ緩和がその時間を跨げない構造的ミスマッチ。単一の段0障害(3ノード同時再起動
  相当のイベント)が全システム全盲を招く。
- **提案**:
  1. **Vault auto-unseal(HSM / Transit / cloud KMS)を段0で検討**。「人間の金庫に着地」の哲学は
     unseal key の**最終**保管には残しつつ、日常の再起動 unseal は自動化して MTTR から人間時間を外す。
     ただし auto-unseal 用の鍵がまた根になるので、そこは Shamir 分割 + 物理保管を維持(哲学と両立可能)。
  2. **broker 短命資格キャッシュの TTL を "Vault MTTR を跨げる長さ" に設定できるオプション**、または
     Observe 専用の read-only 低権限資格を長め TTL で別枠キャッシュ(破壊はできないが全盲は防ぐ)。
  3. allocator 断は §7.3 で「新規払い出し保留 = 未割当は blocked で次周回収」= **効いている**(既存割当は
     保持)。ここは指摘不要。ただし allocator の永続化(§16.5 SQLite)が SPOF なので、割当記録の
     喪失は S-06(a)と同じ再払い出し衝突を招く点は §16.4 の cooldown だけでは不十分——**allocator の
     state 喪失時の再構築手順(現実からの逆引き)** を設計に入れるべき。

## S-08【指摘】マルチサイト分断・スプリットブレイン

- **前提**: シャーディングは shared-nothing・独立収束・デーモン間協調不要(§12.2)。共有基盤は
  「専用 platform シャードが 1 つ所有・変更、テナントシャードは read-only 参照」。分散 Executor は
  §12.3 の段階縮退(分断=加算のみ、lease 失効=Observe のみ)。
- **引き金 (a) platform シャードの二重化**: platform シャードが可用性のため active/standby(§12.2 は
  「リーダー選出は可用性用、active は 1 台」)。standby が「active died」と誤検知してフェイルオーバー、
  だが旧 active は生きている(GC pause / NW 分断の片側)。**2 つの platform シャードが同時に共有基盤へ
  書き込む** = 単一 writer 前提が破れる。
- **進行 (a)**: 設計は「書き手が 1 つなら綺麗」と単一 writer を前提にするが、**その単一性を保証する
  fencing 機構が記述されていない**。「リーダー選出」とだけあり、選出の split(2 リーダー)を防ぐ
  fencing(STONITH / lease token / storage fencing)が無い。共有基盤(NW コア・共有ストレージ)への
  二重書き込みは、順序付きコレクション全置換(§8.5)と組み合わさると**片方の全置換がもう片方を巻き戻す
  = FW ルール/ルーティングの発振**。管理 NW コアなら全機器全盲を誘発しうる。
- **引き金 (b) サイト分断で twin/本番の取り違え無し**だが、**同一 intent を持つ 2 サイトが分断中に
  それぞれ収束**し、復帰時に allocation authority が別々に払い出した ID が衝突。
- **進行 (b)**: allocator が「単一権威」(§16.2)なら分断中は片側が allocator 不達 → 新規払い出し保留
  (§7.3、効く)。だが **allocator をサイトごとに置いた場合**(地理分散で 1 権威は非現実的)、2 権威が
  同じプールから独立払い出し → 復帰時に VLAN/IP 衝突(§16.4 が最悪級と呼ぶ事故)。設計は「採番の
  単一権威」を要求するが、**地理分散(§12.2 の最下段「サイトごとシャード」)で単一 allocator を
  どう維持するか**が未記述。
- **被害**: (a) 共有基盤の発振・全盲、(b) ネットワーク採番衝突。いずれもオンプレ最悪級。
- **設計上の防御は効くか**:
  - §12.3 の段階縮退(分断=加算のみ)は **Executor(データ面 agent)には効く**。だが上記は **制御面
    シャード / allocator 権威**の分断であり、§12.3 の射程外。
  - 「単一 writer」「単一権威」は**前提として宣言されているが、分断下でそれを保証する機構(fencing /
    lease / quorum)が無い**。§12.2 は「分散合意を中枢に戻さない」と明言=**あえて合意を持たない**設計
    選択であり、その代償として split-brain 防止機構も持たないことになる。
- **結論: 防御が不十分**。shared-nothing + 単一 writer + 「分散合意しない」という設計は、平常時は綺麗だが
  **分断時の単一性保証(fencing)を欠く**。特に (i) platform シャードのフェイルオーバー時 fencing、
  (ii) 地理分散時の allocator 単一権威維持、の 2 点が未設計。
- **提案**:
  1. **platform シャード(単一 writer)に fencing token を必須化**。共有基盤 provider の Apply は
     token 検証を通し、古い writer の書き込みを拒否(storage/lease fencing)。「合意は持たないが fencing は
     持つ」は両立する(fencing は合意より軽い)。
  2. **allocator は "1 プールにつき 1 権威" を分断耐性設計とともに規定**。地理分散では「プールをサイトごと
     に静的分割(サイト A は VLAN 1-500、B は 501-1000)して、そもそも 2 権威が同一プールに触れない」=
     shared-nothing を採番プールにも適用するのが設計思想に整合。§16 にこの分割規律を追記すべき。

## S-09【指摘】cause tag C(幽霊 diff)と E(外部入力)の危険シナリオ

- **前提**: C は provider version を diff 入力に含めて検知し、`ProviderUpgradeDiff` Event → 人が dry-run
  確認するまで自動適用しない(§10.3)。「正しい修正でもバグでも同じ見た目」と自認。E は破壊的側に
  重み付け。
- **引き金 (C)**: provider の正規化ロジック修正を含むアップグレードをデプロイ。全既存リソースが
  「今の解釈と違う」= 幽霊 diff。**C 検知は "provider_version が変わったこと" に依存**するが、
  **provider が in-process(§4.4 LocalExecutor)で reconciler バイナリに静的リンクされている v1 では、
  provider version = reconciler バイナリ version**。reconciler 本体の無関係なアップデートでも
  provider_version が動く=**C の誤検知(全リソース ProviderUpgradeDiff)で運用が麻痺**。逆に、
  provider のロジックだけ変えて version 埋め込み(§5.2「version 埋め込み SDK」)を忘れると
  **C を検知できず幽霊 diff が B(drift)に化けて自動適用**=最も危険なケースが素通り。
- **進行 (C)**: version 埋め込みは SDK が「provider ビルド version を diff 入力に自動合成」(§5.2)する
  が、**"provider ビルド version" の粒度が未定義**。モノリシックバイナリで全 provider が同一 version を
  共有すると誤検知、個別 version を手で管理すると付け忘れで検知漏れ。C の安全性は version 粒度の正しさに
  全依存する。
- **引き金 (E-secret)**: シークレット rotate(E-secret)で rendered_revision が変わる。世代が下流入力
  ハッシュに合成される(§14.2)。rotate 直後、使う側の Apply が走る前の一瞬、**"新世代を参照する
  desired" と "旧世代で動いている現実" の diff** が出る。これは正常(rotate 反映)だが、もし Apply が
  rate limit や backoff で遅延すると、**その間に別の観測で "接続断"(旧クレデンシャルが Vault で
  無効化済み)が health として上がり**、reconciler は E-secret diff を埋めようと Apply、しかし相手が
  既に接続断でログイン不能 → permanent エラー → stuck(§6.6)。**rotate が中途半端に止まる**。
- **被害**: (C) 誤検知で全リソース手動確認待ち(運用麻痺)or 検知漏れで幽霊 diff 自動適用(意図しない
  一斉再構成)。(E) rotate の中途半端停止 = 認証断の恒久化。
- **設計上の防御は効くか**:
  - C の検知機構(version を diff 入力に含める)は**思想として正しい**が、**version の粒度と埋め込みの
    確実性**という実装契約が緩い。付け忘れが「検知漏れ = 最悪ケース素通り」に直結する非対称性がある
    (付け忘れが安全側でなく危険側に倒れる)。Schema lint(§5.2)は secret/identity 漏れは見るが、
    **version 埋め込み漏れを静的検出するとは書かれていない**。
  - E-secret の rotate は §14.4 で「rotation の実行は Task/Workflow(順序付き)」とされ、**収束の
    素朴な Apply でなく手順化される**設計 = ここは効く。ただし「存在・鮮度は収束、実行は Task」の
    境界で、**収束側が E-secret diff を見て素朴 Apply しようとするのを、Task 側が担当中だと知る機構**
    (converging マーク)が確実に張られるかが鍵。§9 は「実行中の対象は converging 扱い」とするので
    概ね効くが、rotate の "世代 diff" が収束に見えてしまう時間窓の扱いは要明文化。
- **結論: 防御が不十分(C の埋め込み確実性)**。C は「最も危険・見逃されやすい」と設計自身が最上位
  危険に位置づけながら、その検知が「provider version 埋め込み」という**付け忘れると危険側に倒れる緩い
  契約**に乗っている。E-secret は Task 化で概ね守られる(指摘は C に絞る)。
- **提案**:
  1. **version 埋め込みを provider 登録の必須契約にし、未埋め込みを起動時に拒否**(fail-closed)。
     Schema lint に「version 未宣言」を追加。粒度は「provider の diff/正規化ロジックのソースハッシュ」を
     自動算出(手動 version でなく)し、reconciler 本体 version と分離。これで誤検知・検知漏れ両方を防ぐ。
  2. C 検知時のデフォルトを「全リソース手動」でなく **scope 単位で twin(§22.5)へ自動流し、幽霊 diff を
     本番前に観測**(§22.5 が既に "provider 更新の検証" 用途を挙げている)を運用フローに組み込む。

## S-10【指摘】段0 の単一障害点とブートストラップ循環依存

- **前提**: 段0 = Proxmox 3 ノード + 統合 Ceph + VM-HA に Vault / broker / reconciler を同居(§19.2)。
  依存の向き(§3.3)は「reconciler → broker/Vault/allocator/git(実行時依存)」かつ「reconciler が
  broker/Vault を管理」。循環は「段0が素の起動を保証」で断つ。
- **引き金 (a) Ceph 全損**: 統合 Ceph(§19.2)が段0 の全 VM(Vault/broker/reconciler)のストレージ。
  Ceph が壊れると 3 つ全部が同時に落ちる。**Ceph は段0 内の単一障害点**。3 ノード Ceph で 2 ノード同時
  障害(電源・空調・ラック単位障害)なら quorum 喪失。
- **進行 (a)**: 段0 全滅 → Break Glass L3(§15.6)= Ansible playbook + unseal key で**段0 を人手再構築**。
  これは「数時間〜日」オーダー。その間、段1 の全インフラは reconciler なしで "最後の状態のまま" 動くが
  (制御面が落ちてもデータ面は動く・§19)、**新規障害への自己修復はゼロ**。
- **引き金 (b) 循環依存の実起動順**: reconciler は broker に実行時依存、broker は Vault に依存、Vault は
  unseal に人手依存。**コールドスタート時、Vault unseal(人手)→ broker 起動 → reconciler 起動**の順序
  制約がある。VM-HA が 3 つを同時起動しようとすると、**reconciler が broker/Vault 未 unseal の状態で
  起動 → 全ターゲット unknown で空回り**。§3.3 は「段0が素の起動を保証」と言うが、**起動順序の依存
  (Vault unseal が先)を VM-HA がどう扱うか**が未記述。
- **引き金 (c) reconciler が段0 自身を管理する自己参照**: §3.2「reconciler は broker/Vault を管理対象
  (Resource)」。**reconciler が自分の依存先(Vault/broker)の設定を "収束" できる**なら、誤った理想
  変更で自分の首を絞められる(broker の到達設定を壊す → 自分が全盲 → 直せない)。§19.3 の管理 NW と
  同じ "自傷" 問題が、段0 内部サービスにも存在する。commit-confirm はネットワークの話で、Vault/broker
  設定には適用されない。
- **被害**: (a) Ceph SPOF で段0 全滅・長時間 MTTR、(b) コールドスタート順序未定義で起動デッドロック、
  (c) 段0 サービスの自己収束による自傷。
- **設計上の防御は効くか**:
  - VM-HA(§19.2)は**ノード障害には効く**が、Ceph 自体・quorum 喪失・コールドスタート順序には触れて
    いない。§19.4 は「収束デーモンは VM 再起動の空白を許容」= reconciler の再起動は OK だが、**Vault の
    sealed-on-restart(人手 unseal)がボトルネック**なのは §19.4 自身が認める。
  - Break Glass L3 は最終手段として設計されている=**"段0 全滅は起きうる、そのとき人手再構築" が設計の
    前提**。これは正直だが、Ceph という**単一の共有ストレージに段0 の全 SPOF を集約**している点は、
    段0 最小化(§19.1)と "全部同じ Ceph に乗る" のトレードオフが安全側に振れていない。
  - (c) 自己収束の自傷は、§19.3 が管理 NW について "到達性の最小核は段0(Sakutei は触らない)" と
    切り分けたのと**同じ切り分けが Vault/broker には明示されていない**。
- **結論: 防御が不十分**。(1) 統合 Ceph が段0 の単一障害点で、その全損時の RTO が人手再構築、(2)
  コールドスタート順序(Vault unseal 先行)が未定義、(3) reconciler が自分の依存先(broker/Vault の
  到達性)を収束できてしまう自傷経路が管理 NW と同様に存在するのに、管理 NW のような "触らない最小核"
  の切り分けが明示されていない。
- **提案**:
  1. **段0 内でも「Sakutei が触らない最小核」を Vault/broker の到達性設定にまで拡張**(§19.3 の管理 NW
     切り分けを、段0 サービスの自己参照設定にも適用)。reconciler が自分の broker 到達資格・Vault
     アドレスを収束対象から除外(managed field 的除外)。
  2. **コールドスタート順序を明文化**: VM-HA/起動シーケンスで「Vault unseal 完了 → broker healthy →
     reconciler start」を ready_condition(§6.7)相当で表現。reconciler は依存 unready 時は Observe すら
     試みず待機(空回りログの氾濫防止)。
  3. **Ceph の障害ドメイン**(ノードを別ラック/別電源/別空調)を §19.6 の人手運用要件に明記。段0 の
     SPOF が "共有 Ceph 1 つ" に集約されている事実をリスクとして設計に記載。

## S-11【指摘】reconciler が全インフラの root を持つことの攻撃面と監査ログ改竄

- **前提**: reconciler は物理電源〜ゲスト OS まで全レイヤを変更できる(§1.1)。攻撃面分離のため broker は
  別プロセス(§15.1)。監査は append-only + 連鎖ハッシュ + 日次 head hash を git へ外部アンカー(§17.5)。
  監査 state S4 は「収束経路から不可視」(§6.5)。
- **引き金 (a) reconciler 侵害 = 全インフラ侵害**: reconciler は「値・認可を持たない」(§2-4)が、
  **broker から短命資格を取得して全機器に到達する主体**。reconciler プロセスを侵害すれば、broker に
  「正規の reconciler として」資格を要求でき、**全機器 root を実質取得**。broker 分離は「reconciler の
  広い攻撃面と認証を同居させない」ためだが、**侵害された reconciler は正規経路で broker を使える**ので、
  分離は "broker 自体の堅牢性" は守るが "reconciler 侵害時の被害範囲" は縮小しない。
- **進行 (a)**: 侵害された reconciler は理想状態を書き換える必要すらない——**Apply 経路を直接叩けば、
  rate limit も原因タグも "正規の A" として通す**。安全機構は「誤操作」に対する防御であって「悪意ある
  内部主体」に対する防御ではない。§10 は全て "間違いは止め意図は通す" であり、**攻撃者の "意図" も
  通してしまう**。
- **引き金 (b) 監査ログ改竄**: 監査は連鎖ハッシュ + 日次 head hash を git へ。§17.5 は「連鎖ハッシュ単体
  では head を外部固定しないと全体書き換えで改竄可能」と自認し、日次アンカーで緩和。だが **アンカー間隔
  が日次** = 攻撃者は「最後の head アンカーから今日までの範囲」を自由に書き換え + 再ハッシュ + head を
  次の日次アンカーに間に合わせれば、**最大 24h 分の監査ログを検知されずに改竄**できる。さらに監査を書く
  のも reconciler 自身(または同一ホスト)なら、**侵害された reconciler は "自分の犯行ログ" を書かない
  /改竄する**ことが、次の日次アンカー前なら可能。
- **進行 (b)**: §6.5「S4 は収束経路から不可視」= 収束ロジックからは触れない設計だが、**プロセス侵害
  (収束経路でなくホスト権限)には無力**。append-only の enforcement が「アプリの規律」なのか
  「ストレージ層(WORM / 外部 SIEM への即時 push)」なのかが未記述。前者なら侵害で破れる。
- **被害**: (a) 単一プロセス侵害で全インフラ掌握、安全機構は素通り。(b) 24h 窓の監査改竄で犯行の隠蔽。
- **設計上の防御は効くか**:
  - broker 分離(§15.1)は攻撃面を "分ける" が、**reconciler → broker の正規経路が侵害時の攻撃経路に
    なる**ので、reconciler 侵害時の被害範囲縮小には寄与しない。broker 側に「reconciler からの要求にも
    レート制限 / 異常検知 / per-target の最小権限」があれば緩和されるが、設計は broker を「統一発行」と
    するだけで **reconciler を疑う機構が無い**(reconciler を信頼された単一主体として扱う)。
  - 監査の外部アンカー(§17.5)は**改竄を "後から検知可能" にする**が、日次間隔ゆえ 24h の検知不能窓が
    残る。かつ append-only の enforcement 層が未定義。
  - 「認可を持たない、委譲する」(§2-4)は正しいが、**reconciler 自身の権限(broker を呼べる資格)の
    最小化・監視が設計に無い**。
- **結論: 防御が不十分(セキュリティ)**。(1) reconciler 侵害時、安全機構(rate limit/原因タグ)は誤操作
  防御であり悪意には無力で、broker 分離も被害範囲を縮小しない。(2) 監査アンカーが日次間隔で 24h 改竄窓、
  append-only の enforcement 層が未定義。全インフラ root を持つ単一主体としては防御が薄い。
- **提案**:
  1. **broker 側に reconciler を "半信頼" として扱う機構**: per-target の最小権限(この reconciler
     シャードはこの scope の資格しか取れない)、要求レート/異常検知(短時間に全機器の資格を要求したら
     アラート + 抑制)、破壊的操作用資格は追加ゲート。reconciler 侵害の被害を scope に閉じ込める。
  2. **監査ログを "収束経路から不可視" だけでなく "書き込み後の改変不能" に**: 外部 SIEM / WORM /
     append-only 専用サービスへ**即時 push**(日次でなく)。head アンカーの間隔を短縮(毎周 or 毎時)。
     監査書き込みを reconciler と別権限・別プロセスに(broker と同じ思想)。
  3. **爆発半径の攻撃者視点レビュー**: 安全機構の閾値(rate limit/承認ゲート)を「悪意ある A タグ」でも
     効かせるため、**破壊的操作は原因タグ A でも大量時は承認必須**(現状 A は "意図として通す")。

**防御が不十分と判定したシナリオ: 10 件**(S-05 のみ「防御が概ね効く」として非カウント)

|---|---|---|---|

**設計の勝ち(防御が効いている)と評価した点**(公平のため明記):

- **unknown≠absent / 非対称原則**による破壊回避は Read 経路では堅い(S-04/S-07 の "破壊しない" 側)。
- **converging 3-tier + auto alert-only 隔離**は発振を最終的に検疫する(S-05、非カウント)。
- **allocator の Release 非対称化**(現実消滅を根拠・cooldown・pruneable 保留、§16.4)は再払い出し衝突を
  正しく防いでいる(S-07 の allocator 部分)。
- **render 前回値保持**は "完全不達" に対しては全削除を防ぐ(S-03 は "部分成功" のみが穴)。
- **freeze / 脱出口 / brownfield の alert-only 強制 + prune 禁止**(§23)は導入期の暴走を構造的に抑える。

**通底する構造的弱点**:

1. **安全機構の判定根拠が §26 未決に依存**(rendered_revision 算出・S2 永続化先・Plan 破壊性フラグ)。
   原因タグと rate limit という中核防御が、未定義の下部構造に乗っている。
2. **"瞬間・二値" の障害モデル**が随所にある(cycle 瞬間量・不達/到達・存在/unknown)。現実の障害は
   "じわじわ・部分的" に起きるため、S-01/S-03/S-04 が同じ形の穴を共有する。**"急減/部分欠損を疑う"
   検知を desired 側・List 側・削除累積側に対称に入れる**のが最も効く横断対策。
3. **安全機構が "誤操作" 前提で "悪意/分断/侵害" を想定していない**。S-08(分断)/S-11(侵害)は
   fencing・最小権限・即時監査アンカーという別系統の防御を要する。
